# Week3 모델 테스트: 무엇을, 어떻게, 왜 테스트하는가

작성일: 2026-04-02  
대상: 민원 담당자용 On-Device RAG 시스템의 Week3 모델 비교 실험

## 1. 이 테스트의 목적

Week3 모델 테스트의 핵심 목적은 같은 입력과 같은 조건에서 후보 모델들을 공정하게 비교해, Week4에 단일 baseline 모델을 확정하는 것이다.

이 테스트는 다음 질문에 답하기 위해 설계되었다.

- 이 모델이 구조화된 출력(JSON)을 안정적으로 내는가?
- 답변이 비어 있지 않고 실제 운영 가능한 형태인가?
- 근거(citation)를 검색 컨텍스트와 정확히 연결하는가?
- 데모와 운영 목표 시간 안에 응답하는가?
- 특정 민원 유형이나 위험도 슬라이스에서 성능이 무너지지 않는가?

## 2. 어떤 성능을 테스트하는가

Week3에서는 생성 모델의 절대 언어능력 자체보다, 실제 민원 RAG 파이프라인에서 필요한 운영 성능을 검증한다.

### 2.1 출력 형식 안정성

- 지표: parse_success_rate
- 의미: 모델 응답을 JSON 계약에 맞게 파싱할 수 있는 비율
- 중요한 이유: 파싱 실패는 API 실패와 동일하며, 후속 로직(저장, 표시, 평가)을 전부 중단시킨다.

### 2.2 답변 유효성

- 지표: answer_non_empty_rate
- 의미: answer 필드가 비어 있지 않은 비율
- 중요한 이유: 파싱은 성공했는데 내용이 비어 있으면 사용자 관점에서 실패다.

### 2.3 근거 정합성

- 지표: citation_match_rate
- 의미: 모델이 제시한 citation chunk_id가 입력 context의 chunk_id와 일치하는 비율
- 중요한 이유: 민원 대응 시스템에서 근거 없는 생성 답변은 신뢰성과 감사 가능성을 크게 떨어뜨린다.

### 2.4 지연 시간 성능

- 지표: avg_latency_sec, p95_latency_sec
- 의미: 평균/상위 95% 응답 시간
- 중요한 이유: 데모 및 실제 대응 흐름에서 체감 지연이 크면 사용성이 급격히 나빠진다.

### 2.5 슬라이스 강건성

- 슬라이스 축: scenario_type, risk_level, requires_multi_request, time_sensitivity
- 의미: 전체 평균이 아니라 조건별 성능 편차를 확인
- 중요한 이유: high risk 또는 multi_request 상황에서만 무너지면 실제 운영 리스크가 크다.

## 3. 어떤 방식으로 테스트하는가

## 3.1 입력 데이터

- 기본 테스트셋: 500건 확장 세트
- 파일: docs/40_delivery/week3/model_test_assets/evaluation_set.json
- 생성 규칙: seed 20건 기반 변형, 스키마 유지, 중복 방지, score 범위 보장

각 케이스는 아래 필드를 가진다.

- case_id
- scenario_type
- risk_level
- requires_multi_request
- time_sensitivity
- query
- context(복수 청크: chunk_id, case_id, snippet, score)

## 3.2 실행 조건 고정

공정 비교를 위해 모델 외 나머지 조건을 고정한다.

- 동일 프롬프트 템플릿
- 동일 케이스 입력
- 동일 생성 파라미터(temperature, num_ctx, num_predict, timeout)
- 케이스당 동일 반복 횟수

즉, 모델만 바꾸고 나머지는 모두 동일하게 유지하는 A/B 비교 구조다.

## 3.3 평가 로직

1. 각 케이스를 모델에 질의한다.ㅇ
2. 모델 응답 JSON 파싱 성공 여부를 기록한다.
3. answer 존재 여부를 기록한다.
4. citation chunk_id와 입력 context chunk_id를 대조해 정합률을 계산한다.
5. 응답 지연 시간을 기록한다.
6. 전체 평균과 슬라이스별 지표를 함께 집계한다.

## 3.4 산출물

- JSON 리포트: 케이스 단위 결과 + 집계 지표
- MD 요약: 모델별 핵심 지표 테이블 + 슬라이스 요약

이 산출물은 Week4 baseline 선정 회의와 데모 증빙 자료로 바로 사용된다.

## 4. 왜 이 테스트가 필요한가

### 4.1 데모 안정성 확보

졸업작품 평가에서는 "좋은 한 번"보다 "안정적인 반복 실행"이 중요하다. 2시간 데모 중 재시작 0회를 달성하려면 형식 안정성, 응답 유효성, 지연 시간의 사전 검증이 필수다.

### 4.2 모델 선택의 객관성 확보

선호나 체감이 아니라 동일 조건 수치로 모델을 선택해야 팀 내 합의와 발표 설득력이 생긴다.

### 4.3 운영 리스크 사전 차단

평균 지표만 보면 놓치는 실패 패턴이 있다. 슬라이스 분석으로 고위험 상황에서의 성능 저하를 조기에 발견해야 실제 시연 실패를 줄일 수 있다.

### 4.4 계약 기반 개발 유지

RAG 응답 계약(answer, citations, confidence, limitations)을 지키지 못하는 모델은 기능상 통합이 어렵다. 모델 테스트는 곧 API 계약 준수 테스트 역할을 한다.

## 5. Week3 비교 해석 원칙

Week3는 모델 간 상대 비교를 위한 단계이며, 단일 컷오프 기준으로 통과/실패를 판정하지 않는다.

해석 원칙:

- 전체 평균 지표와 핵심 슬라이스 지표를 함께 비교한다.
- 단일 지표 1등보다 운영 시나리오에서의 균형 성능을 우선한다.
- 고위험 또는 다중요청 슬라이스 약점은 "즉시 제외"보다 "보완 비용"과 함께 비교한다.
- 최종 선택은 성능, 안정성, 지연 시간, 운영 리스크를 종합한 상대 우위로 결정한다.

## 6. 리스크 관리 템플릿 적용

### 리스크 A: JSON 파싱 실패 증가

- 징후: parse_success_rate 급락
- 원인: 모델 출력 형식 불안정
- 예방책: 프롬프트 계약 고정, 저온도 설정, 출력 검증기 사전 적용
- 대응책: 실패 케이스 재실행, 파싱 복구 로직 적용, compact prompt 비교
- 최악의 경우 폴백안: 파싱 안정 모델을 baseline으로 우선 확정

### 리스크 B: 근거 정합성 저하

- 징후: citation_match_rate 저하, citations 누락
- 원인: 모델이 근거 필드 생성 규칙을 준수하지 않음
- 예방책: citation 필드 강제 프롬프트, chunk_id 재검증 로직
- 대응책: 재질의 전략, 후처리 정합성 보정, 슬라이스별 원인 분석
- 최악의 경우 폴백안: 근거 정합성이 높은 대체 모델 채택

### 리스크 C: 지연 시간 증가

- 징후: avg 또는 p95 latency 초과
- 원인: 모델 크기 대비 로컬 자원 부족
- 예방책: num_ctx/num_predict 상한 관리, 실행 환경 사전 점검
- 대응책: 파라미터 축소, 장비 부하 분산, 모델 경량화 후보로 전환
- 최악의 경우 폴백안: 저지연 모델로 즉시 전환해 데모 우선 통과

## 7. 한 줄 결론

Week3 모델 테스트는 "모델 품질 비교"가 아니라 "데모 통과 가능한 운영 모델 선별"을 위한 검증 절차이며, 형식 안정성, 근거 정합성, 지연 시간, 슬라이스 강건성을 동시에 확인하기 위해 반드시 필요하다.
