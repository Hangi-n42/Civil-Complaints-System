## 오류·오탐 결과

민원 평가는 저장된 **정상5·오류5 답변**을 모델별14호출로 평가했다. 무근거 법조항·잘못된 인용·이행 확약·요청 누락·내부 정보 노출을 포함한다.

따라서 **타깃 탐지율이 개선됐다는 근거는 없다**. 확인된 이득은 Q4 오류를 Q5 근거선택 문제로 전이하는 오탐 감소와 법적 주장·인용 존재의 해석 개선이다. 저장 응답을 기존 그룹 파서/Q4 후처리에 재생한 검사는 추가 모델 호출0회다.

K6 내부 D는 신규 각9건에서 Q7 정상 방향의 필수 유형 설명 누락(N)과 역방향 공공분양 당첨 조건 오판(C)2사례를 개선했다. 그러나 PDF985호를 현재 공실985개로 해석하는 질문에서는 건설호수 설명 N이 남았고 `not_established`를 `contradicted`로 강화한 판정 위험이 생겼다. CSV990의 집계 범위 설명도 경계 사례로 남는다. 원질문에 없는 동수·날짜·추가 수량 생략은 독립 실패로 세지 않았다. **조건2건 개선을9건 전체 또는 공개 A 정확도 개선으로 일반화하지 않는다.**

K4는 형식만 보면 세 모델 모두 JSON을 만들었지만 결과가 달랐다. 기존은 고유 정상 수량3+중복1, 수락 불가 합성 주택유형2; Qwen은 정상 수량3, 수락 불가 합성 유형1; Gemma는 수량3의 범위 근거 누락과 합성 유형1로 해당 출력의 수락 가능 사실0이다. Qwen의 오류 레코드2→1은 같은 합성 오류의 반복 감소이며 고유 핵심 오류 해소가 아니다. 따라서 K4는 EXAONE을 유지하며, 기존 근거·형식 검사도 유지한다.

### 실제 흐름 실패 후 좁은 추가 비교

저장된 최종 답변·근거·점수로 피드백 입력1개를 고정해 EXAONE/Qwen/Gemma 각1회 비교했다. 기존 답변을 다시 생성하지 않았다. **최초 실패 피드백의 초안 입력과는 다르므로 동일 실패 재현이라고 주장하지 않는다.** 부서·접수 방법·일정·이행 확약 창작과 요청/예정의 완료 사실화를 판정 기준으로 미리 고정했다.

3개 모두 핵심 문제를 남겼다. EXAONE은 제XX조 보강을, Qwen은 근거 없는 부서·접수경로·일정을, Gemma는 과거 사례를 현재 실행 확약으로 바꾸도록 권했다. 세 모델 모두 차단봉 설치 요청·의도를 이미 효과가 달성된 사실로 서술한 원답변의 오류를 구체적으로 잡지 못했다. 신규 모델의 '기존 정상→실패' 회귀 사례는 아니며, **기존도 실패하고 신규가 다른 위험한 실패 양상을 추가한 사례**다. 기존 유지가 품질 통과를 뜻하지 않는다.

후속 시간은 EXAONE10.226초, Qwen50.834초, Gemma49.042초.3호출110.102초를 더한 **총 비교119호출3262.147초(약54분22초), 고정 입력42개**다. 정상 JSON117개·시간 초과2개. 호환성2호출, 별도 중단2호출, 실제 서비스 경로 호출은 여전히 별도다. 독립 검수는 `feedback_followup_review.json`에 기록했다.

```dotenv
STRUCTURING_MODEL=exaone3.5:7.8b
CIVIL_STRUCTURING_MODEL=gemma4:31b-it-q4_K_M

```

다른 컴퓨터에서 이 프로필을 선택할 때 필요한 모델 설치 명령이다. 현재 컴퓨터에서는 이미 설치돼 있어 다시 다운로드하지 않았다.

```sh
ollama pull gemma4:31b-it-q4_K_M
ollama pull exaone3.5:7.8b
```

- `app/core/config.py`: 민원 구조화·K6 검색·피드백·재작성의 선택적 모델 override4개. 빈 값은 기존 공유 모델을 따른다. `STRUCTURING_MODEL`은 EXAONE으로 유지해 K3 초안·K4 추출을 보존하고, 민원 구조화만 `CIVIL_STRUCTURING_MODEL`로 분리한다.
- `app/generation/service.py`, `app/structuring/structured_extractor.py`: 새 모델을 비추론으로 호출. 공통 호출의 문자열/선택적 metadata 반환 유지, 명시적 `think=None` 생략 동작도 유지.
- `app/api/routers/generation.py`: 피드백·재작성은 각각 선택한 기존 모델 사용. 기존 `revision_model` 기록도 실제 모델과 일치. 평가5회, Q2 요청 내 캐시와 재작성 후4회 평가·수정1회 흐름 유지.
- `app/knowledge/search.py`: K6 공개 A는 별도 설정으로 EXAONE을 유지한다. `extraction.py`는 명시적 `think=None`으로 기존 K4 요청의 추론 설정 생략 동작만 보존한다. `ontology_run.py`는 변경하지 않는다. K3 초안·K4는 기존 `STRUCTURING_MODEL`, K3 반례 검토는 기존 `CIVIL_LLM_RUBRIC_MODEL`을 사용한다. 기존 성공 실행·스냅샷·자료는 다시 생성하지 않는다.
- `app/retrieval/pipeline/stages/llm_relevance_filter.py`: 선택적 파이프라인도 기존 `GROUNDING_FILTER_MODEL`을 따르게 해 생성 모델 변경이 필터에 전파되지 않게 함. 명시적 모델 인자 우선순위 유지.
- 관련 테스트, 이 문서·호출부 조사, `.env.example`, 로컬 비교 자료 제외용 `.gitignore`만 변경. 새 의존성·병렬 처리·fallback·판정 루프를 추가하지 않았고 임베딩·리랭커·추출/검색 알고리즘은 유지.

두 대형 모델은 비교에서 모델별로 순차 실행했고 배치 마지막 요청에서 해당 모델을 해제했다. 서비스에서는 동시에 상주한다고 전제하지 않는다. 현재 선택하지 않은 자기검증·담당부서 LLM은 off, 인사이트는 fake를 유지하며 품질 검증 대상으로 확대하지 않았다. 해당 기능을 나중에 활성화하면 상속 모델과 품질을 따로 확인해야 한다.

[Ollama thinking 문서](https://docs.ollama.com/capabilities/thinking)의 요청 제어와 최종 응답/추론 분리 방식을 사용했다. 모델별 [Qwen](https://ollama.com/library/qwen3.8), [Gemma](https://ollama.com/library/gemma4) 기본 샘플링 설정을 확인했지만, 비교에서는 역할별 기존 temperature와 예산을 유지했다. 설치나 공식 모델 설명을 품질 우위의 근거로 사용하지 않았다.

## 실제 흐름·검증

실제 검색 → 생성 → 평가 → 피드백 → 재작성 → 재평가와 민원 구조화1건을 기존 라우터에서 실제 모델로 실행했다. 검색 결과3건을 사용했다. 첫 QA 요청은 확인 스크립트의 complaint_id 누락으로400이었고 생성 호출은 없었다. 스크립트만 고친 뒤 저장 검색 결과를 재사용했다.

- 검색 필터 EXAONE1회(4.872초), 이후13회(전체 처리396.811초): Gemma 생성1·평가5·피드백1, EXAONE 재작성1, Gemma 재평가4·구조화1. Q2는 요청 안에서 재사용됐으며 새 수정 루프는 없었다. 검색 요청 처리시간은18.039초다.
- 실제 요청에서 생성·평가·피드백·재작성·구조화 `think=false`, 정상 종료·추론 출력0자를 확인했다. 기존 EXAONE 검색 필터는 원래대로 think 옵션을 보내지 않았다. 모델 설치·HTTP200·JSON 성공을 품질 통과로 세지 않았다.
- Gemma→EXAONE 재작성 로드2.898초, EXAONE→Gemma 재평가 로드2.654초를 관측했다. 생성 첫 로드3.663초와 구조화 context 변경 로드3.165초는 서로 다른 원인이다. 두 대형 모델을 동시 상주시키지 않았다.
- **실패:** Gemma 피드백이 자료에 없는 ‘가상의 담당 부서’를 구체적으로 쓰도록 권했다. 최종 재작성에도 근거 해석 문제가 남았다. 별도 저장 최종 답변으로 피드백3모델을 추가 비교했다. 최초 피드백 입력을 복원한 재현 시험은 아니다.
- **기존 계약 충돌:** 구조화 프롬프트는 빈 context를 허용하지만 후속 검증은 `empty_field:context`로 실패 처리했다. 네 요청과 시간·장소 의미는 다른 필드에 보존됐다. 의미 누락과 검증 실패를 구분하며 이번 모델 교체에서 검증 규칙은 변경하지 않았다.
- **평가 입력 범위 한계:** 평가 Q4는 R1–R3에 없는 법령을 지적했으나 응답의 별도 legal_citations에는 확인된 도로교통법 제32조가 있었다. 법령의 존재와 사안 적용 타당성은 다르며, 그 점수만으로 법령 환각이라고 확정하지 않았다. 본문 인용과 구조화 citations 해석 차이도 남았다.

최종 설정 분리 후 구조화1호출(Gemma19.129초, 요청 전체20.408초)과 피드백1호출(EXAONE10.915초)을 실제 서비스 함수로 추가 확인했다. 구조화는 올바른 모델로 실행됐으나 빈 context 검증 실패는 유지됐고, EXAONE 피드백도 앞서 발견한 불필요한 법령 보강 요구를 반복했다. 최종 피드백 분리 뒤 전체 재작성 흐름을 다시 실행한 것은 아니다. 서비스 경로 확인은 합계16모델 호출이며 비교119호출과 별도다.

관련 자동 테스트는 최종 코드에서75개 통과했다(구조화·Ollama 반환/추론 옵션·K4 기존 recipe·관련성 모델 선택25, 피드백/재작성 계약2, 민원 평가 runtime·K6 검색48). 전체 프로젝트 테스트를 반복한 것은 아니다. 독립 에이전트는 호출 분리와 원문 기반 판정을 검수했으며 별도의 현업 품질 인증이 아니다.

진행 중 지식 실행과 연결이 없음을 확인하고 이 프로젝트의 백엔드만 재시작했다. 최종 PID28658의 `/health` 정상 응답을 확인했다. 새 프로필은 현재 백엔드에 적용됐다. 구조화 실행 중 기존 sklearn 저장 모델1.7.2와 실행 라이브러리1.8.0 불일치 경고가 관측됐으며, 이번 LLM 교체에서 해당 모델·라이브러리를 변경하지 않았다.

원결과는 로컬 `selected_flow.json`, `selected_flow_retry.json`에 보존했다. 비교와 실제 서비스 경로의 품질 결과가 다르므로 전체 운영 정확도 향상으로 일반화할 수 없다.

## 남은 한계·다음 작업

- 피드백의 무근거 정보 보강 요구와 구조화 context 검증 불일치, 평가의 별도 법령 근거 범위 불일치가 우선 보완 대상이다. 이번에는 모델 선택과 호출 분리만 수정했다.
- 생성의 무근거 신속 조치 확약, 평가 Q1 오탐, K3 의미·안정 ID 문제, K4 합성 주택유형, K6 조건/건설호수 설명 문제는 모델 교체만으로 해결되지 않았다.
- 고정된 소규모 개발자료에 노출된 비교이며, 독립 전문가 역할 에이전트의 원문·실제 검증 함수 대조는 AI 개발 검수다. 현업 전문가 승인·블라인드 평가·전체 정확도 입증이 아니다.
- 공통 코드에 macOS 경로나 의존성을 넣지 않았다. Windows 실환경 실행은 하지 않았다.
- 다음은 남아 있는 실제 핵심 오류를 역할별로 좁게 수정하는 작업이다. K6 이슈516은 이번 모델 교체만으로 해결됐다고 닫지 않는다. 기존 자료 일괄 재구조화·인덱스 재구축 없이 K7 진행과 별도로 관리할 수 있다.
- 커밋·푸시하지 않았다. 현재 사용자 결정이 필요한 사항 없음.
