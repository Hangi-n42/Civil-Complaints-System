# BE3 매뉴얼(현석)

문서 버전: v1.0  
기준 문서: [PRD](../00_overview/prd.md), [MVP Scope](../00_overview/mvp_scope.md), [WBS](../00_overview/wbs_8weeks_v2_updated.md), [API Spec](../10_contracts/api/api_spec.md), [Schema Contract](../10_contracts/schema/schema_contract.md)  
작성일: 2026-03-11

## 1. 문서 목적

이 문서는 BE3가 프로젝트의 안정성과 정합성을 책임지는 역할로서 무엇을 해야 하는지 상세히 설명한다.  
다른 멤버가 이 문서를 읽으면 BE3가 JSON 파싱, 근거 하이라이팅, 성능 최적화, 스키마 검증을 어떻게 맡는지 한눈에 알 수 있어야 한다.

## 2. BE3 한 줄 정의

**BE3는 생성 결과가 깨지지 않게 만들고, 근거를 정확히 보여주며, 로컬 환경에서 시스템이 안정적으로 돌아가게 만드는 품질/안정성 담당 역할이다.**

## 3. BE3의 최종 책임 범위

### 주 책임
- JSON 파싱 안정화
- 근거 하이라이팅 구현
- 스키마 검증 로직 구현
- 성능 최적화
- 4-bit/8-bit 비교
- OOM 폴백 로직 설계

### 협업 책임
- BE1의 구조화 결과를 검증 가능한 형태로 점검
- BE2의 QA 응답이 안정적으로 파싱되도록 입출력 규칙 협의
- FE가 표시할 validation/citation/error 정보를 구조화해서 전달

### 하지 말아야 할 것
- 검색 품질 실험을 메인으로 맡지 않음
- 업로드/검색/챗 UI 구현을 직접 맡지 않음
- 발표 전체 스토리라인을 주도하지 않음

## 4. BE3가 끝까지 만들어야 하는 산출물

- 스키마 검증 로직
- validation 오류 포맷
- JSON 파싱 및 재시도 로직
- citation/근거 하이라이팅 모듈
- 성능 로깅 포맷
- 모델 설정별 비교 결과
- OOM 폴백 정책 문서

## 5. 주차별 상세 할 일

## M1 (1~2주)

### 이번 단계 목표
- 검증과 안정성의 기준을 세운다.

### 해야 할 일
- 스키마 검증 항목 정의
- validation 오류 코드 초안 작성
- JSON 파싱 실패 유형 조사
- 4-bit/8-bit 비교 기준 및 성능 측정 항목 정리
- OOM 발생 시 대응 흐름 설계

### 이 단계 산출물
- 검증 규칙 메모
- 오류 코드 초안
- 성능/양자화 조사 메모

### 완료 기준
- 어떤 경우를 validation error로 볼지 명확하다.
- 파싱 실패 시 어떻게 재시도할지 팀이 이해하고 있다.

## M2 (3~4주)

### 이번 단계 목표
- 구조화 검증과 기본 파싱 안정화 코드를 만든다.

### 해야 할 일
- 스키마 검증기 구현
- 구조화 결과에 대한 validation 로직 구현
- JSON parser 초안 구현
- 파싱 실패 에러 처리 흐름 구현
- validation 결과를 FE에 보여줄 수 있는 포맷으로 정리

### 이 단계 산출물
- schema validator
- validation 결과 포맷
- JSON parser 초안

### 완료 기준
- 구조화 결과를 자동으로 검증할 수 있다.
- 파싱 실패 시 명확한 에러를 남길 수 있다.

## M3 (5~6주)

### 이번 단계 목표
- QA 응답의 정합성과 가시성을 높인다.

### 해야 할 일
- JSON 파싱 재시도 로직 구현
- citation 정합성 확인 로직 구현
- 근거 하이라이팅 포맷 정의
- 성능 로깅 구현
- 응답 시간 병목 포인트 측정

### 이 단계 산출물
- retry handler
- citation builder
- 성능 측정 로그

### 완료 기준
- QA 응답이 JSON으로 안정적으로 반환된다.
- FE에서 근거를 표시할 수 있는 데이터가 제공된다.

## M4 (7~8주)

### 이번 단계 목표
- 성능과 안정성을 최종 마감한다.

### 해야 할 일
- 4-bit/8-bit 비교 실험 마무리
- OOM 폴백 로직 구현 및 테스트
- validation 규칙 최종 정리
- 근거 하이라이팅 완성
- 장애 발생 시 fallback 메시지 및 처리 흐름 정리

### 이 단계 산출물
- 양자화 비교 결과표
- OOM 폴백 로직
- 최종 validation 규칙 문서
- 안정화 결과 메모

### 완료 기준
- JSON 파싱 성공률 목표에 근접한다.
- OOM 상황에서도 데모를 이어갈 수 있는 대응책이 존재한다.
- citation과 validation 정보가 최종 UI에 반영된다.

## 6. BE3가 받아야 할 것 / 넘겨줘야 할 것

### 받아야 할 것
- BE1의 구조화 필드 규칙
- BE2의 QA 응답 예시와 검색 trace 구조
- FE의 화면 표시 요구사항

### 넘겨줘야 할 것
- validation 결과 포맷
- citation 및 하이라이팅 데이터 형식
- 파싱 실패 시 오류 코드 및 메시지 규칙
- 성능/양자화 테스트 결과

## 8. 주간 체크리스트

- 이번 주 파싱 실패 사례를 수집했는가?
- validation 규칙이 최신 스키마를 반영하는가?
- citation 정보가 실제 검색 청크와 맞는가?
- 응답 시간과 메모리 사용량을 기록했는가?
- OOM 발생 시 대체 경로가 준비되어 있는가?

## 9. BE3가 놓치면 안 되는 리스크

### 리스크 1: QA는 생성되는데 JSON 형식이 자주 깨짐
- 징후: 파싱 실패로 UI나 API가 자주 에러남
- 대응: 재시도 로직과 엄격한 출력 포맷 강제

### 리스크 2: citation이 보기만 그럴듯하고 실제 근거와 안 맞음
- 징후: 답변은 자연스러운데 인용이 엉뚱함
- 대응: chunk_id, case_id, snippet 연결을 강하게 검증

### 리스크 3: 성능 문제를 후반에야 다룸
- 징후: 데모 직전에 응답이 너무 느리거나 OOM 발생
- 대응: M3부터 응답시간/메모리 로그를 수집하고 M4 전에 폴백 경로 확정

## 10. 최종 완료 기준

- 스키마 검증이 자동으로 동작한다.
- JSON 파싱 및 재시도 로직이 안정적이다.
- citation/근거 하이라이팅이 최종 응답과 UI에 연결된다.
- 성능 병목과 OOM 대응 전략이 문서화되어 있다.
- 안정성 측면에서 데모 실패 가능성을 실질적으로 낮췄다.
