## 1. 문서 목적

이 문서는 FE의 구현 우선순위를 Week3~Week8 기준으로 고정한다.  
핵심은 업로드-검색-QA의 데모 흐름을 끊김 없이 보여주고, 백엔드 계약 변경을 빠르게 UI에 반영하는 것이다.

## 2. FE 한 줄 정의

**FE는 구조화-검색-QA 결과를 사용자가 신뢰할 수 있는 화면 흐름으로 전달하는 데모 경험 오너다.**

## 3. 현재 단계 진단 (2026-03-27)

- M1(W1~W2): 완료
	- 기본 화면 구조와 상태 처리 기준 정리
- M2(W3~W4): 진행중
	- 우선순위: 검색 화면 연결, 필터 UX 안정화, Week3 벤치마크 결과 시각화 준비
	- Week4 진입 게이트: QA 화면에서 citation/limitations/오류 상태를 일관 표시

## 4. FE 최종 책임 범위

### 주 책임
- 업로드/구조화 결과 확인 UX
- 검색/필터/결과 카드 UX
- QA 응답 및 citation 표시 UX
- 오류/로딩/빈 상태 처리
- 데모 시나리오 및 발표 시연 흐름 고정

### 협업 책임
- BE1의 구조화 필드와 검증 상태를 UI로 해석
- BE2의 SearchResult 계약을 UI 컴포넌트에 정확히 연결
- BE3의 validation/error/citation 정보를 사용자 메시지로 번역

### 담당 제외
- 백엔드 로직을 UI에서 우회 구현
- API 계약을 FE 단에서 임의 변경
- 성능 실험 자체를 주도(시각화/피드백만 담당)

## 5. 핵심 산출물 (현재~종료)

### UI 코드
- 엔트리: `app/ui/Home.py`
- 페이지/컴포넌트: `app/ui/pages/`, `app/ui/components/`
- 서비스 레이어: `app/ui/services/`

### 문서/시각화
- 데모 시나리오 문서
- 화면별 상태 정의서(success/loading/error/empty)
- 벤치마크 결과 시각화 반영안

### 연동 대상
- 통합 리포트: `logs/evaluation/week3/model_benchmark_report_final.json`

## 6. 마일스톤별 실행 계획

## M2 (W3~W4, 현재 진행중)

### 목표
- 검색 경험 완성 + QA 진입 준비

### FE 실행 항목
- [ ] 검색 입력/필터/결과 카드 화면 연결
- [ ] `region`, `category`, `date` 필터 UX와 상태 메시지 정리
- [ ] 검색 실패/빈 결과/지연 상태 처리 통일
- [ ] 벤치마크 리포트 시각화 요구 필드 확정
- [ ] 데모 클릭 동선 1차 고정(업로드 -> 검색 -> QA)

### 완료 기준
- [ ] 검색 기능이 FE에서 E2E로 동작
- [ ] API 에러 코드가 사용자 메시지로 해석되어 표시됨
- [ ] 결과 화면에서 핵심 필드 누락 없이 표시됨

## M3 (W5~W6)

### 목표
- Adaptive RAG 구간 대응 UX 준비

### FE 실행 항목
- QA 화면에서 citation/limitations 시각적 구분 강화
- multi-request 응답 표시 레이아웃 적용
- 운영자용 디버그 정보(선택) 표시 기준 정리

### 완료 기준
- 분기 응답 구조 변화에도 UI가 깨지지 않음
- 사용자가 근거와 답변 관계를 빠르게 이해 가능

## M4 (W7~W8)

### 목표
- 발표 최적화 UI 동결

### FE 실행 항목
- 데모 3시나리오 기준 클릭 동선 최소화
- 최종 오류/복구 UX 정리
- 발표용 캡처/GIF/시연 스크립트 마감

### 완료 기준
- 발표자가 문서 순서대로 바로 시연 가능
- 화면만으로 구조화/검색/QA 가치가 구분되어 전달됨

## 7. 입출력 계약 (핸드오프 명세)

### FE가 받아야 할 것
- BE1: 구조화 결과 샘플과 검증 상태 필드
- BE2: 검색 응답 포맷(SearchResult)
- BE3: validation/error/citation 출력 규격

### FE가 넘겨줘야 할 것
- 화면 기준 필수 응답 필드 목록
- 사용자 메시지 정책(오류/경고/정보)
- UI 관점 이슈 리포트(재현 절차 포함)

## 8. 주간 운영 체크리스트

- [ ] 3클릭 이상 우회하는 불필요 동선이 남아있는가?
- [ ] loading/error/empty 상태를 모두 처리했는가?
- [ ] 검색 결과와 QA 결과가 명확히 구분되는가?
- [ ] citation/limitations가 사용자가 이해 가능한 형태인가?
- [ ] 백엔드 계약 변경을 주간 단위로 반영했는가?

## 9. FE 핵심 리스크 관리

### 리스크 1: 기능은 동작하지만 시연 동선이 복잡
- 징후: 발표 중 재입력/뒤로가기 반복
- 원인: 사용자 중심 시나리오보다 개발 순서 중심 UI 구성
- 예방책: 데모 시나리오 우선 화면 설계
- 대응책: 핵심 동선 단순화(입력 단계 축소, 기본값 제공)
- 최악의 경우 폴백안: 시연용 프리셋 시나리오 화면 제공

### 리스크 2: 오류 상태가 사용자에게 불명확
- 징후: 실패 원인을 알 수 없어 재시도 실패
- 원인: 에러 코드와 사용자 메시지 매핑 부재
- 예방책: 코드별 메시지 표준 테이블 운영
- 대응책: 공통 에러 컴포넌트 적용
- 최악의 경우 폴백안: 오류 유형별 가이드 메시지 강제 출력

### 리스크 3: 대시보드 과투자로 핵심 화면 지연
- 징후: 검색/QA 완성 전 차트 작업 비중 증가
- 원인: 우선순위 역전
- 예방책: 핵심 화면 완료 전 대시보드 최소 기능 유지
- 대응책: 대시보드 태스크를 후순위로 재배치
- 최악의 경우 폴백안: 정적 요약표 기반 발표로 대체

## 10. 최종 완료 기준

- 업로드/검색/QA 핵심 흐름이 중단 없이 동작한다.
- citation/validation/error 정보가 UI에서 명확히 표현된다.
- 데모 시나리오 문서만으로 발표자가 그대로 시연 가능하다.
- FE 산출물이 KPI와 데모 성공 가능성에 직접 기여한다.
