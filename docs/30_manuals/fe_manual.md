작성일: 2026-03-11

## 1. 문서 목적

이 문서는 FE가 프로젝트 완성까지 책임져야 할 화면, 사용자 흐름, 데모 준비 항목을 명확히 정리한다.  
또한 다른 멤버가 FE 문서를 읽었을 때 어떤 API와 데이터가 UI로 연결되는지 바로 알 수 있게 작성한다.

## 2. FE 한 줄 정의

**FE는 업로드, 검색, 챗, 대시보드 화면을 통해 프로젝트의 기능을 실제로 보여주는 데모 경험을 완성하는 역할이다.**

## 3. FE의 최종 책임 범위

### 주 책임
- 업로드 UI 구현
- 검색 UI 구현
- 챗 UI 구현
- 대시보드 시각화
- 사용자 흐름 설계
- 데모 시나리오 구성

### 협업 책임
- BE1의 구조화 결과를 이해하기 쉬운 화면으로 보여줌
- BE2의 검색 및 QA API를 실제 사용자 흐름으로 연결함
- BE3의 근거 하이라이팅 결과를 시각적으로 드러냄

### 하지 말아야 할 것
- 백엔드 로직을 UI 단에서 우회 구현하지 않음
- API 규격을 FE 편의대로 임의 변경하지 않음
- 평가 스크립트와 성능 실험을 주도하지 않음

## 4. FE가 끝까지 만들어야 하는 산출물

- 업로드 및 구조화 결과 확인 화면
- 검색 결과 리스트 및 필터 UI
- 챗 기반 QA 화면
- citation/근거 표시 컴포넌트
- 지연시간/오류 상태 UI
- 관리자용 단순 대시보드
- 데모 시나리오 문서
- 발표용 화면 캡처 및 시연 흐름

## 5. 주차별 상세 할 일

## M1 (1~2주)

### 이번 단계 목표
- 사용자가 어떻게 앱을 사용할지 전체 흐름을 설계한다.

### 해야 할 일
- 업로드 화면 와이어프레임 작성
- 검색/챗 화면 와이어프레임 작성
- 데모 시나리오 3종 초안 작성
- 주요 상태(success, loading, error, empty)를 정의
- 어떤 필드를 어디에 보여줄지 정리

### 이 단계 산출물
- 화면 흐름도
- 와이어프레임
- 데모 UX 시나리오 초안

### 완료 기준
- 팀원이 FE 화면만 봐도 사용자 흐름을 이해한다.
- 어떤 API 응답이 어떤 컴포넌트에 들어가는지 설명 가능하다.

## M2 (3~4주)

### 이번 단계 목표
- 업로드와 구조화 결과 확인 화면을 구현한다.

### 해야 할 일
- 업로드 폼 구현
- 파일 입력 또는 텍스트 입력 UI 구현
- 구조화 결과 JSON/카드 표시 컴포넌트 구현
- validation 성공/실패 메시지 표시
- loading/error 상태 컴포넌트 구현

### 이 단계 산출물
- 업로드 페이지
- 구조화 결과 표시 화면
- 상태 배너 컴포넌트

### 완료 기준
- BE1/BE3가 넘겨주는 구조화 결과를 화면에서 안정적으로 확인할 수 있다.

## M3 (5~6주)

### 이번 단계 목표
- 검색과 QA 흐름을 사용자 입장에서 자연스럽게 연결한다.

### 해야 할 일
- 검색창 구현
- 필터 UI 구현
- 검색 결과 카드 UI 구현
- 챗 입력창 및 응답 패널 구현
- score, summary, snippet, citation 표시 구조 정리
- 대시보드 초안 구현

### 이 단계 산출물
- 검색 페이지
- 챗 페이지 초안
- 대시보드 초안

### 완료 기준
- 사용자가 검색 후 바로 QA로 넘어갈 수 있다.
- 결과가 복잡해도 화면이 이해 가능하다.

## M4 (7~8주)

### 이번 단계 목표
- 데모 시연에 최적화된 UI로 마무리한다.

### 해야 할 일
- 챗 UI 마감
- 근거 하이라이팅/복사 UX 반영
- 지연시간 및 오류 상태 UX 정리
- 관리자 대시보드 마감
- 데모 시나리오를 실제 클릭 순서로 정리
- 발표용 캡처, GIF, 시연 순서 정리

### 이 단계 산출물
- 최종 UI
- 데모 시나리오 문서
- 발표용 캡처 자료

### 완료 기준
- 발표자가 막히지 않고 자연스럽게 시연할 수 있다.
- 사용자가 구조화, 검색, QA 차이를 UI로 직관적으로 이해할 수 있다.

## 6. FE가 받아야 할 것 / 넘겨줘야 할 것

### 받아야 할 것
- BE1의 구조화 결과 샘플
- BE2의 검색/QA 응답 형식
- BE3의 citation, validation, error 필드 정의

### 넘겨줘야 할 것
- 화면에서 필요한 API 응답 필드 요구사항
- 데모 흐름 문서
- 사용자 관점의 오류/불편사항 피드백

## 7. 다른 멤버는 무엇을 하는가

| 멤버 | 한 줄 요약 | FE와 연결되는 지점 |
| --- | --- | --- |
| [BE1 매뉴얼](be1_manual.md) | 데이터 파이프라인, 구조화 품질, 평가, 발표 담당 | 업로드 및 구조화 결과 화면 데이터 공급 |
| [BE2 매뉴얼](be2_manual.md) | 검색/벡터DB/Ollama RAG API 담당 | 검색 결과와 QA 응답을 UI에 연결 |
| [BE3 매뉴얼](be3_manual.md) | JSON 파싱, 근거 하이라이팅, 검증, 성능 담당 | citation, validation, 상태 메시지 UI 반영 |

## 8. 주간 체크리스트

- 현재 UI에서 사용자 흐름이 3클릭 이상 꼬이는 구간이 있는가?
- loading/error/empty 상태를 모두 처리했는가?
- 검색 결과와 QA 결과를 혼동 없이 보여주고 있는가?
- 발표 시연 기준으로 불필요한 입력 단계가 없는가?
- 다른 멤버가 바꾼 응답 필드를 최신 화면에 반영했는가?

## 9. FE가 놓치면 안 되는 리스크

### 리스크 1: 기능은 되는데 화면 흐름이 복잡함
- 징후: 시연 중 여러 번 뒤로 가기/다시 입력 필요
- 대응: 데모 시나리오 기준으로 클릭 동선 최소화

### 리스크 2: 오류 상태를 숨김
- 징후: 실패했는데 사용자가 이유를 모름
- 대응: 에러 코드와 사용자용 메시지를 분리해서 표시

### 리스크 3: 대시보드에 시간 과투자
- 징후: 핵심 화면보다 차트에 시간 사용
- 대응: 업로드/검색/챗이 안정화되기 전에는 대시보드 최소 기능만 구현

## 10. 최종 완료 기준

- 업로드/검색/챗 핵심 화면이 모두 동작한다.
- citation과 validation 정보가 UI에 반영된다.
- 대시보드는 최소한의 발표용 시각화를 제공한다.
- 데모 시나리오 문서만 봐도 발표자가 그대로 시연 가능하다.
- FE 화면을 통해 프로젝트의 핵심 가치가 바로 보인다.
