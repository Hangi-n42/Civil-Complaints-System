## 1. 문서 목적

이 문서는 BE2가 검색과 생성 파이프라인의 중심 역할로서 무엇을 구현해야 하는지 정리한다.  
다른 멤버가 이 문서를 읽으면 BE2가 임베딩, 벡터DB, 검색 품질, Ollama RAG API를 어떻게 책임지는지 이해할 수 있어야 한다.

## 2. BE2 한 줄 정의

**BE2는 구조화된 민원 데이터를 검색 가능하게 만들고, Ollama 기반 RAG API로 실제 질의응답을 연결하는 핵심 백엔드 역할이다.**

## 3. BE2의 최종 책임 범위

### 주 책임
- 임베딩 설계 및 구현
- 벡터DB(ChromaDB/FAISS) 설계
- 검색 품질 개선
- 하이브리드 검색 검토
- Ollama 기반 LLM 서빙 연동
- RAG API 구현

### 협업 책임
- BE1의 구조화 결과를 인덱싱 가능한 형태로 연결
- BE3의 JSON 파싱/근거 하이라이팅이 잘 동작하도록 QA 입력/출력 구조 제공
- FE가 검색/QA 화면을 만들 수 있도록 응답 형식을 안정적으로 유지

### 하지 말아야 할 것
- 구조화 품질 보정 규칙을 메인으로 맡지 않음
- 스키마 검증 로직 세부 구현을 주도하지 않음
- 발표 자료 전체 총괄을 맡지 않음

## 4. BE2가 끝까지 만들어야 하는 산출물

- 임베딩 선택 근거 문서
- 벡터DB 저장 구조
- 인덱싱 코드
- 검색 API
- 필터 검색 로직
- Ollama 연동 코드
- RAG API
- 검색 성능 리포트
- 파라미터 튜닝 결과 정리

## 5. 주차별 상세 할 일

## M1 (1~2주)

### 이번 단계 목표
- 검색과 생성 기술 스택을 현실적으로 확정한다.

### 해야 할 일
- 임베딩 모델 후보 비교
- ChromaDB와 FAISS 장단점 비교
- Ollama 로컬 실행 확인
- RAG API 입력/출력 초안 작성
- 검색용 메타데이터 키 정의

### 이 단계 산출물
- 임베딩 비교 메모
- 벡터DB 선택 근거
- Ollama PoC 로그
- 검색/QA API 초안

### 완료 기준
- 팀이 어떤 모델과 DB를 쓸지 합의되어 있다.
- 검색과 QA의 연결 구조가 명확하다.

## M2 (3~4주)

### 이번 단계 목표
- 인덱싱과 검색 기본 골격을 만든다.

### 해야 할 일
- 구조화 결과를 청킹하는 기준 수립
- 임베딩 생성 코드 구현
- ChromaDB 인덱싱 코드 구현
- 필터 메타데이터 구조 설계
- `/index`, `/search` API 골격 구현
- Ollama 호출 기본 함수 구현

### 이 단계 산출물
- 인덱싱 모듈
- 검색 모듈 초안
- LLM 호출 모듈 초안

### 완료 기준
- 구조화 데이터 1건 이상을 인덱싱할 수 있다.
- 질의에 대해 Top-K 검색 결과를 반환할 수 있다.

## M3 (5~6주)

### 이번 단계 목표
- 검색 품질과 QA 연결을 끌어올린다.

### 해야 할 일
- Recall@K 측정 및 튜닝
- top_k, chunk 크기, 메타데이터 필터 조정
- 하이브리드 검색 적용 여부 검토
- `/qa` API 구현
- 검색 결과를 RAG 입력으로 넘기는 흐름 안정화
- 검색 성능 로그 수집

### 이 단계 산출물
- 검색 성능 리포트 초안
- `/index`, `/search`, `/qa` 동작 API
- 파라미터 튜닝 결과표

### 완료 기준
- FE에서 검색/QA 기능을 호출할 수 있다.
- 검색 품질 개선 방향을 수치로 설명할 수 있다.

## M4 (7~8주)

### 이번 단계 목표
- 검색과 RAG 응답 품질을 최종 안정화한다.

### 해야 할 일
- 리트리버 파라미터 최종 튜닝
- Ollama 기반 RAG API 안정화
- 검색 품질 결과 정리
- 최종 성능 병목 문서화
- 발표용 검색/RAG 아키텍처 설명자료 작성 지원

### 이 단계 산출물
- 최종 검색 품질 리포트
- 안정화된 QA API
- 아키텍처 설명용 자료

### 완료 기준
- 검색 결과가 데모에서 일관되게 의미 있게 나온다.
- QA API가 FE와 BE3 요구사항에 맞춰 안정적으로 동작한다.

## 6. BE2가 받아야 할 것 / 넘겨줘야 할 것

### 받아야 할 것
- BE1의 구조화 결과와 메타데이터 정의
- FE의 검색/QA 화면에 필요한 응답 필드
- BE3의 citation/parsing/validation 요구사항

### 넘겨줘야 할 것
- 검색 결과 객체 형식
- QA 입력 컨텍스트 형식
- API 응답 예시
- 검색 품질 측정 결과

## 8. 주간 체크리스트

- 현재 검색 품질을 Recall@K로 측정했는가?
- 메타데이터 필터가 실제 데이터와 맞게 동작하는가?
- QA API가 검색 결과를 충분히 활용하는가?
- Ollama 응답 지연이 데모 허용 범위 안에 있는가?
- FE와 BE3가 요구한 응답 필드가 누락되지 않았는가?

## 9. BE2가 놓치면 안 되는 리스크

### 리스크 1: 검색 품질은 낮은데 QA만 손봄
- 징후: 답변이 자주 틀리는데 검색 근거부터 약함
- 대응: 먼저 retrieval 품질부터 측정하고 개선

### 리스크 2: 벡터DB 선택과 구조 변경이 늦게 계속 바뀜
- 징후: 후반까지 ChromaDB/FAISS를 계속 고민함
- 대응: M1~M2 안에 1차 선택 고정, 이후는 교체 실험만 수행

### 리스크 3: QA API가 검색과 느슨하게 연결됨
- 징후: 답변은 생성되지만 근거 정합성이 낮음
- 대응: QA 입력에 반드시 검색 결과 trace와 citation 후보를 함께 전달

## 10. 최종 완료 기준

- 구조화 데이터를 임베딩/인덱싱할 수 있다.
- 검색과 필터가 안정적으로 동작한다.
- Ollama 기반 RAG API가 응답을 반환한다.
- 검색 품질 개선 결과를 수치로 설명할 수 있다.
- FE/BE3가 연동 가능한 안정된 응답 형식을 제공한다.
