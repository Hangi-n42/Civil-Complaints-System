## 1. 구현 범위와 선택 이유

기존 SQLite 스냅샷·사용 상태·단일 실행기·Ollama를 재사용했다. ID/수락 별칭으로 대상을 연결하고 최대 2단계 관계를 조회한다. 기존 한국어 토큰화와 bm25s로 주장/근거 묶음을 정렬하며, 조건이나 출처별 수치 묶음을 입력 상한 때문에 쪼개지 않는다. 새 패키지·그래프 DB·검색 캐시·평가 모델·자동 재작성은 추가하지 않았다.

- `app/knowledge/search.py`: 범위 고정, 대상 선택, 관계 경로, 1회 생성, 인용 연결 검사, 생성 전후 최신 사용 상태 확인, 실행 기록.
- `app/knowledge/schemas.py`, `app/api/routers/knowledge.py`: 검색 요청과 문서 범위 로컬 개체 등록 접점.
- `app/knowledge/extraction*.py`: 일반 개체를 고정 추출 입력에 포함, HTML 같은 표 행과 헤더 보존, PDF 동수/호수 구분. 기존 단지/공고 경로는 등록부 요구 유지.
- `frontend/components/KnowledgeSearch.tsx`, `KnowledgeExtraction.tsx`, `frontend/app/knowledge/page.tsx`: 검색 탭, 버전/대상/자료/기준일, 근거·경로·상태·시간 표시, 일반 개체 등록/선택.
- `scripts/prepare_knowledge_k6_pilot.py`: 기존 로컬 블록으로 최소 스키마와 검토할 사실 후보 준비. 앱 실행 경로가 아닌 개발 자료 준비 스크립트.

답변 모델은 기존 `OLLAMA_MODEL`(이번 환경은 `exaone3.5:7.8b`)을 유지했다. 입력 12,000자 상한, 컨텍스트 16,384, 출력 1,536토큰, temperature 0. 설치 모델의 선언 컨텍스트 32,768 안에서 호출했다. 정상 생성 1회, 대상 미일치/모호성/근거 부족 0회다. 실패한 생성도 호출 수에 포함한다.

최종 `local-v4`는 출처별 사실 묶음과 `source_ref`를 사용한다. 모델이 반환한 주장 ID가 해당 출처에 속하는지 확인한 후 서버가 Evidence·원문 위치·자료 날짜를 연결한다. 외부 응답은 문장별 `assertion_ids`·`evidence_ids`를 유지한다. **존재하는 ID를 인용해도 문장 의미가 맞는 것은 아니다.** `answered`는 응답 생성 상태이며 평가 통과 판정이 아니다.

## 3. 실제 3건 확인 결과

고정 질문과 동일 수락 지식을 실제 API 라우터→검색→Ollama로 실행했다. 정답 기준은 프롬프트에 넣지 않았다. 최초 3건 이후 실패한 DEV-03/NEW-02만 6회 재확인했다. **총 모델 9회, 모델 대기 합계 60.587초, 처리 합계 69.810초**다. 이 합계는 9회 개발 실행이며 3건을 처리하는 정상 비용이 아니다.

로컬 증거 파일은 `data/knowledge/pilot_v1/k6_prepared.json`, `k6_result.json`, `k6_retry_result.json`, `k6_retry2_result.json`, `k6_final_retry_result.json`, `k6_v4_result.json`이다. SQLite Run에도 요청·입력 의존 ID·프롬프트/모델·원출력·시간을 저장했다. 이 데이터는 Git 추적 대상이 아니다.

## 5. 사용과 다음 작업

기존 백엔드/프런트엔드 실행 방법과 로컬 `.env`를 그대로 사용한다. 새 의존성·환경변수는 없다. `/knowledge` → **지식 검색** → 과제용 버전 선택 → 대상/질문 선택 → 검색 순서다. 현재 활성 버전에는 NEW-01/02 준비 지식이 없으므로 해당 비활성 버전을 명시적으로 선택해야 한다. Global은 K7 준비 안내이며 API 실행은 422다.

**다음은 K6 답변 생성의 범위·조건 보존 보완이다.** 필요한 자료가 입력에 있었으므로 현재 실패의 우선 해결 지점은 검색 엔진 추가가 아니라 자유 문장 합성이다. 검토된 수치·단위·범위·조건을 서버에서 출처별로 그대로 표시하고 모델은 연결 설명을 맡기는 좁은 대안을 검토한다. 별도 판정 모델이나 재작성 루프를 추가할 근거는 없다. 두 실패 사례를 보완한 뒤 최종 버전의 NEW-01 확인 및 검색 인용 버튼의 원문 열람을 마쳐 K6 완료 여부를 다시 판단한다. K7 착수 전제는 아직 충족하지 않았다.

현재 사용자 결정이 필요한 사항 없음. 이번 작업은 기능 브랜치의 미커밋 변경이며 커밋·푸시·PR·GitHub 이슈 상태 변경은 수행하지 않았다.


## 6. K6 잔여 보완 최종 결과

최종 실측 후 전문가 지적에 따라 서버 고정 안내를 “여기에 근거가 없는 현재 상태(실시간 공실 등)·개인별 적용 여부는 이 응답으로 확인할 수 없습니다”로 명확히 했다. 이 문구 변경은 추가 모델 호출 없이 관련 단위 확인으로 검증했으며 저장된 실측 원응답은 덮어쓰지 않았다.

분석·검수·수정 순서는 [잔여 문제 분석/계획](../05_plans/company_knowledge/k6_followup_plan.md)에 기록했다. 근본 원인은 검토된 정본을 자유 문장으로 재작성하면서 의미 보존을 모델에 다시 맡긴 것이었다. 존재하는 ID를 인용하는 것만으로 문장 속 숫자/조건의 정확성을 보장하지 못했다.

### 최종 동작 (`local-v6-reviewed-facts`)

- 기존 모델 1회는 **우선 추천 묶음 선택**에만 사용. 자유 본문·한계 문장·q별 미해결 판정 제거.
- 서버가 출처·시점·값·단위·범위·조건·예외를 정본에서 그대로 표시. 긴 Q7 설명도 재요약하지 않음. 수치 합산·환산·차이 원인 추론 없음.
- 같은 대상/속성의 비교값과 관계 앞단을 함께 보존. 추천 밖의 `chosen` 사실도 '함께 조회된 맥락'으로 구분해 표시. 필터/예산 밖 자료는 추가하지 않음.
- `answer_style=reviewed_facts`, `sentences[].section`, coverage의 추천/맥락 ID를 추가. `used_assertion_ids`·인용·경로는 실제 표시한 양쪽 사실에 대응. 빈 추천은 근거 부족.
- 기존 자유 종합답변에서 **근거 중심 응답으로 제품 동작을 좁힌 것**이다. 추천과 맥락의 구분은 신뢰도 등급이 아니며, 표현이 길어진다는 비용이 있다.

### 남는 한계와 다음 단계

## 7. 2026-09-29 재검토와 완료 판정 정정

v6는 모델이 추천하지 않은 사실도 펼쳐 표시해 정보 누락을 보완했다. A-5 본문은 v4 491자에서 v6 1,474자로 늘었고, 동수는 모델 추천 8개에 서버가 2개를 추가했다. 이는 선택/요약 능력 향상의 증거가 아니다. Q7은 원문 보존으로 369자에서 263자로 줄었으므로 원문 전체 인용 자체를 일괄적으로 장황한 방식이라고 판단하지 않는다. 길이는 저장된 `answer`에 출처명/공백/줄바꿈을 포함한 문자 수이며 별도 인용/한계 패널은 제외한다.
