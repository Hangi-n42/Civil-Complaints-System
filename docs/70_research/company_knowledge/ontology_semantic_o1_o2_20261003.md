## 진행 이유와 O1 변경

N3에서 Builder는 원문의 입주자 선정을 ‘선정 절차를 통해 입주 자격을 부여받는 자’라는 정의로 확장했고, 관측 Critic도 원시 응답부터 이를 지지했다. 인용·저장·현재 지문의 오류가 아니라 생성과 의미 검수의 미탐이었으므로 기존 역할 지시에 한정해 보완했다. Ponytail full에 따라 기존 helper·schema·reason·직렬 실행기를 재사용했으며 새 schema·프레임워크·키워드 차단은 추가하지 않았다.

- O1 커밋 `25d1320`: Concept/Builder/Revision에 동일한 짧은 `DEFINITION_RULE`을 적용했다. 원문으로 확인되는 대상·역할·포함 범위를 정의하고, 근거 없이 새 행위·권리·자격 발생·인과·결과를 추가하지 않도록 했다. 원문에 명시된 효과와 근거 있는 역할 추상화는 허용한다. 역할 정의에 모든 행위 조건을 복제하거나 외부 법정 정의를 요구하지 않는다.
- Builder의 서버 보존 설명은 원명제 보존이며 새 정의의 의미 검증을 대신하지 않음을 명시했다. 관측 Critic 지시는 정의의 사실적 주장마다 원문 구절을 확인하고 기존 reason에 구체 대응·차이·미확인을 쓰도록 교체했다. design_reason·미승인 후보·모델의 출처 관계 설명을 새 주장의 원문 증거로 사용하지 않도록 했다.
- 원명제·연결 전용 지시의 SHA256과 응답 schema는 그대로다. prompt v51과 recipe 지문을 갱신해 과거 성공 단위와 새 지시를 섞지 않는다. 실제 작성·관측 prompt에 규칙이 전달되는 회귀 및 관련 계약 69개가 12.56초에 통과했다. 기존 합성 직렬화 경고 13개가 있었다.
- 이것은 지시 전달·코드 계약의 검증이다. 이후 생성·수정 모델을 호출하지 않았으므로 Concept/Builder/Revision의 새 규칙이 실제 생성 품질을 개선했는지는 미측정이다.

## O2: 최초 미관측 예약과 동일 묶음 재개

- 기존 process_group은 미관측 Concept/Relation/Builder/Critic2에 호출 제한시간 360초씩을 예약했다. 첫 분석부터 1800초 추정이 되어 1500초 예산에서는 Scout 이후 진입하지 못했다. 실제 호출의 시간·횟수 상한과 계획용 추정치의 차이를 구분했다.
- O2 `e4f67b4`: 기존 미완료 검수가 없고 정상 호출 수 조건이 충족되며, 실제 추출 시도와 Builder/Critic 실측이 아직 없고 필요한 추출 역할의 시간은 남아 있을 때 최초 한 묶음만 허용한다. 바로 기존 `synthesize(...allow_revisions=False)`를 수행하고 기존 finish를 복사본에서 조회해 필수 검수/분석 미완료면 다음 추출을 막는다. 정상 예약·CQ 순환·실제 hard limit은 유지한다.
- 실행 전문가가 최초 추출 실패·취소 후 저장된 초기 묶음 표지 때문에 재개가 다시 차단되는 경계를 지적했다. pytest 모의 모델과 monotonic 모의시간으로 Scout와 Concept를 각각 100초로 설정하고 Concept 출력 잘림 후 취소한 작은 재현에서, 수정 전에는 재개 호출이 0회였다. `2b9e010`에서 최초 선택과 이미 선택된 동일 묶음의 남은 역할 재개를 분리했다. 같은 묶음만 남은 실제 역할의 호출·시간 범위에서 재개하고 직후 검수 장벽을 유지한다. 다른 묶음으로 예외를 확대하지 않는다.
- 과거 예산 검사 3개 실패는 실제 계약으로 고쳤다. 14묶음은 Builder 전 미확정 예약과 Builder 후 실제 분할 배치를 구분한다. 후속 round 실패는 실제 review_unit_ids로 소유 묶음을 찾아 주입한다. 1500초는 고정된 단일 Critic 단계 수 대신 첫 추출→필수 분할 검수→실측→후속 추출 순서를 확인한다.
- 예산+focused 19개/5.09초, analysis의 취소·재개·예산·복구 20개/5.19초가 통과했다. 동일 묶음 취소 재현 보완 후 예산 파일 9개/3.56초가 통과했다. 이 검사들은 모의 모델·시간을 사용하는 코드 계약 검사이며 실제 모델 실험이 아니다. 서로 겹치므로 독립 사례 수로 더하지 않는다. 첫 binding 실패의 후속 차단·성공 단위 재사용, 모의시간 기준 1500초 소진 때 모의 호출 6회에서 중단, 호출/추출 시간 부족 시 예외 미적용, 24회·2CQ 순환을 확인했다. 모든 호출이 360초를 써도 1500초에 완료된다는 주장은 아니다.

## 보존·실행 연결의 한계와 다음 작업

- 실행 후 runtime30/원본9/준비8 파일 해시 불일치0. 두 복사 DB에서 runs를 제외한 15테이블이 원본과 같았다. 관측 근거 참조6개의 quote·span·version·parse를 원장과 대조했다. 운영 온톨로지·snapshot·사람 결정은 변경하지 않았다. 원문·DB·원응답·미추적 data는 커밋하지 않는다.
- 평가 투영은 과거 source_refs를 같은 block/span/quote의 현재 handle로 연결했다. 실제 supplied와 저장 검수 지문은 일치하지만 case.group.candidates에는 원래 handle을 보존해 D-2 revise 계획의 valid_ids와는 맞지 않았다. 따라서 revision_targets가 비어 있는 것을 자동 교정 연결 성공으로 해석하지 않는다. 원래 수정 예산0이고 D-1 미탐으로 후속이 금지된 이번 의미 결과의 원인은 아니지만, 향후 교정 입력을 준비할 때는 같은 현재 투영 지문을 사용해야 한다. 이번 원본·동결·응답을 사후 수정하지 않았다.
- 확인된 남은 병목은 새 정의의 추가 효과를 근거 있는 역할 추상화로 허용한 모델 판단이다. 명시적인 발동 조건 변경은 검출했지만 이 사례의 추가 인과·자격 부여는 구절 대조 지시만으로 해결하지 못했다. 모델 내부 원인이나 지시·입력 배치 각각의 기여율은 확인되지 않았다.
- 다음 최소 작업에 대한 전문가 의견: 관계 끝점에서만 도출한 역할형 후보에 한해 기존 source_relation_ids·원명제 끝점 표현으로 해당 출처에서 맡는 역할을 설명하게 하고 자유 정의를 줄이는 대안을 검토한다. 이 설명은 출처에서 관측한 역할이며 유형 전체의 필요충분조건이나 모든 적용 범위가 아니다. design_proposal 전체를 역할형으로 취급하지 않고 직접 정의 근거가 있는 후보와 출처별로 구분해야 한다. 명시적 정의 추출·검수와 원명제·연결 검수는 유지한다. 문구 추가나 reason 세분화만으로 잘못된 의미 등치가 해결된다는 증거는 없으며, 이 대안의 실제 효과도 미검증이다. 이번 작업에서 추가 구조 변경·모델 실험은 수행하지 않았다.
