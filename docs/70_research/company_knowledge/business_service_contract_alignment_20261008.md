# 업무 지식 서비스 검사 계약 정렬 — 2026-10-08

## 진행 이유와 범위

시작 HEAD는 `7b7d074af36f926294ef671df00079131f8a5aed`, 브랜치는 `feature/business-knowledge-repair-retrieval`이다. 지정 worktree에서 시작 상태가 clean임을 확인했다. 이전 [사건형 교정 보고서](business_native_event_repair_20261008.md)에 남은 서비스 검사 두 건을 현재 계약에 맞게 복구했다. #616/#617/#620의 기존 범위를 사용하며 새 이슈·제품 검수 계층·모델 호출은 추가하지 않았다.

변경은 `app/tests/unit/test_knowledge_business.py`와 이 보고서·추적 기록뿐이다. 제품 코드·기본 v8 계약·승인 기준은 변경하지 않았다.

## 확인된 원인과 기각한 가설

1. **두 검사의 최초 원인: 오래된 근거 응답 fixture.** `pytest-401`의 두 실패 DB를 읽기 전용으로 열어 `SelectedScopedRequirementSourceCheck`의 `schema_error`를 확인했다. 서버가 요구하는 `e1` 등의 선택 ID 대신 모의 모델이 `{block_id, quote}` 객체를 반환했다. 정확한 인용문을 담은 객체도 현재 응답 계약에서는 거부된다. source 호출 실패로 meanings가 비고, 이후 mock의 `source.meanings[0]`·`local_judgments.checks[0]` 접근이 추가 실패했다. 제품이 정상 의미를 삭제한 사례가 아니다.
2. **`requirement_quote` 누락 가설은 해당하지 않는다.** 저장된 실행은 `requirement-local-review-v8-owned-errors`다. 해당 필드를 요구하는 별도 실험 계약으로 변경하지 않았다.
3. **잘못된 자유 인용 생성은 현재 모델 응답의 유효한 실패 재현이 아니다.** 모델은 서버 제공 근거 ID를 선택한다. 과거 검사의 목표인 서버 인용 오류 귀속·재판정 전달은 별도로 유지했다. 정상 응답으로 만들어진 source의 인용만 손상시킨 **합성 legacy source JSON**을 임시 파일에 저장·복원해 source 반환 경계에 주입했다. 실제 과거 사용자 DB의 손상이나 실제 모델의 인용 오류를 재현했다는 뜻이 아니다.
4. **국소 판정과 종합 입력의 역할 불일치.** 독립 전제 `premise_keys=[]`를 명시하고, 종합이 정상 국소 판정과 후보 위치를 받아 보존하는지 확인한다. 변경할 연결 쟁점이 없으면 `review_meaning_keys=[]`, 보존 대조 대상이 있으면 해당 의미키가 포함되어야 한다. 의미 배열이 비어도 통과하도록 분기하지 않았다.
5. **정상 추출 fixture의 Scope 누락.** 최초 두 실패의 원인과 별개로, 정상 서비스 fixture는 현재 추출 요청이 요구하는 Scope가 없었다. 원문 주소·참여자·의미·전제를 갖춘 합성 Scope를 추가하고 저장된 해석의 주소 오류가 없음을 확인한다. 이 누락으로 실제 제품 연결 결함이 입증된 것은 아니다.
6. **보존 검사의 현재 응답 계약.** 교정 전후 대상이 있으면 종합에 보존 검사 행이 필요하다. 기존 mock은 그 행을 생략했다. 유효한 `unknown` 행을 반환하도록 정렬하고, 호출 자체는 성공해도 보존 미확정으로 assessment가 `partial`이고 `preservation_complete=false`임을 확인한다. 형식 실패를 보존 실패처럼 이용하지 않는다.

## 수정 및 검증

최종 12개와 직전 통과한 선택 근거 검사 1개를 합쳐 **서로 다른 13개 검사**를 확인했다. 중간에 반복한 정상 서비스 검사를 별도 성과로 더하지 않는다. 이전 134개 전체 묶음이나 이미 통과한 native 사건형 교정 검사를 다시 실행하지 않았다. 최종 보존 응답은 `unknown`이며 저장 unit은 `succeeded`, 오류 없음도 확인했다.

정상 서비스 검사는 원문 파싱 → 추출·원문 의미·표현 판정 → 명시적 모의 운영자 승인 → 동일 요청 재사용 → 저장 후보 재판정을 수행한다. 재사용 시 부모 기록이 유지되고 새 호출이 없으며, 저장 후보 재판정에서 기존 후보·개념을 유지하고 평가·승인을 자동 상속하지 않는지 확인한다. 이후 승인 snapshot의 후보를 BM25로 선택하여 모의 QA 인용 ID를 복원하고, 원문 차단 후 답변·승인을 막는 경계를 확인한다.

잘못된 저장 인용 검사는 관계없는 출처를 재판정에 섞지 않고 원래 의미키로 오류를 전달하며, 모델의 의미 이의 없이 서버 오류로 재판정이 1회 실행되는지 확인한다. 인용 정정 후 정상 진술은 유지되고 오류 이력은 남는다. 후보가 없으므로 전체 결과는 `partial`, 승인 가능 후보는 빈 목록이다. 빈 승인 snapshot에서는 그래프 답변 호출을 하지 않으며, 문서 기준선의 모의 QA는 별도 경로로 동작한다.
