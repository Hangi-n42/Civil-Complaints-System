# 필수 문맥·수정 의미 보존·요구 충족 연결 확인

- 대상: #595 → #596 → #597. 기준 `58cc43b`, 작업 브랜치 `feature/ontology-critic-grounding`.
- 기존 source/version/parse/block 원장, 후보 ID·revision_history·직렬 call·SQLite·Pydantic·복구 경로를 확장했다. 정의 충분성, 교정 유용성, 업무 요구 충족을 각각 저장해야 후보가 생성됐다는 사실을 의미 성공으로 잘못 집계하지 않는다. 새 프레임워크·DB·큐·운영 활성화는 추가하지 않았다.
- 코드 계약 검사, 실제 모델 호출, 독립 AI 의미 검수, 사람 시험을 구분한다. 실제 사람 참가자 0명이며 효용은 미측정이다. 이 기록은 전체 온톨로지·지식 그래프의 정확도 평가가 아니다.

## 구현

1. 생성자는 `context_needs`로 필요한 문맥을 제안한다. Critic은 `required_meanings`에 필요한 의미·적용 대상·실제 원문·현재 후보 필드 또는 기존 구조의 충족 위치·판정·이유를 저장한다. 구조적 인접 구간을 기존 원문 읽기와 함께 제공하며, 큰 추가 문맥은 잘라 넣지 않고 공백으로 남긴다. 출처 역할을 전체 법정 자격으로 확대하지 않고, 외부 조문 부재와 제공 의미 누락을 구분하도록 계약을 명시했다. 이 지시만으로 실제 모델의 준수를 보장하지 않는다.
2. 선택 계층과 그 끝점·상위 정의를 검수 지문에 포함한다. A3는 선택 참조를 정본 target ID로 변환하고 전이 의존 내용을 보존한다. 정본 변경 시 검수 현재성을 해제하며, K4에 필요한 선택 구조와 실제 정의를 제공한다.
3. 수정 후 Critic에 before/after와 이전에 지지한 의미를 함께 제공한다. 유지·근거 있는 정정·소실·판단 불가를 기록하고, 오류 제거·정상 의미 보존·충분성을 함께 현재 수정 지문에 연결한다. 표현·필드 이동을 허용하며, 과거 지지가 틀린 경우 실제 원문과 이유를 갖춰 삭제할 수 있다. 기존 사람 수정 권한과 이력은 유지한다.
4. CQ/범위별 `requirements` 검수를 기존 직렬 호출에 추가했다. synthesize 후 복구 전에 실행하며 마지막 라운드에도 저장한다. `finish`는 모델을 호출하지 않고 현재 지문의 저장 판정만 읽는다. 필수 요구 미충족은 전체 partial이며 개별 후보의 유효성·수락과 별개다.
5. 생성 누락은 기존 Concept/Relation의 소유 구간·중복 방지·비교 경로를 사용한다. 끝점 오류는 현재 원명제 검수 조건을 확인한 뒤 새 요구 검수의 unit/지문/근거를 명시한 입력으로 기존 Builder 교정에 연결한다. 과거 Critic supported를 refuted로 바꾸지 않는다. 수정 후 기존 Critic 재검수를 거친다. extraction_missing은 해당 의미의 현재 충족 판정이 있어야 해결된다.

## 전문가 검토와 보완

- 사전 아키텍처·온톨로지 및 의미 평가·실행 검토 후 작업했다. 조율 세션의 독립 재검토에서 실제 입력 계산 이후 문맥이 커지는 경계, A3의 전이 끝점 의존 누락, K4의 실제 선택 정의 전달 누락, 기존 상위 유형 선택 누락을 보완했다.
- 요구 전체 입력이 한도를 넘으면 기존 분석 구간으로 나누며 문서 간 전체 결합이 미확인되면 unknown을 유지한다. 기존 Critic에서 시작한 공유 복구 요청도 대상에 포함한다. 새 누락 의미 및 원문의 주분석/문맥 범위가 바뀌면 과거 검수를 재사용하지 않는다.
- 분할 검수는 실제 소유 span과 요청 target으로 복구 대상을 배정한다. 각 요청을 맡은 부분의 현재 판정만 집계하므로 다른 구간의 근거 미제공이 이미 해결한 요청을 영구 보류하지 않는다. 상충 판정이나 해당 소유 부분의 검수 누락은 해결로 세지 않는다.

- 세 경계 모두 수정 전 실패를 재현했다. 특히 총 2호출·요구 검수 1회 예약에서 기존 코드는 Critic이 2회를 사용했다. 보완 후에는 Critic 1회→다음 후보 검수는 호출 전 보류→requirements 1회로 총상한을 지킨다. 10초의 작은 시간 여유에서도 timeout이 요구 예약을 침범하지 않는 대역 검사를 추가했다.
- 전체 요구 packet은 **21,799자/30,741bytes**로 24,000자 한도 안이었다. 기존 context 32,768에서 출력 4,096을 예약한 보수적 바이트 한도 28,672만 초과해 6분할됐다. 실제 토큰 컨텍스트 소진은 확인된 원인이 아니다.
- 설치 모델의 지원 context 262,144를 확인한 뒤 기존 recipe의 context를 **36,864**로만 늘리고 v61로 구분했다. 출력 4,096·문자 24,000·원문 무절단·바이트 검사·실제 prompt_eval_count 검사는 유지한다. 새 바이트 한도 32,768 안에 같은 전체 packet이 들어간다. 단계별 프레임워크를 추가하지 않았다.
- 같은 최종 후보·원문·CQ의 공동 검수 **1회만** 별도 동결했다. 새 Concept/Relation 생성·전체 제품 재실행·동결 원본 교체는 없다. freeze `14dc23bab81167dc5442ca4fdacaddb8743677b6d5912486d8351eb3d95f101c`, `joint_inputs.json`/`joint_once.py`/`joint_freeze.json`. 기존 호출과 합산한 34회/6600초 상한 안에서 추가 최대 1회/300초다.

- v61 공동 검수는 **1HTTP/153.078초**로 끝났다. 실제 전송 context 36,864, `prompt_eval_count=9895`, 출력 1168토큰, done_reason=stop이다. 같은 자료를 6부분으로 나누던 입력을 **단일 공동 입력으로 처리한 사실**은 확인했다.
- 유효 판정 저장은 실패했다. 모델이 두 의미에 `supported`와 `scope_conflict`를 함께 반환해 ‘충족 판정과 미완료 원인 충돌’ 검사에서 거절됐다. 세 번째 의미는 문서 사이 연결이 원문에 없다고 설명하면서 `refuted/extraction_missing`으로 분류했다. 동결 기준의 기대 판정은 미제공 시행령에 따른 `unknown/source_absent`다. 독립 검토에서도 이 차이를 확인했으며, 출력 형식만 고쳐 해결할 수 없는 별도 의미 오판이다. 전체 파이프라인 성공이나 품질 개선으로 보고하지 않는다.
- 마지막 독립 검토는 기존 후보 10개의 값 동일성, 법2 1,974자와 규칙15 539자의 전체 원문 포함, 실제 토큰·시간을 대조했다. 이 공동 실행은 요구 검수 예약 정책 전체를 검증한 시험은 아니다.
