## 현재 엔진과 모델

실시간 확인: 브랜치/HEAD 일치, 시작 worktree clean, Ollama 0.35.0 serve만 실행 중이며 로드된 모델은 없다. `qwen3.8:27b-q4_K_M` 태그 digest는 `25b843619e944cd0ae6069f94ff4e5e26a16e109ccbc0a66a0f05979ed70098e`다. CAD가 쓴 text GGUF 파일 SHA-256 `f5f1dd8920d417aac2718b0bda3403da274301efdd6760b4f0f4b864ff2ad57d`, 16,810,714,464 bytes를 다시 검증했다. 태그 digest와 가중치 파일 digest는 다르다. 태그의 부가 레이어를 포함한 전체 크기와 text 모델 크기도 구분한다.

기존 설치 native 엔진 `/Applications/Ollama.app/Contents/Resources/llama-server`는 0.4.1-dev, build 1, commit `161755f29`, 바이너리 SHA `c8bbfac5e73a6f04f0dd2d91dde8f9934c0f1526b862f6129703be8d158a25db`다. 기존 CAD의 전체 248,320개 token ID와 `post_sampling_probs=false` logprob 반환/외부 선택 token append 증거를 읽었다. **실제 반환값은 raw logits가 아니라 sampling 전 정규화 log probability**다. 저장된 확률 합의 근사 오차가 있으므로 새 실행에서도 유한값·ID·어휘 coverage를 확인해야 한다. 기능 증거를 이번 의미 성과로 재사용하지 않는다.

Ollama show의 표시 template은 `{{ .Prompt }}`, 별도 renderer `qwen3.8`이다. native 수동 ChatML/빈 think 템플릿과 제품 renderer의 동일성을 입증하지 않았으므로 **A도 native에서 새로 실행**해야 한다. 과거 CAD는 네 사례·compact status/reason·구 제품 상태이고, HC는 모델까지 다르므로 정확한 매칭 기준선으로 재사용하지 않는다.

## 동결한 A/B 방법과 계산

두 팔은 같은 GGUF/엔진/수동 ChatML think-off/temperature 0/repeat penalty 1/top_k 0/top_p 1/min_p 0, 같은 원문 블록·부모·raw 후보·건별화·세 판정 정의를 사용한다. 예제·새 모델·정밀도·라벨 보정은 추가하지 않는다. context 8,192, 단일 슬롯, A 출력 상한 2,048을 사용하며 실제 tokenization으로 여유를 확인한다. 입력 잘림은 두 팔 모두 실패다. A 출력 잘림은 첫 라벨을 읽을 수 있어도 의미 이득 기준에서 제외한다. B의 출력 1 token limit 종료 자체는 예정된 측정이므로 실패가 아니다.

공통 정의는 지지/미지지/명시반증이다. 구 제품 `incorrect`를 명시반증으로 소급하지 않는다. 숫자 code 1/2/3을 각각 지지/미지지/명시반증에 연결하고, 공통 assistant 접두부 `{"label":"`에서 시작한다. 이 숫자는 평가 정답이 아니라 모든 입력에 같은 판정 선택지를 표현하는 기호다.

- A: label code, 실제 error_fields, 정확 원문 evidence, reason을 생성한다. 단일 후보로 동등화한 설명 포함 기준선이며 과거 제품 호출 그대로가 아니다. 임의 수리 없이 전체 계약과 읽을 수 있는 최종 라벨/이유를 별도로 평가한다.
- B: 동일한 세 정의에서 label code만 요구한다. 그 첫 위치의 전체 어휘 log probability를 1회 받아 세 code의 점수를 비교한다. 세 답변을 생성하거나 다수결하지 않는다. JSON/필드/이유 생성은 하지 않는다.
- 공통 입력에서 허용하는 차이는 출력 지시문과 실제 생성 길이/선택 절차다. 출력 지시 변경도 모델 입력 변경이므로 설명 부담의 단일 인과 효과나 내부 의미 능력 변화로 확정하지 않는다.

각 code의 점수는 `s_i = log p(token_i | frozen_prompt_B)`다. B는 `argmax(s_i)`를 선택한다. 보고용 제한 정규화는 `q_i = exp(s_i - logsumexp(s_1,s_2,s_3))`, margin은 1위와 2위 logprob 차이다. 전체 어휘에서 세 code에 배정된 질량과 native greedy token이 선택지 밖인지도 기록한다. **q는 세 출력 기호 사이의 상대 선호이며 정답 확률이나 신뢰도 보정값이 아니다.** source support와 세계의 참/거짓도 구분한다.

메타데이터상 code 1/2/3은 token ID 16/17/18의 단일 토큰이다. 정확한 접두부에서의 tokenization 및 detokenization은 생성 전 preflight로 검증하며, 일치하지 않으면 방법을 임의로 바꾸어 점수화하지 않는다. 길이가 같으므로 token 길이 정규화나 EOS 점수 추가는 하지 않는다. 유한 점수/coverage 실패·정확 동률은 실행 미확정이며 미지지 정답으로 바꾸지 않는다. 낮은 질량을 임의 threshold로 미지지에 매핑하지 않는다.

숫자·순서의 선호는 남는다. 주 비교에서 실제 의미 개선이 확인된 경우에만 두 팔 모두 같은 사전 순환 mapping `1=미지지, 2=명시반증, 3=지지`로 같은 16건을 한 번 확인하는 최소 민감도 대조를 동결했다. 결과를 보고 좋은 순서를 고르거나 점수를 보정하지 않는다. 이 대조도 독립 문서 증거는 아니다. 실행 진입 기준과 설정은 모델 출력 전에 동결했다.

## 평가·후속·현재 한계

기존 합의15건과 H07 별도를 재사용한다. 원래 입력 전체를 보존하고 기대 라벨/오류 이유/수정문은 제품 입력에서 제외한다. 정상8 보존, H02의 명시반증, A02의 자료 부족, 조건·주체·의무 오류를 함께 본다. c47은 유일 관문이 아니다.

동결한 다음 단계 진입 조건은 (1) A에서 명확히 틀린 의미 라벨을 B가 최소 1건 바로잡음, (2) 합의15에서 A가 맞춘 의미 라벨을 B가 새로 틀리지 않음, (3) 정상8/H02/A02 보존이다. A의 형식 실패만 줄이거나 A의 읽을 수 없는 라벨을 B가 선택한 경우만으로 의미 개선을 인정하지 않는다. H07/동률/실행 실패를 합의 정답으로 채우지 않는다. 순서 민감도 대조와 미사용 확인도 개선이 있을 때만 진행한다.

B는 오류 위치·이유·수정 내용을 생성하지 않으므로 label 개선만으로 기존 error_fields/근거/자동 교정 계약을 대체할 수 없다. 실제 오류 특정·정상 보존·같은 요구·저장/활용의 후속 증거 없이는 제품 목표 완료가 아니다. 이번 진단의 라벨 결과를 제품 상태에 저장하거나 자동 교정에 연결하지 않는다.

기존 미사용 자료 조사에서는 H/A/K 모두 실제 호출 노출, 도서관 E 예제는 개발 입력 노출, pilot 새 과제는 설계 정답 노출을 확인했다. 다른 corpus의 이력 불명 자료를 미사용으로 간주하지 않는다.
