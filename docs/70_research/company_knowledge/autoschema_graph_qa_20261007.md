# AutoSchemaKG 그래프 검색·QA 연결 — 2026-10-07

## 범위와 출발점

기준 커밋은 `2ae34f92d70a877cfffff5c7bfd067140e5e4c1e`다. 별도 브랜치 `codex/autoschema-graph-qa`에서 작업한다. 기존 중단 작업, 패치, 원문, 평가 DB를 수정하거나 재개하지 않는다.

기존 제품에는 세 추출 → 출처 있는 임시 그래프 → 실제 연결 이웃을 사용하는 개체·사건·관계 개념화가 있었다. 그러나 `business_use.query()`의 `graph`는 그래프 탐색이 아니라 승인 후보의 본문에 개념 관련어를 붙인 BM25였다. 따라서 기존 결과는 논문의 그래프 검색·QA를 재현한 결과가 아니다.

논문은 ToG와 HippoRAG2를 대안으로 비교한다. 이번 구현은 **HippoRAG2 경로를 추출·개념화 이후의 제품 검색·QA에 연결**한다. ToG를 함께 순차 실행하는 구조가 아니며, ToG 구현이나 논문 전체 벤치마크 재현은 이번 결과에 포함하지 않는다.

## 직접 가져온 부분과 변경한 부분

기준은 [HKUST-KnowComp/AutoSchemaKG, d0a1666](https://github.com/HKUST-KnowComp/AutoSchemaKG/tree/d0a1666ae6621806faf814504c73678de4e809f2)이다.

- `atlas_rag/retriever/hipporag2.py`, `atlas_rag/llm_generator/prompt/rag_prompt.py` 원본을 vendor에 보존하고 SHA256·원본 경로를 `provenance.json`에 추가했다. 원본 MIT 고지를 유지한다.
- 관계 임베딩 검색, 후보 관계 LLM 필터, 끝점별 점수 평균, 원문 유사도와의 결합, Personalized PageRank, 관계 선택이 없을 때 원문 임베딩 검색으로 돌아가는 흐름을 가져왔다. 필터의 원본 지시문을 사용하면서 출력은 제공된 관계 ID 선택으로 바꿨다.
- 공식 코드가 반환 트리플을 임베딩으로 다시 매칭하는 부분은 제공 ID의 정확한 선택으로 바꿨다. 다른 관계·출처로 잘못 재매칭하지 않는다. 필터 호출 실패는 빈 선택과 구분하여 실패로 저장한다.
- 논문 부록의 작은 QA 설정을 따라 관계 후보 30개, 끝점 10개, PPR alpha 0.9, passage weight 0.9를 사용한다. 공식 저장소의 설정 기본값과 논문 실험 설정은 서로 다르므로 구분한다.
- FAISS 근사 검색 대신 기존 NumPy의 정확한 유사도 정렬을 쓴다. 현재 자료 규모에서 별도 서버나 인덱스 의존성이 필요하지 않다. PPR은 기존 NetworkX를 사용한다.
- 임베딩은 설치된 로컬 `BAAI/bge-m3`, 관계 선택·답변은 실행 recipe의 로컬 review 모델이다. 임베딩 모델을 자동 다운로드하지 않는다. 모델 한도를 넘는 입력을 조용히 자르지 않는다.
- 기존 출처별 노드 ID를 유지한다. 원문 위치가 다른 동명 개체를 이름만으로 합치지 않는다. MultiDiGraph로 같은 두 끝점의 복수 관계를 보존한다. 이는 공식 DiGraph 및 이름 기반 병합과 다른 프로젝트 변형이다.
- 개체·사건의 개념은 공유 검색 노드와 `has_concept` 연결을 만든다. 승인 `is-a`가 아니다. 미승인 개념 상태를 보존하고 변경·실패 상태의 개념은 제외한다. 관계 개념은 공식 방식처럼 관계의 속성으로 보존한다.
- 공식 그래프 생성·retriever 코드의 방향 그래프를 따른다. `has_concept`와 `mention in`에 임의의 역방향 사실을 추가하지 않는다. **공유 개념 노드가 있다는 것만으로 그 개념에서 다른 개체로 역방향 이동이 가능하다고 설명하지 않는다.** 해당 방향과 sink 노드가 검색에 미치는 영향도 결과 해석의 한계다.

## 제품 호출과 근거 경계 — 최종 구현

`POST /knowledge/business/search`에 두 소비 경로를 제공한다. 원형에 가까운 추출 그래프·원문 QA는 승인 snapshot 없이 종료된 추출 실행을 직접 지정한다.

```json
{"source_run_id":"…", "question":"…", "retrieval":"hipporag2", "graph_variant":"full", "limit":12}
```

기존 승인 지식 소비 경로도 유지한다.

```json
{"snapshot_id":"…", "question":"…", "retrieval":"hipporag2", "graph_variant":"full", "limit":12}
```

`retrieval`: 기존 `bm25` / 원문 임베딩 `dense` / 그래프 `hipporag2`.
`graph_variant`: `entity` / `entity_event` / `full`. 삭제 비교에서 원문 구간은 동일하게 유지한다.

새 흐름은 **기존 원문 추출·개념화 → 출처 그래프 → 관계 선택 → 그래프 순위 → 검색된 원문 구간 자체 → 답변**이다. 개념은 검색 연결이며 답변의 사실 근거는 원문이다. `source_run_id` 경로는 snapshot·승인 결정을 만들지 않고 미승인 추출을 승인된 온톨로지로 바꾸지 않는다. 오류/대체 처리된 추출은 검색 그래프에서 제외한다.

UI에서 답변 근거를 승인한 버전 또는 선택한 추출 실행의 원문으로 선택할 수 있다. 검색 방식도 선택한다. 효과 확인 당시 검색 기본값은 BM25였다. 이후 사용자 결정으로 개념 포함 HippoRAG2를 개발 기본값으로 변경했다(아래 개발 기본값 변경 기록 참조).

논문처럼 `source_run_id` 경로는 검색한 passage를 직접 reader에 제공한다. 연결된 주장 전체의 원문을 다시 합쳐 넣지 않는다. 인용 위치와 추출 연결은 서버 기록에 보존하고, 답변에는 실제 원문·출처를 제공한다. 원문 QA는 업무 Requirement 전체의 충족 판정이 아니며 `requirement_ids`를 받지 않는다.

별도로 `snapshot_id` 경로는 기존 승인 주장 묶음과 조건을 유지한다. 그 경로에 한해 원문 순위에서 승인 주장으로 변환한다. 따라서 **승인 지식 소비 경로의 결과와 원형에 가까운 원문 QA의 결과를 혼합하지 않는다.** 출처의 접근 제한은 두 경로 모두 적용한다. 원문 QA가 후보를 자동 승인하거나 이전 의미 검수를 통과시켰다는 뜻은 아니다.

검색 기록에는 그래프 변형, 노드·관계·개념 수, 관계 후보 및 선택 ID, seed 점수, 전체 원문 순위와 출처·주장 ID, 임베딩 모델, fallback 여부, 경과 시간을 저장한다. QA에는 개념을 사실 근거로 넣지 않는다. 출처 제한·요구 변경·필수 승인 의미를 포함하는 기존 경계는 유지한다.

## 비교 기준과 입력 용량 수정

v1~v3의 연결 점검은 부산의 `f265809c600e4ab692ead654ca0438f9` snapshot(승인 주장 25개)을 사용했다. 원문 순위에서 첫 구간에 연결된 주장을 한꺼번에 선택하면 답변 입력이 한 출처에 편중되는 연결 문제를 확인했다. v3에서는 기존 승인 지식 기준선 6개 응답까지 보존하고 중단했다.

**첫 완결 비교 v4는 종료된 전체 추출 실행 `899f5a8f82ac46b59c074a088c1ed5a7`과 원문 passage reader를 사용한다.** 승인된 25개만으로 제한하지 않는다. 원래 추출·개념화 결과와 원문을 고정하여 검색의 효과를 비교한다. 개념화 기록 280개는 고유 개념 수가 아니다. 기존 추출의 품질을 새로 입증하거나 새 모델로 추출을 재실행한 비교는 아니다.

고정 참조의 BUSAN-01/05/09/13/15/17을 결과를 보기 전에 선택했다. 공통 조건, 법인 조건, 신청기한, 센터 범위, 두 문서의 결합, 두 기간의 구분을 포함한다. 질문·선택지만 제품 입력에 제공하며 참조 정답은 답변 저장 후 코드 채점한다. 같은 모델·질문·자료·한도·답변 프롬프트로 아래 네 군을 실행한다.

1. 동일 원문 구간의 BM25. 개념 관련어를 주입하지 않는다.
2. 원문 임베딩 검색: 그래프 순위 계산을 하지 않는 비교군.
3. 개체+사건 그래프의 HippoRAG2.
4. 개념을 포함하는 full 그래프의 HippoRAG2.

3↔4는 개념 그래프의 효과, 2↔3은 그래프 검색의 효과, 1↔4는 동일 원문 reader에서 검색 방식 변경의 효과다. 이는 이전의 동일 정보 plain/structured 개념화 입력 비교와 다른 실험이다. 작은 두 문서의 결과를 일반 정확성이나 새 추출·교정 성공으로 확대하지 않는다. v3 승인 지식 결과는 별도 참고이며 이 네 군의 점수로 합치지 않는다.

첫 실행 v1에서 QA 입력 예상량이 기존 49,152 한도를 넘었다. 같은 출처 주소·위치가 인용마다 반복되는 문제가 확인되어 실험을 중단·보존했다. 검색 실패와 QA 미실행을 품질 수치로 섞지 않는다.

v2 공통 reader에서는 원문과 개별 주장별 인용 범위를 보존하고, 출처/버전/parse/block 주소를 감싸는 원문 항목에 한 번만 둔다. HTML locator는 snapshot에 보존하고 모델 입력에 반복하지 않는다. 확인한 입력 예상량은 기존 최대 약 85,581에서 43,243 이하로 줄어 기존 모델 한도를 유지한다. 모든 비교군에 동일하게 적용한다. 이 수치는 토큰 추정치이며 실제 모델 보고 토큰 수와 구분한다.

v2의 첫 실제 답변은 입력 35,095토큰, 출력 136토큰, 모델 경과 244.72초로 저장됐다. 별도 full 그래프 점검에서 관계 개념을 처리할 때 이미 추가된 `has_concept` 연결의 `claim_id`에 접근하는 오류를 발견했다. 첫 응답과 중단 이력을 보존하고 이 오류를 고쳤다. 개체·관계 개념이 함께 있는 회귀 검사도 추가했다.

v3에서는 기존 참조 ID 변환을 출처·parse·block 식별자에도 적용했다. 원래 주소는 서버의 역변환 맵에 남는다. 개별 인용 범위와 precision도 유지한다. 이후 원문 reader를 분리한 비교는 **각 동결 버전 안에서** 비교하며 중간 버전의 일부 결과를 좋은 점수로 골라 합치지 않는다.

실행 기록은 `data/knowledge/evaluations/autoschema_graph_qa_20261007_v1/`, `…_v2/`, `…_v3/`, `…_v4/`의 새 DB·코드 동결·응답·점수로 남긴다. 기존 DB는 읽기 전용으로 열어 SQLite backup으로 복사한다.

### v5: 원문 문맥 연결 보완

v4의 실패 원인은 일부 표 셀의 검색 결과가 같은 행의 센터명 셀과 분리된 데 있었다. 기존 `autoschema.chunks()`가 이미 보존하는 표 행·rowspan·상위 제목·목록의 조건/예외 문맥을 검색 후 reader 입력에도 연결했다. 한 원문 단위별 묶음을 만들고 선택 구간에 필요한 문맥만 가져온다. 이미 제공한 구간은 ID로 참조하여 원문을 중복 직렬화하지 않는다. 문서 전체를 다시 읽히거나 별도 검수 모델을 추가하지 않는다.

원문과 추출이 연결되지 않은 구간도 검색 대상에 남긴다. 관계 seed가 없으면 원형의 원문 임베딩 fallback을 사용하며, 추출 실패를 추출 성공으로 표시하지 않는다. 이 보완은 v4 자료의 그래프를 바꾸지 않았음을 세 graph variant의 내용 fingerprint로 확인했다.

같은 여섯 질문과 네 검색 방식을 v5에서 재실행했다. 이는 **문맥 보완의 효과와 개념 추가의 효과가 서로 다른 변경**임을 구분하기 위한 비교다. 코드 검사 통과나 객관식 정답만으로 최종 의미 완성을 선언하지 않는다.

### 선택지 없는 답변의 별도 확인

v4 이후 같은 원문에서 BUSAN-15/17에 대응하는 질문을 선택지 없이 실행했다. 개념 미포함/포함 각각 2문항, 총 4개 답변을 `autoschema_graph_qa_20261007_open/`에 보존했다. 이는 사전 고정 객관식의 분모에 추가하지 않는 탐색적 확인이다.

두 조건은 같은 오류를 보였다. 미방문 양수인의 대리 신청을 본인 방문 의무로 잘못 설명했고, 15일 신청기한을 찾지 못했다. 제품의 `answered` 상태는 응답 형식과 인용 ID가 유효하다는 뜻이며 의미의 정확성 인증이 아니다. 이 결과는 객관식 6/6만으로 전체 흐름의 품질을 성공 처리할 수 없는 이유다. v5의 문맥 연결 보완 후 같은 두 질문을 개념 포함 경로에서 재확인했다.

`comparison_summary.json`, `scores.json`, `postrun_citation_revalidation.json`에 각각 측정치·원래 채점·저장 출력 재검증을 구분해 남겼다. 마지막 보완에는 매우 큰 필수 문맥의 연결 분할을 reader에서도 이어받도록 한 처리도 포함한다. 이번 24개 입력의 문맥은 이 수정 전후 동일함을 대조했다.

실제 의미는 다음과 같다.

- **개선:** v4에서 확인 불가로 남았던 동부산센터의 행과 제외 조건을 v5에서는 연결해 설명했다. 금련산센터와 2~3일 교부기간의 표 문맥도 입력에 보존했다. 이는 모든 비교군에 적용한 원문 문맥 보완의 효과이며 개념 그래프만의 효과가 아니다.
- **부분 개선:** BUSAN-15에서 미방문 양수인의 날인 요건이 없다는 잘못된 설명은 사라졌다. 그러나 개념 미포함/포함 그래프 모두 구포센터의 정확한 행을 확보하지 못해 적용을 확정하지 못했다. 정답 C를 고르고도 그 정답에 필요한 센터 범위를 확인 불가로 설명하므로 전체 의미 완성으로 계산하지 않는다.
- **동일:** 개념 미포함/포함의 상위 12개 구간은 4문항에서 같았고 2문항은 11개가 같았다. 첫 v4 비교의 4문항에서 개념 연결이 실제 관계 선택에 사용됐으므로, 기능 미실행으로 효과가 없었다고 설명할 수 없다.
- **비용:** 이번 실행의 개념 포함 경로는 BM25보다 호출 수 2배, 입력 토큰 약 1.43배, 총 경과 약 1.48배였다. 한 번의 로컬 실행으로 일반 비용 비율을 보장하지 않는다. 문맥 보완은 품질과 함께 입력량도 증가시켰다.

원래 추출 실행에서 한 주장의 근거가 최대 98개 구간에 연결돼 있다. 넓은 `mention in` 연결과 같은 문구가 반복되는 표 셀은 검색의 구별력을 제한할 수 있다. 이는 확인한 구조와 원인 가설을 구분해야 한다. 이번 비교는 추출 결과를 고정했으므로 근거 연결 정밀화의 효과를 직접 측정하지 않았다.

## 채택 판단과 남은 병목

**기능은 제품에 선택 가능한 방식으로 연결하되 기본 검색을 바꾸지 않는다.** 현재의 작은 비교에서 개념 포함 그래프의 QA 품질 우위는 확인되지 않았고 비용은 증가했다. 추출 → 개념화 → 그래프 검색 → 원문 QA를 연결한 것은 의미 있는 기능 변경이지만, 곧바로 더 정확한 업무 지식 플랫폼이 됐다는 근거는 아니다.

1. **검색 단위의 적용 범위가 약하다.** 지금은 개별 원문 구간을 검색하고 그 뒤에 표 행·상위 조건을 붙인다. 잘못된 센터의 행을 먼저 선택하면 사후 문맥 보완만으로 정답 행을 확보하지 못한다. 다음은 표의 같은 행·병합 셀·상위 조건을 검색 인덱스에서도 구별하는 작은 변경과 비교다. 관련 없는 문서 전체를 합치거나 새 검수 계층을 추가하는 것을 기본 해법으로 삼지 않는다.
2. **고정 그래프의 출처 연결이 넓다.** 이번에 재사용한 오래된 추출에서 한 주장이 최대 98개 구간을 참조한다. 최신 코드에 이미 있는 작은 추출 단위와 조건 보존 기능을 사용한 새 그래프를 별도 생성해, 더 정확한 원문 연결이 검색에 도움이 되는지 비교해야 한다. 이번처럼 기존 그래프를 고정한 비교의 점수와 혼합하지 않는다.
3. **원문이 검색돼도 해석 오류가 남는다.** 선택지 없는 OPEN-15에서 v5는 구포센터의 명시적 번호 변경 제외를 읽고도 가능 여부가 불확실하다고 답했다. 미방문 서류가 검색되지 않은 문제와 별개의 답변 판단 오류다. 같은 근거를 고정한 작은 답변 비교로 확인해야 하며, 검색 개선만으로 해결됐다고 가정하지 않는다.
4. **평가 범위가 작고 선택지가 답변을 돕는다.** 두 문서·6개 객관식과 별도 2개 자유 질문만으로 개념화 일반 품질이나 전체 Requirement 충족을 입증하지 않는다. 다음에는 위 두 원인을 고친 버전에서 기존 질문을 유지하고, 연결이 실제로 필요한 다른 소수 질문으로 전이 여부를 확인한다. 현재 사용자 판단 없이 대규모 평가나 ToG 추가 구현으로 범위를 확장하지 않는다.

이번 작업은 `codex/autoschema-graph-qa`의 별도 checkout에만 남겼다. 원래 checkout·원본 DB·중단 작업을 변경하거나 재개하지 않았다. 커밋·푸시·PR·배포는 수행하지 않았다.

## 개발 기본값 변경 — 사용자 결정

사용자 요청에 따라 `retrieval=hipporag2`, `graph_variant=full`을 API의 기본값으로 지정하고 화면 초기 선택도 개념·관계 연결 검색으로 변경했다. 앞의 BM25 유지 판단은 평가 직후의 기록이며 이 결정으로 대체된다. 이 변경은 복잡한 업무 관계·개념 검색을 중심으로 개발하겠다는 선택이지, 기존 작은 평가에서 품질 우위가 입증됐다는 뜻이 아니다.

BM25와 원문 임베딩, 개념 없는 그래프는 명시적으로 선택할 수 있다. 기존 문서/승인 주장 BM25 비교 runner에는 `retrieval=bm25`를 명시해 과거 비교의 의미가 기본값 변경으로 바뀌지 않도록 했다. 모델 실행 결과·고정 코드·DB는 재작성하지 않았다. 기본 요청이 실제 full 그래프 검색으로 들어가는 기존 통합 검사와 화면 기본 선택 검사를 확인한다.

### 출처 분산과 중복 후순위의 정확한 의미

현재 BM25의 `FrozenIndex.search()`는 점수가 양수인 검색 결과를 `source_group`별로 묶고, 각 그룹에서 한 개씩 번갈아 최종 목록에 넣는다. 업무 지식 QA에서는 source_group이 원문 버전 ID다. 한 문서가 검색 슬롯을 모두 차지하는 것을 줄이는 처리이며 BM25 점수 공식 자체와는 별개다.

중복은 의미 유사도 판단이 아니라 공백을 제거한 본문이 정확히 같은지로 판정한다. 같은 본문은 삭제하지 않고 고유 본문 뒤로 배치한 뒤 전체 한도를 적용한다. 따라서 동일 문구라도 출처·대상·조건이 다른 경우를 의미적으로 구별하는 중복 제거는 아니다.

그래프 검색에도 근거 편중과 중복을 줄이는 목적은 필요하다. 다만 무조건 문서별로 같은 수를 선택하면 무관한 출처가 포함되거나 실제로 필요한 한 문서의 여러 근거가 밀릴 수 있다. 동일 문구의 표 셀이라도 센터·기간·범위가 다르면 같은 근거로 취급해서는 안 된다. 적용한다면 관련성 있는 결과 내에서 출처/적용 범위를 보존하며 중복과 편중을 조정하고, 비교군에 같은 정책을 적용해 그래프 효과와 분리해야 한다. 이번 기본값 변경에는 해당 검색 후처리를 추가하지 않았다.

구현·검사·보고서는 이번 브랜치에서 함께 커밋·푸시한다. 로컬 평가 DB와 원시 실행 자료는 기존 보존 경로에 남기며 Git에 강제로 추가하지 않는다.
