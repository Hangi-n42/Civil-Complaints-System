## 왜 이 범위를 바꿨는가

K4에서는 정상 역할 정의의 조건·예외가 불필요하게 unknown이 되었고, 원문 밖 정의 추가도 unknown에 머물렀다. 연결 오류 표지를 맞힌 경우에도 공통 reason은 정상 원명제 설명뿐이어서 수정에 쓸 사유가 부족했다. 누락 의미 판단은 이미 제공된 관계를 무시하거나 현재 묶음 밖 구간까지 누락으로 단정했다.

기존 세 판정(supported/refuted/unknown), Critic 정규화, 후보별 수정, 원문 구간, 직렬 실행기를 확장했다. 새 판정 엔진·N/A 상태·의미 추정 정규식·추가 모델 검열·별도 원장은 만들지 않았다. 원시 응답과 과거 평가를 유지하면서 생산자부터 실제 재추출 소비자까지 범위를 맞췄다.

| 단계 | 구현 | 커밋 |
| --- | --- | --- |
| L1 | 정의의 원문 적합성과 외부 사실 여부 구분. 정의 전체가 주장한 한정에 조건·예외 판정 적용. 빈 필드 자동 지지는 하지 않음 | `e5f565a` |
| L2 | 끝점별 binding_reasons 추가. 새 binding_reason_contract에서만 필수화. endpoint/보류 사유·Builder 입력에 해당 이유 전달, content_error는 명제 reason 유지 | `6a929d0` |
| L3 | 실제 분할 primary의 저장 근거·coverage로 원문 역할과 소유 범위 재산정. 누락 인용과 재추출 대상에 같은 범위 적용 | `720f870` |
| L4 동결 | 실제 제품 projection, 별도 정답, 모델·코드·예산·독립 교정 관측 경로 고정 | `e15e9d1` |

- L2의 review_contract는 checks-v1 유지, 별도 binding_reason_contract=per-endpoint-v1 추가. 옛 레코드는 binding_reasons={}로 읽으며 소급 판정 변환 없음. raw relation과 관측에는 불필요한 연결 이유를 요구하지 않는다. 서버는 키·공백·길이·참조를 검사하고 설명의 의미적 참 여부는 판정하지 않는다.
- L3는 다른 항의 원문을 지우지 않고 참고로 남긴다. 정확 인용이 항보다 좁으면 실제 제공된 본문 안에만 주소 view를 추가하고 기존 text_from으로 본문 중복을 제거한다. legacy 블록 ID만으로 세부 항의 소유 범위를 추정하지 않는다.
- 소유 범위는 review_batches→MissingMeaning 생성 schema→모든 인용의 정규화 검사→queue_recovery→recovery_groups까지 유지한다. 마지막 단계에서 상위 구간으로 다시 넓어지던 경로도 수정했다. 다른 일반 검수의 참고 인용은 제한하지 않으며 전역 미처리 coverage를 완료로 바꾸지 않는다.
- prompt 버전은 v46→v47→v48. 새 의존성 없음, 기존 raw/data/DB 보존.

## 서버 계약 확인

- L1: 관련 판정 검사 9 통과(0.11초). 정상 역할, 정의 본문의 조건 누락, 추가 구체 사실, 필요한 참조 부재에 대해 공급된 판정을 저장·쟁점·수정 요청으로 구분하는 검사. 프롬프트 문자열 검사는 추가하지 않았다.
- L2: binding/corrections/analysis 관련 112 통과(16.49초). 끝점 이유와 명제 이유 분리, 공백·누락·unknown·과거 레코드·raw relation, Builder 전달, 재개·현재 지문·A3 경계 확인.
- L3: 최초 관련 검사 87 통과·7 실패. 새 테스트의 자료 구조 누락 4건을 수정했고, comparison_only에 분석 역할이 되살아난 회귀 1건을 고쳤다. 기존 전체 coverage/역할 불변 기대 2건은 현재 primary coverage와 원문 불변을 검사하도록 갱신했다. 실패 경로 포함 8건 재확인 통과(1.55초), 좁은 인용·실제 생성 schema 추가 후 해당 6건 통과(0.80초), 최종 recovery_groups 변경의 기존 2건 통과(0.33초). 이미 통과한 전체 검사를 반복하지 않았다.
- 위 결과는 결정적 응답을 사용한 서버 계약 검사다. 자연 모델의 의미 정확도나 자동 교정 성공률을 뜻하지 않는다. 기존 Pydantic serializer 경고는 초기 L3 관련 검사에서 13개 관측됐다.

## 증거 보존과 해석 범위

- 독립 AI 의미·평가 전문가의 최종 검수 모두 완료. E 경계 및 전체 진단 실패, 교정/C2/current 0회를 확인했다. E-A의 잘못된 포함 주장은 원시 응답부터 존재하며 정규화가 새로 만든 오류가 아니다. 서버 계약 검증·실제 모델 관측·독립 AI 검수·사람 효용 측정을 구분한다.
- 로컬 `data/knowledge/semantic_l4_20261003/diagnostic_once/`에 호출별 원응답·정규화·요청·복사 DB를 보존했다. `inspection/`에 판정과 무결성 검사를 기록했다. 해당 데이터와 원문·DB는 커밋하지 않는다.
- 무결성 검사에 포함한 고유 동결 파일 75개 해시 일치. 세 DB의 sources, versions, blocks, evidence, ontology_versions, ontology_heads, decisions, changesets, snapshots, snapshot_events가 원본과 동일하다. 정규화 근거 4개의 원문·위치·버전·parse·evidence→block 연결 일치. 사람 수락 0건.
- 검사 스크립트 복사 후 이전 K4 동결 파일 경로가 남아 첫 무결성 검사가 KeyError로 중단됐다. 검사 도구의 경로만 L4로 수정해 재확인했으며 제품·동결 설정·진단 원응답은 바꾸지 않았다.
- K4의 E 대조는 양쪽 유형을 함께 제공했고 L4는 실제 제품 projection이므로 E-A에서 정상 입주자 유형이 빠졌다. 판정 변화가 L1·L2·L3 중 어느 하나 때문인지, 비교 유형 부재 때문인지 이번 결과로 특정할 수 없다. 전체 성능 향상·회귀의 단일 원인 주장도 하지 않는다.
