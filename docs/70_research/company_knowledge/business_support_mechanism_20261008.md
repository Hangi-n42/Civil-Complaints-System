## 1. 비교 근거와 범위

- [Context-faithful Prompting](https://aclanthology.org/2023.findings-emnlp.968/)은 문맥을 화자의 진술에 귀속하는 표현과 반사실 예제를 평가했다. 이번에는 화자 귀속 표현만 바꿨다. 반사실 예제를 추가하거나 기존 예제 A/B를 반복하지 않았다. 논문의 독해·관계 추출 결과가 한국어 행정문서 조건 판정 성능을 보증하지 않는다.
- [Context-aware Decoding](https://aclanthology.org/2024.naacl-short.69/)과 [공식 코드](https://github.com/xhan77/context-aware-decoding)는 문맥 유무에 따른 토큰 분포 차이를 증폭한다. 이번 비교도 같은 선택 토큰 접두부에서 전체 어휘 분포를 대조한다. 응답 투표나 상위 일부 토큰의 대조가 아니다.
- [MiniCheck](https://aclanthology.org/2024.emnlp-main.499/)는 근거 문서에 대한 작은 검증 모델을 학습하는 접근이다. [원 Flan-T5-Large 공식 카드](https://huggingface.co/lytang/MiniCheck-Flan-T5-Large)는 MIT, English, supported/unsupported 이진 출력을 명시한다. Bespoke 7B의 라이선스 제약을 모든 변형에 적용하지 않는다. 논문 성과와 이 프로젝트의 한국어·미지지/명시 반증/자료 부족 분리·오류 위치 성능은 별개다. 이번에 새 학습·가중치 설치·제품 모델 실행을 하지 않았다.

기존 입력 축소, 원문 우선 읽기, 조건 구조화, span 연결, Qwen/Gemma thinking, EXAONE, 대조 예제 실패는 이전 보고서에 보존했다. c13/c46/c47은 반복 노출된 개발 자료다. 박물관 자료는 이번 화자 비교 이전에는 제품 모델에 실행되지 않은 별도 문서였으나, 이번 실행 이후에는 미노출 자료로 다시 부를 수 없다.

## 4. CAD 실행 경계

Ollama 0.35.0의 공개 API는 [해당 태그 routes.go](https://github.com/ollama/ollama/blob/v0.35.0/server/routes.go)에서 top_logprobs를 20 이하로 제한한다. 앱에 포함된 native `llama-server` 0.4.1-dev, commit `161755f29`의 `/completion`은 같은 설치 GGUF에서 전체 248,320개 어휘의 logprob를 반환했다. 새 엔진 설치나 가중치 다운로드는 없었다.

실제 호스트는 Apple M4 Max, 메모리 36 GiB, 논리 CPU 14개, macOS 27.0.1 arm64이며 기존 프로젝트 Python 3.11.9를 사용했다. 운영체제 보고값을 `environment.json`에 저장했다.

4회의 단일 토큰 기능 probe에서 ID 전 범위·중복 없음·유한 점수, alpha0 argmax와 native greedy 일치, 두 prefix에 외부 선택한 동일 토큰을 붙여 다음 분포를 얻는 동작을 확인했다. 점수는 raw logits가 아닌 post_sampling_probs=false의 logprob이다. 확률 합은 1.00002~1.00192로 수치 근사 차이가 있었다. 정규화 상수 차이를 제외하면 `(1+alpha)logp(context)-alpha logp(no context)`는 logits 식과 같은 argmax를 갖지만, 수치 근사와 구현 차이는 남는다. 기능 probe는 의미 정확도 결과가 아니다.

동결 `cad/freeze.json`: 같은 native 엔진·GGUF·수동 ChatML/think-off 템플릿에서 alpha0과 alpha1, c13/c46/c47/A02 각 1회, 최대 192 tokens. alpha=1은 단위 대조 강도로 사전 고정했고 최적값이라는 주장은 없다. 원래 지지·조건 규칙은 유지하되 두 팔 모두 후보 하나와 compact status/reason 출력으로 변경했으며, 기존 checks/evidence/preservation 출력 지시는 충돌하지 않게 제거했다. 문서 없는 분포에서도 후보·지지 판정 지시는 유지하고 blocks/source_parents/source_versions만 제외했다. 후보 내부에 인용문·운영자 정정·평가 라벨은 없다. 정답 grammar나 토큰 필터는 사용하지 않았다.

각 단계의 전체 점수 배열, raw 응답 해시, 두 분포의 선택 점수, 선택 토큰, prefix 길이, timing/cache 정보를 보존한다. 고유 입력 길이와 엔진의 재처리 토큰·분포 호출 수는 별개다. Ollama와 native 엔진을 동시에 상주시킨 실행은 없다. 수동 템플릿은 Ollama 제품 템플릿과 같다고 입증하지 않았다.

c13 alpha1은 `supported` 한 단어 뒤 EOS로 끝나 이유와 JSON 계약을 충족하지 못했다. 첫 토큰 17675의 context/no-context logprob는 -6.81604/-13.62765, 대조 점수는 -0.00443이었다. 같은 단계의 native greedy 토큰 4754는 -0.42718/-0.19628, 대조 점수 -0.65807이었다. 즉 해당 단계에서 대조식이 일반 분포의 선호보다 형식을 벗어난 토큰을 선택했다는 것은 저장 배열로 확인된다. 이 국소 수치 설명을 모델 내부 지식의 원인이나 모든 CAD 설정의 결과로 확대하지 않는다.

c46 alpha1의 진행 중 native 서버 로그에서 큰 캐시 항목 누적과 응답 지연을 관찰했다. 같은 구간의 engine timing은 prefix 대부분을 재사용하고 `prompt_n=1`을 처리했다. 따라서 전체 prefix를 매번 다시 계산했다고 설명하지 않는다. 캐시 누적·메모리 압박과 지연의 인과 원인은 이 관찰만으로 확정할 수 없다. 완료된 생성 경계 이후 남은 비교는 같은 서버 명령·가중치·설정으로 새 프로세스를 시작하도록 동결했다. 이 운영 복구는 생성 중 토큰 접두부나 대조 강도를 바꾸지 않지만, 앞선 실행과 프로세스 캐시 이력이 다르므로 환경 차이로 기록한다.

8팔 중 7팔은 EOS, 1팔은 실행 실패다. 엄격한 JSON 계약 통과는 alpha0 3/4, alpha1 1/4이고, 판정·이유·형식을 함께 충족한 것은 각각 2/4, 1/4다. 실패·미완료를 분모에서 숨기지 않았다. 이는 4개의 고정 진단 결과이며 일반 정확도 추정이 아니다. A02도 앞선 화자 비교에 이미 사용했으므로 CAD의 독립 미노출 보류 평가라고 하지 않는다.

A02 alpha0의 형식 실패는 동결 진단의 Markdown 금지·원시 `json.loads` 계약 기준이다. 기존 제품 파서의 코드 블록 처리와 같다고 입증하지 않았으므로 제품 통합 자체가 불가능하다는 결론으로 확대하지 않는다. 내용상 자료 부족 판정은 올바르다.

A02 alpha1은 16개의 선택 토큰 이후 다음 context 분포에서 `IncompleteRead(20713147 bytes read, 4114936 more expected)`로 종료됐다. 원인은 확인 불가다. 메모리 부족·모델 실패로 단정하지 않으며, 이 응답을 자료 부족 보존 성공으로 계산하지 않는다. 활성 생성의 설정을 바꾼 재시도는 없다.

실패 result 저장 뒤 driver가 반환하고 wrapper가 서버를 정리한 순서를 로그·시각·종료코드로 확인했다. 따라서 관찰한 서버 종료는 실패 후 cleanup이며, 도구 실행 수명에 의한 선행 강제 종료는 확인되지 않았다. 완료 분포는 전체 점수 배열과 raw 응답 해시로 보존했다. 불완전 HTTP 본문 자체는 저장되지 않았고, 오류의 수신/미수신 byte 수·직전 분포·선택 접두부·경과 시간은 남아 있다.

완료 분포 504개, 각 248,320점, 총 125,153,280점의 배열을 보존했다. 추가로 불완전 HTTP 응답 1건이 있으며 완료 분포와 구분한다. 선택 출력은 총 374 tokens와 완료 7건의 EOS다. 8팔 경과 합계는 3,579.746672초(약 59분 40초), 이 중 c46 alpha1이 3,261.550872초다. 서버 로딩·기능 probe·관리 실행 시간은 이 합계에 포함하지 않는다.

**시험한 alpha1 CAD는 기각한다.** 핵심 c47 검출 개선이 없고 정상 c13의 출력 계약도 악화했다. 추가 alpha·grammar·형식 재시도나 보류 자료 확장은 하지 않았다. 화자 귀속과 CAD 모두 채택 근거가 없어 새 자동 오류 발견→자동 교정→같은 요구 답변 연결은 수행하지 않았다. 아래 관리 경로는 기존 명시 정정본과 실제 원문 변경을 사용하는 독립 진단이다. 이 기각을 CAD 이론 전체의 실패나 유일한 모델 내부 원인으로 확대하지 않는다.

## 5. 독립 변경 영향 연결

기존 `review_impacts`는 요구 질문·상태·현재 평가 포인터를 넘기지만 해당 평가의 실제 의미·후보·근거를 조회하지 않았다. 이 때문에 실제 R02 비영향 이유가 “정정 대상이 R05”라는 소유 ID에 기대고 있었다.

수정은 같은 공유 함수에서 포인터가 가리키는 정확한 run/assessment/revision/source versions를 확인하고, 저장 의미의 조건·미확정 전제·연결 후보·오류 후보·검수 상태·원문 부모 문맥을 전달한다. 포인터 불일치는 unknown으로 남긴다. 두 기존 변경 경로의 상태 저장은 공통 작은 함수로 옮겨 판정 중 요구 또는 현재 평가가 바뀌면 unknown/needs_review를 기록한다. 기존 평가 포인터나 원문을 정답에 맞게 고치지 않는다.

후보별 chunk 근거의 반복 제공은 약 190만 bytes였다. 모델 호출 전에 이를 발견했고 기존 `compact_claim`, `join_source_meaning`, 원문 bundle을 재사용했다. 원문 부모와 미확정 의미를 삭제하거나 컨텍스트 한도를 늘리지 않았다. 전체 8개 정정+R02/R04 입력은 축약 후에도 출력 예약 포함 64,902 추정 tokens로 49,152를 초과했다. 이 전체 경로는 미완료다.

제한 진단은 실제 저장 `transfer_certificate` 정정 1개에 대해 R02/R04를 각 1회 판단한다. 이는 실험 범위 선택이며 제품에서 다른 7개 정정을 버리는 코드가 아니다. 동결된 두 요청은 43,592/24,479 추정 tokens, 원문 86/35 blocks이다. 정상 대조 R04의 신청 기한·당일/2~3일 교부·제외 의미와 R02의 기존 저장 조건을 직접 대조한다.

실행 `e692b28a63e14bb38af30e0e3672d361`에서 R02는 affected로 바뀌어 `needs_review`가 됐고, R04는 unaffected로 기존 `partial` 상태를 유지했다. 두 현재 평가 포인터는 그대로다. R02의 이유는 실제 미방문 부모 b29와 서류 b30/b31, 저장 의미를 연결했으며 정정 소유 ID가 R05라는 이유로 제외하지 않았다. R04는 기존 15일·당일·2~3일·제외 의미가 변경되지 않았다는 독립성 근거를 제시했다. 실제 2호출은 입력 28,186/출력 839 tokens, 응답 시간 208.687612초다.

이는 **제한된 정정 영향 전달과 재검토 상태 갱신의 개선**이다. R02 후속 재검수·교정·QA나 R04 전체 업무 완료가 아니다. R02 설명에는 “미방문 시에만 vs 항상”이라는 비교가 남았고, 원문이 반대 상황의 면제·금지를 입증하지 않으므로 설명 오류·한계로 보존한다. 과거 5요구·8정정 결과와 이번 2요구·1정정 결과는 입력 범위가 달라 엄격한 동일 입력 A/B가 아니다.

## 6. 독립 조건별 답변·버스 갱신 범위

R05는 기존 동일 스냅샷·전체 질문에서 정확한 공개 질문 구절 두 개를 별도 answer item으로 나눴다. 현재 `reviewed_items` 기능으로 1회만 진단하며 원하는 기관 목록이나 정답을 입력하지 않는다. 교부 기간에서 번호 변경 권한을 추론하면 실패다. 이전의 requested_parts/directly_stated 실험을 복원하지 않는다.

실행 `331cbe46fc2a4a0084818c1b396f6c81`, 스냅샷 `f238a00cc00b474fad2f890782510a35`에서 변경 항목은 지역 번호 반납 조건과 부전·구포·동부산의 제외 범위를, 비변경 항목은 명지·금련산·세 센터의 업무 범위를 선택했다. c47 지역 조건, c13 미방문 조건, 당일·2~3일을 보존했고 `상시`나 전체 질문 직접 지지 표시는 추가하지 않았다.

그러나 최종 답변은 검토된 의미의 나열이며, 변경을 처리할 기관을 확정하는 데 어떤 연결 근거가 부족한지 구체적으로 설명하지 못했다. 일반적인 “추가 연결 전제의 독립성은 확인되지 않았습니다” 10개만 붙였다. 따라서 **조건별 공개 항목 분할만으로 같은 질문에 정확하고 유용한 답을 완성하지 못했다.** 새 제품 필드·생성 단계를 추가하지 않았고 이 결과를 자동 판단 개선으로 채택하지 않는다. QA 시도 1회에 기존 그래프 검색 필터와 QA 생성의 실제 모델 호출 2회가 포함되며, 응답 합계는 131.526307초다. 필수 검토 의미를 강제 포함하는 기존 검색도 사용했으므로 순수 그래프 순위 개선이라고 하지 않는다.

저장한 모델 응답은 네 항목 모두 `unconfirmed=[]`와 선택한 `direct_fact` 목록만 반환했다. 구체적인 부족 연결이 생성된 뒤 렌더링에서 사라진 것은 아니다. 현재 계약 자체가 자유로운 조건별 결론 작성보다 의미 선택·기존 문장 렌더링에 머무는 한계와, 해당 선택을 충분하게 취급한 모델 판단을 함께 구분한다. 최종 `answered` 상태나 필수 포함된 19개 후보를 질문 충족으로 계산하지 않는다.

버스는 실제 저장된 after JSON의 ROUTE_ID `100100143`, 순번 12/13만 기존 정형행 직접 읽기로 처리한다. 모델 재추출·개념화 없이 새 현재 범위 후보를 만드는 경로이며 동일 pool 재검토가 아니다. 같은 BUS-NEW-13 요구를 변경 영향→새 평가/현재 포인터→스냅샷→full 검색→QA까지 연결한다. 순번 12의 값·연결 유지와 과거 원기록 보존을 각각 확인한다. 과거의 정확한 v1/v3 후보를 서로 현재 오류로 보았던 실패는 별도 남으며, after 선택만으로 일반 다중 버전 검수 문제를 고쳤다고 주장하지 않는다.

[이전 보고서](business_repair_retrieval_20261007.md)에는 이후 snapshot `5b28faefe77a4b609629530ff36bd19e`에서 최신 순번 13과 정상 순번 12 값을 맞힌 QA도 있다. 이는 206후보를 유지한 후속 검증이며 이번의 현재 2행 후보 갱신과 다르다. 이전의 정상 결과를 지우거나 이번을 최초의 올바른 버스 QA라고 표시하지 않는다. 기존 두 날짜는 2025-05-13/2025-06-24 file_snapshot이며, 60행 중 1행의 4개 값이 변하고 59행은 동일하다. 실제 도로 이동·운영 정책 변화·보행 효과를 증명하지 않는다.

이번 영향 실행은 `9fd8657075c84ba2b4b9da2e52ac3f82`, 새 2행 후보 실행은 `e82031d7f77a4326b23601677281c4c0`, 스냅샷은 `996dcfe5a4054404af531942ef1b5862`다. 순번 12는 unaffected, 기존 연결이 없던 순번 13은 affected로 찾았다. 다만 순번 13의 부가 `new_relevance=false`는 연결 없는 요구의 신규 관련성을 표시하지 못한 불일치로 남긴다.

두 후보 모두 실제 eligible 목록에 있었고 승인 목록은 그 목록과 같았다. 후보 승인과 요구 전체 완료는 별개다. BUS-CONTROL-12는 첫 종합의 범위 오류를 보존한 채 기존 재검토에서 satisfied, BUS-NEW-13은 partial로 현재 평가 포인터가 갱신됐다. 수동으로 상태를 satisfied로 바꾸지 않았다. 버스 전체 실행도 partial이다.

순번 13의 실제 모델 입력에는 `period=최신 제공 정차표 스냅샷`, 파일 `1127_after.json`, `file_snapshot=2025-06-24`가 전달됐다. 날짜 누락은 아니다. 동일 원문 계보의 title은 `1127_before.json`으로 남아 filename과 달랐고, 해당 원문 검수 단위에는 after 한 버전과 로컬 범위만 주어졌다. 이 제목 차이를 최신성 미확정의 단독 원인으로 확정하지 않는다. 종합은 최신성 finding을 `not_required`로 처리했으나 `source_completeness=unknown`이 남아 요구는 partial이다. QA는 이 한계를 표시하지 않은 채 답했다. **제공 스냅샷의 값 전달·새 포인터·스냅샷 연결은 확인했지만, 최신 제공 범위의 판정과 요구 전체 완료는 미달이다.** 현실의 현재 값이라는 보증도 하지 않는다.

## 7. 중단된 R02의 동일 실행 재개

R05 명시 정정이 저장된 `fd10ffa6e523437eb2ab1b31411dba8b`의 119개 후보·26개 참고 의미를 같은 R02 질문으로 재검수했다. 과거 R02 평가는 정정·참고 의미가 없고 후보도 달랐으므로, 이 후속 입력은 과거 실패의 무변경 재시도가 아니다. 정정 소유는 R05로 유지했고 R02 정답 주입·후보 재추출·개념화·자동 교정은 하지 않았다.

실행 `d48c7584989c4ef28050dce84668971c`은 사용자의 중단 지시에 따라 18개 완료 응답(신규 16개, 기존 재사용 2개)을 보존하고 마지막 종합 중 취소됐다. 신규 완료 응답 시간은 933.693110초이며 저장되지 않은 취소 응답의 토큰·비용은 확인 불가다. 10월 9일 명시적인 재개 지시 후 같은 실행을 이어갔다.

일반 resume가 저장 후보 풀 표시·참고 의미를 잃어 재추출 경로로 들어가는 문제를 확인해, 같은 원문·요구 버전 검사 이후 해당 저장 입력을 복사하는 6줄만 추가했다. 일반 캐시 조건은 바꾸지 않았다. 또 `summarize_local`의 set 순회로 `claim_support` 객체 키 순서가 프로세스마다 달라 기존 종합 메시지와 원시 문자열이 일치하지 않았다. 이번 진단 드라이버의 완료 종합 단위 `912667eb91d345b68b06682195070225`에만 객체 순서를 복원했다. 값·문장·배열·system/schema/reference_map·모델 설정/identity가 같고 복원 후 전체 원시 메시지가 저장 메시지와 정확히 같을 때만 기존 캐시를 사용했다. 다른 차이는 예외로 중단한다. 전후 해시와 변경 JSON 경로는 `r02_resume/map_order_recovery.json`에 남겼다. 제품 캐시 완화나 평가 결과 복사가 아니다.
