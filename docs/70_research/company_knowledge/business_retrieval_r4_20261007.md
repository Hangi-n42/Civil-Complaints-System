## 실제 변경

- `FrozenIndex.rank()`로 양수 BM25 점수 순위를 노출했다. 기존 `search()`의 문서별 번갈아 선택·본문 문자열 중복 후순위는 다른 기존 소비 경로에 유지하고, 순수 `source_run_id` 비교에서는 사용하지 않는다. 네 방식에 개념 관련어·필수 승인 claim 강제 포함을 주입하지 않는다.
- `select_passages()`는 원순위를 따르면서 **같은 출처 버전·parse·block·span과 필수 문맥이 이미 제공되는 경우에만** 후순위로 둔다. 다른 센터·조건·기간·출처의 같은 문구는 합치지 않는다. 문서 할당 비율, 추가 모델, top-k 확대는 없다. 원순위·최종 선택 순위·후순위 사유·어느 선택 구간이 문맥을 제공하는지 저장한다.
- `source_context()`의 기존 표 행·rowspan·제목·목록 조건 선택을 그대로 재사용한다. 후순위 구간은 삭제된 사실이 아니라 선택 구간의 문맥으로 전달된다. 더 이상 새로운 원문 묶음이 없을 때는 후순위 항목으로 남은 슬롯을 채운다.
- `passage_search_texts()`는 같은 필수 문맥을 검색용 본문에 붙인다. BM25와 BGE에 같은 본문을 제공하며 그래프 관계·passage ID·원문 인용은 재작성하지 않는다. 그래프 PPR과 관계 선택 방법은 기존 방식이다. 실제 검색 본문은 `passage_index`에 저장하고 임베딩 캐시 키에도 포함한다.
- 공통 선택과 검색 본문 변경은 `source_run_id` 경계에 적용한다. 승인 snapshot은 기존 claim 묶음·필수 승인 의미 계약을 유지한다. 원문과 승인 claim의 단위가 다르므로 같은 선택을 적용한 것처럼 비교하지 않는다.

## 후처리만 변경한 저장 순위 재생

`data/knowledge/evaluations/business_retrieval_r4_20261007_replay_v1/`에 원래 본문 인덱스의 저장 순위를 재생했다. 원문 run 전체 해시·질문·선택지·모델·설정·passage 주소·claim 대응이 같음을 확인했다. BM25 원점수 순위는 CPU로 다시 계산했고, 기존 BM25 전용 선택 결과도 별도 저장했다. 모델 호출은 0이다.

| 질문 | BM25 교체 슬롯 | entity_event 교체 슬롯 | full 교체 슬롯 | 필요한 원문 |
|---|---:|---:|---:|---|
| OPEN-15 | 5 | 1 | 1 | 그래프 두 군의 미방문 서류 누락 유지 |
| OPEN-17 | 3 | 4 | 4 | 그래프 두 군의 매매 15일 누락 유지 |
| BUSAN-01 | 2 | 0 | 0 | dense·두 그래프는 reader 정확히 동일 |

교체 슬롯은 각 방식의 **raw top-12 대비**이며 과거 BM25 번갈아 선택 대비 수치가 아니다. OPEN 두 질문의 저장 dense 순위는 없어 미실행으로 남겼다. 이 단계는 저장 순위·문맥 재생이고 새 QA 점수가 아니다.

OPEN-15의 full 원순위에서 미방문 위임장 구간은 34위, 양도증명서 양수인·특약사항 날인은 45위였다. OPEN-17 매매 15일 문장은 31위였다. 이 구간들은 reader 필수 문맥에 업무 제목·미방문 조건·기간 제목이 있었지만, 기존 순위 계산은 구간 본문만 사용했다. 후처리만으로 필요한 구간에 닿지 못했으므로 검색용 문맥 보완을 별도 변경으로 진행했다. 이것이 유일한 품질 원인이라는 주장은 아니다.

- **OPEN-15 그래프 실패 유지:** entity_event/full은 위임장·양수인/특약 날인 원문이 실제 reader에 없었다. 새 인덱스의 해당 구간 순위는 27/28위였고 공통 선택 후 12개에 들지 않았다. 미방문 조건 제목을 선택한 것만으로 그 하위 서류가 전달되지는 않는다. 두 답변 모두 구포센터의 명시적 제외도 불확실로 해석했다. 검색 누락과 QA 오독이 동시에 남았다.
- **BUSAN-01 정상 대조 유지:** 네 군 모두 기존 고정 정답 B와 공통사항을 유지했다. entity_event/full 선택 12개 중 11개가 같았다. 이 세 질문에서 개념 추가의 QA 우위는 확인되지 않았다.

### 표행 문맥의 별도 원인 수정

v2 원시 입력 확인에서 `autoschema.chunks()`의 일반 `siblings/notes` 분기가 table 셀의 공통 `element_path`를 일반 형제 문맥으로 해석하는 결함을 찾았다. 12·13·14행의 제외 셀이 명지·금련산을 포함한 다른 행에도 `supports_context_ids`로 연결돼 있었다. 예컨대 금련산 이전등록 셀의 검색 본문에 부전·구포의 번호 변경 제외와 동부산 말소/저당 제외가 함께 붙었다. 명시적 row/column은 남았지만 적용 범위가 다른 조건을 필수 문맥이라고 연결한 것은 별도 오류다.

기존 정확 표 행·rowspan·머리글 분기는 유지하고, 일반 siblings 후보에서 `locator.row`가 있는 셀을 제외하는 한 줄을 수정했다. 타행의 표 셀 예외를 일반 주석으로 다시 전파하지 않는다. 실제 표행 밖 주석과 기존 목록의 조건·예외 처리는 유지한다. 표행·긴 문맥을 포함한 그래프 검사 16개, 기존 일반 목록/상위 조건/TXT 문맥 검사 3개가 통과했다. 승인 요구 QA 검사 1개는 앞 단계에서 통과했다.

`live_v2/context_row_fix_replay.json`에 모델 없는 수정 전후를 저장했다. 171 passage 중 54개 검색 본문에서 타행 조건이 제거됐다. 기존 raw 순위를 고정한 OPEN 8개 결과에서는 선택 ID 변화 0이었고 필수 문맥의 잘못된 타행 연결이 바뀌었다. **새 검색 순위·새 QA 품질 검증은 아니다.** v2 원시 입력과 답변은 수정하지 않았다.

### 선택된 부모 목록에서 빠진 하위 근거 연결

추가로 원문의 `양수인 미방문시` 부모 `li::text` 아래 `ul`에 위임장/신분증과 양도증명서 날인의 두 자식 `li`가 있음을 확인했다. 기존 연결은 자식→부모 방향만 보존했고, 부모가 검색됐을 때 그 조건의 실제 서류가 붙지 않았다. v2 OPEN-15 그래프 QA 입력의 부모 제목만 존재한 현상과 일치한다.

실제 `element_path`의 `li::text` 부모에서 바로 아래 `ul/ol` 하위 구조로 제한하여 필수 문맥을 연결했다. 다른 부모의 형제 목록·다른 출처·문서 전체를 추가하지 않는다. 키워드나 정답 위치로 분기하지 않으며, 긴 하위 항목은 기존 연결 분할로 보존한다. 실자료 `list_parent_preflight.json`에서 부모만 선택해 두 자식 서류가 모두 전달되고 양도인 신청의 별도 목록은 붙지 않음을 확인했다. 그래프/목록/상위조건/TXT 검사 20개가 통과했으며 이 사전 확인의 모델 호출은 0이다.

수정 후 실제 확인은 새 `business_retrieval_r4_20261007_live_v3_full/` 사본에서 개발 기본 full의 OPEN-15/OPEN-17/BUSAN-01 세 질문으로 한정했다. v2의 네 군 비교를 최종 코드의 네 군 결과로 바꾸지 않으며 네 군 12개를 반복하지 않았다. 제품 코드는 v2 동결 사본에서 `autoschema.py`의 표행·중첩 목록 문맥만 바꿨다. 같은 메시지·스키마·참조 맵·recipe·모델의 저장 출력은 기존 제품의 정확 재사용 경계로 가져왔다. GPU를 조율해 실행했고 QA 프롬프트는 변경하지 않았다.

최종 문맥에서 공통 선택만의 실제 QA 효과를 분리하기 위해 raw top-12 대조 1건을 추가했다. OPEN-15→OPEN-17의 고정 순서에서 원시 순위와 공통 선택의 reader가 처음 달라지는 OPEN-15를 해당 ON 답변 생성 전에 고정하고, 두 reader와 해시를 `ablation_preselection.json`에 보존했다. 해당 ON은 위 세 건 중 결과를 사용했다. OFF는 동일 snapshot·질문과 ON의 정확한 전체 raw 순위 해시를 검증하고 재사용하여 순위 생성 변동을 제거했다. QA 입력이 저장 요청과 정확히 같으면 다시 호출하지 않도록 했으나 이번 네 QA 입력은 모두 새 요청이었다. 최대 QA 요청 4건을 지켰으며 다른 검색군이나 factorial 반복은 없다. 이 비교도 최종 문맥의 full 한 질문에 한정하며 개념 추가의 효과로 귀속하지 않는다.

### v3 결과와 실제 QA의 남은 한계

네 요청 모두 답변을 저장했고 실행/형식 실패는 없었다. 실제 새 QA 4회, 기존 관계 선택 3회 정확 재사용, 새 입력 19,494·출력 867토큰, 새 모델 경과 합계 157.17초다. 원본 run·동결 코드 불변, 네 요청의 검색 본문 동일, OPEN-15 ON/OFF raw 순위·QA system·schema 동일과 reader 입력 차이를 확인했다. `summary.json`, `input_output_audit.json`, 각 요청 JSON과 동결 runner에 기록했다.

| 질문/선택 | 새 입력 / 출력 토큰 | 확인 결과 | 실행 ID |
|---|---:|---|---|
| OPEN-15 ON | 5,424 / 294 | 미방문 위임장·양수인/대리인 신분증·양수인란/특약사항란 날인과 구포 번호 변경 제외를 본문에 명시 | `fa5ea97933904bb589d83bca98f4df17` |
| OPEN-17 ON | 5,043 / 76 | 매매한 날부터 15일 이내와 금련산 번호판 교부 2~3일을 정확히 구분 | `1f2053c2ab4f4cd1b7e80c3d9cfaefd4` |
| BUSAN-01 ON | 4,779 / 96 | 정상 대조 정답 B와 공통사항 유지 | `1078ed3a38314b09989d1210b1b51069` |
| OPEN-15 OFF | 4,248 / 401 | ON과 같은 핵심 서류·구포 제외를 본문에 명시. 포괄적인 미확인 limitation은 남음 | `9d0f8fb037384c5881e05cba77c2faa8` |

OPEN-15 ON은 raw top-12의 반복 슬롯 5개를 다른 출처 구간으로 교체했다. 필수 문맥은 ON 31개, OFF 27개였고 ON 입력은 1,176토큰 증가했다. 반복 선택을 줄였다는 사실을 총 입력 비용 감소로 바꾸지 않는다. **ON/OFF 모두 기존 핵심 실패를 회복했으므로, 이 질문에서 공통 선택 단독의 핵심 정답 향상은 확인되지 않았다.** 최종 문맥 구성과 검색용 본문을 함께 제공한 full의 제한된 관찰이다. v2→v3에는 표행 문맥과 부모 목록 두 수정이 함께 들어가 각 수정의 QA 효과를 따로 식별하지 않았다.

OPEN-15의 전체 답변을 무결하다고 판정하지 않는다.

- ON의 첫머리는 “구포센터에서 … 번호 변경을 하려면”이라는 질문 전제를 반복했다. 뒤에서 제외를 명시했지만, 가능한 절차처럼 시작하는 안내 우선순위 문제는 남았다.
- 실제 ON 입력은 “번호판변경시 기존번호판 2매 및 봉인(지역 번호는 반드시 기존번호판 2매 및 봉인 반납 후 번호 변경하여야 함)”이었다. 원문의 일반 부분은 구비 항목이고 **반납 후**라는 순서는 지역 번호에 한정돼 있다. 답변의 일반 “번호판 변경 시에는 … 반납해야” 확대를 직접 지지하는 근거는 이 입력에서 확인되지 않았다. 외부 업무 절차까지 조사해 거짓이라고 판정한 것은 아니다.
- ON의 실제 다운로드 가능 여부 확인 필요, OFF의 질문과 무관한 법인 설명 등 부가 내용도 완전성 향상으로 세지 않는다. OFF는 본문에서 구포 제외를 명시하면서 limitation에서 “구체적인 업무 처리 가능 여부와 제한 사항은 원문에 명시되지 않았습니다”라고 넓게 서술했다. 같은 입력의 명시적 업무 범위와 어긋나는 불필요한 불확실성이다. 다만 제외 자체를 본문에서 말했으므로 기존처럼 핵심을 전부 미확인 처리한 실패와 동일하게 집계하지 않는다.

후속 QA 지시를 검토한다면, 특정 정답이나 센터명을 넣지 않고 “질문 전제가 원문의 제한과 충돌하면 그 제한을 먼저 밝히며, 서류·물품 목록을 원문에 없는 수행 의무나 순서로 확대하지 않는다”는 일반 경계를 최소 후보로 삼을 수 있다. 이번 동결 비교에서는 이를 적용하거나 검증하지 않았다. 새 검수 계층이나 추가 모델 호출은 도입하지 않았다.

## 검사와 남은 경계

네 검색 방식의 공통 선택 진입, BM25 원순위/기존 정책 분리, 같은 표 문맥 반복 후순위, 다른 범위·출처 보존, 원문 미변경, 기존 snapshot QA와 필수 승인 의미 강제 포함, 표 문맥·긴 필수 문맥과 인용 계약을 확인했다. 모의 검사는 실제 로컬 모델 품질 증거가 아니다.

별도 승인 snapshot `f265809c600e4ab692ead654ca0438f9`에는 승인 claim 25개가 있고 단일 passage에 claim 최대 15개가 연결돼 있다. 현재 passage→claim 변환은 첫 passage의 여러 claim이 limit을 채울 수 있다. 같은 원문을 인용하는 서로 다른 승인 의미를 단순 중복 취급하면 정상 의미를 누락시키므로 이번 공통 passage 선택을 그대로 이 경계에 복사하지 않았다. R5의 실제 수정 snapshot·질문에서 정확 claim 근거와 필수 의미를 확인한 후 판단해야 한다.

현재 사용자 결정이 필요한 사항 없음. R4의 고정 실패 핵심 회복과 정상 대조를 위 범위에서 확인했으며, 남은 QA 범위 표현 문제를 전체 성공으로 덮지 않는다. 이 결과는 R5의 후보 교정·승인 소비나 개념 그래프의 일반 우위를 입증하지 않는다.


## 최종 QA 범위 지시 후보의 별도 비교와 기각

R4 v3 원시 결과를 보존한 뒤, 같은 full OPEN-15 한 건과 별도 R05 승인 snapshot의 같은 질문 한 건에서만 일반 범위 지시를 추가해 비교했다. 질문·reader·schema·인용 맵은 이전과 정확히 같고 관계 선택은 정확 재사용했다. 새 QA는 총 2회다. 이 비교는 검색 선택/개념의 효과 비교가 아니다.

OPEN-15 새 run `aa7002d518434d018c93f238ae40882a`는 핵심 미방문 서류를 유지했지만, 기존 v3가 명시한 구포 번호 변경 제외를 다시 ‘가능 여부 확인 필요’로 흐렸다. 질문 전제를 먼저 반복하고 일반 번호판 반납 의무 확대도 남았다. 새 비용은 QA 1회, 입력 5,494·출력 359토큰, 모델 57.41초/제품 83.96초, 관계 선택 재사용 1회다. R05도 번호 변경 허용 단정을 해결하지 못했다.

이 후보는 **기각했고 제품 QA 지시는 기존 버전으로 복원**했다. 원본 DB·코드 동결·응답은 불변으로 보존했고 추가 프롬프트/모델 재시도는 없다. [통합 기록](business_repair_retrieval_20261007.md)의 마지막 QA 절에 R05와 비용·판정 경계를 함께 기록했다. 기존 R4 검색/문맥 관찰을 새 지시의 성과로 바꾸지 않는다.
