# 회사 지식 계획의 검증·승인 부담 점검

- 버전: v1.0 · 2026-09-26
- 수행: 주 에이전트의 문서·관련 코드 정적 점검. 별도 전문가 에이전트 검수나 제품 실행 결과 아님.
- 대상: 현재 PRD와 architecture/implementation/milestones, 파일럿 입력/평가 계약. 이전 연구·민원 기록은 신규 P0 의무로 승격하지 않음.
- 결과: 핵심 무결성 요구는 유지하고 중복 검증·역할 승인·선행 조건을 좁혔다. 실제 개발시간 절감은 측정하지 않았다.

## 1. 위치 확인과 이번 산출물

기준 PRD는 `docs/00_overview/company_knowledge_prd.md`(이번 v1.5), 상세 계획은 `docs/05_plans/company_knowledge/`, 과거 조사·선정 기록은 `docs/70_research/company_knowledge/`다. 중간에 사용했던 `05_plans/company_knowledge/prd.md`는 현재 없다. 이동된 기존 문서를 다시 만들지 않았다.

[비교 절차](../../05_plans/company_knowledge/evaluation_protocol.md)는 B0/B1/B2별 입력·작업·12건 시작 상태·시간 계산·빈 기록 양식을, [최소 계약](../../05_plans/company_knowledge/contracts.md)은 데이터 의미·상태·API 입출력과 구현 단계를 확정한다. K1 설계 산출물 완료이며 실제 운영 이용허락·실험 참여·효용·앱 구현 완료는 아니다.

## 2. 부담이 커질 수 있는 문구와 조치

아래는 이미 과도한 코드가 구현됐다는 발견이 아니라, 계획을 구현하는 과정에서 과도하게 확장할 수 있는 지점이다.

| 위치·기존 해석 위험 | 이번 적용 결정 | 유지하는 최소 요구 |
|---|---|---|
| PRD §3·7: 자료 분석/설계/반례 검토를 모든 사실마다 3개 AI 호출로 확대 | 온톨로지 생성·변경 묶음에 반례 검토 1회, 후보 수정 최대 1회. 사실별·질문별 AI 재평가 없음 | 공식 ID·발췌·스키마 검사와 사람의 후보 검토 |
| PRD §3·8: 검토자와 배포 책임자를 별도 인력/승인 티켓으로 구현 | 단일 운영자가 한 화면에서 묶음 검토·활성화. 수락과 활성화의 데이터 의미만 구분 | 미검토 항목 제외, 결정 기록·원자적 활성화 |
| architecture §2 / implementation §5: 파생 요약 저장→질문 캐시·무효화 체계 확대 | Global 요약은 요청 내 유지, Run에 의존 ID만 기록. 요청 간 캐시 없음 | 원문 인용·처리 범위·응답 전 상태 확인 |
| PRD §6 / implementation §3: 모든 형식·정규화 조합의 문자 대응 엔진 선행 구현 | 선정 형식의 원문 위치부터 처리. 보존 block.text 기준 범위 사용, 실제 정규화할 때만 대응 추가 | 모호한 위치를 성공으로 처리하지 않음 |
| milestones §3: 앞 단계의 모든 외부 확인이 끝나야 다음 개발 가능 | 기술 의존만 순서 유지. 현업·Windows·기관 승인 대기와 Mac 로컬 구현을 분리 | 실제 확인하지 않은 OS·업무 효용은 미검증 표시 |
| implementation §8: 모든 라이브러리 설치/전체 호환성 확인부터 시작 | K2 파서, K3 스키마, K4 정렬, K8 diff 등 필요 시점에 도입·관련 영향만 확인 | 관련 의존성 충돌 해결·Windows 호환 코드 |
| PRD §12 / milestones §5: 단계마다 12건×3방식 반복 또는 개발 로그를 효용 결과로 취급 | 변경 기능의 사례만 누적. 기능 준비 후 비교 가능한 36개 최초 시도, 실패 항목만 재확인 | 정답 고정·입력 동일·구축 비용 포함·오류 선행 판정 |
| 구현 계획 API 초안: 본문 계약과 별도 계약이 계속 다른 상태로 유지 | 최소 계약을 단일 세부 기준으로 링크, endpoint 구현 시 Pydantic/OpenAPI 동시 작성 | API 경계 검증과 기존 민원 계약 보존 |

## 3. 줄이지 않은 항목과 이유

- **근거·공식 ID·조건·시점:** 이번 제품이 해결하려는 오류 그 자체다. 제거하면 빠른 대신 원문 없는 사실을 확정할 수 있다.
- **accepted와 active 분리, 불변 스냅샷·최신 사용중단 상태:** 롤백으로 철회 근거가 되살아나는 실제 요구를 막는다. 단일 DB 트랜잭션과 상태 정수로 구현하고 분산 일관성 시스템은 만들지 않는다.
- **검색 시작 확인+상태가 변했을 때의 재확인:** 생성 중 제외된 근거를 최종 답변에 쓰지 않는 요구를 충족한다. 매 단계 동일 ID를 재검증하는 별도 계층은 만들지 않는다.
- **포맷별 원문 위치, 관련 오류의 재현 확인, 백업/복원 1회:** 데이터 손실·잘못된 근거 연결을 찾는 직접 확인이다. 전체 상태 조합이나 대규모 벤치마크로 확대하지 않는다.
- **원문 재배포 제한·loopback·파일 경로 제한:** 기존 이용 경계와 로컬 서비스 입력 경계다. 현업 운영 인증·SSO·보안 플랫폼을 P0에 추가하지 않는다.

## 4. 실행 순서와 남은 결정

1. 다음 개발은 K2: 등록·파싱·원문 위치 조회. 처음에는 양산 한 계열로 연결하고 같은 단계에서 CSV/HTML/PDF/HWPX 선정 샘플까지 확장한다.
2. K3 이후 온톨로지 초안·근거 연결·검토·Local/Global을 순서대로 구현한다. 12개 과제 밖의 전체 프레임워크 비교는 추가하지 않는다.
3. 실제 B0/B1/B2 수행자와 공통 런타임 값은 측정 시작 전에 기록한다. 사람이 없으면 기술 확인은 진행하되 사람 시간 절감은 미확인으로 둔다.

현재 추가 사용자 결정은 필요 없다. 구현 방법 선택과 이번 문서 수정은 승인된 범위다. 실제 시간 측정 참여자, 외부 배포/기관 운영 범위는 그 단계에서 결정할 사항이다. 이번 작업은 문서·로컬 산출물 제외 규칙만 변경했고 앱 코드·패키지 설치·모델 호출·커밋·푸시는 하지 않았다.

## 5. 이번 작업의 확인 결과

수정한 기준/계획 문서의 상대 파일 링크가 실제로 존재하는지 확인했다. 실행표의 ID는 고정 과제와 12개 모두 대응하며 중복이 없다. 빈 JSON 기록 양식이 파싱되고 원문·정답 freeze의 파일 해시도 일치한다. 로컬 원문·평가 기록·DB의 Git 제외를 확인했다. 문서 작업이므로 앱 테스트·모델 실험·전체 테스트를 실행하지 않았다.
