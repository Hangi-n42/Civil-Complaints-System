# J3 집중 검수의 직렬 실행 연결

- 관련 이슈 #568, 선행 J2 e64f98c. 고정 진단에서 정상 4/오류 2를 구분한 Gemma+분할을 종단 실행 후보로 연결한다. 전체 품질 향상을 이미 달성했다는 의미는 아니다.
- 기존 SQLite 실행 원장과 a2.call을 사용하여 group/역할/후보 묶음/revision 기반의 실제 검수 단위 ID를 저장한다. 성공 단위의 응답·입력 해시·근거·시도 기록은 재개 시 재사용한다. 완료 메타데이터와 미실행 도구 작업은 기존 재개 계약을 따른다.
- 수정 입력은 개별 실제 검수의 정규화 결과를 일시적으로 합치되 원시 응답은 각 호출에 보존한다. 각 응답의 expected∩valid 범위 안 쟁점만 자동 수정에 전달하고 비교 쟁점만으로 needs_revision을 전파하지 않는다.
- 범위 밖 비교 쟁점은 원기록을 보존하면서 role=review/manual_review로 기록한다. 담당 후보의 revision 요청과 중복 키를 분리한다. J2의 비교 장관 추가 오탐을 숨기거나 삭제하지 않는다.
- Builder 전에는 원후보 수와 기존 출력 계약의 설계 유형·계층 상한을 예약하고, 성공 직후 실제 분할 단위 수로 좁힌다. 수정은 기존 1회와 실제 후속 검수 수를 예약한다. 부분 성공을 전체 완료로 세지 않으며 finish와 A3는 현재 후보 지문의 개별 검수 결과를 사용한다.
- A2 전용 KNOWLEDGE_DISCOVERY_REVIEW_MODEL(default Gemma)과 recipe v42를 사용한다. 기존 K3 KNOWLEDGE_REVIEW_MODEL은 유지한다. 새 모델·큐·DB·프레임워크는 추가하지 않았다.

## 사전 실행량과 확정 예산

- H4의 보존 산출을 현재 제품 helper로 계산하면 분석 3 + Builder 2 + 검수 3+3 = 11회다. 각 그룹 수정 1 + 재검수 3을 둘 다 수행하면 총 19회다. 새 산출에 필요한 단위 수가 동일하다는 보장은 없다.
- 동결 전 #568의 C2 상한을 20HTTP/3,000모델초로 확정했다. round0/revision1, 각 HTTP 300초. 기존 16회로는 예상된 두 그룹 수정 경로를 수용하지 못하므로 사전 조정했다. 런타임 자동 증액과 사후 재실행은 없다.
- 최초 진입 예약은 Scout 이후 분석 2 + Builder 1 + 최소 검수 2의 5×360=1,800초로 시간 상한 안이다. Builder 전 최악 예약을 전역 실행 차단 조건으로 추가하지 않고 성공 후 실제 단위로 좁힌다.
- C2 최종 필수 의미·유형 연결·근거·전체 의존 preview·현재 검수·미처리 없음이 확인될 때만 current를 최대 40HTTP/3,600초, round1/revision1로 한 번 실행한다. 실패하면 current는 0회다.
- 사람 0명, 총 작업시간 null, 사람 효용 미측정. 현재 사용자 결정이 필요한 사항 없음.
