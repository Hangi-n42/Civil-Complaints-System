# 회사 지식 PRD — 추가 조사 및 제3자 관점 검토 기록

- 기준일: 2026-09-25
- 최종 정리: 2026-09-26
- 대상: [회사 지식 온톨로지·지식그래프 PRD](../../00_overview/company_knowledge_prd.md)
- 범위: 공개자료 추가 조사, 현재 소스 대조, 작성 문서의 AI 에이전트 검수. 제품 구현·실제 기관 인터뷰·성능 실험은 수행하지 않았다.
- 사용자 요구: 앞서 제안한 다음 조사를 수행하고, 구체적인 PRD 작성 후 제3자 전문가 관점에서 검수한다.

## 1. 추가 조사: 실제 역할과 변경 반영 절차를 어디까지 확인했는가

조사 질문은 ‘회사 지식이 바뀔 때 누가 어떤 자료로 검토·반영하며, 무엇을 측정해야 하는가’였다. 현재 확보된 자료로 현업 인터뷰를 대신할 수 없으므로 공식 직무·발주 원문에서 확인되는 역할과 절차 요구를 구분했다.

검토 자료:

- [LHCS 공식 직무소개](https://www.lhcs.or.kr/view.do?no=88)
- [2025-09-19 공식 LLM 플랫폼 입찰 공고 및 첨부 제안요청서·과업내용서](https://www.lhcs.or.kr/view.do?idx=19139&no=82&pageIndex=1&pgMode=show&sv=&sw=)
- 기존에 실제 원문을 확인한 양산 국민임대 공고·정정공고, LH 공개 단지 CSV·규정·안내 자료. 상세 출처는 PRD §15에 기재했다.

아래 페이지는 과업내용서 **인쇄 페이지**다. ‘기관 발주에 존재하는 요구’와 ‘현재 기관에서 실제 수행 중인 절차’를 구별해야 한다.

| 단계 | 원문에서 확인한 내용 | 아직 확인하지 못한 것 | PRD에 반영한 결정 |
|---|---|---|---|
| 담당 역할 | 시스템개발팀의 구축·연계·검토·인수 운영, 유관부서의 자료·FAQ 제공과 품질검증 참여(p6~7); 직무소개에 데이터 표준·품질관리 | 개별 변경 건의 일상 담당자·구매 결정자 | 논리적 운영자/업무 검토자/배포 책임자를 정의, 실제 부서는 미지정 |
| 입력 | 내부 문서·공고·법령·표, 정기·비정기 수집과 출처 기록(ECR-003 p15, SFR-005 p26~27) | 실제 수집 대상·주기·지연 | 자료별 출처·버전·수집 시점 보존 |
| 변경 식별 | 데이터 항목 추가·변경·삭제 절차·이력(DAR-001~006 p35~38) | 실제 의미 단위 변경 탐지 방식 | 문서 차이와 사실 변경 후보를 분리 |
| 검수 | 원문·전처리 매칭, 작업 이력, 값 검증 및 공동 모델 검증(ECR-003 p15, DAR-002~003 p36) | 매 건 운영 검수 주체·기준 | 근거·ID·조건·시점 중심의 묶음 검토 |
| 승인 | 승인된 사용자만 데이터 수정(SFR-005 p27) | 지식 내용별 승인·결재 프로세스 | 사용자 권한을 내용 승인과 혼동하지 않고 최소 결정 단계 제안 |
| 배포·실패 | 검증·버전·배포, 정책변경 반영 점검(SFR-005 p27), 오류 개선·운영자 개입(DAR-006 p38, SFR-008 p30~31) | 실제 배포 지연·되돌리기·운영 장애 | 검토된 묶음 활성화, 실패 시 기존 버전 유지 |
| 로그 | 원문 매칭·변경 이력·문서/모델/프롬프트·실패 원인(ECR-003, SFR-005, SFR-008) | 실제 운영 로그·보존 정책 | 변경 전후·근거·검토 결정·실행 버전을 연결 |

공식 도메인에서 운영 개시·성과를 추가 검색했지만, 해당 사업의 검수 완료와 실측 업무시간 개선을 확인할 자료는 확보하지 못했다. **검색 결과를 찾지 못했다는 사실은 미운영의 증거가 아니다.**

## 2. 이번 조사로 내릴 수 있는 결론

- 공개자료만으로도 문서 버전·공식 ID·조건 차이·정정 반영을 검증할 수 있는 제한된 파일럿은 설계할 수 있다.
- 지식 관리 부담 경감과 수명주기 관리 수요가 발주 문서에 존재한다. 그러나 기존 기관 제품보다 우리 제품이 우수하다는 증거는 없다.
- 실제 온톨로지 필요성은 문서 diff·메타데이터·ID 연결·수동 관계표라는 단순 기준선과 비교해야 한다.
- 프로젝트 평가자의 작업시간은 측정 가능하지만 LH 직원의 업무 절감량·기관 ROI로 해석할 수 없다.
- 실제 업무 절차, 반복 작업량, 승인 권한, 현재 KMS 기능, 내부 시스템 스키마는 미확인으로 남겼다. 이번 문서 작성 중 외부 담당자에게 연락하거나 인터뷰를 진행하지 않았다.

현업 확인이 남은 세 질문은 PRD §14에 기재했다. 사용자가 제공한 기존 Knowledge Layer PRD와 OntoGPT 분석문은 참고자료로 읽었으며, 이후 사용자가 정한 ‘회사 지식 중심·민원은 활용 예시’ 방향을 우선 적용했다.

## 3. 현재 코드 확인과 반영

코드 담당 에이전트가 API·검색·QA 근거·평가 모델·환경·FE를 읽었다. 코드와 오래된 README의 설명이 다르면 현재 소스를 기준으로 삼았다.

- `app/knowledge`는 아직 없다. 신규 지식 레이어를 이미 구현한 것처럼 기술하지 않았다.
- QA 입력은 `chunk_id/case_id/snippet`을 요구한다. 회사 지식은 별도 출처 계약으로 관리하고 P1에서 지식 패널로 연결한다.
- 검색 평가 파이프라인의 `RetrievedDoc`과 운영 검색·QA 타입을 구분했다. 운영 검색에서는 filters 유무에 따라 hybrid 적용이 달라진다.
- 현재 민원 평가 모델 기본값은 Qwen `qwen3.5:4b`, 초기 5그룹/답변 수정 후 Q2 재사용 시 4호출이다. 본 문서 작성에서 실제 LLM 호출 실험은 하지 않았다.
- API/FE에서 사용자 인증·역할 권한 경로를 찾지 못했다. 로컬 파일럿과 기관 운영 승인을 분리했다.
- 기존 미커밋 코드 변경은 보존했다. PRD 작성을 위해 앱 코드를 수정·테스트·재시작하지 않았다.

## 4. 문서 작성 후 에이전트 검수

검수자는 실제 인간 전문가나 LH 직원이 아닌 **별도 AI 에이전트**다. 서로 다른 검토 관점으로 작성된 파일을 읽고 비판한 결과다. 기관 도입 승인이나 성능 정확도 인증에 해당하지 않는다.

### 검토 역할과 최종 판정

| 별도 에이전트 | 검토 관점 | 최초 판정 | 수정 후 재검토 |
|---|---|---|---|
| `lh_access` | 제3자 제품 심사위원·산업계 지식관리 도입 담당자 관점 | 수정 필요 | **조건부 적절**. 지적한 중요 문서 문제 해결. M0에서 과제·필수 산출물·측정 구간 고정 필요 |
| `lh_regulations` | 소프트웨어 아키텍처·KG/데이터 신뢰성 관점 | 수정 필요 | **적절**. 재검토 범위의 중요 문서 문제 해결. 구현 충족 여부는 별도 확인 |
| `lh_entities` | LH 원문·요구사항 번호·자료 특성 사실 확인 | 중요 사실 오류 없음, 표현 수정 권고 1건 | 작성자가 ‘최종 정정’을 ‘조사 시점 최신 정정’으로 반영. 이 표현 수정에 대한 별도 에이전트 재검토는 생략 |

두 주요 검수 에이전트는 수정 후 같은 파일의 지적 부분을 다시 읽고 판정했다. 모두 초기 조사 맥락을 알고 있으므로, 사전 노출 없는 독립 실험 평가자라고 표현하지 않는다.

### 지적과 반영 내역

| 번호 | 발견한 문제 | 반영한 변경 | PRD 위치 |
|---|---|---|---|
| R-01 | 재검토가 필요한 기존 지식을 어떻게 다시 사용 가능하게 만드는지 불명확 | 영향 없음·수정·철회·보류 결정과 재허용/잔여 작업 정의 | §8.1 |
| R-02 | 동일 스냅샷에서 현행성 상태가 달라질 때 재현·복원 의미가 불명확 | 불변 스냅샷과 별도 상태 이력, status_revision/checked_at, 복원으로 사용중단 해제 금지, 업무 기준일과 시스템 시점 구분 | §6.3·8.1·10.3 |
| R-03 | 사실을 수락해도 의존 개념·관계·별칭이 보류됐을 수 있음 | 의존 항목의 검토 완료 조건과 부분 활성화 제외 사유 명시 | §8.1 |
| R-04 | assist에 임의 evidence_id를 전달하여 제외 근거를 사용할 수 있음 | snapshot_id/assertion_ids/범위 입력, 서버의 근거·상태 재확인, 생성 중 상태 변경 확인 | §10.3 |
| R-05 | AI 자동화의 효과와 KG의 효과가 비교에서 혼재 | B1에도 동일 모델의 원문별 초안 제공. B2 결과는 기능 묶음 효과로 한정 | §12.1 |
| R-06 | 최초 구축비와 반복 갱신비의 합산 범위·합격 기준이 모호 | 최초 구축 1회+12개 작업 묶음, 필수 산출물·시간 구간, 결과 이전 확정할 총 사람 작업시간 10% 감소 기준 | §12.2~12.3 |
| R-07 | B2 추가 효용 실패가 민원 활용까지 막는 단계 의존 문제 | 관계 자동화 확장 여부와 채택 방식의 민원 활용 가능 여부 분리 | §12.3·13 |
| R-08 | 취소 수용 기준은 있으나 동작·상태 계약이 없음 | cancel API와 cancel_requested/cancelled, 처리 단위 종료 시 중단 정의 | §8.1·10.3 |
| R-09 | ‘최종 정정’은 이후 정정이 없다는 의미로 읽힐 수 있음 | 조사 시점 최신 정정으로 표현 제한 | §5.1·15 |

10%·20개 문서 버전·12개 작업은 **이번 제품의 제안 기준**이다. 공개자료에서 관측한 성과나 업계가 요구하는 표준 수치가 아니다. M0에서 이 기준을 실제 평가 자료와 연결해야 하며, 결과를 본 뒤 유리하게 변경하지 않는다.

## 5. 문서 확인과 남은 한계

- PRD의 내부 파일 링크·UTF-8 인코딩·코드 블록 닫힘·불필요한 공백과 변경 범위를 확인했다. 누락된 로컬 링크나 해당 형식 오류는 없었다. 앱 테스트나 모델 실험은 수행하지 않았다.
- 변경 산출물은 PRD, 이 조사·검수 기록, 개요 문서의 진입 링크다. 기존 코드 변경은 보존하며 커밋·푸시는 하지 않는다.
- 실제 담당자 인터뷰·내부 작업 로그·자료 이용 권한의 기관 승인·새 평가 6건의 고정·제품 구현과 양 OS 실행 검증은 남아 있다.
- 최종 판단: **공개자료 기반 파일럿의 구현 범위를 정하는 PRD로 사용할 수 있다. 기관 구매 타당성·운영 준비·정확도·ROI를 입증한 문서는 아니다.**
