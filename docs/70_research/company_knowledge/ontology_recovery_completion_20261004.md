# 정상 의미 보존 교정과 실제 누락 복구 — 2026-10-04

## 현재 구현과 완료 증거

기존 SQLite 원장·직렬 실행기·후보 ID·원문 위치·수정 이력을 유지하면서 후보별 실패 격리, 누락 요청의 요구 귀속과 복구, 정상 의미·필수 문맥 보존, 내용 수정 후 유형 재연결을 보완했다. 별도 프레임워크나 DB를 추가하지 않고 기존 검증·파싱·현재성·예산 계산을 재사용했다. 자료에 없는 의미와 긍정 판정을 서버가 만들어 채우지 않는다.

마지막 상태 전파 보완 전 관련 7개 테스트 파일은 **194개 통과·0개 실패(19.52초)**였다. 최종 보완은 좁은 회귀 **21개 통과(0.42초)**와 실제 저장 응답의 HTTP 0회 재집계로 확인했다. 두 결과를 최신 코드의 전체 검사 합계로 합산하지 않는다. 실제 호출 직전 응답 형식과 저장 검증의 일치, 현재 typed 주소·끝점 의존성, 과거 이력 불변을 포함한다. 7회 실제 모델 실행 동안 production 코드의 동결 해시는 변하지 않았다. 이후 상태 전파 보완은 모델 재호출 없이 별도 복사본에서 계산 결과만 확인했다. 이전 단계의 넓은 검사에서 기준 커밋에도 동일하게 존재한 fixture 실패는 아래에 별도 기록하며 현재 194개 결과와 합산하지 않는다.

정의한 핵심 완료 증거는 실제 실행과 독립 실행·의미 검토로 확보했다. 이는 #598~#602의 좁은 교정·복구 확인이며 원래 두 문서 전체, 모든 후보의 승인, 일반적인 온톨로지 품질·현업 효용의 완료를 뜻하지 않는다. GitHub 이슈의 최종 본문과 종료는 조율 세션이 같은 증거를 기준으로 처리한다.

## 남은 제한

- 최종 원요청 실행의 전체 상태는 partial이다. 비교 후보7개와 의존 유형은 개별 검수 미완료이며 전부 승인됐다고 주장하지 않는다. 사람 검수 상태도 unreviewed다.
- 같은 dbba 끝점의 review 요청 be6201…에 해결 결과가 전파되지 않던 집계 결함도 보완했다. 최종 사본에서는 64b와 해당 요청 모두 현재 해결됐고 미해결 요청 목록과 active_blockers가 비었다. 원 status=manual_review와 감사 이력은 보존하며 semantic_status만 현재 근거로 계산한다. 이 제한 사본의 결과를 원래 전체 실행 원장 해결로 확대하지 않는다.
- 정상 계층 대조의 실제 검수는 저장됐으나 구성 입력에 모델 작성 양방향 검수가 없어 마지막 A3 변환은 미완료다. 가짜 a_to_b/b_to_a 판정을 넣거나 모델을 재호출하지 않았다. 전체 A3 발행 성공으로 계산하지 않는다.
- 주체·목적어의 whole_field 위치는 현재 typed ID를 복원한 주소다. 자연어 정확 인용이 아니라 현재 후보 주소·유형 끝점 의존성과 별도 binding 검수로 의미 연결을 확인한다.
- v4 CQ의 병렬 witness와 missing_source='원천 미제공' 문구는 해당 실행의 한계로 보존한다. 최종 원요청 실행은 두 실제 proposal을 직접 지목하고 missing_source도 빈 값이다. 원래 두 문서 전체 CQ 완료나 전체 모델 품질은 입증하지 않았다.
- 실제 사람 참가자가 없어 작업시간·오류·현업 효용은 미측정이다. Windows 실기, 전체 민원 테스트, 전체 C2/current 평가는 이번 완료 조건에 추가하지 않았다.

## 원인과 후속 범위

주요 원인은 행 단위 오류가 정상 후보까지 실패시키던 검증 경계, 필수 답칸·위치의 생성 형식과 저장 규칙 불일치, 수정 후 남은 유형 연결을 이어 처리하지 않던 계획, 실제 요청 귀속·현재 검수·해결 집계의 단절이었다. 원문 의미와 바깥 모델화 표시를 비교 화면에서 섞는 문제도 고쳤다. 기존 원장과 검증 함수를 확장하는 방식이 ID·근거·과거 이력을 보존하면서 이 경계만 고치는 최소 변경이었다.

개발 중 Qwen의 다른 원문 분기 귀속 오탐도 관측했다. 이는 비교 화면 보완 전 실패 이력이며 최신 코드에서 같은 Qwen 조건을 다시 실행하지 않았다. 현재도 같은 오류가 남는다고 단정하지 않고, 이후 Gemma 제한 사례의 성공을 일반적인 검수 정확성으로 확대하지 않는다. 모든 실패·원본 DB·실제 HTTP·동결 기록은 로컬에 보존한다.

다음 범위는 개별 미검수 후보의 사람 검토와 별도 승인된 범위에서의 전체 요구 평가다. 같은 끝점의 해결 상태 전파 누락은 이번에 보완했으므로 사용자 판단 대기 항목으로 남기지 않는다. 이번 커밋에 원본 자료·평가 DB·개인 기록·.env를 포함하지 않는다. 현재 사용자 결정이 필요한 사항 없음.

## 목적과 판정 범위

#598~#602는 오류를 발견해 보류하는 데 그치지 않고, 제공 원문 안의 잘못된 표현을 고치고 빠진 의미를 복구한 뒤 같은 요구를 다시 확인하는 작업이다. 기존 SQLite 원장·직렬 실행기·후보 ID·Pydantic 모델·수정 이력·원문 위치 참조를 확장했다. 별도 에이전트 프레임워크, 법령별 정답, 퍼지 인용 보정은 추가하지 않았다.

이 보고서의 구성 진단과 실제 제품 오류는 서로 다르다. `dc_effect`, `dc_parent`는 이전 진단 실행기가 작성한 후보다. 실제 로컬 모델이 이를 검수·교정해도 제품에서 자연 발생한 오류의 복구로 계산하지 않는다. 제품 검증은 이전 실행 `d5715251ada74d7280d190b1f1a6ca2c`에서 실제 빠진 규칙 제15조 제3항과 미선언 유형 연결 오류를 출발점으로 한다.

실제 사람 참가자는 없으며 사람의 작업시간·오류·현업 효용은 미측정이다. AI 검수의 supported와 A3 현재성은 사람 승인이나 전반적인 온톨로지 품질 보증이 아니다.

제품 복구는 실제 이전 후보·오류·누락 요청을 사용하지만, CQ는 원실행의 두 문서 업무 연결 요구에서 제1항 유형 연결 또는 제3항 누락으로 좁힌 별도 진단이다. 이 보고서의 “같은 CQ”는 각 제한 진단의 복구 전후를 뜻한다. 원실행 전체 CQ 완료나 처음부터 전체 제품 실행에 성공했다는 의미가 아니다.

## 구현

- S1(#598): Concept 응답의 후보 행을 독립 검증한다. 정상 행과 서버 발급 ID는 저장하고 실패 행의 원응답·오류 ID·실행 단위·소유 span을 보존한다. 공유 선언을 갖는 Builder 응답은 기존 원자적 계약을 유지한다. 반복 발췌는 명시적인 occurrence로 구분하며, 긴 연속 발췌는 정확한 시작·끝 구절 선택도 지원한다.
- S2(#599): 주분석 범위의 미귀속 누락 요청을 요구 검수에 전달한다. 실제 관련성 판정·현재 원문 지문·누락 판정이 있는 요청만 기존 복구 단계로 보낸다. 정상 후보 보존, 후보별 교정·필수 재검수·요구 검수 예산 예약, 실제 복구 증거에 연결한 현재 차단 집계를 추가했다. 과거 오류는 삭제하지 않는다.
- S3(#600): 구성 항목과 항목별 조건·예외·기간을 실제 정의나 선택 계층·자식 필드와 대조한다. 자료 부재는 unknown/source_absent, 제공 의미 누락은 refuted/extraction_missing으로 생성 스키마와 서버 검증을 일치시켰다.
- S4(#601): 교정 전에 정상 의미 보존 기준을 전달한다. 미충족 요구와 생성 context_needs는 별도 required_context로 수정 이력과 후속 Critic까지 연결한다. context_checks의 maintained는 현재 표현에서 충족, corrected는 원문으로 요구 자체를 정정, lost는 미충족, unknown은 판단 불가다. 모든 키의 개별 대조·실제 근거·현재 표현 위치를 검사하고 수정 지문에 포함한다.
- S5(#602): 이전 실패와 원본 DB를 보존한 격리 사본에서 작은 실제 모델 검증을 진행한다. 모델·입력·코드·레시피·호출/시간 상한을 사전 고정하고 원인 수정 없는 재시도는 하지 않는다.

v75는 미귀속 요청 답칸의 related 분기에 실제 의미 목록을 두고, 서버가 모델이 선택한 답칸 ID만 기존 recovery_ids로 옮긴다. 서버가 원문 겹침으로 관련성을 추론하거나 의미 판정을 변경하지 않는다. 미관련·미확인 답칸에는 의미 연결을 허용하지 않고, 일반 의미에는 기존 요청 연결을 유지한다. 한 요청의 여러 의미는 모두 supported여야 해결로 집계하며 단일 의미 안의 중복·범위 밖·응답 누락은 거부한다. 처음 발견된 구체적 누락 의미는 현재 귀속 검수 원장에서 꺼내 기존 생성·제출 목록과 후속 요구 검수에 전달한다. 원래 누락 요청과 실패 응답은 그대로 보존한다. 관련 6파일 138개 검사와 중첩 의미만 있는 응답의 기존 저장 계약 왕복 검사가 통과했다.

v76은 반복된 범위 오판에 대해 원문 발견 후 별도의 작은 적용성 판정을 둔다. 기존 context 실행 단위와 모델 호출·SQLite 저장을 재사용한다. 후보의 현재 정의나 과거 supported 없이 원문·현재 CQ·출처 역할·원제안만으로 required/not_applicable/mixed/unknown을 판정한다. mixed는 원제안과 연결된 남은 ContextNeed 목록이며 충족 위치나 supported를 생성하지 않는다. 후보 국소 판단과 CQ 전체 판단의 키를 분리하고, CQ는 후보에서 제외한 결과가 아닌 원래 발견 제안 전체를 다시 검토한다. unknown·실패·예산 부족은 미결로 남긴다. 정상 의미 보존 기준은 이 제외 절차와 독립적이다.

같은 영수증을 생성 경로와 읽기 전용 조회 경로가 공유하고, 변경된 CQ·원문·발견 출력·모델/설정·스키마는 캐시 키에 반영한다. 후 Critic 입력과 요구 지문에 영수증을 포함하고 완료 재조회에서도 최신 영수증과 근거 유효성을 대조한다. 최신 검수가 무효면 이전 supported로 후퇴하지 않는다. 예정 호출은 실제 미실행 문맥·적용성·요구 키로 계산하고 미확정 예약은 실제 키로 교체한다. 적용성 분리의 실제 모델 효과는 아직 검증 전이며, 현재 코드의 관련 6파일 145개 검사가 통과했다.

v76의 첫 실제 적용성 진단은 성공한 원문 발견과 정규화된 출처 역할을 재사용해 후보 국소 2회·CQ 전체 1회, 합계 3회·229.684초를 사용했다. 원본·실행 중 코드는 보존됐다. 제2·3항의 다른 권한과 별표의 세부 기준은 범위 밖으로 구분했지만, 외부 정의 전체를 필수로 남긴 오판이 세 호출에 공통으로 있었다. 두 번째 호출은 세부 기준의 제외와 참조 자체의 제외도 혼동했다. CQ 전체 호출은 별표 참조 자체를 mixed.remaining으로 정확히 보존했으나 외부 정의 문제는 남았다. 따라서 적용성 분리의 일부 개선과 전체 기준 미달을 구분한다. 후 Critic이나 전체 복구 성공으로 집계하지 않는다.

독립 예약 검토에서 실패한 요구 검수(attempts가 비어 있어도 재호출하지 않음)를 예약에 포함하는 문제와, 확정 실패한 원문 발견 뒤의 실행 불가능한 적용성 임시 예약이 발견됐다. 진행 중이던 진단은 성공한 발견만 사용하여 이 두 경계가 해당하지 않았고 동결을 유지했다. 종료 후 v77에서 각 단계의 실제 재호출 조건에 예약을 맞췄으며 작은 재현 두 건이 통과했다. 실패 이력과 의미 미결 상태는 삭제하지 않았다.

v78은 required가 원제안 전체를 전달한다는 실행 의미와, 참조 조건의 표현 검사와 외부 실제 자격 검사를 구분하는 지시를 명시했다. 같은 세 범위의 후속 적용성 진단(v2)은 3회·261.886초를 사용했고 원본·코드가 보존됐다. 주체 호출은 혼합 판정 이유에서는 외부 상세를 제외했으나 실제 remaining.meaning/missing_source는 원래 상세 요구를 복사했다. 대상 호출은 외부 정의 전체를 required로 유지하고, 별표 참조만 남긴 의미에도 상세 자료 부재 메타를 유지했다. CQ 호출은 순수 외부 정의·별표 상세를 제외했지만 혼합 제안에서 같은 문제가 남았다. 따라서 이유 서술의 개선을 실제 필수 요구 축소 성공으로 집계하지 않는다. 모델 내부의 유일 원인이라고 단정할 근거도 없다. 관련 6파일 147개 검사가 통과했고 저장 계약의 유효성과 실제 의미 품질을 구분한다.

Qwen 동일 입력 비교는 `qwen3.8:27b-q4_K_M`(digest `25b843619e944cd0ae6069f94ff4e5e26a16e109ccbc0a66a0f05979ed70098e`)으로 1회·96.371초를 사용했다. v2 주체 역할 호출의 prompt·스키마·옵션·think는 동일하고 모델만 다르다. 실제 remaining은 시행령 참조가 공급 전제라는 의미로 좁아졌고 missing_source는 비워졌다. 별표 상세를 not_applicable로 둔 것을 처음에는 참조 소실로 단정했으나, 독립 의미 검수는 후보 국소 범위에서 상세만 제외한 것이며 원명제 참조 삭제를 지시하지 않는다고 판단했다. 그 최초 실패 단정을 정정한다. 이 한 건에는 확정적 의미 실패가 발견되지 않았으며, 원명제·관계조건·CQ 전체에서의 참조 보존은 실제 후속 경로에서 확인한다. 모든 후보 검사에 같은 참조를 중복 생성할 필요는 없다. 이 결과를 Qwen의 일반 우월성으로 확대하지 않는다.

v12 실제 제3항 확인은 Qwen 요구 검수 1회·114.388초 후 저장 계약에서 거절됐고 생성은 0회다. 관련 요청 답칸 안의 주체·공급조건 의미와 빈 missing_source는 적절히 작성했지만, 같은 미귀속 요청 ID를 최상위 의미의 recovery_ids에도 중복 기입했다. v75 서버는 이를 거절했으나 출력 스키마에는 미귀속 ID가 여전히 최상위 허용값으로 남아 있었다. v79는 이 구현 불일치를 수정해 최상위 연결을 기존 recovery_targets로만 제한하고 모순된 안내 문장도 일치시켰다. 중첩 답칸의 의미 판정과 ID 복원은 그대로다. 기존 요청이 있는 경우와 없는 경우의 정상 왕복·중복 거절을 확인했고 관련 6파일 149개 검사가 통과했다. v12의 실패 응답을 소급 수정하지 않는다.

v13은 요구 귀속 저장 뒤 실제 제3항 관계를 생성했다. 첫 두 관계(call03)는 장관/시도지사 각각의 공급조건, 지방공사의 제49조 주택사업 목적 한정, 우선공급 대상자·비율·선정 순위, 제1·2항에도 불구함과 지역 실정 고려, 별도 기준을 정할 수 있는 권한을 보존했고 독립 의미 검수도 통과했다. 이후 Builder는 한 묶음에서 선언 없는 t1/t2/t3를 참조했고, 다른 묶음에서는 장관 출처 역할로 선언한 유형을 시도지사 관계에도 공유했다. Qwen binding은 후자를 더 넓은 행정 주체 유형으로 수락했지만 실제 정의에는 그 넓은 범위가 없었다. 독립 의미 검수에서 이 수락은 오류로 확인됐다. 작성 사유가 오수락의 원인이라는 인과는 입증되지 않았다.

또한 진단이 원래 두 문서 질문의 cq1 ID를 제한된 제3항 질문에 재사용하면서, 수입한 제1항 비교 후보의 예전 cq_ids가 남아 있었다. 이로 인해 요구 검수에 제1항 미연결 끝점 요청까지 섞였다. 이 증거만으로 제품에 일반 재귀속 기능을 추가하지 않는다. v15는 원제1항 후보의 본문·원문·ID를 유지하고 원래 질문 연결은 출처 메타에 보존한 채 현재 CQ 연결만 분리한다. 같은 비교 후보를 참조하더라도 실제 제3항 누락인 요청들은 그대로 유지한다.

v13의 마지막 관측 검수(call13)는 장관 역할이 제1호에 한정된다는 점과 원문 조건을 올바르게 설명했지만, 비어 있는 후보 conditions/exceptions/time 필드에 원문 또는 role_source의 구절을 자기 주장으로 인용해 저장행이 거절됐다. 확인된 문제를 반복하지 않도록 기존 취소 API의 호출 저장 경계에서 중단했다. 총 13회·1,207.396초이며 원본 DB·실행 중 코드·정상 후보는 보존됐다.

v80은 binding 입력에서만 미검증 작성 사유(classification_reason/design_reason)와 계획된 binding_uses를 제외한다. 실제 명칭·정의·조건·예외·role_basis·role_source 및 요청 관계의 원명제와 연결 선택은 보존한다. 후보별 ObservationCheck의 claim_reviews.field는 그 후보의 실제 비공백 definition/conditions/exceptions/time에만 한정한다. 필수 문맥, role_source 위치 대조, 실제 인용과 전체 주장 포괄 검사는 그대로다. 관련 7파일 166개 검사와 후보별 필드 분리 확인이 통과했다.

v15는 과거 질문의 귀속 혼입을 분리하고 3회·374.924초를 사용했다. 현재 제3항 요구 검수는 의미 표현을 supported로 판정했으나 미검증 유형 연결이 포함되어 있어 완료로 집계하지 않았다. Concept는 빈 observations와 누락 설명을 반환하여 의미 생성은 0건이다. 이후 진단 실행기의 재사용 기록 파일을 독점 생성 모드로 같은 이름에 두 번 쓰는 오류로 중단됐다. 제품 파이프라인 오류와 구분하며, 다음 실행은 기록을 개별 파일로 저장했다.

### v87: 현재 내용 재검수에서 유형 재연결로 이어지는 경계
