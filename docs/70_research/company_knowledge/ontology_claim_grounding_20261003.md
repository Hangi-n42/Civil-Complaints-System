## 실제 변경

- 새 실행 계약 `authored-v2`, `claims-v1`, prompt `discovery-a2-v59`. 기존 응답 모델/legacy direct를 소급 변환하지 않는다. 기존 직접 작성에 원문 참조가 있다는 이유로 정확한 원문 추출로 승격하지 않는다.
- Concept/Revision의 `source_extract`: 제공 source_ref와 하나의 연속 인용을 선택하면 서버가 정확한 정의와 버전/구간을 복원한다. 떨어진 구절 조합·자유 한정과 혼용을 거절한다.
- `synthesis`: 자유 정의·한정·설계 사유와 근거를 남긴다. `source_role`은 기존 역할 구성 재사용. Builder 신규 유형은 역할 선언만 가능하며 제공 유형 ID 연결은 기존 정의를 보존한다.
- 관측 Critic은 실제 후보의 field/candidate_quote/claim/nature/source_refs/judgment/reason을 제출한다. 서버가 현재 구절 위치와 공백 외 전체 텍스트 포괄, 근거 유효성을 확인하고 `refuted → unknown → supported` 우선순위로 정의 판정을 집계한다. 모델이 definition 최종 판정을 따로 쓰면 완료 처리하지 않는다.
- `definition_completeness`는 사실성 별도로 실질적 역할·범위·필수 의미 충족을 판단한다. 이름 반복 정규식으로 의미 판단을 대신하지 않는다. 설계 선택 표기도 구체 효과·범위의 검수 면제가 아니다.
- Revision에 현재 지문, 오류/정상/미확인 주장과 정확한 근거 위치를 전달한다. 기존 입력 축소·서버 전체 검증 분리 및 수정 이력 재사용. 수정 후 변경 후보와 의존하는 관계/역할/계층만 주검수 대상으로 삼는다.
- 사람 수정은 최초 생성 근거/방식을 이력에 보존하고 현재 방식은 `human_edited_unclassified`로 구분한다. 과거 AI 검수 지문과 현재 내용을 대조한다. 새로운 AI 승인을 사람 수정·수락의 조건으로 추가하지 않는다.
- 기존 정의와 `same`으로 대응하여 정의를 유지하면 기존 작성 방식도 유지한다. 새 관측의 구절 검수는 `proposal_*`에 별도로 남기며 유지된 정본의 현재 검수로 승격하지 않는다.
- 정본과 재조회에 작성 방식/주장 검수/이력을 보존한다. K4 추출 입력에 선택된 관계의 실제 끝점 유형, 정의의 qualifiers와 source-role 적용 범위를 전달한다. 화면에 주장 구절·판정·이유·근거 원문 연결과 현재 작성 성격을 표시한다. 기존 사람 편집 경고 재사용.

문자 포괄 검사는 의미 분해의 완전성, 인과 해석, 이유와 판정의 일치 또는 유용성을 보증하지 않는다. 원문 참조가 유효한 것과 주장 지지는 별개이며, 최종 사람 수락도 원문 명시 사실로의 승격이 아니다.

## 전문가 검토와 회귀 검사

조율 세션이 두 독립 전문가(아키텍처·온톨로지 / 의미 평가·실행)를 실제 호출해 사전 검토한 결과를 전달받았다. 원문 추출/합성 구분, legacy 유지, Builder 책임, 사실성과 설계 구분, 정의 충분성, 사람 편집 현재성, 실제 두 문서 종합 대조를 반영했다. 같은 전문가 사전 검토를 중복 호출하지 않았다.

구현 중 독립 검토의 확정 코드 지적 두 건도 반영했다.

1. 기존 source_relation_ids가 있는 역할 후보를 원문 추출로 바꿔도 support_type을 design_proposal로 덮던 상속을 새 명시 전환에서 제외했다. 역할→추출 explicit, 역할→합성 design_proposal과 과거 상속을 구분했다.
2. same 대응으로 유지된 정본의 다른 문장에 새 제안의 claim/작성 출처를 현재 검수로 붙이지 않도록 분리했다.

확인 결과:

- 관련 Python 130개 통과: 작성/주장·역할·공유선언·인용·수정 문맥·교정·A3·추출 실행 경계. 이후 영향 재검수/전환/동일대응 보완을 포함한 최종 집중 29개 통과. 중복 검사로 합산하지 않는다.
- 화면 관련 17개 통과, TypeScript 검사 통과.
- 새 계약의 대역 통합 검사: 생성→Critic 오류 판정→Revision의 실제 source_extract 전환→필수 재검수→A3 사람 수정·수락→정본·재조회. 대역 결과는 실제 모델 의미 품질 증거가 아니다.
- 기존 대역 검사들은 이전 source-role-v1 응답 계약을 명시 고정해 회귀를 확인한다. 새 authored-v2는 별도 새 검사에서 실제 동적 JSON Schema와 함께 확인한다.
- 기존 P2의 candidates/recovery 8개 실패는 이번 해결 범위로 주장하지 않으며 해당 전체 묶음을 반복하지 않았다. 전체 민원·Windows 실기·사람 효용은 미검증이다.

## 실제 모델 확인의 고정 범위

첫 개발 사례의 오류 판정은 모델이 실제로 생성했다. 정답 판정을 수정 경로에 주입하지 않았다. 수정 전후 ID·이력·정확 구간·현재 지문 검수와 A3 변환까지 실행했고 사람의 수락은 하지 않았다. **오류 탐지와 불충분한 수정의 보류는 확인했지만, 수정 자체의 유용성은 실패**했다.

모델은 두 주장에 같은 전체 후보 구절을 선택할 수 있으며 코드가 각각의 실제 위치를 기록했다. 이를 세밀한 최소 구절 선택 성공으로 주장하지 않는다. 전이 오류의 semantic_checks.exceptions도 refuted였으나 주된 확인 근거는 기간/대상 조건 차이다. 세부 항목과 이유의 완벽한 의미적 일관성을 보증하지 않는다.

다문서 Concept는 111.143초/실제 입력 3152토큰/출력 1275토큰으로 종료했다. 두 문서가 실제 같은 생성 입력에 있었으나 후보 5개(공공주택·공공임대주택·공공분양주택·국민임대주택·공공주택사업)가 모두 source_extract였고 synthesis는 0개다. 따라서 **여러 문서의 유용한 종합 정의 생성 기준은 미충족**이다. 원문을 정확히 복원한 것을 종합 설계 성공으로 계산하지 않는다. 출력 5개는 기존 상한에 도달한 값이며 전체 온톨로지 후보 수가 아니다.

후속 Critic은 기존 2개 주후보 묶음 규칙에 따라 3회 실행했다(92.084·103.783·65.560초). 5개 정의 모두 전체를 하나의 claim으로 묶고 supported, definition_completeness supported, needs_revision false로 판정했다. 정규화 record_errors는 0이었다. 문자 포괄과 응답 구조 통과가 의미 단위 분해·충분성의 성공은 아니다.


독립 의미 검토는 초기 정의 4개(정상 2·오류 2) 모두 적절히 구분했고 unknown은 0개라고 확인했다. 목적어 연결 2개(정상·오류 각 1)와 정상 주체 대조 2개도 맞게 판정했다. 최초 6 HTTP는 262.282초다. 이는 작은 고정 사례에 대한 결과이며 전체 자료/온톨로지의 정확도 분모가 아니다.

자연 교정 완성은 0/1, 부실 교정 재탐지는 1/1이다. 수정 후 conditions/exceptions의 unknown 2개는 최종 refuted 후보 안의 하위 판정이며 초기 정의 진단의 unknown 0과 구분한다. call_03에서 언급한 “어떤 자격”을 미제공 상세 자격 목록까지 새로 요구해야 한다는 뜻으로 확대하지 않는다. 명칭 반복과 선정 역할 설명의 소실만으로 해당 수정의 미완성을 판단한다.

## 다문서 독립 검토와 최종 후보 연결

독립 의미 검토는 5개 추출문이 제공 원문에 각각 정확히 한 번 일치함을 확인했다. 동시에 synthesis 0개, 각 후보 source_ref 1개, 선정 업무 연결 후보 0개, gaps=[]이므로 동결한 종합 기준은 실패했다. 다음은 원래 정상/오류 4개와 별개로 발견한 보충 분석이며 새 정확도 분모를 사후 구성하지 않는다.

- 공공주택: “다음 각 목” 뒤의 가/나목을 정의에서 제외했다. Critic은 원문 그대로라는 이유로 충분성까지 supported로 처리했다.
- 국민임대주택: 제공되지 않은 시행령 제2조를 가리키는 명칭만 남아 실질 정의가 부족하다. 외부 시행령의 세부 내용은 확인 범위 밖이다.
- 공공주택사업: 제공 본문에 있는 일부 유형(제3호마목)의 2029-12-31 유효 한정이 정의/time에 없다.
- 공공임대·공공분양: 상위 공공주택 요건과 연결하지 않고 독립 정의로 사용할 때 범위 확대 위험이 있다. 이 위험을 새 오류 개수로 합산하지 않는다.

앞의 세 누락을 후속 Critic은 검출하지 못했다. 인용 불일치나 새 사실 발명이 아니라 **정확한 인용을 정의 충분성으로 오인한 의미 미탐**이다. 원문 추출 경로도 유용한 정의를 자동 보장하지 않는다.

원 실행의 최종 A3 5개는 모두 deferred, observation_checks=[]였다. 이는 모델이 누락을 발견해서 보류한 결과가 아니다. 좁은 추적 결과 진단 실행기가 Concept의 원시 observations를 바로 검수에 넘겨 정상 `synthesis.assemble → identities.view`의 `candidate_view_version`을 생략했다. 저장 단계 finish는 대표 뷰를 구성하므로 검수 지문과 달라졌다. 5개 모두 검수 지문은 원시 후보와 일치하고 대표 뷰와 불일치했으며, 차이는 이 필드 하나였다. 진단 경로 문제로 분류하며 제품의 지문 검사를 완화하지 않았다.

별도 DB 복사본에서 기존 `identities.rows`로 후보를 준비하고 call_08~10 저장 응답을 재사용하는 **HTTP 0 재생**을 했다. 3회 모두 프롬프트·스키마가 원 실행과 완전히 같았다. 최종 5개는 observation_checks 각 1개, ai_review_current=true, review_status=unreviewed로 연결되고 지문 오류가 사라졌다. 사람 승인·정본 반영은 하지 않았다. 검수 연결 복원과 의미 품질 성공은 별개다. `revised=True`와 `revision1:review` 이름은 이 진단에서 추가 도구를 억제하는 용도였으며, 다문서 후보를 실제 Revision한 것으로 계산하지 않는다. 개발 오류의 자연 Revision 1회와 구분한다.

- 재생 실행기: `data/knowledge/semantic_claims_20261003_v3/replay_linkage.py`
- 성공 재생: `data/knowledge/semantic_claims_20261003_v3_linkage_replay_v2/{result,run,a3_candidates,preservation_checks}.json`
- 최초 재생은 프로세스 모델 설정을 복원하지 않아 기존 설정 검사에서 차단됐다(HTTP 0). 해당 DB·실행기를 `..._linkage_replay/`에 보존한 뒤 동일 설정을 복원했다.
- 원래 `..._v3_once/` 파일은 재생 전후 전체 해시가 동일하다. 원본 DB SHA-256은 `b31277736284a6d17fe3085322d78a3618014e7b95eefabd8572ea885fdb412d`로 유지됐고 복제본의 16개 테이블에 기존 모든 행이 그대로 남았다. 10개 HTTP 요청/응답과 포착 프롬프트/스키마/모델 텍스트의 대응, 추출 정의와 정확 인용의 일치도 확인했다.

## 최종 결과와 다음 최소 작업

최종 실제 실행은 **10 HTTP / 634.852초**, 모두 JSON Schema 유효·정상 stop이다. 최초 준비 실패 1 HTTP / 2.886초는 별도다. 실제 입력 최대 6382토큰, 출력 최대 1275토큰이므로 이번 종합·교정 실패를 입력/출력 한도 소진 탓으로 설명할 근거는 없다. 독립 실행 검토도 코드·입력·기준·원본 DB 해시와 HTTP 원장을 확인했다.

구현 계약과 저장·재조회·UI 연결은 완료했다. 실제 작은 정상/오류 구분 및 부실 수정 재탐지는 확인했지만, 유용한 수정 완성(0/1)과 다문서 종합 생성(0개)은 실패했다. 정규화에서 의미 판단을 대신하지 않으므로 Critic이 누락을 supported로 판단하면 집계 코드도 이를 고칠 수 없다. 전체 온톨로지·지식 그래프 품질 향상, 이전 코드 대비 우위, 사람 효용은 입증하지 않았다.

다음 최소 작업은 이번 실패를 개발 사례로 명시하고 다음 세 경계를 보완하는 것이다. 구현 전 기대 기준을 고정하고 보완 뒤 작은 정상 대조와 별도 전이 자료에서만 확인한다. 현 결과를 성공할 때까지 재실행하지 않는다.

1. 원문 추출에서도 지시어 목록·상위 적용 요건·본문 유효 한정이 독립 정의에 필요한지 검수한다. 정확 인용 여부와 정의 충분성의 이유를 구분한다.
2. Revision이 정상 역할·조건을 보존하도록 현재 preserve_claims와 실질 정의 검사를 활용한다. 한 단어 추출로 축소된 경우 교정 성공으로 처리하지 않는다.
3. Concept에서 요구된 문서 간 업무 연결을 종합 설계 또는 구체적인 미완료 이유로 남기게 한다. 무조건 synthesis를 강제하거나 복사를 금지하는 것으로 설계 유용성을 대체하지 않는다.
