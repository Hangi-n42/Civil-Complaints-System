# 원문 인용 복원·부모 연결과 의미 교정의 경계 — 2026-10-07

시작 커밋 `f8daa8469eb359b99b470b7d23d2c0b30f66b210` 이후 #617 → #616 → #620의 제한된 후속 작업이다. [이전 원문 경계 검증](https://github.com/Hangi-n42/Civil-Complaints-System/blob/00ecdc34791ec3192b2e6b66886809cb5e1a4bd0/docs/70_research/company_knowledge/business_source_boundary_20261007.md)의 실패를 유지했다. **원문 인용 복원과 파서 연결 전달은 수정했지만, 번호판·양도증명서 의미 교정과 실제 후보 교정은 실패했다.** 금련산센터의 필수 의미 선택은 실험에서 개선됐으나 추가 의미 스키마의 오류 때문에 해당 분기를 제품에 채택하지 않았다. 세 이슈의 전체 완료 기준은 충족하지 않았다.

## 진행 이유와 변경 경계

이전 결과에는 서로 다른 문제가 있었다. 금련산센터의 제목·본문을 합친 인용이 하나의 원문 주소에 귀속됐고, 저장 `plate_change_documents`와 후보 c47·기존 R은 일반 번호판 변경에도 반납 의무를 확대했다. `transfer_certificate`는 양수인 미방문이라는 상위 조건을 놓쳤다. 기록 오류, 모델의 의미 해석 오류, 후보 자체의 오류를 분리해 확인했다.

원본 DB·raw·요구 revision·후보·snapshot을 유지하고 새 사본·run ID를 사용했다. 기존 Gemma/Qwen 역할과 CPU BGE 설정을 바꾸지 않았다. 재추출, 새 judge, LH, 외부 모델, 검색 방식 비교, 추가 승인·배포는 없었다. 원래 R04/R05의 question·criterion을 유지했고, 모델 입력에 예상 정정 문장이나 정답 근거 참조를 넣지 않았다.

## 제품에 남긴 두 변경

1. 기존 `evidence_ref` 선택·서버 복원을 `LocalSourceCheck`에도 연결했다. 여러 원문은 각각의 ID를 선택하며 서버가 block/version/parse/span/text를 복원한다. 다른 셀을 합쳐 한 주소의 인용으로 쓰는 오류를 막는다. 참조 복원은 의미의 지지를 증명하지 않는다.
2. `autoschema.chunks`가 이미 사용하는 파서 조상 탐색을 공통 함수로 재사용하고, E 입력에 `source_parents`를 전달한다. 원문의 목록 조상 ID만 보존하며 조건의 의미를 서버가 결정하지 않는다. 정상 R 입력과 기본 검수 계약 v8은 유지한다.

새 effect-scope v12, E의 추가 의미 대응 출력, R의 효과·조건 비교와 교정 대상 연결, 중첩 인용 변환 및 전용 검사 코드는 제거했다. 기존 `business_models.py`, `business_review.py`, `business_use.py`, `discovery_segments.py`는 시작 커밋과 같다. 실패한 분기는 동결 코드와 patch로 남겼다.

### 인용 복원과 금련산 필수 범위

주소 복원 실험은 이전과 같은 원문 8개 구간·R04 질문·기본 지시문을 사용했다. 센터명, 이전등록 제목, 업무 본문이 서로 다른 주소로 복원됐고 `record_errors=[]`였다. 정상적인 번호판 교부 2~3일은 유지됐다. 다만 업무 전체 설명까지 required로 선택한 문제는 남았다.

추가 효과 대응 실험에서는 넓은 업무 설명이 `required=false/background`, 교부 2~3일이 `required=true/direct_answer`가 됐다. 이 선택 개선은 실제 관찰이다. 그러나 scope는 두 의미를 `statement_type=design_proposal`, `relation_kind=obligation`으로 분류하고 정상 2~3일도 `time.state=unresolved`로 기록했다. 필수 범위 분리 하나를 근거로 전체 의미 대응이나 기본 제품 경로가 개선됐다고 판단할 수 없다.

### 번호판의 효과 확대와 양도증명서의 부모 조건

첫 v12 출력의 번호판 statement는 구비 항목과 지역 번호의 반납 후 변경을 구분했다. 그러나 scope 첫 항목은 다시 일반 번호판 변경 신청인의 `반납/obligation`으로 확대했다. 같은 출력 내부에서 정상화된 설명과 잘못된 세부 대응이 공존했다. 이 scope를 후속 R의 정답으로 넘겨 c47을 정상화하지 않았다.

양도증명서 호출에는 ‘양수인 미방문시’ 부모 문구가 실제로 포함돼 있었다. 따라서 부모 문구의 입력 누락이 아니다. 별도로, 기존 `source_packet`이 원본 `locator.element_path`를 제외하면서 어느 자식에 해당 부모가 붙는지는 전달하지 않는 경계를 확인했다.

원본 파서에서 b30 위임장과 b31 양도증명서는 b29 미방문 항목의 자식이고, b32 번호판은 바깥 형제다. 구조 비교 입력에 추가된 연결은 정확히 `b30→b29`, `b31→b29` 두 개다. 이전 호출과 원문·요구·스키마·참조 map은 같고, 이 연결과 한 줄 설명만 추가됐음을 검사했다. 의미 라벨이나 정정 조건은 사람이 넣지 않았다.

모델은 연결 추가 후에도 양도증명서를 공통 서류로 일반화했다. 이유에는 b29 부모 관계를 언급하면서도 b31에 별도 조건이 없다고 썼고, 제공하지 않은 b32→b29 관계까지 언급했다. 이는 **연결 전달 이후에도 남은 해석 실패**다. 기존 v6 간단 출력 계약에서도 같은 조건 누락이 남았다. 부모 연결 수정은 정보 전달 개선이며 의미 교정 성공이 아니다. 번호판 행 내부의 반납 효과 확대 역시 별도 실패다.

저장 후보 c13 `claim_ad6bfe8f0b9d960379667f2c`의 Head와 c46 `claim_9d2ba40285f82ff7bc48e7e7`의 Event는 이미 양수인 미방문 조건을 보존한다. 이번 양도증명서 실패는 source meaning 재판정의 실패다. 정상 후보를 이 잘못된 source 해석에 맞춰 교정하지 않았다. 반면 c47 `claim_6804020432957407c5cf6595`의 일반화 오류는 기존 그대로 남는다.

- 버스 NEW13·CONTROL12의 전후 버전 원문 4개 입력 묶음을 기존 코드와 최종 코드로 구성했다. 공개 요구, 원문 행값·ID·좌표·표 위치·버전이 같고, 신규 목록 조상 연결은 생기지 않았다. 바뀐 부분은 E의 원문 참조 선택 계약이다. 각 주소를 원문으로 복원했고 기존 후보·snapshot도 같다. 버스 QA·추출·모델 호출은 반복하지 않았다. 이는 입력·복원 계약 검사이며 새 버스 답변 품질 평가가 아니다.
