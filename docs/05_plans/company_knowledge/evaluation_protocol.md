# 지식·온톨로지 평가 계약 — B0/B1/B2와 공통 품질 비교

- 버전: v1.1 · 2026-10-05. §1~6은 2026-09-26의 B0/B1/B2 계약을 보존하고, §7에 온톨로지 파이프라인의 공통 품질 평가를 추가했다.
- 상태: §1~6의 최초 K1 실행 계획과 §7의 신규 평가 기준을 구분한다. 이번 문서 개정은 새 모델 실행·성능 측정 결과가 아니다.
- 기준: [PRD §12](../../00_overview/company_knowledge_prd.md#12-효용-검증-설계와-출시-판단), [고정 입력·정답](../../../configs/knowledge/pilot_v1/README.md).
- 고정된 12개 질문·정답·원문 해시는 변경하지 않는다. §1~6의 실행 상태·순서·비용 계약과 §7의 별도 개발 평가를 혼합 집계하지 않는다.

## 1. 방식별 허용 작업과 같은 완료 조건

| 방식 | 허용 작업 | 추가 비용 |
|---|---|---|
| B0 | 사람이 원문 뷰어 검색·CSV 정렬/필터·표 편집으로 사실/관계/변경표와 인용 답변 작성. LLM·자동 의미 추출은 사용하지 않음 | 읽기·작성·교정·원문 확인 전부 |
| B1 | 동일 파서·공식 ID·메타데이터·문서 diff·기본 RAG, 동일 생성 모델의 문서별 사실/변경 초안, 수동 관계표와 문서별 요약→종합 허용 | 등록·색인·AI 대기·사람 수정·수동 관계 관리 전부 |
| B2 | B1에 개념/관계 후보·검토·관계 기반 영향 탐색·최대 2단계 Local 및 활성 주장 기반 Global 추가 | 온톨로지 생성·반례 검토·관계 수정·재추출·활성화 전부 |

공통 산출물은 대상 ID, 사실/관계, 조건·예외·단위·날짜 의미, 원문 위치, 검토/사용 상태다. 검색은 답변·인용·범위, 변경은 전후 사실·결정·미확인 사유까지 포함한다. B0에 LinkML이나 시스템 스냅샷 작성을 강제하지 않고 표와 버전 파일로 같은 의미를 표현한다. B1의 관계표도 허용하며 B2만 가진 그래프 알고리즘의 부재를 B1 오답으로 세지 않는다. 화면 모양·온톨로지 명칭은 정답이 아니다.

## 2. 입력·실행 격리와 비용 중복 방지

각 방법은 별도 작업 폴더/DB에서 시작한다. 다른 방법의 후보·정답·답변·검토 결과를 복사하지 않는다. 원문 bytes만 공유하고 B1/B2 파서/공통 모델 설정은 동일하게 한다. 미리 실행한 파싱·색인·요약을 무료 입력으로 넘기지 않는다. 이미 캐시된 결과를 재사용하면 생성 비용을 해당 방법에 귀속한다.

**측정 묶음은 준비 구축 S0 + 12개 과제 + 검색용 구축 보완 S1**이다. S0/S1은 추가 평가 문제가 아니라 최초 구축 비용의 두 부분이다. 구축형 과제에서 생성한 결과는 후속 단계에서 재사용하고 같은 추출·검토를 다시 청구하지 않는다.

- **S0 준비 구축:** 선택 자료의 출처 등록, B1/B2 파싱, 기본 검색 준비, B0 작업표 준비, B2 초기 온톨로지 생성·검토. 최신 정정 `20796` HTML/PDF는 DEV-01의 새 입력이므로 이때 등록·읽기·추출하지 않는다. 구 정정 `20794`의 선정 기준 사실과 근거를 검토하여 DEV-01 시작 상태를 만든다. 그 밖의 과제 대상 사실은 아직 생성·검토하지 않는다. 기준표 준비만 끝내고 실질 지식 구축 전체가 완료됐다고 표시하지 않는다.
- **구축형 과제:** 아래 순서대로 실행한다. 이전 과제에서 생성된 같은 개체·사실은 재사용한다. 해당 과제의 아직 없는 속성/조건만 추가한다.
- **S1 검색용 구축 보완:** 구축형 6건 이후, 나머지 선정 범위의 사실·관계와 검색 자료를 생성·검토한다. 특히 안내와 Q&A Q5/Q7/Q12를 포함한다. 이미 처리한 Q8/Q13·단지 사실은 중복 생성하지 않는다. 정확한 필요한 근거 ID를 정답 파일에서 모델에 전달하지 않고 `sources.json`의 선정 범위 전체를 사용한다. S1 비용도 최초 구축 비용이다.
- **검색형 과제:** 방법별로 준비한 지식에서 수행한다. 서로 다른 지식 품질도 제품 효과의 일부이므로 정답 지식을 무상 주입해 동일하게 만들지 않는다. 허용된 원문·자료 상태·기대 산출물만 동일하게 맞춘다.

## 4. 시계와 기록 양식

별도 타이머 앱·평가 서버를 만들지 않는다. 작업자가 초 단위로 기록하고 모델 호출은 기존 Run 기록에서 합산한다. 사람 시간은 실제 참여자가 측정해야 하며 에이전트 수행시간으로 대체할 수 없다.

| 값 | 정의 |
|---|---|
| `human_active_s` | 읽기·판단·작성·조작·수정·제출 전 원문 확인. 대기 중 원문을 읽으면 포함 |
| `system_wait_s` | 사람의 다른 작업과 겹치지 않은 시스템 대기. 겹친 구간을 다시 더하지 않음 |
| `elapsed_s` | 시작~종료의 경과시간에서 명시된 외부 중단만 뺀 값 |
| `model_total_s` / `llm_calls` | 실제 모든 모델 호출의 시간 합/횟수. 실패·재시도 포함. 경과시간에 다시 더하지 않음 |
| `grading_s` | 제출 후 고정 정답과 비교하는 평가자 시간. 업무시간 합계에서 제외 |
| `repair_s` | 채점 후 발견한 문제 수정의 사람 시간. 최초 제출과 별도 시도에 기록하며 완료 비용에 포함 |

시작은 과제/새 입력을 받은 시점, 종료는 결과 제출 또는 보류/실패 사유 기록 시점이다. 정상 원문 대조는 채점으로 빼지 않는다. 최초 실패를 수정 후 성공으로 덮어쓰지 않는다. 중단한 과제도 소요시간과 미완료를 기록하고 빠른 완료로 집계하지 않는다.

결과 파일은 로컬 `data/knowledge/evaluations/<session>/records.jsonl` 한 개와 산출물 링크면 충분하다. 아래는 **빈 양식**이며 0초 측정 결과가 아니다. 한 행은 S0/S1 또는 한 과제의 한 시도다. 작업자·모델·예산 메타데이터는 같은 폴더의 `session.json`에 한 번 기록한다. 필드는 session_id, operator, prior_exposure, code_revision, dirty_diff_hash, input_freeze_hash, os, hardware, models(tag/digest), parser_versions, prompt_hashes, options, execution_order이며 미확인 값은 null로 둔다.

```json
{"method":"B1","task_id":"DEV-01","attempt":1,"phase":"update","status":"not_run","started_at":null,"finished_at":null,"human_active_s":null,"system_wait_s":null,"elapsed_s":null,"model_total_s":null,"llm_calls":null,"grading_s":null,"repair_s":null,"edited_items":null,"added_missing_items":null,"deferred_items":null,"failed_check_ids":[],"critical_errors":[],"artifact_path":null,"interruption_note":null}
```

`status`: not_run / pass / partial / fail / deferred.해당 없음과 미측정 값은 null, 실제 0만 0이다. 수정/누락 수는 기존 검토 결정에서 세고 별도 LLM 판정기를 만들지 않는다. 산출물·원문은 Git 제외 로컬에 두고 요약 결과만 보고한다.

## 5. 실행 설정·순서와 판정

- 비교 시작 전 세션에 코드 revision+dirty diff 식별, 입력 freeze 해시, 작업자·사전 노출, OS·하드웨어, 모델 tag+digest, 공통 프롬프트/파서 버전, 예산과 실제 옵션을 기록한다. 재현에 필요한 설정만 남기고 실행마다 반복 입력시키지 않는다.
- B1/B2 공통 생성에는 현재 `STRUCTURING_MODEL`, B2 온톨로지 반례 검토에는 `CIVIL_LLM_RUBRIC_MODEL`을 사용한다. Qwen 요청은 `think=false`. 기존 민원 평가 루프는 호출하지 않는다.
- 최초 실행 설정 제안은 context 8192, 출력 상한 추출/온톨로지 2048·답변/요약 1024, temperature 0이다. 이는 품질/적합성 검증값이 아니다. 측정 전 개발 과제 1건으로 절단·입력 크기만 확인하고 필요하면 조정한 **같은 공통 설정**을 B1/B2에 적용·기록한 뒤 비교한다. 신규 6건을 예산 튜닝에 쓰지 않는다. 전체 입력 예산에는 지시문·질문·스키마·출력 예약분이 포함된다.
- Global의 묶음별 요약→한 번 종합을 B1에도 허용한다. 입력 부족은 범위를 표시하고 무제한 요약·재작성으로 숨기지 않는다. B2 추가 호출은 별도 포함하되 호출 수를 B1과 강제로 맞추지 않는다.
- 같은 12건을 각 방식 1회: **36개 최초 시도**와 방법별 S0/S1 기록. 관련 오류 수정 외 반복 측정·전체 조합 탐색은 하지 않는다. K2~K8 개발 과정의 튜닝 결과를 그대로 통제된 효용 실험이라고 부르지 않는다. 설정·입력·작업자가 비교 가능하게 기록된 실행만 재사용한다.
- 의존 순서를 유지하면서 S0/각 행마다 방법 순서를 B0→B1→B2, B1→B2→B0, B2→B0→B1로 순환한다. 순서 교차가 기억 효과를 제거하지 않는다. 한 사람이면 사전 노출과 후행 방법의 이점을 명시하고 작은 시간차만으로 채택하지 않는다.
- 최초 구축 비용 = S0 + S1 + 구축으로 분류된 5개 과제. 갱신 = DEV-01. 조회 = Local/Global 6개. **총 사람 작업시간 = 모든 S0/S1/12건의 human_active_s + 채점 후 repair_s**. repair_s는 동일 시도의 human_active_s에 넣지 않아 중복을 막는다. 부분 합과 총합을 모두 제시한다.
- B1/B2가 같은 필수 산출물을 완료한 경우 절감률 = `(B1 총 사람시간 - B2 총 사람시간) / B1 총 사람시간`. 분모가 0/미측정이면 계산 불가. 중대한 오류·영향 누락이 늘지 않고 10% 이상 줄어야 PRD 확장 조건 충족이다. 미완료·비교 불공정이면 추가 효용 미확인이다.
- DEV-01은 날짜 정정과 확인 불가 구분이 중심이라 복잡한 다단계 영향 탐색의 효용까지 입증하지 않는다. 고정 기준 밖 영향 누락의 정답을 사후 추정하지 않는다. KG 단독 인과효과·산업 ROI·연간 절감률을 주장하지 않는다.

## 6. 다음 단계와 사람 참여

프로토콜은 확정했지만 작업자와 실제 모델 digest/예산 적합성은 실행 시 기록할 값이며 현재 측정 완료가 아니다. 사람 실험 참여자 확보는 구현의 선행 조건이 아니다. K2 자료 등록·추출부터 진행하고 기능 준비 후 기록 가능한 범위에서 비교한다. 현업 참여 없이 개발자만 측정하면 개발자 파일럿으로 보고한다.

## 7. 온톨로지 파이프라인 공통 품질 평가

### 7.1 목적과 적용 범위

- 기준 ID: `ontology-quality-v1`, 승인일 2026-10-05. 이후 동일 자료의 재비교는 이 절의 지표·분모·비교 조건을 따른다. 지표나 정답을 바꾸면 새 버전으로 남기고 과거 결과를 덮어쓰지 않는다.
- 주 평가는 **추출 정확성 → 개념 정합성 → 정보 보존 → 검색·질의응답 성능**이다. 개별 오류 하나로 모든 성과를 성공/실패 하나에 합치지 않는다. 범위 오류·정상 의미 보존·실제 교정·허위 복구·CQ/A3 도달 여부는 별도 제품 진단으로 함께 보고한다.
- [AutoSchemaKG](https://aclanthology.org/2026.acl-long.942/) §4 및 부록 C/E/G/H의 평가 축을 채택한다. 해당 논문의 짧은 유형/관련 개념 정합성과 우리 정의·역할의 적용 범위 정확성은 서로 다른 지표다. 한국어 자료·인코더·정답·추출 계약이 다른 점수를 논문의 92%와 직접 비교하지 않는다.
- 이 절은 평가 방법의 변경이다. 승인 정책, 자료 부족을 복구 명령으로 만들지 않는 원칙, 기존 실패 기록을 바꾸지 않는다. A6 최초/보완 평가, 기존 K9 사람 효용 시험, 고정 후보 교정 재현은 각자의 기록으로 보존한다. 이번 평가에 사람 오류율·총작업시간 측정을 추가하지 않는다.

- 정보 보존의 답변 정답률과 제공 산출에 의한 근거 지지율을 함께 기록한다. 모델의 사전 지식으로 맞힌 답을 산출물의 정보 보존으로 단정하지 않는다. 질문·정답·채점 지시는 양군 동일하며 사후 유리한 질문만 선택하지 않는다.
- 기본 집계는 전체 고정 단위를 합친 수치와 문서/사례별 수치를 함께 제시한다. 같은 원문을 국소 사례와 전체 문서에서 중복 채점한 점수를 독립 표본처럼 더하지 않는다. 사전 선정 범위만 채점했다면 그 범위를 표시한다.
- 생성 실패·빈 출력에서는 기준 의미의 회수 0과 실행 실패를 함께 기록한다. 산출이 없으면 P는 정의 불가, 기준이 있으면 R/F1은 0으로 둔다. P=R=0의 F1은 0, 기준 분모가 없으면 해당 없음이다. 유효 부분 산출은 실제 범위만 채점하고 전체 기준의 누락을 제외하지 않는다. 후속 제품 경로 미도달은 전체 계획 질문에서 실패/미도달로 유지하고, 실행된 질문만의 점수도 별도로 표시한다. 진짜 자료 부족 질문에서 올바른 확인 불가는 사전 정답에 따라 정답이다.
- 단일 가중 총점은 만들지 않는다. 네 공통 축과 제품 진단·실행률·비용을 나란히 보고한다. 한 축 향상과 다른 축 악화가 동시에 있으면 상충 결과로 남긴다.

### 7.3 동일 기준으로 다시 비교하기 위한 동결

기존 실행 폴더의 manifest/freeze/session/입출력 기록을 재사용한다. 새 평가 서버나 범용 프레임워크를 만들지 않는다. 첫 호출 전에 다음을 한 번 고정한다.

1. `protocol_id`, `study_id`, `corpus_id/version/hash`, 원문·parse·허용 자료 범위·업무 질문·초기 DB/온톨로지 버전/기준 유형, 개발 노출 여부. 기존 실패·정상 대조를 포함하되 필요한 원문이나 당시 존재했던 적합한 유형을 인위적으로 빼지 않는다.
2. 채점 범위·대상 ID, 기준 명제/유형·허용 대안·필수 조건, 질문·정답·정답 근거·판정 규칙의 버전/해시. 출력 조건을 가린 독립 검토자가 원문으로 확인하며 생성기의 자기평가를 정답으로 쓰지 않는다. AI 검토와 실제 사람 검토를 구별한다. 정답/기준은 생성 입력에 제공하지 않는다.
3. 코드 SHA와 dirty diff, 실제 실행 파일/프롬프트/스키마 해시, 역할별 모델 tag/digest·옵션·seed 지원 여부, 인코더·검색기·분할/정규화 설정, 하드웨어, 호출·시간·입출력 상한과 종료/기술 재시도 정책.
4. 군별 바뀌는 설정, 실제 단계 순서·전송 패킷, 측정 위치(최초 생성/제품 내부 교정 후/후속 활용), 원문 비교 답변과 검색 기준군, 반복 횟수·실행 순서·채택 판단 기준. 비용은 실제 실행으로 측정하며 상한을 실측치처럼 쓰지 않는다.

향후 같은 `protocol_id`라도 자료·정답·모델·평가기 설정이 다르면 동일 조건의 연속 성능 비교가 아니다. 비교표에 달라진 항목을 표시한다. 원시 기록은 Git 제외 로컬에 보존하고 문서에는 재현 식별자·요약·실패 원인을 남긴다.

### 7.4 첫 비교: 현재 이웃 경로 전체 비활성/활성

| 군 | 실제 제품 설정과 흐름 | 비교에서 고정할 것 |
|---|---|---|
| P0 | `KNOWLEDGE_DISCOVERY_NEIGHBORS=false`, recipe `neighbor_contract=disabled`. 현재 기본 Concept→Relation 흐름과 기존 문맥 공급 | 같은 코드·원문/CQ·초기 상태·모델·단계별 예산·핵심 근거/표현 판단·검색/답변 설정 |
| P1 | `KNOWLEDGE_DISCOVERY_NEIGHBORS=true`, recipe `neighbor_contract=relation-neighbors-v1`. Relation→이웃 문맥→Concept 및 Builder의 연결 문맥 사용. 직접 정의 경로 유지 | P0와 같으며 군별 실행 DB/캐시/새 후보·검수 결과는 격리 |

- 이것은 **순서 변경과 연결 문맥 공급을 포함한 현재 기능 묶음의 효과**다. 선택기 단독 또는 같은 원문의 순수 직렬화 효과라고 부르지 않는다. 기존 고정 Relation/Concept에 이웃 패킷만 더한 N0/N1 시험과 별도 `study_id`를 사용한다. 설정 문자열뿐 아니라 저장 recipe와 실제 전송 입력·호출 순서로 군 차이를 확인한다.
- 원래 두 문서의 선정 범위를 주 비교로 사용하고, 그 안의 연결 문맥이 필요한 역할/범위 대상과 직접 정의 정상 대조를 분석 구간으로 미리 표시한다. 역사적 국소 사례 결과는 참고 또는 별도 진단이며 전체 문서 점수에 중복 합산하지 않는다. 두 군은 동일한 전체 허용 자료를 사용하되 실제 선택된 문맥과 비용의 차이는 처치 효과로 기록한다.
- 양군은 동일 초기 snapshot에서 새로 실행한다. 전체 경로 비교에서는 한 군의 Relation/Concept 출력이나 올바른 교정안을 다른 군에 넣지 않는다. 처치와 무관한 공통 파싱/색인만 같은 캐시를 사용할 수 있으며 비용을 명시한다.
- 네 평가 축은 가능한 같은 실행 산출에서 측정한다. 같은 질문의 원문 조건과 문서 검색 기준군은 불변이면 한 번 실행해 공유한다. 일반 문서 검색 대비 KG의 추가 효과와 P0 대비 P1의 효과를 각각 표시한다.
- 정보 보존은 승인 전 산출도 평가할 수 있다. 실제 KG 활용에 승인·사실 추출이 필요하면 준비된 기존 격리 경로를 사용하고 승인/수정 주체·비용을 기록한다. 양군 원산출을 채점 후 임의로 고쳐 비교하지 않는다. 후보 산출을 평가 전용으로 검색한 경우 `draft_proxy`로 표시하며 제품 KG/승인/A3 성공으로 세지 않는다. 정답 KG를 주입하거나 운영 승인 경계를 우회하지 않는다.
- 처음에는 양군 각 1회의 제한 개발 비교로 시작한다. 같은 설정의 재현 여부·횟수·순서는 출력 전에 고정하며 승리한 군/사례만 재실행하지 않는다. 1회 차이는 관측 결과이며 일반적 품질 향상·유의성·기본 활성화의 근거로 확대하지 않는다.

### 7.5 실행 중단·보고·채택

- 먼저 모델 없는 입력/군 격리/기록 경계 확인과 예상 호출·시간 상한을 고정한다. 실제 비교 중 모델·프롬프트·예산·판정 기준을 조정해 통과할 때까지 반복하지 않는다. 필요한 수정은 별도 버전으로 양군에 적용하고 최초 실패를 남긴다.
- 개별 의미 오류는 성능 측정 대상이다. 그 오류만으로 상대 군이나 기술적으로 독립 가능한 추출/개념/정보 보존 평가를 취소하지 않는다. 제품 실행기가 중단한 경계는 그대로 기록하며 평가를 위해 성공으로 바꾸지 않는다. 실행 불가능한 후속 단계는 구체적 의존성과 미도달 수를 보고한다.
- 보고 순서: ① 동결 조건·실제 비교 범위 ② 네 공통 축의 P0/P1 분자·분모·차이 ③ 실행률과 최초/교정 후 산출 ④ 범위·교정·허위 복구·CQ/A3 진단 ⑤ 호출·입출력·시간 ⑥ 개선/악화/동등/판단 불가 사례와 채택 의견. 미측정 지표는 이유와 필요한 최소 후속 작업을 적는다.
- 기존 완료 기준인 **“정상 의미를 유지하며 실제로 수정했고, 같은 요구를 다시 확인했으며, 필요한 다음 단계까지 이어졌다”**는 교정·제품 경로의 완료 주장에 적용한다. 이를 못 달성해도 실제로 측정한 추출/개념/정보 보존 성과는 따로 보고한다. 반대로 공통 점수가 높다고 미완료 교정이나 A3를 완료 처리하지 않는다.
- 현재 문서는 기준 확정까지이며 P0/P1 신규 비교 결과는 없다. 자동 기본 활성화, 사람 효용·일반 정확성 입증, 이슈/PR 변경 지시를 포함하지 않는다.
