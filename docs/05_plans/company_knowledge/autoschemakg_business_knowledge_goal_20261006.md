## AutoSchemaKG를 실제로 가져와라

공식 저장소는 `HKUST-KnowComp/AutoSchemaKG`, 계획의 기준 SHA는 `d0a1666ae6621806faf814504c73678de4e809f2`다. 논문과 이 버전의 코드를 대조하고 계획 §3의 스키마·프롬프트·메시지 구성·개념화에서 그대로 가져올 부분과 수정해 가져올 부분을 반입하라. 출처·커밋·원본 MIT 고지와 변경 이유를 남겨라.

**원리만 인용하고 전부 재작성하거나 현재 Concept/Relation의 이름만 바꾸지 마라.** 반대로 전체 패키지의 서버·의존성·파일 포맷을 그대로 설치할 필요도 없다.

유지할 핵심은 같은 원문에 대한 **개체–개체 / 사건–개체 / 사건–사건 추출 → 출처 있는 임시 그래프 → 개체·사건·관계 개념화**다. 개체 개념화는 실제 연결 이웃을 사용한다. 한국어·로컬 모델·근거/조건/버전 보존에 필요한 변경은 하되 추출을 승인된 온톨로지에 종속시키거나, 모든 후보 검수를 개념화 전에 직렬로 붙여 원형을 무너뜨리지 마라.

명시적 정의 직접 추출은 유지하고, 추출 후보를 확정 사실로 취급하지 마라. `has_concept`와 승인 `is-a`를 구분하라. 같은 두 끝점의 서로 다른 관계·조건·시점·출처를 보존하라. 무작위 이웃 표본의 개수는 정답이 아니며, 필수 조건·예외·기간·참조를 선택 예산 때문에 버리지 마라.

## Requirement와 복구에서 놓치면 안 되는 점

Requirement는 무엇이 있어야 질문에 충분히 답할 수 있는지 나타내며 원문 사실이 아니다. 지속 관리할 핵심 업무 질문에만 만들고 대상·상황·기간·충족 기준을 갖춰라. 사용자 합의와 원문을 대조해 조율 세션이 기준을 정하고, 생성 모델이 자기 출력에 맞춰 기준을 줄이지 못하게 하라. 원문 기대 정답은 생성 입력과 분리하라. 모든 항목의 사용자 사전 승인이나 실제 사람 시험을 구현 선행조건으로 추가하지 마라.

- 근거를 못 찾았다는 이유로 자료 자체가 없다고 단정하지 마라. 미읽기·미선택·자료 부족·해석 미확정·반증을 구분하라.
- 미확인은 반증이 아니다. 미확인 주장을 확정 사실로 사용하지 않되 거짓으로 자동 판정·삭제하지 마라. 확인된 모순이나 과도한 의미 추가와 구분하라.
- **원문이 해당 의미와 범위를 지지하고 현재 표현이 빠진 경우**에 실제 생성 복구를 요청하라.
- 근거 없는 주장이 이미 있으면 해당 부분만 고치고 정상 의미를 보존하라. 근거 주소·상태 필드의 존재를 의미 검증으로 취급하지 마라.
- 필요한 목록·조건의 일부가 연결됐다고 전체 Requirement 충족으로 처리하지 마라. 문서 간 연결의 전제·대상·시점도 확인하라.
- 새 근거·모순이 발견되면 이전 근거 판단과 그에 의존한 교정 요청을 정정할 수 있어야 한다.
- 변경 때는 기존 근거 의존과 새로 추가된 의미의 관련성을 함께 확인하라. 연결 경로가 없다고 영향 없음으로 확정하지 마라.

## 평가와 과도한 검증 방지

**정답셋은 작업 세션이 계획 §9.0의 GPT-6 Astra 전문가 에이전트에게 맡겨 실제 구축하라.** 작성·검토 에이전트 각각에 `gpt-6-astra`를 지정하고 제품 구현 이력·생성 결과를 상속하지 않는 별도 문맥으로 시작하라. 원문·공개 업무 범위만으로 문제·정답·근거를 만들고 평가할 파이프라인의 그래프·답변을 출제 기준으로 주입하지 마라. 제품의 Gemma·Qwen으로 출제·정답 확정을 대신하지 마라. 너는 범위·근거·고정 상태를 확인하라. 이 작성·검토 목적의 원문 외부 처리는 이미 승인됐으며, 새 제품 에이전트 계층을 만드는 작업은 아니다.

- 업무 요구의 필수 의미·조건·교정 목표와 변경 영향 참조도 원문 기반으로 작성하고 별도 검토 에이전트로 대조하라. ID·전후 값·인용 위치 같은 확인은 기존 코드와 원본 표를 이용하라.
- 검토 에이전트에는 초안 정답·해설·작성 과정을 처음부터 주지 마라. 원문과 문항에서 답과 근거를 먼저 도출·저장한 뒤 초안 정답과 대조하게 하라. 복수 정답·조건 누락·잘못된 범위가 있는 항목만 고치고, 미확정 항목은 이유를 보존하라. 합의가 날 때까지 무한 검수하지 마라.
- 같은 비교군에 사용할 질문·선택지·정답·기대 의미·근거·모델/프롬프트·평가셋 버전을 실행 전에 고정하라. 제품 생성 입력에는 정답·해설·평가용 기대 관계·근거 매핑을 주지 마라. QA에는 질문·선택지만 제공하라.
- 모호한 문항의 제외 내역을 남기고, 시스템이 틀렸다는 이유로 문항을 빼거나 필수 요구를 없애지 마라. 고정 정답 오류를 발견하면 원문 근거와 버전을 남겨 관련 비교군을 공통 기준으로 재채점하라. 정답만 바뀌면 저장 응답을 쓰고, 질문/입력이 바뀐 항목만 다시 실행하라.
- 실제 작성/검토 모델·프롬프트·에이전트/실행 ID를 남기고 사용 기록이 확인될 때만 **GPT-6 Astra 기반으로 작성·검토한 참조 정답셋**이라고 표시하라. 사용 모델이 불명확하면 그 명칭을 쓰지 말고, 사용 불가 시 로컬로 몰래 대체하지 말고 구축의 미완료 범위를 보고하라. 독립적으로 가능한 구현은 이어가라.
- 작성·검토가 같은 모델이라는 한계를 밝히고 서로 다른 모델의 교차 검증·인간 정답셋·일반 정확성으로 확대하지 마라. 유효 문항의 실행 실패·빈 답변을 분모에서 숨기지 말고 제외·미확정 비율과 정답셋 작성·검토 사용량/시간을 별도로 보고하라. 사람의 전수 정답 작성·항목별 승인을 선행조건으로 추가하지 마라.

작업 세션은 관련 코드 검사와 작은 재현을 수행하고, 너는 결과·원문 대조와 후속 연결을 평가하라. 통과한 검사를 근거 없이 반복하거나 단계마다 새 검수기·승인 체계·전수 평가를 추가하지 마라. 코드 검사 통과와 실제 모델 품질은 구분한다.

**계획 §9.4의 실행 확인은 필수다.** 변경 경계의 코드·통합 검사, 부산의 실제 제품 전체 흐름, 실제 오류 교정·누락 복구, LH 실패·정상 대조, 이웃 A/B 실제 개념화, 버스 실제 전후 재검토를 수행하라. 평가용 runner만 별도 로직으로 작동시키지 말고 제품 진입점을 사용하라. 실행별 코드/자료/설정 식별자·run ID·실제 출력·판정을 남기고 완료/실패/미실행을 구분하라. 모의 결과·과거 결과·단위 검사로 로컬 실제 모델 실행을 대신하지 마라. 반복 실패로 완료하지 못한 항목은 미완료로 보고하라.

평가축은 원형의 추출 정확성·누락·개념화·정보 보존·QA를 참고하고, 여기에 우리의 요구 충족·허위 복구 요청·실제 교정·변경 재검토를 추가한다. 제품 모델과 분리해 만든 고정 정답셋에 대해 객관식은 코드로 채점하고, 자유 표현·필수 의미의 로컬 채점은 원문·고정 참조와 대조하는 보조 판정으로 사용하라. 로컬 채점 모델이 정답을 바꾸지 못하게 하고, 이를 모델상 독립 검증으로 부르거나 자기평가만으로 성공을 확정하지 마라. 판정 미확정을 별도 보고하고 실제 사람의 총작업시간 실험과 AI 검토를 구분하라.

이웃 효과는 연결 문맥이 역할·범위 구분에 필요한 대상으로 측정하라. 동일 원문·관계 풀·모델·설정·핵심 판단에서 **일반 문맥 A / 연결 관계로 구조화한 문맥 B**를 비교하고 A의 필수 정보를 인위적으로 빼지 마라. 선택 정보 집합이 달라졌으면 구조화 효과와 선택 효과를 혼동하지 마라. 전체 경로가 막혀도 가능한 개념화 제한 비교는 수행하되 전체 성공으로 확대하지 마라.

같은 실패를 원인에 대한 새로운 변경 없이 반복하지 마라. 해당 경로가 개선되지 않으면 잠시 중단하고 구체 실패·원인·이번 변경의 효과·다음 수정을 보고하라. 한 경로의 실패로 독립적인 구현·시험까지 자동 중단하지 마라. 사용자에게 매번 재승인을 요구해 진행을 끊지 말고 승인된 범위의 통상적인 구현 판단은 직접 하라.

## 완료와 최종 보고

완료 기준은 **“정상 의미를 유지하며 실제로 수정했고, 같은 업무 요구를 다시 확인했으며, 필요한 후속 단계까지 이어졌다”**다.

보류 증가·후보 삭제·후보 수 증가·형식 검사 통과만으로 성공 처리하지 마라. 올바른 자료 부족 판정은 진단 성과로 분리하고, 근거가 충분한 과제의 실제 복구·교정·활용을 완료하라. 해결되지 않은 필수 과제가 있으면 전체 완료로 표시하지 마라.

최종 보고에 다음을 포함하라.

1. 실제로 바뀐 구조와 동작, AutoSchemaKG 직접 재사용/변형/우리 신규 구현.
2. 부산·LH·버스 각각의 결과와 근거. 개선·악화·동일·미확인을 구분.
3. 실제 교정, 정상 의미 보존, 같은 요구 재확인, 필요한 후속 단계 연결의 달성 여부.
4. 기존 병목 개선과 이웃 선택 자체의 효과를 분리한 결과 및 채택 판단.
5. 호출 수·입출력량·시간과 미측정 범위. 제품용 외부 API 어댑터는 모의 계약 검사만 했다는 한계와 평가셋용 외부 모델 사용을 구분.
6. 남은 병목이 있다면 무엇이고 왜 남았는지, 이번 변경이 의미 있었는지, 다음 개선 우선순위.
7. 평가셋의 실제 작성/검토 모델·에이전트/실행 ID·버전·포함/제외/미확정 수와 근거, 정답 정정 내역, 작성·검토 사용량/시간. 같은 모델의 별도 에이전트 검토라는 한계와 로컬 의미 채점의 한계를 밝히고, 출제 완료와 실제 제품 평가 완료를 구분.

구현·검증 산출물과 변경 파일을 명확히 남겨라. 커밋·푸시·PR·이슈 처리는 이 실행 세션에 유효한 사용자 지시에 따라 진행하되, 이 프롬프트만으로 PR 병합·배포·제3자 메시지 권한을 추가하지 마라.
