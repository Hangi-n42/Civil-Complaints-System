## 1. 결론과 조사 범위

확인된 개선 가능한 설계 문제는 **이미 확보한 자료 구조와 주체 식별 정보를 버리거나 약화한 뒤, 모델이 대상·속성·값·근거를 다시 조합하도록 맡긴 것**이다. 출력 계약의 불일치와 누락을 세지 않는 완료 지표도 함께 확인했다. 원인별 기여도는 분리 측정하지 않았다. 수락 검사는 존재·자료형·문자열 위치를 주로 확인하므로 의미가 틀린 조합을 모두 막지 못한다.

따라서 PDF 표의 알려진 구조는 코드로 매핑하고, AI는 설명문의 속성·범위·조건 해석에 집중시킨다. 온톨로지·SQLite·직렬 실행기·후보 검토·LinkML·LangExtract를 유지한다. 모델 교체, 그래프 DB, 자동 재평가 루프, 범용 매핑 플랫폼이 먼저 필요한 상황은 아니다.

이번 자료는 이미 오류가 드러난 양산 공고군이다. 원인이 관찰된 입력으로 분석 비용을 줄이는 선택이며, 다른 공고·기관·레이아웃으로 일반화한 품질 평가가 아니다. 기존 수락 134개는 개발 검토로 수정한 결과로서 자동 추출 정확도의 근거로 사용하지 않는다.

## 3. 세 관점의 원인

### 3.1 근본: 온톨로지, 추출 계약, 사실 정확성을 혼동

온톨로지는 ‘세대수/준공일/입주예정월/최초입주월이 무엇인가’를 정의한다. 어떤 PDF 셀에 해당 값이 있는지, 어느 행의 대상에 속하는지, 여섯 행 모두 처리했는지는 별도 추출 책임이다. LinkML에서 JSON Schema를 생성하는 것만으로 이 책임이 충족되지 않는다.

현재 한 번의 모델 출력에 주체 찾기, 명칭 복사, 슬롯 선택, 값 복사, 정규화, 인용 선택, 범위·조건 해석을 함께 맡긴다. 여기서 대상·행·숫자 정규화처럼 코드로 고정할 수 있는 부분까지 생성 대상으로 둔 것이 불필요한 오류 경로다. ‘인용이 있음’, ‘스키마 검사 통과’, ‘수락됨’은 서로 다른 상태이고 사실 정확성과도 구분해야 한다.

### 3.2 거시: 처리 흐름과 검토 비용의 문제

1. **K2→K4 구조 활용이 부족하다.** PDF의 행·열·병합 범위와 HTML의 공식 단지 코드가 이미 있지만 K4가 이를 자유 생성 입력으로 사용한다.
2. **완료의 분모가 잘못됐다.** 입력 블록을 모델에 보냈으면 processed, 반환 후보가 형식상 처리됐으면 succeeded다. 누락한 행·선택 속성이 검토 목록에 나타나지 않는다.
3. **등록부와 추출 대상을 섞는다.** PDF만 재확인해도 CSV 사실이 재생성되어 검토량을 늘린다.
4. **검토가 복구를 완결하지 못한다.** 기존 후보 값은 수정 가능하지만 없는 후보 추가와 잘못된 predicate 교체가 불가능하다. 근거 ID 직접 입력도 원문 검토보다 저장 구조 이해를 요구한다.
5. **재사용 범위가 명시적이지 않다.** LH 필드와 안정 슬롯 ID가 전역 매핑·프롬프트·날짜 검사에 분산돼 있다. 다른 reviewed 온톨로지를 선택할 수 있다는 UI가 모든 온톨로지와 매핑 호환을 뜻하지 않는다.

## 4. 해결 설계

### A. 이미 구조화된 자료는 코드로 읽는다 — 최우선

- LH 파일럿의 문서 매핑 설정 하나에 입력 유형·헤더·슬롯 ID·자료형·단위·날짜 역할·변환·버전을 모은다. 기존 `FIELDS`와 이번 PDF 매핑 범위만 옮긴다. 자동 매핑 엔진은 만들지 않는다.
- LinkML은 의미의 정본을 유지한다. 실행 시작 시 매핑이 사용한 개념·슬롯의 안정 ID·의미 정의·domain/range·다중값 여부를 확인한다. 같은 ID라는 이유만으로 다른 의미의 정의에 재사용하지 않는다. 라벨·근거 ID·생성 시각·무관한 정의 추가는 호환 서명에서 제외하고, 실제 사용한 정의의 불일치만 해당 매핑의 재검토 사유로 표시한다. 계보 관리 엔진은 만들지 않는다.
- PDF 행 키는 원문 버전·파싱 실행·페이지·side·table·row로 구성한다. 단지명과 주소는 연결 근거, `호` 값은 건설호수, `최초입주`는 월 속성에 매핑한다. 병합 헤더의 두 열 중 `개동`을 호수로 읽지 않는다.
- `1,300호→1300 + 호`, `201106→2011-06 + month`는 코드로 변환한다. 실제 셀 전체 원문을 raw로 남기고 원래 블록·문자 위치를 연결한다. 단지명·수량·날짜 정답을 설정 파일에 하드코딩하지 않는다.
- 현재 알려진 표 구조 밖의 입력은 미지원/검토 필요로 남긴다. 임의 위치 추측이나 자동 모델 fallback은 추가하지 않는다. 새 양식은 필요할 때 매핑 한 건을 검토해 추가한다.
- PDF 별칭→공식 개체의 연결은 기존 검토된 출처 범위 별칭 또는 사람의 이름·주소 확인을 유지한다. 행에서 값이 정확히 읽혔다고 공식 개체 연결까지 자동 승인하지 않는다.
- 등록부는 연결 문맥으로 읽는다. 사용자가 CSV도 추출 대상으로 선택한 경우에만 CSV 후보를 생성한다. 전역 중복 제거로 서로 다른 출처의 주장을 합치지 않는다.

### B. 설명문 AI의 일을 의미 선택으로 줄인다

- HTML의 `official_code`가 있으면 해당 설명문의 주체를 코드로 고정한다. LLM에게 다시 단지명·공식 ID를 발명하도록 요구하지 않는다. 공식 식별이 없는 문장은 기존 미해결 연결 경로를 유지한다.
- 단지별 설명 문맥을 입력 단위로 고정하고 기존 글자 예산 안에서 묶는다. 한 호출에 여러 단위를 보낼 수 있으나 결과는 단위 ID로 구분한다. 각 단위에 `facts[]`와 미추출/검토 필요 사유를 반환하게 한다.
- 각 사실은 허용 `predicate_id`와 해당 사실의 범위·조건·예외 및 각각의 근거를 갖는다. 리터럴은 `raw_value`·값 근거·단위, 관계는 대상 표기/연결·대상 근거로 구분하고 기존 `object_entity_id XOR value` 계약을 유지한다. 리터럴 null은 만들지 않는다. 동일 속성이라도 A5의 총 985·국민임대 521·영구임대 464는 범위가 다른 별도 사실로 표현할 수 있게 한다.
- 이번 LH 매핑·축소 출력 계약은 실제 사용하는 단일값 속성에 한정한다. 범위가 다른 사실 여러 개와 한 사실의 다중값 배열을 혼동하지 않는다. 새 입력의 미지원 다중값 슬롯은 명시적으로 표시하고 기존 다중값 저장 결과의 읽기·검토 동작은 유지한다. 관계의 `value=null`은 정상적인 기존 표현이다.
- `raw_value→value`의 숫자·월·일 변환은 코드가 담당한다. 월만 있는 원문에 일 01을 붙이지 않는다. 자유 서술의 의미를 숫자 파싱 성공으로 승인하지 않는다.
- 자료 단위에서 허용한 근거 ID만 선택하게 하고 서버에서도 동일하게 검사한다. 공식 ID용 문맥과 사실의 값·범위 근거를 분리한다. 리터럴의 출처는 값 근거에서, 관계의 출처는 관계를 서술한 근거에서 결정하며 다른 출처를 참조하면 명시적으로 남긴다.
- CQ는 온톨로지/추출 범위 선택과 실행 이력에 보존하되, 고정된 사실 추출 입력에서 질문을 주체의 원문처럼 사용하지 않는다. 해당 단위의 허용 속성만 설명하고 짧은 계약 예시를 넣는다.
- 현재 EXAONE·호출당 1회·기존 예산을 유지한다. 스키마 변환은 기존 `materialize` 앞의 작은 어댑터로 처리하고 API의 후보·결정 형식은 유지한다. 계약/매핑 버전 변경은 새 Run이며 기존 성공 산출물과 섞지 않는다.

### C. 누락을 보이게 하고 검토로 복구한다

- 이미 존재하는 Run/단위 payload에 입력 단위별 처리 결과를 저장한다. 새 테이블은 필요 없다. 표는 **선택된 행×선택된 슬롯**, 설명은 **제공한 설명 단위**가 분모다.
- 서버가 기대한 입력 단위 ID와 반환 ID를 대조해, 결과 자체가 없는 단위·중복 반환·대상 밖 ID를 표시한다. 모델이 ‘누락했다’고 보고할 때만 세는 구조로 만들지 않는다.
- 실행 완료, 형식/참조 검사 통과, 미처리/검토 필요, 검토 수락을 분리해 표시한다. 설명문 ‘처리됨’은 모든 사실을 찾았다는 뜻이 아니다. `facts=[]`/‘사실 없음’도 모델 판정으로 표시하며 검토할 수 있게 한다.
- 기존 후보 화면을 단지/원문 행 기준으로 묶고 근거 셀을 선택하여 수정하도록 한다. ID 복사 절차를 줄이고 값 수정 시 파생 월 메타데이터를 같이 갱신한다.
- 누락 복구는 고정 원문의 셀/구간·현재 개체 연결·검토된 속성을 선택하는 수동 후보 추가 한 경로로 처리한다. 자동 수락하지 않고 기존 결정 이력을 사용한다. 잘못된 속성 후보는 기각 후 새 후보로 만들며 기존 predicate를 몰래 바꾸지 않는다.
- 수동 생성은 후보와 생성 결정에 `origin=manual`을 기록한다. 기존 changeset revision으로 원자적으로 추가하고 기존 Run의 고정 입력 범위 안에서만 허용한다. 별도의 수동 후보 키를 사용해 원본 `units.records`·자동 산출물·호출 수를 바꾸지 않으며, 자동 재시도에서 생성/덮어쓰지 않는다. 자동 산출 후보 수와 수동 추가 수를 구분한다. 새 수동 Run·새 저장소는 필요 없다.
- 알려진 표의 값 셀과 대상 셀에는 같은 행 규칙을 적용하되, 헤더·각주/범위 근거와 공식 ID 확인용 등록부는 역할별로 구분한다. 여러 행을 덮는 병합은 덮는 범위로 판정할 수 있는 경우에만 허용하고 그 밖은 미지원으로 표시한다. 자유 서술의 정당한 다중 근거를 무조건 같은 행 규칙으로 제한하지 않는다. 숫자 변환 값 불일치 검사는 수동 후보에도 적용한다.

확인은 기존 오류를 재현하는 좁은 사례에 한정한다.

1. PDF 6행/18필드, 동수·호수, 다른 행의 값 결합, 숫자 raw/value 불일치, 월→임의 일 생성.
2. HTML A5 총 985/국민임대 521/영구임대 464의 독립 범위와 근거. CSV 990·HTML 메타데이터 521은 별도 출처 주장으로 유지.
3. null/빈 결과·없는 근거·잘못된 속성·누락 수동 복구와 기존 revision 충돌/결정 이력. 출력 단위 누락, 기존 관계의 대상·근거 보존, 정상 헤더/등록부 근거 허용, 수동 추가 후 자동 재시도의 중복 방지를 각 경계 사례로 확인한다. 새 변경에 영향받는 기존 테스트만 실행.

5. 보고 지표: 대상 행/필드 누락, 주체·슬롯·값·근거 오류, 수정 필요 후보/필드 수, 호출 수·시간. 새 검토 시간은 측정할 수 있지만 과거 시간이 없으므로 과거 대비 시간 절감률을 만들지 않는다.

전체 12과제, 모델 대결, Windows 실기, 새 현업 승인 절차는 이번 수정의 선행 조건으로 추가하지 않는다. 이 표의 6행/18필드는 알려진 문서의 회귀 확인이며 일반 자동 정확도 입증이 아니다. 자유 서술 오류가 남으면 해당 단위만 보완한다. 모델 교체 여부는 입력 계약 개선 뒤에도 남는 오류를 보고 판단한다.

## 6. 전문가 검수

LLM/정보추출 관점과 온톨로지/데이터·산업 적용 관점의 독립 에이전트가 코드를 읽고 원장을 대조했다. nullable 계약, 병합 헤더 손실, 행 누락, 수락 검사의 숫자/행 귀속 반례, 24개 후보의 수정 이력을 지적했다. 위 진단과 설계에 반영했다.

추가 제3자 설계 검수는 PDF 매핑→설명 계약→검토 복구 순서와 파일럿 1회 비교가 적정하다고 평가하면서 아래 보완을 요구했다. 모두 설계에 반영했다.

- 리터럴에만 raw 변환을 적용하고 관계의 대상·근거 계약 보존.
- 서버가 입력/출력 단위를 대조해 반환 자체가 누락된 경우도 표시.
- 수동 후보 생성 위치·이력 명시, 기존 AI Run 원출력·호출 수 불변.
- 원인별 기여도를 확정하지 않는 표현, 사용한 온톨로지 정의만 호환 확인.
- 데이터 관점 재검수: 단일값과 범위별 복수 사실 구분, 정상 헤더·등록부와 병합 범위 허용, 수동 추가와 자동 재시도의 독립성 명시.

이는 AI 에이전트의 코드·설계 검수이며 외부 현업 전문가 승인이나 해결 효과의 실제 검증을 뜻하지 않는다.
