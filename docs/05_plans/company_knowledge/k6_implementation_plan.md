- **인도 상태(2026-09-29):** K6 구현은 인도하고 K7으로 진행한다. [세 핵심 문제 보완·독립 검수](../../30_manuals/knowledge_k6_targeted_fix_result.md)의 D는 조건 방향 오판·조회 회귀로 미채택. 기본 A 유지, 품질 잔여 작업은 [모델 교체 후 #516](https://github.com/Hangi-n42/Civil-Complaints-System/issues/516)으로 분리. 구현 인도와 FR-11 품질 목표 전체 달성은 구분한다.

- 기준일: 2026-09-29. 상태: **정보 보존형 조회 구현, 정확하고 간결한 답변은 미완료**. [질문 해석·선택·요약 개선 계획](k6_answer_quality_plan.md)에 따른 28회 비교를 완료했으나 세 후보 모두 미채택했다. [실제 결과](../../30_manuals/knowledge_k6_answer_quality_result.md)를 우선하며 수치/근거 보존과 PRD FR-11 완료를 구분한다.

- Ponytail 원칙: 기존 SQLite·직렬 실행기·Ollama·화면 재사용. 신규 그래프 DB, 작업 큐, 에이전트 프레임워크, 별도 평가 모델, 자동 재작성 루프 없음.

## 1. 완료 범위와 실제 시작점

K5 활성 스냅샷은 개체 7개(단지 6·공고 1), 수락 연결 32개, 주장 107개다. 스냅샷 `8fc330a1085f44b4813466e015fdd549`는 현재 로컬 원장에만 존재한다. 코드 복제만으로 자료가 준비되지는 않는다.

K6는 `/knowledge`의 검색 탭에서 질문·대상·자료 범위·버전·기준일을 선택하고, **대상 연결 → 최대 2단계 관계 조회 → 근거 정렬 → 1회 답변 생성 → 최신 사용 상태 확인**을 연결한다. Global은 K7 안내만 표시하고 실행 요청은 422로 거절한다. 기존 민원 Search/QA 및 Q0~Q7은 변경하지 않는다.

고정 Local 과제는 다음 **3건 그대로** 사용한다. 과제 정답·기대 판정은 생성 프롬프트에 넣지 않는다.

| 과제 | 필요한 범위 | K5에서 시작할 수 있는 부분 / 보충 필요 |
|---|---|---|
| DEV-03: 사송 A-5 수치와 공실 | 정정 HTML·PDF·단지 CSV의 수량/범위·시점 | 521/464/985/990과 CSV 주택유형은 수락됨. PDF 5개동·CSV 6동의 속성/근거는 보충 필요. 자료 시점과 수량의 범위를 함께 보존. 차이 원인·현재 공실은 확인 불가 |
| NEW-01: 우선공급 확인서와 발급기관 | 안내 1025의 중소기업근로자 해당 표 행 | 원문은 파싱 완료, 현재 활성 공고군에 없음. 자격 유형→서류→발급기관의 두 관계와 적용 조건을 새 검토 묶음으로 준비해야 함 |
| NEW-02: Q7 청약통장 재사용 | 2026 Q&A 임대주택 Q7 | Q7 원문은 파싱 완료, 현재 활성 공고군에 없음. 이전 주택 유형·다음 청약 유형·재사용 조건을 문서 범위 안에서 준비해야 함 |

NEW-01/02에 현재 스냅샷으로 `insufficient`가 나오는 것은 올바른 제한 표시일 수 있으나 **과제 성공이나 K6 전체 완료로 세지 않는다**. 새 확인용 문항도 설계자에게 노출된 자료이며 blind 평가로 보고하지 않는다.

## 2. 검색 전에 필요한 최소 지식 보충

1. 안내 1025 해당 표와 Q7은 현재 원장에 파싱 완료돼 있으므로 해당 고정 블록을 재사용한다. 고정 자료 목록과 블록/자료 버전 매핑을 기록한다. 새 웹 수집·전체 PDF 재추출을 선행하지 않는다.
2. K3 LinkML에 필요한 개념·관계가 있는지 확인하고 없는 것만 기존 후보/결정 흐름으로 보충한다. NEW-01은 자격 유형·서류·발급기관과 두 관계, NEW-02는 Q&A 항목과 조건을 보존한 설명 속성부터 시작한다. 주택 유형 전체를 그래프로 만드는 작업은 필요 없다. DEV-03의 동수 속성도 원문 기준으로 추가한다. 평가 기대값에서 지식 레코드를 복사하지 않는다.
3. 현 K4 자동 등록은 `LH:complex`·`LH:notice` 중심이다. 일반 개체가 이미 지원된다고 가정하지 않는다. 필요한 경우 **근거가 있는 수동 로컬 개체 등록**만 기존 entities/entity_links에 추가한다. 내부 UUID, 공식 ID 없음, 문서 버전/절 범위, 검토된 concept_id·명칭·Evidence를 보존한다. 이름만 같은 개체를 자동 합치거나 가짜 LH 공식 ID를 부여하지 않는다. 같은 대상을 재사용할 때 기존 ID를 명시적으로 선택한다.
4. 해당 블록을 고정한 기존 K4 추출/수동 후보·결정 경로로 사실과 관계를 준비한다. 일반 개체를 frozen run에 포함할 작은 접점을 추가한다. 일반 문서 경로에서는 현재 필수인 registry_source_version_id를 선택 사항으로 만들고, 기존 단지/공고 경로에서는 등록부 요구를 유지한다. 새 범용 추출기를 만들지 않는다. NEW-01은 자료 버전·파싱 실행·HTML element_path·행 번호를 키로 같은 표 행의 세 셀과 제목/열 헤더를 묶는다. 행 번호만으로 다른 표를 섞지 않는다. NEW-02는 Q7 답변의 이전 조건과 다음 청약 유형을 한 묶음으로 보존한다. 기존 수동 사실 추가도 주체·대상 링크와 허용 관계를 그대로 확인한다.
5. 기존 검토 후 K5의 **새 스냅샷**으로 묶는다. 온톨로지가 바뀌면 서로 다른 온톨로지 버전의 묶음을 그대로 합치지 않는다. 기존 K5 버전은 보존하고 과제별 명시적 스냅샷을 사용해도 된다. DEV-03은 동수 속성이 추가된 새 온톨로지로 A-5의 HTML·PDF·CSV 해당 블록만 추출/검토해 과제용 묶음을 만든다. 기존 107건 전체를 재처리하거나 구버전 묶음에 새 속성을 덧붙이지 않는다. 자동 수락·자동 활성화는 추가하지 않으며, AI 개발 검수와 현업 사람 승인을 구분한다.

이 보충은 과제 3건을 실행하기 위한 제한된 데이터 준비다. 범용 개체 병합, 외부 온톨로지 grounding, 추가 정정 영향 시스템은 범위 밖이다. 원문 확보/검토가 끝나지 않으면 검색 기능 완료와 자료 준비 미완료를 나누어 보고한다.

## 3. 요청 처리 절차

### 3.1 범위 고정과 대상 연결

- `snapshot_id=null`이면 시작 시 활성 ID를 한 번 고정한다. 활성 버전이 없으면 `insufficient`와 설정 안내, 명시한 버전/대상이 없으면 기존 오류 계약을 따른다.
- 선택 자료는 스냅샷의 자료 ID로 한정한다. 빈 목록/범위 밖 ID는 422. K5 최신 상태·명시적 유효기간 검사를 재사용하고 원장 payload를 직접 무필터 검색하지 않는다. K5 기본 조회에는 source_ids 필터가 없으므로 검색에서 주장·경로 관계·주체/대상 링크·공식 식별 근거 등 **필수 의존 출처가 모두 선택 범위 안인 묶음만** 포함한다. 예를 들어 PDF 사실이 CSV 식별 근거에 의존하면 CSV 제외 시 해당 묶음도 dependency_source_out_of_scope로 제외하고 자료 선택 안내를 제공한다. 제외한 출처를 몰래 입력에 추가하지 않는다.
- 공식 ID·대표명·**사용 가능한 수락 링크의 별칭**으로 연결한다. 공백/대소문자 등 표기 정규화만 하고 숫자/블록 구분을 지우지 않는다. 중첩 이름은 구체적인 긴 표기부터 일치시킨다.
- 동명 대상이 여러 개면 `ambiguous`, 후보·출처를 반환하고 모델을 호출하지 않는다. 사용자는 `scope.entity_ids`로 선택해 다시 요청한다. ID 선택도 현재 범위·상태를 확인한다.
- 정확히 연결되지 않으면 근거 없는 추정 연결을 하지 않는다. 문서/개념 중심 질문은 준비된 로컬 개체 또는 화면의 대상 선택을 사용한다. `scope.text`는 추가 검색어이며 새로운 권한/자료 범위를 만들지 않는다.

### 3.2 관계와 근거 선택

- 필터된 스냅샷의 주장으로 작은 인접 목록을 만들고 최대 2단계만 순회한다. SQL/표준 dict·set으로 충분하며 NetworkX를 추가로 연결하지 않는다.
- 대상의 직접 사실과 요청에 관련된 관계를 우선한다. 역방향으로 관계를 탐색할 수 있지만 반환 경로에는 **저장된 관계의 주체·대상 방향**을 보존한다. 같은 공고의 다른 단지를 질의 대상의 속성으로 섞지 않는다.
- 질문에 명시한 여러 대상은 각 대상의 경로를 구분한다. 2단계 이웃 전체를 자동으로 생성 입력에 넣지 않는다. 개체 경로와 종점의 값 주장 ID를 함께 반환하되 값 주장을 추가 개체 관계 hop으로 세지 않는다.
- 검색 단위는 **주장과 필요한 근거 묶음**이다. 값·단위·scope·conditions·exceptions·날짜 역할, 경로의 관계 주장, 연결 근거와 field_evidence를 함께 보존한다. 같은 대상·속성에서 출처/범위가 다른 값은 하나만 top-k로 남기지 않는다.
- 스냅샷에 고정된 Evidence 발췌를 사용한다. K2 원문 전체에서 미검토 사실을 답변 지식으로 끌어오지 않는다. 화면의 원문 블록 열람은 기존 감사 경로를 사용한다.

### 3.3 재사용 방식과 예산

| 자산 | K6 적용 |
|---|---|
| LightRAG, 고정 커밋 `4a319ecdc14f36446ae98b34952ab6719b2c322b` | 개체/관계와 텍스트 근거를 결합하는 방법만 현재 원장에 재구현. 엔진·자동 병합·별도 저장소 도입 없음 |
| 기존 BM25와 한국어 토큰화 | 기존 tokenizer와 `bm25s`를 직접 사용해 허용된 주장/발췌 묶음을 요청 안에서 정렬. 공식 ID/별칭 연결은 토큰화와 별도로 처리 |
| 기존 Chroma/RRF | 이번 최소 구현에서는 보류. 기존 BM25 stage 전체는 민원 Chroma의 case_id에 결합돼 있으므로 그대로 호출하지 않음. 독립된 검색 순위가 하나인 현재 단계에 RRF를 억지로 넣지 않음 |
| K5 상태/스냅샷 함수 | 필터·의존 근거 확인 재사용. 검색과 화면 간에 별도 상태 판정 규칙을 만들지 않음 |
| 기존 `GenerationService.call_ollama()` | 기존 `OLLAMA_MODEL` 그대로, 메타데이터 반환 사용. 민원 생성/평가 파이프라인 전체 호출 없음 |

이는 포괄적인 [재사용 계획](implementation.md)의 K6 첫 구현을 좁힌 결정이다. 품질 실패가 실제 확인되면 지식 전용 collection과 evidence_id 어댑터로 벡터/RRF를 추가할 수 있으나 이번 선행 조건은 아니다. 새로운 패키지나 임베딩 모델 설치는 필요 없다.

- 초기 생성 입력 상한 12,000자, `num_ctx=16384`, `num_predict=1536`, temperature=0. 기존 모델 선언 범위 확인 후 적용한다. 문자 수를 정확한 토큰 수라고 가정하지 않는다.
- 작은 파일럿은 관련 묶음 전체가 들어가면 모두 넣는다. 초과할 때만 BM25 순위로 **묶음 단위** 제외한다. 조건·예외·상충 수치 묶음을 쪼개거나 뒤를 잘라 보내지 않는다.
- 필요한 묶음 하나도 온전히 들어가지 못하면 `insufficient`, 일부만 담으면 `partial`과 omitted ID·범위를 표시한다. 자동 요약/추가 호출 없음. 첫 3건에서 실제 부족한 예산만 조정한다.

### 3.4 생성과 응답 직전 상태 확인

- 정상 생성 **1회**, 모호성/빈 근거 **0회**. JSON 출력은 사실 문장별 `text`, 출처 묶음 `source_ref`, 비어 있지 않은 `assertion_ids`, 별도 `limitations`로 제한한다. 구현 중 ID 혼동이 확인돼 출처별 주장 선택지를 JSON Schema로 제한하고, `evidence_ids`는 서버가 주장에 연결된 근거에서 구성하도록 좁혔다. 외부 응답의 문장별 주장/근거 ID는 유지한다. 현재 공실을 확인할 수 없다는 설명처럼 원문 사실이 아닌 한계는 limitations로 구분하여 화면에 렌더링한다. 한계에 허구의 근거 ID를 요구하지 않으며 그 안에 새로운 사실을 쓰도록 지시하지 않는다. 인용 URL·원문·위치는 모델이 만들지 않고 서버가 ID로 채운다.
- 각 문장의 ID 존재, 해당 주장과 Evidence 연결, 제공 입력 범위, 출력 잘림/JSON 오류를 확인한다. 잘못된 ID를 제거한 뒤 답변을 성공으로 반환하지 않는다. 실패는 기존 생성 오류 및 failed Run으로 남기고 재작성하지 않는다.
- 이 검사는 참조 일치 검사다. 문장이 원문 의미를 정확히 보존한다는 보장은 아니므로 실제 3건에서 조건·수치·인용을 대조한다. 질문별 Qwen 심사/전문가 합의는 추가하지 않는다.
- 생성 입력에 사용한 주장·관계·별칭·식별 근거·Evidence·자료 버전의 의존 ID를 기록한다. **모델이 최종 인용하지 않은 입력 근거도** 영향을 줄 수 있으므로 상태 재확인 대상에 포함한다.
- **최초 검색 필터에 사용한 status_revision을 기준으로 유지**한다. 생성 직전 revision이 달라졌으면 의존 항목을 다시 확인하여 차단된 입력을 모델에 보내지 않는다. 직전 revision으로 기준을 덮어써 초기 변경을 놓치지 않는다. 생성 직후에도 마지막으로 확인한 상태와 비교하고 변경되면 그 의존 항목만 최신 상태로 다시 확인한다. 관련 항목이 중단/재검토로 바뀌었으면 `stale`, `answer=null`, 파생 인용·경로를 비우고 재조회 사유를 반환한다. 자동 재생성 없음. 무관한 상태 변경만으로 답변을 폐기하지 않는다.
- 활성 포인터만 바뀌면 처음 고정한 스냅샷의 답변을 반환한다. 사용한 snapshot_id와 확인 시각을 표시한다. 기준일 근거가 없으면 `unverified`를 유지하며 현실의 현재 공실/법적 자격을 확정하지 않는다.

## 4. API·저장·화면 변경

- `POST /api/v1/knowledge/search`: [기존 계약 §4](contracts.md#4-localglobal-입출력)의 봉투·필드 유지. HTTP 성공 안에서 answered/partial/insufficient/ambiguous/stale 구분. Global은 K7 전까지 명시적 미지원 오류.
- 자료 준비 접점: `POST /entities`에 ontology_version_id·concept_id·name·source_version_id·evidence_ids·actor·reason을 받아 근거 있는 로컬 개체를 등록한다. 기존 entity_link 검토가 수락 경계이며 등록만으로 활성화하지 않는다. 추출 요청에는 선택한 local_entity_ids를 추가하고 고정 입력에 포함한다. 같은 이름의 새 ID 자동 생성/병합은 하지 않는다.
- 새 `app/knowledge/search.py`에 순차 검색만 구현. schemas/router 연결, 필요하면 snapshots.py의 기존 필터를 작은 내부 helper로 공유. 검색을 위해 새 DB 테이블/영속 인덱스/결과 캐시는 만들지 않는다.
- 내부 `kind=search` Run에 질문·범위·선택 스냅샷·입력 의존 ID·모델/프롬프트 버전·상태·실제 metrics 기록. 기존 단일 executor에 넣고 API가 결과를 기다린다. 등록/진행 검사에는 기존 lock을 쓰되 LLM 대기 중 lock을 잡지 않아 사용 중단 요청이 처리되게 한다.
- 다른 작업 실행 중이면 기존 RUN_BUSY로 응답한다. 실패/서버 재시작은 기존 Run 규칙을 적용하며 parse 포인터를 변경하지 않는다. 호출 실패도 횟수와 벽시계 시간에 포함한다. 내부 search Run을 `/runs`의 추출 재시도로 보내지 않는다.
- `KnowledgeSearch.tsx`: 질문·스냅샷·자료·선택 대상·기준일 입력, Local 선택과 Global 준비 중 안내. 답변 옆에 출처·짧은 인용·원문 위치, 텍스트 관계 경로, 범위/제외·시간·호출 수 표시.
- 모호한 대상은 선택 후 재검색. stale은 기존 답변을 지우고 재검색 버튼 표시. 버전/필터 변경은 명시적으로 검색한 결과와 구분한다. 그래프 캔버스·챗 기록·추가 승인 화면 없음.

## 5. 필요한 확인과 작업 순서

자동 확인은 작은 fixture와 가짜 모델로 다음 경계에만 집중한다.

1. ID/별칭과 동명 대상 분기, 서로 다른 대상 혼합 방지, 2단계 제한과 실제 관계 방향.
2. 선택 자료·최신 사용 상태·날짜 필터, 조건/범위가 다른 수치와 근거 묶음 보존.
3. 인용 ID/주장 연결 오류·잘린 출력이 성공 처리되지 않음, ambiguous/insufficient 0회 및 정상 생성 1회.
4. 생성 도중 관련 제한 변경은 stale, 무관한 변경은 유지. 상태 변경 API가 모델 대기에 막히지 않음. search Run이 parse 포인터를 건드리지 않음.

실제 확인은 **DEV-03·NEW-01·NEW-02 각 1회**로 제한한다. 질문·정답 기준은 고정 파일 그대로이며, 답변·근거·경로·scope·누락·실제 호출/시간을 저장한다. 실패가 나오면 해당 사례만 재확인한다. 자료 미준비는 미실행/미완료로 보고하고 성공으로 대체하지 않는다. 모호성·동시 변경은 위 자동 확인으로 다루며 실제 모델 사례를 늘리지 않는다. 변경 UI의 TypeScript/ESLint 및 근거 열람 1회 확인으로 마친다. 전체 민원/12과제·Windows 확보·모델 비교·B0/B1/B2 전체 벤치마크는 K6 선행 조건이 아니다.

| 구현 묶음 | 예상 | 산출물 |
|---|---|---|
| K6-A 검색 기능 | 1~2일 | K5 공고군 기반 범위 고정·대상 연결·관계/근거·생성·상태 재확인·API/화면·경계 테스트 |
| K6-B 과제 자료 보충과 최종 확인 | 1~2일 | 부족한 최소 개념/로컬 개체·근거/관계 검토 경로, 과제별 스냅샷, 고정 3건 결과 |

기존 K6의 2일 추정은 현재 활성 자료에 없는 NEW-01/02 지식 준비 비용을 포함해 검증된 일정이 아니다. 두 묶음으로 구분하되 K6 전체 완료는 자료 준비와 3건 확인까지다. 현업 검토 대기와 원문 확보 지연은 개발 기간과 별도 기록한다.

## 6. 검수와 인도

- 독립 AI 전문가 검수: 지식 모델/평가 준비 검수에서 원문 파싱 완료, 일반 개체 등록 공백, CSV 필수 입력, HTML 표 행 분리, DEV-03 동수 누락을 확인해 §1~2에 반영했다. 검색/계약 검수에서는 최초 필터~생성 사이 상태 변경 누락, 자료 필터의 교차 출처 의존, 사실 문장과 확인 불가 설명의 분리를 지적해 §3에 반영했다. 단일 생성·BM25 우선·2단계 탐색 범위를 유지했다. 수정 후 두 관점으로 반영 내용을 재확인했으며 새 검증 체계를 추가할 필요는 없다는 검수 결과를 받았다. 이는 코드·원장 기반 AI 검수이며 현업 전문가 승인·실제 모델 품질 검증과 구분한다.
- 완료 보고: 변경 이유·파일, 대상/근거 선택, 실제 호출/시간, 과제별 통과/실패/미실행, 수정된 오류, 남은 한계 및 K7 착수 조건.
- 현재 다음 단계: K6에서 질문 요구 정리·출처별 맥락·짧은 답변의 비교 개선. 기존 3건과 추가 4건으로 정확성/선택/간결성을 나눠 확인한 후 K7 착수 여부 판단.
- 현재 사용자 결정이 필요한 사항 없음. 최초 작성은 계획만 수행했으며, 후속 구현에서 개발용 자료를 원문 대조·수락해 비활성 스냅샷 3개로 준비했다. 기존 활성 버전은 유지했다. 실제 범위·미검증 항목은 위 결과 기록을 따른다.
