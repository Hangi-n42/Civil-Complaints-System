## 현재 변경의 구현 범위

- 입력 용량 계산의 선행 보완에 더해, 공통 의미 참조·원문 근거(E)/후보 표현(R)/전체 연결(join) 분리·서버 행동 도출·기존 교정/복구 연결을 부분 구현했다. 새 DB나 실행 프레임워크는 만들지 않았다.
- 사전 검사와 실제 호출은 같은 응답 스키마를 사용한다. 프롬프트와 스키마의 UTF-8 바이트 합계는 보수적 입력 계산이며 실제 토큰 수와 구분한다.
- 실제 동결 실행 v102는 E HTTP 2회에서 중단했다. 첫 E의 의미 오류와 둘째 E의 length/최종 JSON 없음은 서로 다른 실패다. R·실제 교정/복구·join·A3는 실행하지 않았고 후보 19개는 그대로다.
- 종료 후 v103에서 부모 원문 구간이 하위 구간을 포함하는 서버 검사만 수정했다. 저장 응답 재검사에서도 자료명 누락으로 계속 실패했으며 의미 오류를 성공으로 변환하지 않았다. 집중 코드 검사 212개 통과는 실제 의미 품질 개선을 뜻하지 않는다.
- join 용량 초과 분할, 패킷 간 상충/전제 연결과 관련된 부분만 무효화하는 동작, 실제 수정·정상 보존·같은 요구/A3 검증은 남아 있다. 작업 N은 구현하지 않았다.
- 아래 작업별 내용은 승인된 목표 설계이며, 현재 달성 범위는 위 상태와 [실행 보고서](../../70_research/company_knowledge/ontology_grounded_meanings_20261005.md)를 기준으로 판단한다.

## 실제 의존성과 공유 범위

현재 `discovery_requirements.packet/assess`와 `discovery_scope.requirement_application`은 원문·현재 후보·업무 요구·기존 문맥 발견 결과를 사용한다. `process_group`은 기본 Concept→Relation 순서로 이 입력을 만든다. 새 이웃 선택 결과나 Relation→Concept 재배치가 있어야 근거/표현 분리를 구현할 수 있는 의존성은 확인되지 않았다. 핵심 작업에서는 기존 생성 순서를 유지한다.

공유하는 것은 작업 1의 의미키·근거/범위 참조·입력 지문, 기존 원명제와 문맥 기록, 호출 예산 함수다. 작업 N은 이 계약과 성공한 Relation 출력을 받아 선택 이력을 보탠다. 역으로 핵심 판단은 선택 이력이 없어도 실행되어야 한다. 같은 모듈을 수정한다는 사실은 편집 순서 조정의 이유이며 의미적 선행조건은 아니다. 필수 원문 보존·현재성 확인은 양쪽에 필요하지만 새 이웃 선택기나 개체 통합 기능을 요구하지 않는다.

## 작업 1 공통 의미 참조와 입력 계약

**문제와 가설:** 동일한 연결에 대해 상위 판단은 unknown인데 하위에서는 생성 누락이 되는 사례가 있다. 현재 여러 설명의 의미적 동일성과 필수 전제를 서버가 알 수 없다는 한계가 있다. 명시적 참조를 공유하면 내부 불일치를 줄일 수 있다는 가설이며, 서버가 자연어의 의미적 동일성을 증명하는 것은 아니다.

**기존 → 변경:** `ContextNeed`의 meaning/applies_to/source_refs/missing_source와 현재 `meaning_key`를 유지하되, 원문 판단과 후보 표현 판단이 같은 버전의 의미를 참조하도록 한다. 자유 서술 이유만으로 새로운 요구를 만들거나 변경하지 않는다.

**입출력과 저장:**

- `meaning_key`: canonical 의미 본문·적용 범위·근거 주소에서 서버가 계산하는 불변 키. 내용이 바뀌면 새 키와 `supersedes=이전 키`를 남기며 같은 키의 본문을 덮어쓰지 않는다. 모델은 제공된 키를 참조하고 새로운 의미 본문은 서버가 새 키를 부여한다. 자연어 유사도로 서로 다른 요구를 자동 병합하지 않는다.
- 의미 본문: 원문 명제/정의 또는 필요한 연결, 대상·범위·조건·예외·부정·시점, CQ/범위 ID, 원문/Relation 참조.
- `premise_keys`: 해당 연결에 실제 필요한 의미키. 표현상 관련 있다는 이유로 모두 필수 전제로 연결하지 않는다. 독립 의무와 미제공 상세 정의는 별도 의미로 유지한다. 이 목록은 각각 필요한 AND 전제에 한정한다. OR·부정·예외가 있는 조건은 원문 그대로의 복합 의미 단위로 보존해 모델이 대조하며 일반 Boolean 엔진을 추가하지 않는다. ‘A 또는 B’를 둘 다 필요한 목록으로 펴서 한쪽 unknown을 전체에 전파하지 않는다.
- `source_assessment`: 근거 판정·판정 이유·전제별 근거·가용성 기록·입력 지문.
- `representation_assessment`: 후보 위치·표현 상태·입력 근거 판정 지문·후보 지문.
- 기존 source/version/parse/block/span 계약을 사용한다. 후보 ID와 원문 언급 주소는 다른 식별자다.

**호출 순서:** 기존 생성 순서에서 각 단계에 현재 확보된 원문/문맥의 의미키를 제공하고, 직접 정의·Relation 출력·기존 독립 문맥 발견 결과를 같은 참조 계약에 연결 → 원문 근거 판정 → 표현 판정 → 대상 교정/복구 → 정상 의미 보존과 표현 재검수 → 원래 요구 재확인. 최초 Concept에 아직 없는 Relation 출력을 요구하지 않는다. 현재 입력·범위와 일치하는 발견 결과는 생성부터 재사용하고, 뒤 단계에서 확보한 새 의미는 영향받는 후보와 교정 입력에 연결한다. 최초 발견 목록을 완전한 정답으로 고정하지 않는다.

초기 문맥 준비는 기존 구조 분할·상위 조건·명시 참조·현재 재사용 가능한 발견 결과를 사용한다. 별도의 작업 단위 전체 `context` 선행 호출을 신설하지 않는다. 현재 독립 발견은 대상 명칭·role_source·CQ에 조건화돼 있으므로, 이를 전체 묶음 발견으로 바꾸고 ‘동일 결과 캐시’라고 해석하면 안 된다. `discovery_requests/discovered_context/candidate_application/context_unit_ids/attach_saved/current_applicability_ids`의 기존 범위 키를 유지한다. 처음 만든 후보의 후검수에서 새 필수 의미가 발견되면 해당 의미를 현재 후보와 교정 입력에 연결한다. 필수 내용을 알고도 제외하는 것과 아직 발견하지 못한 누락을 구분하며, 후자는 독립 검수·집중 대조로 확인한다.

원명제 ID와 의미키는 별개다. 단계 출력이 실제 참조한 키만 연결하고, `premise_keys`는 해당 packet이 제공한 현재 유효 키로 제한한다. 자기 참조·순환·없는 키는 판정 불완전으로 남기며 그 의존 부분의 완료/복구를 허용하지 않는다. 코드가 검사하는 것은 명시 의존의 정합성이지 누락 전제의 의미적 완전성이 아니다.

**수정 모듈:** `discovery_models`, `discovery_scope.required_context/discovered_context`, `discovery_requirements.fingerprint`, `discovery_analysis.recipe/make_prompt/normalize`, `discovery_review`의 현재성 계산. 기존 digest·canonical refs·Pydantic을 사용한다.

**단순화:** 같은 필수 의미를 생성·Critic·requirements마다 별도 자유 서술 목록으로 복제하지 않고, 본문과 참조를 분리한다. 과거 저장 결과는 변환해 새 판정인 것처럼 사용하지 않는다. 새 recipe와 이전 recipe 사이의 재개를 기존 호환성 검사로 거절하고, 이전 결과는 읽기만 유지한다.

**한계:** 잘못 분해된 전제 목록, 누락된 의미, 잘못된 원문 해석은 여전히 가능하다. 전제 의존은 범위/시점이 같은 특정 명제에만 적용한다. 설명이 닮았다는 이유로 unknown을 전체 후보에 전파하지 않는다.

**선행/완료:** 다른 작업의 참조 기반. 의미 변경 시 의존 판정만 무효화되고, 같은 정상 의미가 생성·교정·후검수에서 같은 주소로 추적되며, 과거 실행이 수정되지 않는 집중 계약 검사가 완료 조건이다. 이것만으로 의미 품질 완료를 선언하지 않는다.

## 작업 2 근거 판단과 표현 판단 분리

**문제:** 현재 cause/judgment/source_refs의 형식 조합만으로는 v11의 잘못된 생성 누락을 구별하지 못한다. 근거가 해당 관계의 모든 필수 전제를 지지하는지 모델이 잘못 판단할 수 있다.

**기존 → 변경:** 기존 CQ 적용성 호출을 `context_phase=grounding`으로 확장·교체하고, 기존 requirements 호출은 그 결과에 대한 표현 대조를 담당한다. 기존 적용성 호출 + 새 근거 호출 + 기존 종합 판정을 그대로 중복 실행하지 않는다. 후보별 Critic/적용성은 역할·정의 검수 책임을 유지하고, CQ 전체를 다시 판정하지 않는다.

**호출·저장·행동의 연결:** 먼저 원문 근거 판정과 그 입력 지문을 기존 `analysis_units`에 저장하고, 표현 판정은 그 판정 ID/지문과 같은 의미키를 입력으로 받는다. 두 판정이 현재 유효한 경우에만 아래 행동을 도출해 기존 `recovery_requests` 또는 부분 교정 경로에 연결한다. 근거 판정이 없거나 오래됐으면 자유 서술 cause로 생성 요청을 우회하지 않는다. 필드/프롬프트만 나누고 기존 복구 분기를 그대로 남기는 구현은 완료가 아니다.

**근거 판단 입력:** 같은 CQ, 원문 독립 발견 목록, 원명제/명시 정의의 출처 주소, 원문, 참조 가용성. CQ가 연결을 원한다는 것은 사실 근거가 아니다. 업무상 원하는 연결과 후보에서 유래한 연결은 모두 ‘검토할 가설’로 구분하고, 제공 원문이 이를 지지하는지 판단한다. 현재 후보 정의·기존 supported·표현 유무·복구 요청의 결론은 주지 않는다.

**근거 판단 출력:** 의미키별 적용성, `source_status=supported/refuted/unknown`, 관계 종류·적용 범위, `premise_keys` 및 각 전제의 근거·판정, 구체적인 자료/용량/해석 공백. 해당 관계가 성립하려면 어떤 전제가 필요한지와 그 전제 목록의 충분성도 판단 이유에 남긴다. 단순 참조, 비교, 실제 동일성, 상속, 권한을 같은 연결로 취급하지 않는다.

**표현 판단 입력:** 고정된 source assessment, 현재 후보·유형·관계·계층과 원문 주소, 수정이 있으면 before/after와 정상 의미. 원문을 재확인할 수 있게 하되 근거 결론을 이유 문장으로 조용히 덮어쓰지 않는다.

**표현 판단 출력:** 의미키별 `represented/missing/incorrect/unknown`, 실제 `locations`, 잘못된 필드와 정상 보존 대상. locations의 현재 표현이 `asserted/qualified_unknown/negated/absent` 중 어느 상태인지 함께 남긴다. represented라는 레이블만으로 근거가 확인된 것으로 처리하지 않는다. 이 의미와 반대되는 새 원문/범위 문제를 발견하면 `source_challenge`를 해당 의미키에 연결하여 앞 판정을 갱신하게 한다. 그동안 관련 복구만 pending이며 정상인 독립 후보는 유지한다. 새 필수 의미도 같은 경로로 추가한다.

**서버가 도출할 행동:**

| 근거와 전제 | 현재 표현 | 행동 |
|---|---|---|
| 해당 범위에서 지지, 모든 필수 전제 현재 유효 | represented | 유지·충족 |
| 동일 조건 | missing | 소유 원문과 의미키를 지정해 기존 Concept/Relation 복구 |
| 동일 조건 | incorrect | Builder 끝점 또는 Revision 원명제/정의 교정 |
| unknown, 관계를 표현하지 않거나 올바르게 미확정 표시 | missing/unknown/qualified_unknown | 자료/판단 공백 기록. 미확정 표시는 유지, 확정 관계 생성 금지 |
| refuted, 긍정 관계를 표현하지 않음 | missing/unknown | 반증과 가설 불성립 기록. 자료 부족으로 바꾸지 않음 |
| unknown/refuted인데 현재 표현은 확정적 긍정 주장 | represented 또는 incorrect라도 asserted | 충족 처리 금지. 과장된 주장만 수정하고 확인된 의무·참조·역할 보존 |
| CQ가 부정/비포함 확인을 요구하며 그 결론이 원문으로 확인됨 | 정확한 부정 표현 또는 미표현 | 부정 결론을 별도 근거 있는 의미로 대조·필요시 표현. 임의로 관계 방향을 뒤집지 않음 |
| 범위가 다른 원문 또는 표현 | scope conflict | 맞는 범위의 자료/표현을 별도로 대조 |
| 근거/표현 판정이 stale·미완료 | 모든 상태 | 해당 판단 갱신. 정상 후보 전체를 무효화하지 않음 |

`cause`는 위 결과에서 서버가 산출한다. 같은 신규 계약에서 모델이 별도 cause를 선택해 서버 행동을 바꾸지 않는다. 근거 주소·필드 유효성은 기존 검사로 확인하고, 의미 판정은 실제 모델/독립 검수의 증거로 구분한다.

근거 판정과 표현의 주장 상태가 서로 모순되면 해당 위치를 다시 대조하고 related-only pending으로 둔다. unknown을 올바르게 표현한 문장을 억지로 삭제하지 않는다. 범위 한정으로 가설이 반박된 것과 모든 경우의 부정을 증명한 것을 구별한다. 기존 응답 소비자가 읽는 `judgment/cause/meanings`는 새 판정에서 도출한 호환 뷰로 유지하고, 원시 source/representation 결과는 별도 보존한다. 과거 기록의 판정을 덮어쓰지 않는다.

**저장/모듈:** 작업 1의 필드와 기존 analysis_units를 사용. `discovery_models`의 요구 모델/스키마, `discovery_scope.requirement_application/normalize_applicability`, `discovery_requirements.packet/normalize/assess`, `discovery_analysis.call/model_stage/reservation`을 수정한다. 기존 recipe의 출력·재개는 보존한다.

**호출 수:** 근거 판단은 기존 CQ 적용성 호출 자리를 사용한다. 기존에 발견 목록이 없어 그 호출을 생략했던 경우에는 근거 판정 1개가 새로 필요할 수 있다. 의미 단위 분할과 재판정으로 호출 수가 증가할 수 있으며 사전에 비용 감소를 주장하지 않는다. 반복된 단위는 source/candidate fingerprint가 같을 때만 재사용한다.

**제한된 재진입:** 표현 검수·교정 후 검수·문서 간 연결 확인에서 새 근거나 모순을 발견하면 해당 의미의 `source_challenge`로 근거를 재판정한다. 새 결과를 저장하고 의존하는 표현 판정과 아직 실행하지 않은 복구 요청을 갱신하며, 이미 수정된 후보도 정정된 근거에 맞춰 같은 의미를 다시 확인한다. 과거 판정을 덮어쓰거나 해당 근거와 무관한 정상 후보까지 무효화하지 않는다. 같은 의미키·원문/범위 지문에서는 이 재검토를 한 번만 허용하고, 다시 불일치하면 unresolved로 남긴다. 새 근거/범위도 전체 추가 라운드·호출/시간 예산 안에서만 처리하며 교정 한 번 제한을 우회하지 않는다.

**실패/한계:** 서버는 판정 조합과 명시 의존에 따른 행동을 처리할 뿐 의미의 진위를 보장하지 않는다. source_status 자체의 오판이나 전제 누락은 남을 수 있다. 같은 모델의 두 출력은 독립 정답 합의가 아니다. 일반 법률 추론기를 만들지 않으며 unknown은 그 전제가 필요한 연결에만 전파한다.

**선행/완료:** 작업 1 이후이며 작업 N은 필요하지 않다. 기존 생성 결과와 문맥 기록만으로 v11의 잘못된 복구를 막되 실제 제공된 누락은 복구로 연결해야 한다. 원문에서 확인되는 선정 의무·권한·참조 사실을 외부 상세 자료 부족과 함께 제거하면 실패다.

## 작업 3 판단에 따른 부분 교정·복구와 정상 의미 보존 확인

**문제/근거:** 정상 의미를 잃은 과거 교정과 정상 의미를 유지한 최신 7197 교정이 모두 존재한다. 새 판단 계약이 기존 성공한 교정 경로를 우회하면 회귀 위험이 있다.

**변경:** 복구 요청에 `meaning_keys`, source assessment 지문, current candidate 지문, 수정 필드, preserve 의미키, 의존 유형/관계 ID를 넣는다. 기존 `queue_recovery`, owner span, 중복 억제와 한정된 추가 라운드를 사용한다. 동등 의미의 문구 변경은 허용하지만 근거 없는 역할·효과 확장은 허용하지 않는다.

- 끝점 문제는 기존 Builder 교정에 연결한다. 원명제 변경으로 잘못된 유형을 정당화하지 않는다.
- 원명제 자체의 오류·정의 누락은 기존 Revision에 연결한다. 근거만 보완할 때는 evidence-only 계약을 유지한다.
- 수정 후 기존 focused Critic의 before/after·보존 비교와 변경된 표현 판정을 다시 실행한다. 원문·범위·전제가 같으면 근거 판정은 재사용한다.
- 근거의 의미가 정정되면 과거 preserve 목록도 이유/근거와 함께 갱신할 수 있다. 과거 supported라는 이유로 영구 보존하지 않는다.
- 정상 후보는 수정 대상이 아니라 필요한 비교 문맥으로만 읽는다. 취소·예산 종료는 기존 경계에서 처리한다.

**입출력·호출·저장:** 현재 근거/표현 판정과 before·수정 대상·보존 의미를 기존 Builder/Revision/복구에 전달 → 실제 after 생성 → 기존 focused Critic으로 오류 제거와 정상 의미 보존 확인 → 변경된 표현 판정 재실행 순서다. before/after·보존 결과·판정 지문은 기존 `revision_history/analysis_units`에 연결한다. 보류·삭제로 끝난 대상은 유용한 교정으로 계산하지 않으며, 이 결과를 작업 4의 원래 CQ 재확인 입력으로 넘긴다. 새 보존 검수기를 중복 추가하지 않는다.

**수정 모듈:** `discovery_analysis.queue_recovery/recovery_groups`, `discovery_synthesis.revise/binding_repairs/review_context`, `discovery_scope.preservation_basis/revision_record/preserve`, `discovery_requirements`, `discovery_review`.

**단순화:** 근거/표현 새 cause 분기와 과거 자유 서술 cause 분기를 신규 recipe에서 이중 적용하지 않는다. 현재 원명제 검수·끝점 검수·보존 검수의 역할을 유지하며 전체 후보 재검수 루프를 추가하지 않는다.

**한계/완료:** 7197의 과거 실제 잘못된 끝점을 재현한 사본에서 정상 행위·조건·시점·근거를 보존하며 실제로 수정하고 같은 의미를 재검수해야 한다. 과거 오류 재현임을 표시한다. 새 생성에서 오류가 없으면 교정 효과는 측정되지 않은 것으로 기록한다. 보류·후보 삭제만으로 완료하지 않는다. 선행은 작업 1·2다. 작업 N 없이 완료할 수 있으며 이후 이웃을 사용한 생성 결과에도 같은 교정 계약을 적용한다.

## 작업 4 문서 간 연결과 전체 요구 재확인

**문제:** 모든 원문·후보를 한 큰 입력에 넣는 방식은 비용이 크고, 부분 판정의 집계만으로는 문서 간 결합의 타당성을 확인할 수 없다.

**변경 후 흐름:**

1. CQ를 작업 1의 의미 단위와 필요한 문서 간 연결로 나눈다. 후보가 없는 원문도 기존 frontier/coverage를 통해 독립적으로 읽어 누락을 찾는다. 이웃으로 선택된 원문만을 전체 범위로 삼지 않는다.
2. 단위별 근거/표현 판정을 저장한다. 공통 전제는 중복 자유 서술 대신 같은 의미키로 연결한다.
3. 마지막 `requirements`의 join mode는 **문서 간 연결 대상, 직접 의존 전제, 적용 범위/시점, 현재 후보 위치, unresolved/미처리 목록, 해당 원문 구간**을 읽는다. 전체 원문을 다시 전부 직렬화하지 않는다.
4. join은 필요한 연결 종류와 전제의 충분성을 다시 판단한다. 부분 supported의 개수 합산으로 전체 충족을 만들지 않는다. 연결 명제도 독립 의미로 저장하고 근거 판정에 새로운 전제가 필요하면 해당 부분만 되돌린다.
5. join 입력이 한도를 넘으면 연결별로 나누고 연결들의 공유 전제·충돌을 확인하는 최소 결합 입력을 만든다. 결합을 확인할 수 없으면 `join_pending/capacity`를 남긴다. 전체 원문을 모르는 작은 마지막 호출에 전체 완전성을 추측시키지 않는다.
6. 완료 집계는 원문 범위 조사/분석 완료, 근거로 확인 가능한 의미의 표현, 현재 후보 검수, 연결 판정, 미해결 복구를 함께 본다. 자료가 없는 의미의 정확한 unknown은 진단 결과이며 생성 완료 건수에 합치지 않는다.

**입출력/저장:** 기존 requirement ID 아래 per-meaning 결과와 `join_assessments`, 의존 의미키·후보/원문 지문, 전체 범위/미방문/미처리 목록, 확인된 요구와 자료 공백을 저장한다. `finish`는 저장된 현재 판정만 집계하며 새 모델을 호출하지 않는다.

**모듈/재사용:** `discovery_requirements.packet/packets/assess/saved`, `discovery_analysis.finish/requirement_reservation`, `discovery_scope` 및 기존 A3 preview/선택 의존 검사. 기존 부분은 전체 CQ를 인증하지 못한다는 경계를 유지한다. 신규 경로에서는 기존 거대 전체 CQ 호출과 join 호출을 둘 다 실행하지 않는다.

**실행 연결의 필수 수정:** `pending_calls`는 assess가 사용할 grounding/representation/join의 실제 packet key를 동일 함수로 계산해 예약한다. `requirement_reservation/review_reservation/call`의 단계 수·시간 예약도 같은 목록을 사용한다. `model_stage/make_prompt/response_model/normalize/restore_receipts/output_tokens/context_tokens/model_identity`의 grounding 분기와 스키마를 함께 반영한다. `finish/saved/valid_ids/current_applicability_ids`는 새 receipt의 현재성을 읽기 전용으로 확인한다. join도 동일 입력 지문당 한 번 실행하고, 실제 교정이나 새 근거로 의존 지문이 달라진 경우에만 예산 안에서 다시 실행한다.

**한계:** 원문 분석 단계가 의미를 놓치면 전체 범위 조사를 했어도 완전성은 보장되지 않는다. 필요한 전제 목록도 모델이 누락할 수 있다. 의미/입력의 전체 커버리지와 실제 의미 정확성을 별도 보고한다.

**선행/완료:** 작업 1·2·3 이후. 같은 원래 두 문서 CQ에서 확인 가능한 업무 연결을 실제 표현하고, 확인 불가능한 법적 포함은 정확히 구분한다. 필요한 실제 유형·관계·계층과 전이 의존성이 A3 변경안에 포함되는지 확인한다. 계층이 필요하지 않은 과제에 계층을 억지 생성하지 않는다. 미리보기의 성공 표시만으로 포함을 주장하지 않는다. 사람 승인·활성화는 이번 후속 구현의 자동 완료 조건에 넣지 않는다.

## AutoSchemaKG 원형과 우리 적용 범위

논문 부록 B.2.2와 공개 `concept_generation.py`에서 확인한 이웃 문맥은 **추출 그래프의 개체에 연결된 predecessor/successor와 관계**다. 개체 이름과 이 문맥을 입력해 여러 추상 개념을 만든다. 논문은 제한된 무작위 표본을 설명하고, 확인한 코드 기본값은 앞/뒤 이웃 각각 최대 1개다. 사건·관계 개념화는 자체 문구를 사용하며 같은 이웃 문맥 처리를 하지 않는다.

| 구분 | 이번 설계 |
|---|---|
| 가져오는 원리 | 먼저 추출한 연결에서 대상의 주변 관계를 얻어 개념화에 제공한다. 완성 온톨로지가 필요하지 않다. |
| 우리 변형 | 원문 언급 위치를 구별하는 임시 연결, 원명제의 조건·범위 보존, 결정적 선택, 생략·자료 공백 기록, 개념화 이후 의미 검수. |
| 기존 기능 재사용 | Relation의 원명제, Concept의 정의 직접 발견/사례 귀납, Builder의 끝점·유형 연결, 독립 문맥 발견, 근거 위치와 지문, 제한 교정, 기존 SQLite 실행 기록. |
| 실제 새 변경의 구분 | 핵심 작업 1~4는 공통 의미 참조·근거/표현 분리·부분 교정/복구·보존·전체 요구 재확인이다. 별도 작업 N은 Relation→Concept 순서와 Concept/Builder용 연결 이웃 선택·선택 기록이다. |
| 도입하지 않는 것 | 무작위 1+1 복제, 모든 관계를 일반 `participates`로 바꾸기, 모든 원문에서 전체 KG를 먼저 완성하기, 별도 그래프 DB·NER 서비스·에이전트 서버·범용 추론 프레임워크. |

## 작업 N 개념화 단계의 연결 이웃 선택

이 작업은 선택지가 아닌 **별도 개념화 개선의 구현 대상**이다. Relation→Concept 재배치와 연결 이웃 선택이 개념화 품질·문맥 구성·처리 비용에 주는 효과를 검증하며, 현재 요구 검수의 의미 오판을 해결했다고 미리 주장하지 않는다. 핵심 작업 2~4는 이 작업 없이 구현·검증한다. 공통 계약인 작업 1은 이미 구현되어 있으며 핵심 작업 2~4 성공을 기다리지 않고 이번에 실제 구현·비교한다.

### 적용 위치와 호출 순서

- 작업 N을 적용하는 recipe에서만 정상 작업 단위를 **기존 원문 문맥 준비 → Relation → Concept → Builder → 기존 독립 문맥 발견·Critic** 순서로 실행한다. 핵심 변경만 적용한 recipe는 기존 생성 순서를 유지한다. 순서 변경은 `process_group`의 묶음 내부에 한정하며 모든 문서의 Relation을 먼저 실행하는 전역 2단계 실행기로 바꾸지 않는다.
- Relation은 기존처럼 원문에서 자연어 주체·술어·목적어와 조건 등을 추출한다. Concept의 후보를 받아 원문 관계를 맞추지 않는다.
- Concept은 직접 정의를 읽는 기존 경로를 유지한다. 사례·역할 언급에서 유형을 제안하거나 기존 유형을 재사용할 때 해당 언급의 연결 이웃을 받는다. entity/property_value 관측을 이유 없이 type으로 승격하지 않는다.
- Builder는 원명제의 끝점을 제공 유형에 대응하거나 출처 역할 유형을 설계할 때 같은 선택기를 사용한다. 이미 있는 `source_role`, `source_extract`, `synthesis` 작성 방식과 `relation_bindings` 출력을 유지한다. Builder에 일반 개념 재생성 역할을 추가하지 않는다.
- Concept→Relation의 기존 두 호출을 재배치하므로 이웃 선정을 위한 모델 호출이나 두 번째 Concept pass는 없다. Concept-only 복구는 기존 성공 Relation의 고정 풀을 사용하고, 없으면 이웃 없는 입력임을 표시한다. Relation-only 복구는 Concept 재실행을 강제하지 않는다.
- Relation 결과가 0개이거나 실패해도 직접 정의 원문과 필수 문맥이 충분하면 Concept의 직접 정의 경로는 이웃 unavailable 상태로 진행한다. 취소·공통 예산 종료·필수 원문 준비 실패는 기존 중단 경계를 따른다. 이웃 의존 대상만 그 의존 실패로 구분하며 정상 정의를 동반 차단하지 않는다.
- 현재 Relation에 들어가는 Concept 도구 결과 의존을 없애고, Relation의 허용된 read/search/lookup 결과를 Concept에 전달한다. 각 단계의 공통 dict/deps를 별도 복사한다.

### 최초 구축의 이웃 출처와 식별

승인 KG 없이 현재 run의 유효한 성공 Relation 결과로 Python dict/list 인접 목록을 만든다. 원문은 동결된 허용 범위 안에 있어야 한다. 그래프 구축 전용 모델·라이브러리는 추가하지 않는다.

1. 기본 노드는 `(relation_id, subject 또는 object)`다. 이 자체만으로 해당 명제와 상대 끝점이라는 1단계 연결을 얻는다.
2. 기존 source refs의 정확 구간 안에서 해당 끝점 표현의 실제 언급 위치가 **유일하게 확인되는 경우에만** 서버가 `(source_version, parse_run, block, mention_span)` 주소를 보조 anchor로 만든다. 정확한 일치가 없거나 반복 인용이라 위치가 모호하면 기본 노드를 유지한다. 임의 첫 일치나 새 NER 추론은 하지 않는다.
3. 서로 다른 추출 명제가 동일한 원문 언급 주소를 가리키면 그 언급에 붙은 여러 관계를 이웃으로 묶을 수 있다. **문자열이 같고 위치가 다른 언급은 합치지 않는다.** 같은 단어라도 문서·역할·시점이 다르면 별도 출처의 문맥이다.
4. 제공된 기준 온톨로지/검토된 개체 ID와의 명시적 연결이 이미 있다면 별도의 기준 연결로 참조한다. 새 실행이 임의의 운영 KG 전체를 탐색하거나 모호한 별칭을 확정하지 않는다. 최초 구축에서 이 입력은 없어도 된다.
5. Builder 산출물은 처음 이웃을 만드는 전제조건이 아니다. 다음 라운드에서 재사용할 경우 이전 라운드의 현재 유효 출력만 풀로 고정한다. 생성 중 새 유형이 자기 근거 이웃으로 역유입되지 않는다.

풀은 현재 묶음의 Relation과 그 시점까지 성공한 원문 Relation으로 고정한다. 아직 실행하지 않은 뒤쪽 문서의 관계는 `graph_pool_not_yet_extracted`로 남긴다. 이후 Builder 또는 기존 요구 복구에서 새로 필요해진 연결만 다루며, 앞 Concept을 모두 재실행하지 않는다. 초기 Concept에 전체 문서의 이웃을 제공했다는 보고는 금지한다.

초기 방식은 보수적이어서 여러 문서의 같은 실체를 놓칠 수 있다. `no_connected_neighbor`는 고정한 추출 풀에서 연결을 찾지 못했다는 뜻이며 실제 관계가 없다는 뜻이 아니다. 이 제한을 해결하려고 이름 기반 자동 개체 통합을 이번 범위에 추가하지 않는다.

### 서로 다른 문맥의 종류

| 종류 | 정의 | 사용 책임 |
|---|---|---|
| `relation_neighbor` | 해당 언급에 실제 연결된 추출 명제·관계 방향·상대 끝점 | 이번 새 개념화 이웃 선택 |
| `structural_context` | 같은 문서의 상위 문장·인접 절·표 머리·각주·목록 | 기존 segments/source_context로 문장 해석 보완 |
| `reference_context` | 명시적 조문·문서 참조를 해석하는 허용 원문 | 기존 읽기/검색·문맥 발견으로 필수 전제 확보 |
| `retrieved_comparison` | 검색한 유사 문구·정의·범위 대조 | 관련성 비교 자료. 그래프 이웃으로 표시하지 않음 |
| `reviewed_definition` | 이번 범위에서 사용할 수 있는 승인 정의 | 유형 재사용 대조. 현재 문맥에의 적용성은 별도 |

단지 같은 CQ를 공유하는 후보나 BM25 결과는 `relation_neighbor`가 아니다. 대상이 다르거나 범위가 충돌하는 자료는 명시적인 대조 자료로 남기며 자동 합치지 않는다.

### 필수 패킷과 결정적 선택

먼저 다음을 **필수 패킷**으로 구성한다.

- 개념화 대상의 직접 정의 또는 원명제 전체, 양끝점과 방향, 의무/허용·부정·조건·예외·시점.
- 그 의미를 결정하는 상위 조건, 목록 구성 항목, 표 단위/각주, 이미 발견된 필수 참조. 참조 사실과 참조 문서의 실제 내용을 구분한다.
- 실제 선택하려는 기준 유형 정의와 적용 범위. 정상 의미 보존을 판단하는 수정 호출이면 해당 before/after·보존 의미도 필수다.
- 현재 필수 의미와 충돌하는 것으로 이미 확인된 문맥. 유사도 점수가 낮다는 이유로 제외하지 않는다.

필수 여부는 원문 구조·명시 참조·기존 독립 문맥 발견/적용성 결과로 정한다. 인접 문서 전체를 필수로 지정하지 않는다. 아직 발견하지 못한 예외까지 보장하는 것은 아니므로 독립 문맥 발견은 이웃 선택 결과로 축소하지 않는다.

남는 예산에는 다음 우선순위로 부가 문맥을 넣는다.

1. 대상의 동일 언급 주소에 붙은 다른 명제와 상대 끝점. 직접 사용 역할·행위 대상·범위를 구분하는 연결 우선.
2. 해당 끝점/선택 유형에 명시적으로 연결된 현재 기준 정의와 비중복 대조.
3. 같은 CQ/범위의 유효 비교 후보. 같은 이름만 공유하는 경우 이 순위의 비교 자료일 뿐이다.
4. 기존 검색으로 얻은 추가 보강 문맥.

같은 순위에서는 대상별로 번갈아 선택하고, 같은 범위·시점에서 빠진 연결 방향/관계/한정 종류를 보충하는 항목 → 더 작은 완전 패킷 → 안정 source/record ID 순으로 정렬한다. 관련성 점수를 위한 새 모델 호출·임베딩 모델·학습 가중치는 없다.

**중복:** 동일 source/version/parse/block/span의 원문은 한 번 직렬화하고 참조한다. 명제는 같은 끝점 언급 주소·술어·방향·진술 종류(rule/instance 등)·부정·조건·예외·시점·범위일 때만 입력의 표시 중복을 제거한다. 저장 후보/관계 ID는 합치지 않고 모든 원 record ID와 출처를 유지한다. 다른 버전·다른 조건·부정/예외는 합치지 않는다. 의미가 유사하다는 이유로 자유 요약 병합하지 않는다.

### 예산과 자료 공백 처리

- 기존 `input_size/fits/make_prompt`를 재사용하되 현재는 prompt를 검사하고 `response_schema`는 별도로 전송한다는 경계를 보완한다. 이 공통 입력 크기 계산은 핵심 작업의 새 스키마에도 적용하며 작업 N의 완료를 기다리지 않는다. 지시문·기준 정의·필수 패킷이 포함된 prompt와 별도 schema의 직렬화 크기를 각각 기록하고, 둘을 포함하는 보수적 사전 상한을 같은 계산 함수에서 사용한다. 스키마 전송 크기나 UTF-8 byte가 실제 모델 token 수라는 뜻은 아니다. 실제 tokenizer 정보와 API 사용량이 있으면 함께 기록한다. 현재 함수가 이미 전체 요청을 정확히 토큰 계산한다고 보고하지 않는다.
- 입력 예산은 `필수 패킷 우선 + 남은 공간에 부가 이웃/비교 문맥`이다. 이웃 개수나 임의 비율 때문에 필수 내용을 버리지 않는다. 기존 Builder 묶음 제한(후보 12개/규범·정의 관계 2개)은 초기 작업 묶음 상한으로 유지하며 필수 의미의 개수 제한으로 사용하지 않는다.
- 선택할 이웃은 그 명제의 한정과 필요한 근거까지 포함한 전체 비용으로 평가한다. 공간이 부족하면 부가 이웃 전체를 제외하고 이유를 남긴다. 문장의 끝만 잘라 넣지 않는다.
- `analysis_context.retained()`의 공급 후보/deps 계산과 제거 목록을 함께 수정한다. 이웃 명제·상대 끝점·필수 근거 구간은 한 선택 단위로 추가/제외하고, 하나의 근거 구간을 여러 선택이 공유하면 참조가 남아 있는 동안 보존한다. 기존 `tool_originals` 제거 경로가 이웃 명제만 남기고 원문을 삭제하지 못하게 한다. 제거 즉시 selected/omitted/deps와 실제 입력 크기를 다시 계산한다.
- 필수 패킷이 넘으면 대상을 더 작은 의미 단위로 나누고 공통 필수 전제를 각 단위가 참조한다. 하나의 필수 의미 자체가 여전히 들어가지 않으면 기존 read/구조 분할로 원문을 읽고 결합 판정을 예약한다. 결합까지 못 하면 capacity/partial이며 source_absent가 아니다.
- 최종 사전 검사는 문맥 발견·도구 결과·필수 비교를 모두 추가한 뒤 다시 수행한다. 선택 이전의 예산 검사만으로 호출을 허용하지 않는다. 출력 예산은 기존 역할별 설정을 사용하며 이번 변경에서 자동 증액하지 않는다.

| 상태 | 확인 방법 | 다음 행동 |
|---|---|---|
| 제공 자료에 있고 아직 선택 안 됨 | 동결 목록/블록/생략 주소 확인 | 필요한 구간을 읽고 부가 문맥을 밀어내거나 작업 분할 |
| 필수로 선택했지만 용량·호출 실패 | 필수 주소와 실제 packet/run 결과 대조 | 재편성 또는 기존 재시도 정책. 예산 종료 시 capacity/failed 표시 |
| 제공 목록 밖의 명시 참조 | 목록·버전·참조 대상 대조 | 정확한 필요 자료 기록. 자동 다운로드·관계 생성 없음 |
| 목록 안에서 위치를 못 찾음 | 검색/파싱 상태 확인 | location_unresolved 또는 parse_pending. 자료 자체 부재로 단정하지 않음 |
| 읽었으나 원문으로 관계를 확정 못 함 | 실제 원문 근거 판정 | semantic_unknown. 입력 확대만으로 해결된다고 가정하지 않음 |

### 입력과 출력 및 저장

입력은 대상 언급/후보 ID, primary raw source, 고정 추출 풀 ID·지문, 명제·필수 문맥키, 허용 기준 정의, 현재 가용 예산이다. 출력은 `conceptualization_context` 안의 target별 필수 원문 참조·선택 이웃·비교 자료·생략/공백·선택 이유·실측 입력량이다.

각 이웃에는 relation ID, anchor 방식, 상대 끝점, 방향, 원명제 source projection, source/version/parse/span, scope/time, `unreviewed/supported/refuted/unknown` 등 실제 검수 상태와 그 현재성을 함께 기록한다. 검수 상태가 없으면 unreviewed이며 성공한 추출 호출이라는 이유로 supported로 바꾸지 않는다. refuted 결과는 긍정 근거로 쓰지 않고 오류 대조로만 구분한다.

부가 이웃 원문은 `context_only=true`, `analysis_target=false`로 표시한다. 원래 주분석 span과 겹치는 경우 원문의 주분석 역할은 유지하되 이웃 경로 때문에 분석 범위를 넓히지 않는다. 들어오는 관계를 읽더라도 저장된 사실 방향을 뒤집지 않는다.

미승인 후보의 문구를 사실 근거로 재인용하지 않는다. 새 정의의 근거는 원문 주소/허용 기준 정의이며, 사용한 이웃은 생성 경로의 출처로 별도 남긴다. 선택 기록과 정책 버전·풀 지문·누락 ID를 기존 `analysis_units` 입력 및 `candidate_groups`에 저장하고 검수/재개 지문에 포함한다. 선택하지 않은 후보가 다음 단계에 새로 생겼다고 이전 입력을 소급 변경하지 않는다.

Concept의 `source_extract/synthesis`가 기존 계약상 비우는 `source_relation_ids`에 이웃 ID를 억지로 넣지 않는다. `source_role`의 `role_basis`도 그대로 유지한다. 호출의 재사용 지문에는 실제 입력 이웃 전체가 포함되지만, 후보의 의미 검수 의존성은 실제 채택된 `source_refs/definition_evidence_refs`와 사용 관계에 연결한다. 읽기만 한 모든 이웃을 모든 후보의 의미 의존성으로 승격하지 않는다.

**수정 모듈:** `discovery_analysis.process_group/analysis_context/recipe`, `discovery_synthesis.assemble/context_for/synthesize`, `discovery_design.source_projection`, `discovery_segments`, `discovery_scope`, `discovery_candidates`의 참조/지문 연결. 선택 함수는 `discovery_synthesis`의 작은 공용 helper로 시작한다. 범용 graph API나 새 실행기는 만들지 않는다.

**단순화:** 기존 `prior_comparisons`/CQ 비교/Builder 도구 문맥이 동일 후보를 여러 경로로 넣는 부분은 한 선택 결과로 모은다. 필수 기준 유형 누락 후 재비교하는 기존 경로는 필요한 부분을 재사용한다. 새 선택기를 기존 선택기 위에 덧붙여 모두 실행하지 않는다.

**실패/한계:** 추출이 잘못되거나 이웃이 희소하면 개념화 단서도 부족하다. 안정 ID 정렬은 의미 품질을 보장하지 않는다. 이웃 문맥 선택은 최종 의미 검수를 대체하지 않는다. 후보가 없는 원문의 독립 누락 발견과 최종 CQ 범위는 유지한다.

**선행/완료:** 필요한 것은 작업 1의 추적 계약과 현재 유효한 Relation 출력이며, 핵심 판단이 작업 N에 의존하지는 않는다. 빈 ontology에서 순환 없이 Concept/Builder가 실제 연결 문맥을 받고, 동명이언급·필수 예외·중복·용량 초과·미선택/미제공·재개 고정을 집중 검사한다. 요구 판단 방식을 고정한 실제 모델 비교로 개념화 효과를 별도로 확인해야 품질 개선을 주장할 수 있다. 직접 정의 추출·필수 조건·예외·참조·미승인 상태를 훼손하면 실패다.

## 작업 5 작은 비교와 채택 판단

아래는 승인된 시험 설계다. 현재는 첫 고정 후보 비교에서 중단했으며 이후 실제 교정·전체 제품 경로·이웃 비교는 수행하지 않았다.

### 자료와 대조

- 개발 실패: 최신 v11의 근거 부족→허위 누락 요청. 19후보 사본은 이 판정 재현에 사용하며 신규 생성 품질로 계산하지 않는다.
- 실제 교정 재현: 7197의 과거 잘못된 주택 유형 끝점. 원래 선정 의미의 독립 원문 검토 결과를 보존 기준으로 사용한다.
- 정상 대조: 이미 충분한 출처 역할, 제공된 권한/참조 사실과 미제공 실제 기준을 구분한 후보.
- 문맥 경계: 기존 목록·하위 기간·예외·역할 범위 사례. 새로운 예시 수치를 만들지 않고 기존 원문과 실패 기록을 사용한다.
- 구조 대조: 같은 표면형/다른 출처 위치, 반복 인용, 실제 동일 언급에 연결된 여러 명제, 입력 내부 미선택/외부 미제공. 구성한 대역이면 구성 시험으로 표시하고 실제 자연 오류와 분리한다.

### 먼저 핵심 변경의 실패 해결 확인

작업 1~4를 기존 생성 순서·문맥 구성으로 구현하면서 해당 경로만 집중 확인한다. 작업 N의 구현이나 네 조건 비교를 착수 전 절차로 요구하지 않는다.

1. **판단과 복구 연결:** v11의 19후보 고정 사본과 정상 대조에서 기존/신규 판단을 비교한다. 근거 부족·해석 미확정·반증을 허위 생성 요청으로 바꾸지 않되, 제공 원문으로 확인되는 실제 누락은 복구로 연결해야 한다. 이 사본은 판단 재현이며 신규 생성 품질 시험이 아니다.
2. **실제 수정과 보존:** 기존 누락·7197 오류 재현에서 실제 복구/부분 교정 → 정상 의미 보존 → 같은 의미 재검수까지 확인한다. 보류 증가·후보 삭제·복구 전면 차단은 성공이 아니다.
3. **같은 업무 요구와 후속 결과:** 이웃 선택 없이 원문/CQ에서 시작하는 핵심 변경의 제품 경로 한 건에서 문서 간 연결 전제와 원래 요구를 다시 확인하고 필요한 A3 내용까지 확인한다. 원래 잘못된 후보를 주입한 교정 재현과 원문부터의 실행은 구분하며, 새 실행에 자연 오류가 없으면 그 실행의 교정 효과는 미측정으로 둔다.

### 별도 이웃 효과와 필요한 결합 비교

핵심 변경의 성공 여부와 독립적으로 작업 N을 구현·검증한다. 요구 판단 B는 새 방식으로 고정하고, 같은 작은 추출 묶음에서 기존 문맥 N0와 연결 이웃 N1로 Concept/Builder를 실행해 개념화·필수 의미·비용을 비교한다. **동일한 고정 Relation/원문 관측 출력·독립 문맥 발견 목록·직접 정의 원문·공통 참조 계약**을 사용하므로 이 비교는 선택 효과를 대상으로 하며 생성 순서 변경의 효과와 구분한다.

기존 네 조건은 효과의 상호작용을 확인할 필요가 있을 때만 다음처럼 사용한다. 모든 조건 실행은 핵심 수정의 착수·완료 조건이 아니다. 이를 운영 설정의 범용 조합 관리 기능으로 만들지 않는다.

| 군 | 개념화 문맥 / 요구 판단 | 확인하는 질문과 실행 필요성 |
|---|---|---|
| 00 | 기존 문맥 / 기존 판단 | 01과 비교해 같은 후보에서 판단 변경 효과 확인. 동일 입력의 기존 결과가 있으면 재사용 |
| 01 | 기존 문맥 / 근거·표현 분리 | 이웃 없이 핵심 변경이 실패를 해결하는가. 이후 N 효과 비교의 기준 |
| 11 | 연결 이웃 / 근거·표현 분리 | 01과 비교해 판단 방식을 고정했을 때 이웃 선택의 추가 효과 확인 |
| 10 | 연결 이웃 / 기존 판단 | 이웃 효과가 판단 방식에 따라 달라지는지 분리가 필요할 때만 추가. 00→10과 01→11 비교 |

고정 추출에서 재개념화한 00은 `76cafaa`의 원래 제품 실행 자체가 아니다. v11의 19후보 판단 비교와도 다른 시험이며 결과를 섞지 않는다. N0/N1 산출물을 B0/B1에 재사용하고 입력·모델·지문이 같은 앞단 호출을 반복하지 않는다.

이웃의 결합 적용을 채택할 때만 원문/CQ부터 Relation→Concept 재배치·문맥 전달·교정·같은 요구·필요 A3까지 이어지는 경로를 추가 확인한다. 이 확인은 이웃을 포함한 제품 경로의 완료 조건이며 이미 검증한 핵심 변경의 선행조건이 아니다. 앞 흐름 이후 개발에 쓰지 않은 작은 자료 한 건에서 적용 범위를 확인하며, 실제 확보·선정 전에는 독립 평가 자료라고 확정하지 않는다.

**규모 제한:** 전체 A6/71회 진단을 반복하지 않는다. 핵심 판단은 19후보 사본과 필요한 기존 정상/오류 대조를 우선 사용하고, 이웃 효과는 기존 역할·끝점 사례의 최소 원문 묶음 한 개로 확인한다. 네 조건을 모두 실행하는 경우에도 같은 묶음과 유효한 저장 출력을 재사용한다. 조건별 의미 판단 재시도/다중 샘플링은 0회, 새로운 수정 변형을 통과까지 반복하지 않는다. 기존 제품의 제한 교정은 한 번만 허용한다. 독립된 기술 실패 재개는 기존 정책과 비용 기록을 따른다.

구현 후 모델 실행 전에 실제 패킷으로 호출 목록·입출력 상한·기존 timeout을 계산하고 총 호출/시간 상한을 고정한다. 분할 수를 모르는 현재 문서에서 임의 호출 수·소요시간을 실측치처럼 제시하지 않는다. 예산 초과로 필수 검증이 끝나지 않으면 partial이며 성능 비교의 성공으로 처리하지 않는다. 한 조건만 context/output/timeout을 늘려 공정한 비교라고 하지 않는다.

## 구현 순서와 최종 완료 조건

| 순서 | 작업 | 다음으로 넘어갈 조건 |

실제 의존성은 **작업 1→작업 2→작업 3→작업 4**, 별도 **작업 1→작업 N**이다. 작업 3 안에서는 교정·복구 후 정상 의미 보존을 확인한다. 작업 N의 연결 풀은 기존 Relation 출력에 의존하지만 핵심 작업 2~4는 새 이웃 선택기나 Relation→Concept 재배치에 의존하지 않는다. 이전에는 작업 N을 핵심 검증 뒤에 배치했으나, 이번 사용자 지시에서는 N을 독립 구현·비교한다. 핵심 검증 성공은 기술적 선행조건이 아니다. 공유 모듈의 편집 충돌만 조정하고, 이웃 설계·네 조건 비교를 이유로 핵심 변경 착수를 미루지 않는다.

최종 제품 경로의 완료 기준은 **“정상 의미를 유지하며 실제로 수정했고, 같은 요구를 다시 확인했으며, 필요한 다음 단계까지 이어졌다”**이다. 미제공 자료의 정확한 unknown은 정직한 진단 결과이고, 해당 생성 요구는 미완료로 구분한다. 이미 정상인 후보를 수정 실적을 위해 바꾸지 않는다.

첫 비교에서 실패하면 해당 입력·판정·실패 위치를 보존한다. 작은 충분한 원문에서도 근거 판단 자체가 계속 틀리면 모델 능력 또는 허용할 추론 범위를 별도 판단한다. 이웃 수·프롬프트·검수 단계만 늘려 반복 실행하지 않는다.

## 전문가 검토 기록

이전 버전에서는 세 전문가 에이전트가 초안과 수정본을 읽기 전용으로 검토해 아래 판정을 회신했다. 이 기록은 당시 설계에 대한 검토이며, 이번 강조점·순서 수정에 대한 신규 검토나 구현/모델 품질 검증을 뜻하지 않는다.

| 검토 역할 | 확인한 범위 | 반영한 주요 수정 | 최종 판정 |
|---|---|---|---|
| AutoSchemaKG 방법론 | 개체 이웃의 원형, 우리 대상 범위 확장, 승인 KG 이전의 실행 | Relation 실패와 직접 정의 추출을 분리. 논문 이웃·문서 문맥·우리의 보존/판정 확장을 구분 | 설계 검토 통과 |
| 구현 아키텍처 | 현재 모듈·호출 순서·예산·저장·재개 연결 | 불변 의미키, 원문과 이웃의 원자적 선택, 입력 스키마 비용 경계, 실제 예약/현재성 소비 함수, 제한된 재진입을 명시 | 설계 검토 통과 |

초안의 작업 단위 전체 선행 문맥 발견 호출은 제거했다. 현재의 대상·역할·CQ별 발견과 같은 결과라고 볼 수 없고, 별도 호출·키 변경을 추가하기 때문이다. 기존 발견 대상·시점·현재성 키를 유지하면서 확보된 문맥을 생성과 교정에 공유하도록 범위를 줄였다.

공통으로 남은 한계는 원문 판정 자체의 모델 오판, 필요한 전제의 누락, 희소하거나 잘못 추출된 이웃이다. 필드·주소·검수 단계의 증가만으로 이 한계가 해소된다고 주장하지 않는다. 작업 5에서 핵심 변경의 실패 해결을 먼저 확인하고, 이웃 효과와 필요한 결합 효과는 별도로 판단한다.

## 이번 산출물과 다음 작업

현재 산출물은 공통 의미·판정 분리의 부분 구현, 집중 검사, 고정 후보 실제 비교의 실패 기록과 중단 보고다. 기존 자료·과거 snapshot·동결 실행은 보존했다. PR #609는 초안으로 유지하며 전체 구현 완료나 운영 채택을 선언하지 않는다.

이번 재개는 후속 계획에 정의한 표현 판정 단순화·필수 한정 재판정과 작업 N의 실제 구현·비교다. 실제 교정·정상 보존·같은 요구/A3의 완료 여부와 N의 제한 효과를 구분하며, 한 경로의 실패로 독립 N을 미루지 않는다. 사람 효용과 일반 성능은 미측정이다. 현재 사용자 결정이 필요한 사항 없음.
