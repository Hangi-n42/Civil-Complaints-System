## 1. 제품 목표와 첫 적용 업무

- **목표: 분산된 데이터와 규정을 실제 업무 대상에 연결하고, 사람이 현재 상황·적용 기준·영향 관계를 확인해 필요한 조치를 결정하는 공통 지식 기반 구축.**
- 문서마다 정보를 다시 모으고 관계를 해석하는 작업을 줄이기 위해, 검토된 개념·대상·사실·근거·결정을 여러 기능에서 재사용.
- 첫 완결 업무: **공고·규정이 바뀌었을 때 무엇이 바뀌었고 어떤 지식을 다시 검토해야 하며, 검토 결과가 사용 지식에 반영됐는지 확인.**
- P0: 자료 등록 → 온톨로지·사실 후보 → 사람 검토 → 지식 버전 활성화 → Local/Global 검색 → 변경 영향 검토·갱신.
- P1: 공통 지식 계층 완성 후 **문서 민원 답변 검토 1건과 버스 정류장 변경 영향 검토 1건, 총 2개 사례** 구현. 전자는 근거에 맞는 답변, 후자는 조치에 따른 영향 비교를 핵심으로 시연.
- 후속 확장: 담당자별 작업 배정·처리 상태와 외부 업무 시스템 실행 연동. 현재 P0의 검토 결정·상태 이력을 확장 기반으로 사용하며, 별도 업무 엔진을 이번 범위에 추가하지 않음.

## 2. 문제 정의와 제품 가치

### 2.1 상위 문제 — 데이터에서 업무 판단·조치로 이어지는 연결의 부재

- **조직의 데이터·규정·업무 상태가 서로 다른 문서와 시스템에 분산되어 있어, 사람과 AI가 하나의 업무 대상을 중심으로 현재 상황·적용 규칙·영향 관계를 함께 파악하고 필요한 조치와 결과를 연결하기 어려움.**
- 대상 확인의 반복: 자료마다 다른 명칭·식별 방식 때문에 동일한 대상인지 다시 대조.
- 적용 판단의 반복: 값이나 문장을 찾은 뒤에도 대상·조건·예외·시점을 확인해야 실제 업무에 사용 가능.
- 변경 반영의 단절: 새 문서의 변경점과 기존 안내·사실·답변 근거의 의존 관계를 별도로 추적.
- 기능별 재작업: 검색·민원·보고 기능이 각자 대상·규칙·근거를 해석하면 동일한 연결 작업이 반복.
- 제품이 검증할 핵심 가치: **공통 업무 모델의 재사용을 통해 판단·갱신에 필요한 사람의 총작업시간을 줄이고, 잘못된 적용과 영향 누락을 줄이는 것.**

### 2.2 첫 현장 문제 — 변경된 자료를 사용 가능한 지식으로 반영

| 업무 장면 | 필요한 판단 | 제품의 해결 방식 |
|---|---|---|
| 같은 단지의 HTML·PDF·CSV 수량 비교 | 같은 집계 대상과 시점의 값인지 확인 | 값마다 출처·단위·집계 범위·시점을 보존하고 비교 |
| 원공고 이후 정정공고 등록 | 어떤 사실이 대체되고 어떤 지식이 영향을 받는지 확인 | 버전 차이·정정 연결·직접 의존 관계와 영향 후보 표시 |
| 자격·절차·서류·기관을 함께 확인 | 특정 조건에서 필요한 서류와 담당 기관 연결 | 검토된 개체·관계·원문을 함께 조회 |
| 검토 완료 후 검색에 사용 | 수정·보류·철회 결정이 사용 지식에 반영됐는지 확인 | 결정 이력·활성 스냅샷·사용 상태를 검색과 연결 |

- 공개자료 근거: LHCS 발주의 원문 매칭·버전·데이터 수명주기 요구 [S1], 양산 정정공고 계열 [S3], 공고와 단지 CSV의 대상 연결 및 값 차이 [S3·S4].
- 비교 사례: 분산 지식의 탐색·버전·책임 관리 [S9], 객체·로직·행동을 연결하는 Palantir Ontology [S23].
- 현장 확인 대상: 특정 기관의 반복 빈도·처리 비용·기존 도구의 미충족 업무. 공개자료 사례와 기관의 실제 도입 성과를 구분.

### 2.3 온톨로지·지식그래프의 역할

| 계층 | 역할 | 업무 가치 |
|---|---|---|
| 온톨로지 | 업무 개념·속성·관계 방향·허용 대상의 공통 정의 | 서로 다른 자료와 기능이 같은 의미로 업무 대상을 해석 |
| 지식그래프 | 실제 대상·사실·조건·근거·버전·의존 관계 연결 | 대상 중심 조회, 관련 근거 탐색, 변경 영향 추적 |
| 판단·검토 로직 | 후보 제안, 근거 확인, 변경 비교, 사람의 결정 | 확인할 항목을 구체화하고 결정 사유 재사용 |
| 조치·결과 반영 | 검토 결과에 따른 수정·철회·활성화와 이력 | 결정이 실제 사용 지식과 검색 결과에 반영되는 흐름 완결 |

- 설계 원칙: **업무 대상 → 관련 사실·규칙 → 판단 → 조치 → 결과 기록**을 하나의 흐름으로 연결.
- Palantir에서 참고할 지점: 데이터 모델과 업무 로직·행동을 연결하는 구조 [S23]. 본 제품은 지식 검토·갱신 업무부터 완결하고 외부 시스템 실행은 후속 연동으로 구분.
- 저장 방식: SQLite와 안정 ID·관계·근거 메타데이터 우선. 전용 그래프 DB보다 실제 업무 연결과 재사용을 우선.
- 판단 책임: AI는 후보·근거·설명을 제공하고, 적용 기준의 확정과 운영 반영은 검토 결정에 따름.

### 2.4 민원 활용 — 공통 지식에 기반한 답변 준비·통합 검토

- **문제 정의: 기존 접수·부서 배분 체계 안에서, 개별 민원의 요구를 업무 대상·정책·적용 조건·담당 책임·근거와 연결하고 하나의 답변으로 검토하는 작업 지원.**
- 인터뷰 근거 [S24]: 콜센터 전화·문자·채팅은 Genesys로 통합 관리, 국민신문고 등 문서 민원은 별도 운영. 복합 민원은 주관부서와 협조부서가 처리하고 주관부서가 단일 회신.
- 제품 방향: 기존 채널·접수 시스템을 유지하고, 상담과 문서 회신에서 재사용할 업무 지식 기반 제공.
- 첫 적용: 문서 민원의 요구 구분 → 요구별 근거·조건 확인 → 담당자 검토 → 답변 초안·누락 확인. 상세 범위는 [민원 PRD §1](complaint_system_prd.md#1-문제-정의와-제품-목표) 참조.
- 사건 통합과 지식 공유 구분: 동일인의 여러 채널 사건 연결은 별도 권한·식별·개인정보 설계 대상. 공통 정책·안내 지식 공유부터 추진.
- 도입 판단: 분류 정확도뿐 아니라 근거 탐색·검토·수정 시간, 요구 누락·오적용, 자료 유지·연동 비용을 함께 측정.
- 인터뷰 활용 범위: 콜센터 관리자 진술을 출발 근거로 사용. 문서 민원 담당자의 실제 병목은 비식별 처리 사례로 확인. 타 지자체 예산·실패 원인에 관한 전언은 효과 근거에서 제외.

### 2.5 성공 기준

- 구축: 공통 개념·관계 초안의 작성부터 검토·수정까지 포함한 사람 시간 감소.
- 판단: 다른 대상·조건·시점의 근거 오적용과 핵심 요구 누락 감소.
- 갱신: 실제 영향 대상을 놓치지 않으면서 불필요한 재검토 감소.
- 활용: Local은 필요한 관계·근거를 정확히 선택하고, Global은 자료별 차이·예외를 보존해 종합.
- 비용: 초기 구축·유지·모델 대기·수정 부담을 포함해 수작업(B0) 및 기본 문서 처리·AI 지원(B1)과 비교.
- 채택 기준과 측정 구간: §12 적용. 기능 수나 그래프 크기보다 실제 업무 결과로 판단.

## 3. 대상 사용자와 업무 흐름

### 3.1 논리적 역할

| 역할 | 해야 할 일 | P0 책임 경계 |
|---|---|---|
| 지식 운영자 | 자료 등록, 변경 발견, 후보 묶음 준비, 작업 실패 재실행 | 프로젝트 평가자가 수행 가능 |
| 업무 검토자 | 개념 정의·동일성·조건·시점 확인, 수락·수정·보류·기각 | 검토자 역할과 결정 이력 기록 |
| 배포 책임자 | 검토 완료 묶음 활성화·되돌리기, 미해결 사항 확인 | P0 단일 운영자가 겸임 |
| 지식 사용자 | 개체·관계 검색, 전체 자료 종합 검색, 적용 범위·근거 확인 | P0 지식 화면 사용, P1에서 민원 담당자 화면 연결 |
| 시스템 운영자 | 로컬 실행·백업·실패 확인 | 기관 운영 권한·SLA는 후속 협의 |

### 3.2 제품 업무 흐름

1. 운영자가 자료와 출처·버전을 등록한다.
2. 로컬 AI가 개념·사실·연결·변경 후보를 작성한다.
3. 시스템이 ID 존재·근거 위치·스키마 적합성을 확인하고, AI 검토 역할이 누락·범위 혼동 후보를 표시.
4. 업무 검토자가 원문과 후보를 나란히 보고 변경 묶음을 검토.
5. 배포 책임자가 검토된 부분만 새 스냅샷으로 활성화한다.
6. 지식 사용자는 활성 스냅샷에서 특정 대상의 관련 지식을 찾거나 등록 자료 전체를 종합해 질문한다. 답변의 근거를 조회하고 미해결·현행성 불명 항목은 별도로 확인.

## 4. 범위와 우선순위

| 구분 | 포함 | 제외·후속 |
|---|---|---|
| P0 업무 범위 | 국민임대 공개 지식과 양산 공고 계열 | LH 전체 사업·모든 회사 도메인 동시 구축 |
| P0 자료 | 선택 등록한 CSV, HTML, 텍스트 PDF, HWPX | 대규모 크롤러, 구형 HWP·스캔 OCR 자동화 |
| P0 자동화 | 로컬 역할별 AI의 초안 생성과 반례 검토 | 자율적 사내 시스템 탐색·권한 확대·무제한 토론 |
| P0 핵심 | 원문 보존, ID 연결, 온톨로지 검수, 변경 영향 후보, 활성 버전 조회 | 실시간 법률 판단·입주 자격 확정·자동 업무 처리 |
| P0 저장·화면 | SQLite 기반 지식 원장, 검토 목록·원문 대조·근거 경로 | 전용 그래프 DB, 전체 그래프 시각화 플랫폼 |
| P0 검색·종합 | 개체·관계 검색(Local)과 등록 자료 전체 종합 검색(Global), 원문 인용 | LH 전체 자료 검색, 무제한 다단계 질의·자율 탐색, 전체 조건의 법률 규칙화 |
| P1 활용 | 문서 민원 답변 검토와 버스 정류장 변경안 비교 | 자동 회신·실제 노선 변경·민원 발생 확률 예측 |
| 기관 운영 | 도입 조건을 문서화 | 인증·권한·SSO·다중 테넌트를 P0에 일괄 구축 |

- 구형 PRD `General Complaint Knowledge Layer v1.0`와의 관계:

- 민원 사례 중심에서 회사 지식 중심으로 변경한다. 민원 `case_id`는 코어의 필수 키가 아니다.
- 온톨로지 후보 검토를 후순위에서 P0로 올린다. 로컬 AI가 초안을 자율 작성하되 운영 반영은 검토를 거친다.
- 기존 Search/QA·민원 구조화·Intelligence 보존, SQLite 우선, 근거·ID 검증 원칙은 유지.
- 완전 자율 운영, LLM에 의한 무검토 개념 통합·삭제는 계속 제외.
- 재사용 가능한 라이브러리·코드·프롬프트는 직접 호출 또는 최소 이식한다. OntoGPT의 작성 자산과 LinkML 스키마 처리 등을 실제 구현에 사용하며, 전체 엔진이 필요한지와 기능 단위 재사용을 구분한다 [S11, S13]. 구체적인 채택 결정은 [구현 계획 §2~7](../05_plans/company_knowledge/implementation.md)를 적용.
- GRAG 논문 전체 재현은 범위 밖이다. 그래프 관계를 검색·텍스트 근거로 활용하는 것과 논문 모델 재현을 구분한다 [S12].

### 4.1 두 활용 사례의 목적과 공통 기반

- 개발 순서: **P0 지식 구축·검색·변경 관리 완성 → P1 문서 민원 사례 → P1 버스 정류장 사례**. 사례에 필요한 자료 확보는 P0 개발과 병행.
- 공통 기반: Source/Evidence, 검토된 온톨로지·개체·사실, Snapshot, 사용 상태, 관계 조회, Decision 이력 재사용.
- 도메인 분리: LH 업무 지식과 교통 지식을 각 스키마·자료 범위에서 관리. 공통 메타모델을 재사용하며 서로 다른 기관의 업무를 하나로 합치지 않음.
- 현재 상태: 아래는 확정한 시연 요구사항. 실제 민원 원문, 버스 대상 지역·정류장·변경안은 자료 조사 후 선정. 실제 사례와 재구성한 시연 입력을 명확히 구분.

| 사례 | 사용자의 질문 | 핵심 시연 장면 | 보여줄 가치 |
|---|---|---|---|
| A. 문서 민원 답변 검토 | 이 민원의 각 요구에 어떤 근거로 답해야 하는가? | 요구를 선택하면 적용 조건·근거·답변 문장이 함께 표시 | 요구 누락과 잘못된 적용을 줄이는 지식 재사용 |
| B. 버스 정류장 변경 영향 검토 | 이 조치를 하면 어떤 대상의 편의가 좋아지거나 나빠지는가? | 현행과 변경안을 바꾸면 영향 대상·변화량·관계 경로가 함께 표시 | 실행 전 편익·불편과 추가 확인 사항을 비교하는 판단 지원 |

### 4.2 사례 A — 문서 민원의 요구별 근거와 통합 답변

- 선정 범위: 현재 보유한 국민임대 자료로 답할 수 있는 복합 문의 1건. 제출서류·발급기관과 청약통장 재사용 조건처럼 서로 다른 근거가 필요한 요구를 함께 포함.
- 자료 선택: 기존 공고·안내·Q&A와 수락 지식 재사용. 비식별 실제 민원이 없으면 공개자료 기반의 재구성 문의임을 표시.
- 핵심: **유사 답변 복사보다 요구별 적용 조건과 원문을 확인하고, 답한 부분과 추가 확인할 부분을 구분하는 과정**.

1. 민원 입력과 개별 요구 목록 표시, 담당자가 분해 결과 수정.
2. 요구별 업무 대상·정책·조건·서류·기관을 조회하고 선택 근거와 원문 표시.
3. 요구별 답변 상태를 `근거 확보 / 추가 확인 / 초안 작성 / 검토 완료`로 구분. 처리 완료·회신 완료 상태와 분리.
4. 선택한 근거로 통합 답변 초안 작성. 답변 문장에서 해당 요구와 원문으로 이동.
5. 담당자가 수정·검토 결과를 저장하고, 사용한 스냅샷과 근거 ID 보존.

- 핵심 화면: 민원과 요구 목록, 요구별 근거·조건, 통합 답변의 세 영역. 선택 요구의 관계 경로만 표시.
- 필수 입력: 비식별 민원 또는 명시된 재구성 문의, 적용할 자료 버전, 검토된 사실과 원문.
- 업무 책임 정보: 근거가 있는 경우만 표시. 발급기관을 민원 처리부서로 치환하거나 제공되지 않은 개인 자격·이행 일정을 추정하지 않음.
- 완료 기준: 고정한 요구를 모두 다루고 각 사실 문장의 근거를 열 수 있으며, 조건 누락·근거 없는 부서·이행 약속 없이 담당자의 수정과 검토 결과 재조회 가능.
- 비교 지표: 원문을 직접 찾는 작업 대비 근거 탐색·수정 시간, 요구 누락, 잘못된 조건 적용. 생성 분량과 평가 점수만으로 성공 판정하지 않음.

### 4.3 사례 B — 버스 정류장 변경안의 편익과 불편 비교

- 선정 범위: 한 지역의 **정류장 이전 1건**, 현행 유지안과 이전안 1개 비교. 연결된 노선과 주변 시설의 범위를 자료 확보 후 고정.
- 핵심: **민원인이 요청한 개선과 주변 대상에 생기는 불편을 같은 근거에서 비교하고, 추가 검토할 쟁점을 제시**.
- 시연 입력: 정류장 이전 요청, 이전 후보 위치, 기준 시점. 실제 변경 기록이 있으면 재현하고, 없으면 검토용 가상 변경안으로 표시.

| 필요한 자료 | 용도 | 확보 기준 |
|---|---|---|
| 현행 정류장 ID·좌표와 이전 후보 위치 | 변경 대상과 전후 위치 고정 | 출처·좌표계·기준일 기록 |
| 정류장별 경유 노선·방향·정차 순서 | 연결된 운행과 대체 정류장 확인 | 양방향 및 동일 명칭의 다른 정류장 구분 |
| 주변 시설의 위치·접근 지점과 보행 경로 | 대표 출발지에서 이용 가능한 정류장까지 접근 거리 비교 | 실제 출입구·횡단 가능 경로 등 확인 범위 기록 |
| 시간표·환승 자료 | 시간대별 연결과 환승 조건 비교 | 확보한 경우에만 정량 지표 추가 |
| 변경 사유·의견·관련 과거 민원 | 불편 유형과 추가 확인 쟁점 설명 | 이용 가능한 공개 또는 비식별 자료 사용 |

1. 현행 스냅샷을 고정하고 이전 후보 위치를 별도 변경안으로 등록.
2. 변경 정류장과 연결된 노선·대체 정류장·시설을 탐색. 탐색 범위와 제외 대상을 표시.
3. 동일한 대표 출발지·목적 노선·계산 조건으로 현행과 변경안의 접근 거리 비교. 가능한 경우 대체 정류장 이용도 포함.
4. 대상별 `개선 / 악화 / 변화 없음 / 계산 불가`와 전후 값·차이·판단 근거 표시.
5. 근거가 있는 불편 유형과 유사 민원을 연결하고, 사전 안내·현장 확인·대안 검토 항목 제시.
6. 담당자가 현행 유지·변경안 선택·수정 검토·보류 중 결정하고 사유 저장. 변경안과 결정이 현행 지식을 자동 변경하지 않도록 분리.

- 핵심 화면: 현행/변경안 선택, 정류장과 주변 대상의 지도 또는 위치 보기, 대상별 전후 비교표, 선택 대상의 영향 경로·원문 패널.
- 영향 경로 예: 변경안 → 정류장 위치 → 시설 출입구에서 정류장까지의 접근 경로 → 해당 경로를 이용할 때의 거리 변화. 실제 데이터에 존재하는 노드와 계산 결과만 표시.
- 최소 정량 지표: **고정한 대표 출발지별 이용 가능한 정류장까지의 보행 접근 거리와 증감**. 보행 경로를 확보하지 못한 경우 직선거리는 참고값으로만 표시하고 정량 시연의 완료로 처리하지 않음.
- 환승 횟수·대기시간·운행시간은 시간표와 경로가 확보될 때 추가. 노선·정류장 연결만으로 시간 변화를 추정하지 않음.
- 그래프 역할: 영향 후보 탐색과 근거 경로 표시. 코드 역할: 거리·연결·전후 차이 계산. LLM 역할: 요청 구조화와 계산 결과 설명, 검토 쟁점 제안.
- 판단 경계: 연결 수·중심성을 주민 불편의 크기로 취급하지 않음. 주변 인구를 실제 이용자 수로 대체하지 않고 편익·불편을 임의 종합 점수로 상쇄하지 않음.
- 민원 위험 표시: **예상 불편 쟁점과 그 근거** 제공. 추가 민원 발생 확률·건수나 인과 효과는 이 사례의 산출물에서 제외.
- 완료 기준: 현행과 이전안의 결과 재현, 영향 대상별 증감과 경로·출처 조회, 개선·악화 대상의 구분, 결정 이력 재조회, 현행 스냅샷 보존.
- 비교 지표: 사람이 같은 자료로 작성한 비교표 대비 영향 대상 누락·불필요 후보, 거리 계산 일치, 판단 준비 시간. 실제 시행 효과는 시뮬레이션 결과와 분리.

### 4.4 사례별 추가 범위와 완료 원칙

- 사례 A: 기존 민원 화면·생성·평가와 지식 패널 연결, 요구별 근거 대응 추가.
- 사례 B: 교통 도메인 개념·관계, 변경안, 전후 계산, 국소 영향 화면 추가. 기존 K8의 문서 변경 추적과 구분되는 P1 요구사항으로 관리.
- 변경안 최소 기록: 기준 snapshot_id, 변경 대상 ID, 변경 전후 값, 자료·계산 조건, 대상별 결과·근거, 검토 결정. 새 범용 시뮬레이션 엔진·그래프 DB·작업 배정 플랫폼은 추가하지 않음.
- 계산 결과는 해당 변경안과 입력 버전에 종속. 활성 지식이나 실제 운행 상태로 자동 승격하지 않음.
- 고정 12과제는 P0 평가로 유지. 두 사례는 별도의 활용 시연이며 기존 평가 정답·과제 수를 사후 변경하지 않음.
- 필요한 확인: 각 사례 한 건을 처음부터 끝까지 실행하고, 실패한 단계만 수정·재확인. 전체 민원 재평가나 도시 전체 교통 분석을 선행 조건으로 두지 않음.

### 5.2 P0 입력 제한과 권리

- 최초 실험 예산은 **문서 버전 최대 20개와 CSV 1개**로 제안한다. 이는 조사 결과나 산업 기준이 아닌 구현 범위 제한이다. 장문 규정은 관련 절만 추출하되 원본 위치를 유지. CSV 전체는 ID 등록부로 활용하되 최초 사실 검토 대상은 공고와 연결된 단지로 한정.
- 등록부에 원 URL·발행기관·취득일·파일 해시·문서 식별자·문서 날짜·이용 조건 상태를 기록. 공개 열람 가능과 재배포 허용은 구분.
- CSV [S4]의 이용 조건과 LH 전체 첨부문서의 권리를 동일하게 취급하지 않음. 개별 원문의 처리 가능 범위를 확인한 뒤 사용하고, 불명확한 원문 전체를 Git/공개 배포물에 포함하지 않음.
- LH청약플러스 robots는 일부 첨부 다운로드 경로를 제한한다 [S10]. P0는 허용된 제공 경로와 선택 등록을 사용하며 차단 우회·전면 수집은 하지 않음.
- P0 자료 입력: 선정한 파일과 공개 문서 등록. OpenAPI 연동은 후속 범위.
- 입력은 허용된 자료 목록으로 제한. 사내 시스템은 소유자가 제공한 스키마·필드 사전·비식별 샘플만 후속 등록하며, 에이전트가 임의 DB·계정·로컬 폴더를 탐색하지 않음.

## 6. 온톨로지와 지식 모델

### 6.1 두 계층

- **온톨로지:** 개념의 정의, 포함·제외 기준, 속성 자료형, 관계 방향, 허용 주체·객체 유형, 별칭의 적용 범위를 관리. 업무 개념은 자료에서 후보를 만들고 검토.

- **지식그래프:** 특정 조직·단지·공고·규칙·제출서류와 그 관계를 원문 근거·조건·버전과 연결. 단순 `(주체, 관계, 객체)`만 저장하지 않고 각 사실 주장에 근거와 적용 맥락을 붙인다.

- 고정하는 최소 메타모델은 `개념`, `개체`, `사실 주장`, `출처/버전/원문 위치`, `검토 결정`이다. `조직`, `주택단지`, `공고`, `요건`, `제출서류`, `업무절차`는 **LH 자료용 초기 후보**이며 모든 회사에 강제하는 완성 온톨로지가 아니다.

### 6.2 초기 관계 후보와 금지하는 단순화

| 후보 관계 | 의미 | 혼동 방지 |
|---|---|---|
| 공고→대상 단지 | 공고가 명시한 적용 대상 | 같은 지역이라는 이유만으로 포함 금지 |
| 규칙→적용 대상·조건 | 원문이 명시한 요건과 적용 맥락 | AND/OR·예외를 읽지 못하면 요약 규칙을 확정하지 않음 |
| 절차→필요 서류 / 서류→발급기관 | 해당 단계·조건에서 요구되는 서류와 기관 | 신청자가 항상 모두 제출한다고 일반화 금지 |
| 조직→제도 담당 / 조직→접수 담당 | 서로 다른 책임 관계 | 중앙 정책 담당과 현장 접수를 한 담당자로 합치지 않음 |
| 문서 버전→정정 대상 | 공식 연결 또는 검토된 명시적 정정 | 게시일이 최신이라는 이유만으로 모든 기존 문서를 대체하지 않음 |
| 파생 지식→사용 근거 | 생성 당시 사용한 사실·원문 의존 관계 | 의미가 비슷하다는 이유만으로 영향이 확정됐다고 표시하지 않음 |

### 6.3 필수 논리 데이터

- 물리 테이블 분리는 구현 시 최소화한다. 아래 정보가 손실 없이 표현되는 것이 요구사항이다.

| 객체 | 필수 정보 |
|---|---|
| Source / SourceVersion | 내부 ID, 원 URL·발행기관, 외부 ID·네임스페이스, 파일 해시, 문서군/정정 연결, 발행일·수집일, 이용 범위. 파서 버전·옵션·추출 실행을 별도 참조하여 원문 변경과 재파싱 구분 |
| Evidence / ParsedBlock | source_version_id, parse_run_id, block_id, 문단/표/셀 위치, 원문 텍스트·발췌·문자 범위·정렬 상태, 정규화 전후 대응. PDF 물리 페이지와 인쇄 페이지 분리 |
| OntologyVersion / Concept | 안정 ID, 정의, 포함·제외 예시, 속성·허용 관계, 제안 근거·CQ 연결, 검토 상태, 버전. 원장의 LinkML 스키마 표현과 파생 JSON Schema 해시 |
| Entity / Alias | 내부 ID, 유형, 공식 ID·발행기관, 원문 표기, 검토된 별칭·적용 범위, 연결 방법·결정 근거·통합 이력. 개념 ID와 실제 개체 ID 구분 |
| Assertion | 주체·관계·객체 또는 값, 단위·집계 범위, 적용 조건·예외, 유효기간과 그 근거, Evidence 목록, 추출 방법, 검토 결정 |
| ChangeSet | 이전/후속 버전, 추가·수정·철회 후보, 영향 후보와 경로, 개별 결정, 준비 상태 |
| Snapshot | 불변의 온톨로지·사실 버전과 근거 참조, 활성화 시점·작업자·사유, 이전 snapshot_id |
| AvailabilityHistory | 주장/근거별 재검토·사용중단·재허용 상태, 사유·시점·결정자, 단조 증가 status_revision |
| Run / Decision | 입력 버전, 모델·프롬프트·스키마 버전, 호출 수·시간·실패, 검토자 표기·결정 시점·짧은 사유 |

- 날짜는 `발행일`, `시행/적용일`, `수집일`, `시스템 활성화일`을 구분. 유효일 근거가 없으면 null과 ‘미확인’으로 기록. 지식의 부재는 사실의 부정을 의미하지 않음. 모든 사실을 실행 가능한 법률 규칙으로 변환할 필요는 없다. 복잡한 조건은 원문 구조와 적용 범위를 보존하고 수동 검토 대상으로 유지.

## 7. 로컬 AI 역할과 자동화 경계

- 고정된 순차 작업으로 시작한다. 새로운 멀티에이전트 프레임워크·상주 토론 시스템은 만들지 않는다.

| 역할 | 입력 | 출력 | 할 수 없는 일 |
|---|---|---|---|
| 자료 분석 | 승인된 문서 절·CSV 스키마·샘플 | 용어·개체·관계 표현·근거 위치 후보 | 보지 못한 회사 시스템·업무 관행 추측 |
| 온톨로지 설계 | 분석 결과와 기존 개념 사전 | 추가/재사용/별칭/관계 정의 제안, 기존 정의와 차이 | 운영 온톨로지 직접 통합·삭제 |
| 반례 검토 | 후보와 관련 원문, 기존 정의 | 범위 혼동·누락·근거 불일치·오병합 의심 | 다수결 또는 모델 자신감을 정답으로 취급 |

- 최초 개념 후보 생성→검토 의견 반영은 **최대 1회 수정**으로 제한. 해결되지 않은 항목은 사람이 검토. 실행마다 처리 절·호출 수·소요 시간을 기록.
- 모델은 설치된 Ollama 설정을 재사용. 초안에는 현재 `STRUCTURING_MODEL`을 사용하고, 반례 검토에는 `KNOWLEDGE_REVIEW_MODEL`을 사용하되, 민원 평가 프롬프트는 사용하지 않음. 새 역할의 품질은 별도로 검증한다.
- K3 반례 검토는 `KNOWLEDGE_REVIEW_MODEL`의 Qwen을 사용하고 실제 요청의 `think=false`를 확인. 스키마별 출력 예산을 정하며 긴 문서는 절·표 단위로 나눈다. JSON 절단을 정상 성공으로 기록하지 않음.
- 같은 모델의 역할 분담은 독립적인 전문가 합의가 아니다. 모델 점수나 다중 에이전트 일치율로 정확도를 인증하지 않음.
- LLM은 표현·관계 후보를 제시. 공식 ID 존재 확인과 원문 발췌 일치는 코드에서 검증한다. 이름의 의미와 ID의 실제 대상 일치까지 자동 보장되는 것은 아니다.
- 초기 온톨로지가 없는 단계는 고정 메타모델로 원문 표현·개체·관계 후보를 수집한다. 업무 질문(CQ)과 근거에서 개념 초안을 유도한 뒤 승인된 스키마로 사실을 추출한다. 초기 개념 유도와 승인 스키마 기반 추출을 같은 기능으로 취급하지 않음.
- 기존 Pydantic·Ollama 호출 경계를 재사용하고, LinkML의 스키마 해석·JSON Schema 생성과 LangExtract의 위치 정렬은 라이브러리로 사용. OntoGPT의 작성 자산은 회사 도메인에 맞게 이식한다. 후보 YAML에서 Python 코드를 생성·import하거나 외부 온톨로지 서비스를 자동 호출하는 흐름은 넣지 않는다. 의존성 버전은 [구현 계획 §8](../05_plans/company_knowledge/implementation.md)에 따라 필요한 범위에서 조설정.

| FR-10 P1 민원 활용 | 담당자가 민원 요구별 회사 지식·조건·근거를 확인하고 답변을 검토한다 | 민원 요구와 선택한 지식 근거의 대응을 확인 가능. 기존 민원 API 계약·Q0~Q7·인용 검증을 유지하고, 회사 문서 근거와 기존 민원 인용을 구별해 원문을 열 수 있다. 확정 자격 판정이나 이행 확약을 자동 실행하지 않는다 |
| FR-11 P0 개체·관계 검색 | 특정 단지·공고·서류를 자연어 또는 ID로 검색하고 관련 지식을 질문한다 | 검토된 ID·별칭으로 대상을 찾고 최대 2단계 관계와 연결된 원문을 함께 사용. 짧은 답변·관계 경로·원문 인용을 반환. 동명 대상이 여러 개면 선택을 요청하고, 근거가 부족하면 확인 불가 또는 부족한 항목을 표시한다 |
| FR-12 P0 전체 자료 종합 검색 | 등록한 파일럿 자료의 공통 조건·차이·예외를 자연어로 질문한다 | 선택 범위 내 사용 가능한 활성 지식을 주제별로 묶어 종합한다. 공통 내용과 공고별 차이·조건·예외를 구분하고 주요 사실에 원문 인용을 붙인다. 포함·제외 자료와 요약/입력 제한에 따른 누락 가능성을 표시. 일부 검색 결과만 사용한 답변을 전체 자료 분석으로 표시하지 않는다 |
| FR-13 P1 조치 영향 검토 | 정류장 이전 전후의 영향 대상과 변화를 비교한다 | 현행/변경안의 입력 버전·계산 조건 고정. 대표 출발지별 보행 접근 거리와 증감, 영향 경로·출처·추가 확인 사항 표시. 검토 결정 저장과 재조회, 현행 스냅샷 보존. §4.3의 한 건 시연 기준 적용 |

### 8.1 두 검색의 최소 범위와 처리

- 두 모드는 같은 지식 조회 화면에서 사용자가 선택한다. P0에 자동 질의 분류기나 별도 대화 시스템을 만들지 않는다. Local/Global은 사용자 기능의 구분이며 Microsoft GraphRAG의 특정 알고리즘 재현을 뜻하지 않음.
- 공통 입력은 질문·활성 스냅샷·선택 자료 범위·기준일이다. 범위를 지정하지 않으면 §5.2 예산 내 등록 파일럿 전체를 대상으로 한다. CSV는 ID 조회에 사용하며 종합 대상 사실은 공고와 연결된 검토 대상 단지로 한정.
- Local은 대상 연결→최대 2단계 관계 및 관련 원문 검색→인용 답변 생성으로 시작한다. 임의 길이의 경로 탐색·반복 후속 질의는 제외.
- Global은 선택 범위의 사용 가능한 활성 주장 전체를 훑고 개념/주제별로 묶는다. 컨텍스트에 들어가면 직접 종합하고, 초과하면 묶음별 요약 후 한 번 종합한다. 중간 요약은 원문 근거 ID와 조건·예외를 유지. 관련 묶음만 선택하거나 입력을 줄인 경우 사용 범위와 제외·잘림을 표시. 무관한 주장까지 답변에 나열할 필요는 없다.
- Global 입력 묶음과 출력 예산은 실제 파일럿 자료 크기에 맞춰 설정. 다층 커뮤니티 생성·DRIFT·무제한 map-reduce·자동 재작성 루프는 P0 필수가 아니다. Microsoft GraphRAG를 포함한 구현 도구는 이 기능과 근거 연결을 충족하는지로 선택한다.
- 두 검색은 활성·사용 가능한 지식과 그에 연결된 원문을 사용. 미검토 문서는 탐색 대상 목록에서 구분하며 확정 답변 근거로 섞지 않는다. 답변은 스냅샷을 바꾸지 않는 조회 결과이고, 재사용을 위해 지식으로 저장하려면 기존 후보 검토 흐름을 거친다.
- 입력/참조 ID·사용 상태·인용 위치는 기존 검증 경계를 재사용해 확인. 매 질문마다 별도 LLM 평가·전문가 합의·사람의 답변 승인을 추가하지 않음. 상충하는 조건은 함께 제시하고 자동으로 우선순위를 확정하지 않음.

### 8.2 상태와 갱신의 의미

- 입력 처리: `registered → parsed → extracted` 또는 `failed`. 실패한 절과 완료한 절을 구분하고 실패한 단위만 재실행한다. 실행 중 취소 요청은 `cancel_requested`로 기록하고 현재 모델 호출/처리 단위가 끝나면 다음 단위를 시작하지 않고 `cancelled`로 마친다. 완료된 후보는 비활성 상태로 남는다.
- 후보 검토: `proposed → accepted / deferred / rejected`. 수정 시 기존 제안과 결정 이력을 기록.
- 수락은 활성화와 다르다. 검토 완료 묶음을 스냅샷으로 활성화해야 일반 지식 조회에 사용된다. 해당 사실이 참조하는 개념·관계 정의·개체 연결·근거도 모두 해당 스냅샷에서 검토 완료여야 한다. 보류·기각된 의존 항목이 있으면 그 사실을 활성화에서 제외하고 이유를 표시.
- 새 버전 등록만으로 과거 사실을 삭제하지 않음. 명시적인 정정·철회가 확인됐거나 기존 근거 변경이 발견된 사실은 `needs_review`로 표시하고 현행 확정 근거에서 제외. 스냅샷 자체는 불변이며, 제외·재허용은 별도 상태 이력으로 기록. 조회 응답에는 `snapshot_id`, `status_revision`, `status_checked_at`을 함께 반환하여 사용한 상태를 추적한다.
- 새 문서가 정정인지 불분명하면 자동 대체하지 않음. 관련 기존 지식에 현행성 확인 필요를 표시. 최신 확인일을 항상 반환하며 ‘기관의 현재 모든 지식’이라고 표현하지 않음.
- 검토자는 영향 후보별로 **영향 없음·수정·철회·보류**를 결정하고 근거를 기록. 영향 없음 확인은 재허용 이력으로 사용 가능 상태를 복원한다. 수정·철회는 다음 활성 스냅샷에 반영하고, 보류는 사용 제외 상태와 잔여 작업으로 유지. 사용 중단된 원문을 다시 허용하려면 이용 조건 확인도 필요하다.
- 영향 후보는 직접 출처 의존과 검토된 관계를 우선 사용. P0 관계 탐색은 최대 2단계로 제한하고 경로·잘린 여부를 표시. 범위 밖 의존관계를 모두 찾아냈다고 주장하지 않음.
- 원문이 철회·사용 중단된 경우 해당 근거와 직접 파생 결과를 검색·내보내기에서 제외. 이전 스냅샷으로 되돌려도 최신 사용 중단 상태는 해제되지 않는다. `as_of`는 업무상 적용일을 뜻하며 시스템의 과거 상태 재현과 구분. 과거 상태 재현은 저장한 스냅샷·상태 이력의 검토용 확인으로 한정. 감사용 보존과 실제 삭제의 범위는 자료 이용 조건에 맞추며 별도 상태로 기록.
- 모델 confidence는 검토 순서의 보조값일 뿐이다. 낮은 confidence만 보류하거나 높은 confidence만 자동 배포하는 정책은 사용하지 않음.

## 9. 화면·상호작용

- P0는 그래프 전체를 그리는 화면보다 다음 네 작업을 먼저 완성한다. 한국어 용어·오류 메시지·날짜를 기본으로 한다.

| 화면 | 반드시 보여야 할 정보·행동 |
|---|---|
| 자료 목록 | 자료군·버전·처리 결과·출처·최근 확인일·권리 상태, 등록과 실패 단위 재실행 |
| 온톨로지·사실 검토 | 왼쪽 원문/표, 오른쪽 제안·기존 값·정의·근거, 수락/수정/보류/기각, 필터·묶음 검토 |
| 변경 검토 | 이전/후속 원문, 직접 영향과 간접 후보, 연결 이유·누락 가능 범위, 활성화 전 포함/제외 항목 |
| 지식 조회 | Local/Global 선택, 질문·자료 범위·기준일 입력, 인용 답변, Local 관계 경로, Global 공통점·차이·예외와 사용 자료 범위, 원문 이동, 활성 버전·현행성 미확인 표시 |

- 빈 결과·처리 실패·연결 미확인을 구분. 운영 지식 화면은 mock 데이터를 실제 결과처럼 자동 대체하지 않음. 근거 위치가 열리지 않으면 오류를 알리고 확정 검토를 요구한다. 키보드로 주요 검토 동작과 원문 이동을 수행할 수 있어야 한다.

- P1 민원 화면은 기존 답변 작성 영역 옆에 별도 지식 패널을 제공. 지식 패널의 답변 보조에는 사용한 지식 스냅샷과 문서 근거가 표시된다. 코어에 민원 분류·감정·중복 민원 규칙을 넣지 않는다.

## 11. 비기능 요구와 환경

- **구현·검증 원칙:** P0는 단일 운영자의 제한된 자료를 다루는 파일럿이다. 기존 Pydantic·DB 제약·근거 확인·검토 상태 경계를 재사용. 원문/ID 연결, 조건·시점 구분, 미검토 지식 제외, 활성화·되돌리기 일관성은 유지하되 별도 안전 프레임워크·다중 승인 체계·모델 자동 선택기·복잡한 fallback·상시 LLM 평가를 만들지 않는다. 변경한 기능의 대표 사례와 명확한 오류를 대상으로 확인하고, 전체 테스트 반복·조합별 전수 검사·대규모 벤치마크는 요구하지 않음. 추가 검사는 실제 실패나 구현 변경으로 필요성이 확인된 경우에만 한다.

| ID | 요구 | 수용 기준·경계 |
|---|---|---|
| NFR-01 호환성 | Python 3.11.9, Mac/Windows 네이티브, 필요한 의존성 버전 조정 허용 | pathlib·UTF-8·상대 기본 경로 사용. 채택 라이브러리와 기존 기능이 함께 동작하도록 관련 버전을 맞춘다. 같은 소규모 입력으로 양 OS 등록→조회 smoke 확인 전 Windows 검증 완료라고 보고하지 않음 |
| NFR-02 로컬 처리 | LLM 입력·출력은 설정한 로컬 Ollama로 처리 | 외부 LLM 키·클라우드 추출 서비스 불필요. 자료 다운로드와 모델 추론 네트워크 경계를 구분 |
| NFR-03 무결성 | 활성 버전과 근거 참조 일관성 | 원문 없는 활성 주장 0건, 미검토 후보의 일반 조회 유출 0건을 고정 회귀 사례에서 확인 |
| NFR-04 운영 가능성 | 실패·재실행·백업·복구가 단순해야 함 | 작업 종료/중단 후 재실행 시 중복 없음. 정지 상태 백업→복원 1회로 활성 snapshot·근거 참조 동일 확인 |
| NFR-05 관측 | 시간·오류·검수 수정량을 남김 | run별 처리량·모델 호출·시간·실패 사유·수락/수정/보류 수. 원문 전체를 일반 로그에 반복 기록하지 않음 |
| NFR-06 응답성 | 입력 예산 안에서 사용자가 상태를 확인 | 등록/실행 요청은 run_id를 반환하고 상태 조회 가능. 취소는 다음 처리 단위 전에 반영. 속도 SLA는 최초 측정 후 확정 |
| NFR-07 사용 범위 | P0 단일 신뢰 운영자의 로컬 사용 | API·FE loopback 실행. 기관 배포 시 접근 통제·인증 별도 적용 |

- 최소 설정 제안은 `KNOWLEDGE_ENABLED=false`, `KNOWLEDGE_DB_PATH` 두 개다. 기존 `.env`를 로컬에서 분리하고 `.env.example`에는 비밀 없는 상대 경로 예시만 둔다. 기존 생성·평가 모델 설정을 재사용하며, 역할 품질 때문에 분리가 필요하다는 결과가 나온 경우에만 설정을 추가한다.

- 현재 FE fallback 포트는 8001이며 API 실행 포트와 다를 수 있다. 실행 안내에서 `NEXT_PUBLIC_API_BASE_URL`을 실제 API 포트와 맞춘다. 공통 코드에 Mac 사용자 경로·Homebrew 전용 명령·Quartz 등을 넣지 않는다. PDF/HWPX는 [구현 계획 §2](../05_plans/company_knowledge/implementation.md)에서 선택한 라이브러리를 도입하고 원문 위치 어댑터를 작성한다. 특정 파서가 이미 설치돼 있다고 가정하지 않음.

## 12. 효용 검증 설계와 출시 판단

### 12.1 비교 조건

- 효용 평가는 동일 산출물을 만드는 총작업시간과 오류로 비교. 개별 기능의 실행 성공과 업무 효과를 구분.

| 방식 | 구성 | 확인 목적 |
|---|---|---|
| B0 수작업 기준 | 동일 원문, 문서 비교, ID·변경 검토표 | 프로젝트 평가자가 직접 구축·갱신하는 비용 |
| B1 단순 시스템 기준 | 동일 파싱·공식 ID·메타데이터·문서 diff·기존 RAG, 같은 모델의 원문별 사실/변경 요약 초안, 수동 관계표 허용 | 기본 자동화와 문서 관리로 얻는 효과 |
| B2 제안 방식 | B1 + 개념 정의/관계 제안·검토·근거 관계 기반 변경 영향 후보·Local/Global 검색 | 제안 기능 묶음의 추가 이익 및 유지 비용 |

- B1을 일부러 약하게 만들지 않는다. 같은 원문/버전/과제/필터/생성 모델을 사용. RAG 비교는 같은 컨텍스트 예산으로 수행하고 근거량·호출 수·총시간을 함께 기록. 사람 작업시간, LLM 대기시간, 최초 구축 비용, 반복 갱신 비용을 분리하고 총합도 제시. B1/B2 결과는 기능 묶음의 효과이며 KG 단독 효과로 해석하지 않음. KG 단독 효과를 주장할 때만 후보·검토 결과를 고정하고 관계 탐색 사용 여부를 바꾸는 제한 비교를 추가한다.

### 12.2 평가 자료와 작업

- 고정 과제: [파일럿 기록](../70_research/company_knowledge/company_knowledge_pilot_freeze_2026-09-26.md)의 개발 6건·신규 6건. 신규 과제도 같은 자료에서 선정한 개발 평가이며, 비교 구간은 [측정 절차](../05_plans/company_knowledge/evaluation_protocol.md) 적용.

- 최초 예산은 **12개 작업 사례**로 제안한다. 아래 이미 조사한 6종은 개발·회귀용이며 독립 평가라고 부르지 않는다. 새 6건은 다른 공고/절에서 선정하여 정답과 판정 기준을 잠그는 원칙이며, 튜닝에 사용하지 않은 경우에만 별도 확인 결과로 보고한다. 충분한 새 자료를 확보하지 못하면 개발 확인으로만 보고한다.

- 12개 작업 중 Local 3건, Global 3건을 배정하고 구축·변경 작업과 같은 자료를 재사용. 별도 검색 벤치마크를 추가하지 않음. Local은 대상의 관련 정보, 조건별 서류, 대상 모호성 또는 근거 부족을 확인. Global은 공통 조건, 개별 공고의 차이·예외, 구버전/미검토/부분 처리에 따른 사용 범위 표시를 확인. 실제 입력과 기대 근거의 고정 상태는 아래 2026-09-26 기록을 적용.

| 개발·회귀 사례 | 기대 동작 |
|---|---|
| 양산 원공고→정정 공고 | 정정 연결과 날짜 변경 근거를 보존하고 수정 전 값을 현행 확정 근거로 재사용하지 않음 |
| 단지 코드와 명칭 차이 | 실제 6개 대상의 ID 연결. HTML 공통 스크립트의 무관한 코드 제외 |
| 세대수 차이·혼합 임대유형 | 정의·시점 확인 전 단일 값 확정 금지. 혼합 단지 전체에 한 유형 조건 적용 금지 |
| 예정 입주일과 최초 입주일 | 다른 속성으로 유지. 값 차이만으로 충돌 판정 금지 |
| 일반 안내와 개별 완화 공고 | 적용 범위·예외를 구분. 자동으로 일반 규칙을 전면 덮어쓰지 않음 |
| 현행성 미확인 과거 규정·근거 없는 추가 주장 | 현행 확정 근거에서 구분. 제공 자료에 없는 주장·ID를 근거 있다고 통과시키지 않음 |

- 근거 없는 주장을 넣는 경우 원래 원문을 바꾸지 않고 별도 음성 후보로 명시한다. 실제 사례와 인위적 후보를 섞어 자연 발생 빈도처럼 보고하지 않음. 정답은 원문 위치·ID·범위·시점을 보고 확인하며 LLM 점수를 정답으로 삼지 않는다. 평가자가 판단할 수 없는 항목은 보류하고 그 수를 공개한다.

- M0에서 **공통 자료 준비 이후 최초 구축 1회 + 선정한 12개 작업 전체**를 비교 묶음으로 고정. 등록·초안 검토·수정·활성화·최종 근거 확인까지 필수 산출물을 동일하게 정하고, 실제 사람 조작 시간과 모델 대기를 따로 측정. 시간은 사람이 준비 자료를 열고 작업을 시작할 때부터 완료 또는 보류 사유 기록까지 잰다. 공통 자료 수집·평가 정답 작성 비용은 방법 비교에서 제외하되 프로젝트 비용으로 별도 기록. 초기 구축과 반복 작업의 개별 비용도 함께 제시하며, 실제 갱신 빈도 없이 연간 절감이나 투자 회수기간을 계산하지 않음.

- B0/B1/B2를 한 사람이 같은 순서로 반복하면 학습 효과가 생긴다. 가능한 경우 방법별 순서를 교차하고 동등 난이도 과제를 배정. 사람이 한 명이면 순서·사전 노출과 한계를 기록하고 산업계 ROI를 주장하지 않음.

### 12.3 지표·판정

| 지표 | 계산·판정 |
|---|---|
| 원문 근거 정확성 | 검토된 주장 중 해당 위치의 원문이 실제로 주장·대상을 뒷받침하는 비율, 오류 건수 병기 |
| 연결 정확성 | 정답을 정할 수 있는 연결 후보의 정답/오답/누락 수. 이름만 맞는 ID는 오답 |
| 변경 영향 | 정답 재검토 대상 중 놓친 수, 제시 후보 중 불필요한 수. 후보가 0이면 정확도 100%로 처리하지 않음 |
| 조건·시점 오류 | 범위 다른 규칙 적용·구버전 현행 사용·근거 없는 법령 등 중대한 오류를 사례별 보고 |
| 검토 부담 | 최초 구축 및 변경 1건당 사람 작업시간, 수정/보류 후보 수, 대기시간, 전체 경과시간 |
| 유지 비용 | 온톨로지 정의·별칭·관계 수정 시간, 재추출·재색인 횟수와 시간 |
| 활용 가능성 | 정답이 있는 과제의 완료 수와 미해결 수, 근거까지 추적 가능한지 |
| Local/Global 검색 품질 | Local의 대상·관계·필요 근거 누락, Global의 공통점/차이·예외 누락 및 잘못된 일반화, 주요 사실의 인용 대응을 원문으로 확인. 호출 수·총시간·부분 처리 여부도 함께 기록 |

- **P0 기술 통과:** FR-01~09·FR-11~12·관련 NFR의 고정 사례를 만족하고, 확인 가능한 중대한 오병합·범위 오적용·구버전 확정 사용·없는 근거 통과가 0건이어야 한다. 두 검색은 각 3개 작업에서 필요한 정보 또는 근거 부족 사유와 원문 인용·사용 범위를 확인. 실패하면 해당 처리만 수정하고 관련 사례를 다시 확인. 이는 해당 소표본의 출시 조건이지 일반 정확도 보증이 아니다.

- **B2 확장 조건:** B1 대비 중대한 오류·영향 누락이 늘지 않고, 동일 필수 산출물 완료 조건에서 위 고정 묶음의 **총 사람 작업시간이 10% 이상 감소** 필수. 10%는 미세한 시간차만으로 확장하지 않기 위한 초기 제품 의사결정 기준이며 산업 표준·관측 성과·통계적 유의성 기준이 아니다. M0에서 측정 구간과 기준을 확정하고 결과를 본 뒤 낮추지 않는다. 고정 과제를 끝내지 않은 방식은 빠르다는 이유로 우수하다고 보지 않는다. 표본이 작거나 순서 효과 등 비교가 불공정하면 ‘추가 효용 미확인’으로 보류한다. 개선이 없으면 B1을 유지하고 관계 자동화 확장을 중단한다.

- 이 확장 판단은 P0 두 검색의 제공 여부와 구분. 추가 관계 자동화의 효용이 없으면 B1의 수동 관계표·기본 RAG와 자료별 요약으로 Local/Global을 제공 가능. Global 비교에서도 B1에 동일 예산의 원문별 요약·종합을 허용한다. 두 검색 각각의 결과를 따로 보고하고 초기 도입을 위해 여러 프레임워크·모델의 전체 조합을 벤치마크할 필요는 없다.

- **P1 활용 사례 진행 조건:** B2 채택 여부와 분리한다. 채택한 방식(B1 또는 B2)의 근거·버전·상태·조회 품질이 기술 통과 조건을 만족하고, 두 사례의 입력 자료와 필요한 활용 과제가 정의되어야 한다. B1을 선택한 경우 관계 기반 구축 효용이 검증됐다고 홍보하지 않음. 사례 A는 민원 패널의 호출·인용·기존 API 보존, 사례 B는 입력 자료·보행 경로와 동일 조건의 전후 계산 가능 여부를 확인.

- 실제 기관 도입의 절감률·처리량·SLA는 담당자 인터뷰와 실작업 측정 후 설정. 근거 없는 목표 수치를 산업 표준으로 제시하지 않음. 개발 중 확인을 위해 전체 기존 테스트를 반복하거나 대규모 벤치마크를 구축할 필요는 없다.

| 내부 시스템 연계·권한 | 공개 자료로 회사 내부 지식 완성 불가. P0는 제공된 자료에 한정 | 시스템 소유자, M4 이전 |
| 보안·운영 준비 | 현재 인증 부재, 기존 FE mock fallback. P0 결과와 기관 운영을 분리 | 운영 담당, M4 이전 |

- 현업에 확인할 최소 질문은 다음 세 개다.

1. 최근 변경 한 건을 발견해 FAQ·검색 지식에 반영할 때 누가 무엇을 했고, 작업시간과 승인 대기시간은 각각 얼마였는가?
2. 원문·FAQ·시스템 값이 다르면 누가 결정하며, 보류·반려·재작업은 어디에 남기는가?
3. 기존 KMS/RAG의 변경 감지·정정 연결·버전·출처 기능으로 해결되지 않은 실제 사례를 재현할 수 있는가?
