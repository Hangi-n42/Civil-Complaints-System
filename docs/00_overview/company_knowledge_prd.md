## 1. 제품 요약과 결정

조직의 문서·공고·구조화 데이터에서 업무 개념과 사실을 추출하고, 원문 근거·대상·조건·시점을 보존한 지식으로 검토·관리하는 로컬 워크벤치를 만든다. 새 문서나 정정이 들어오면 기존 지식과 연결하여 **무엇이 바뀌었고 어떤 지식을 다시 검토해야 하는지** 제시한다.

첫 제품 결과물은 **검토 가능한 온톨로지 초안, 근거가 연결된 지식, 변경 검토 목록, 활성 지식 버전과 이를 사용하는 개체·관계 검색 및 전체 자료 종합 검색**이다. 구축·관리는 검색의 신뢰 기반이며, 탐색·종합은 사용자가 얻는 활용 가치다. 민원 답변 보조는 별도 활용 사례로 둔다.

- P0: 공개자료 기반 단일 운영자 로컬 파일럿. 구축→검수→활성화→두 검색→변경 반영까지 완결한다. 두 검색은 §5.2의 등록 자료 예산 안에서 제공한다.
- P1: P0 효용이 확인된 뒤 민원 워크벤치의 별도 지식 보조 기능을 연결한다.
- 기관 운영 도입: 실제 업무 담당자·자료 권한·접근 통제·운영 환경 확인 후 별도 승인한다. 현재 코드가 사내 운영 준비를 마쳤다고 보지 않는다.

## 2. 문제 정의와 근거

### 2.1 가장 먼저 해결할 As-Is

**규정·공고·업무데이터를 함께 사용하는 조직은 새 자료를 기존 업무 지식에 반영할 때, 같은 대상인지와 적용 조건·예외·유효시점·원문 근거를 대조하고 재검토 대상을 결정해야 한다. 이 대조를 지원하는 구조가 충분하지 않으면 검토 부담이나 잘못된 연결·갱신 누락이 발생할 수 있다.**

앞 문장의 업무 필요성은 공개자료로 뒷받침된다. 그러나 특정 LH 부서가 현재 이를 수작업으로만 처리한다거나, 하루 몇 시간을 낭비한다거나, 갱신 누락이 빈번하다는 사실은 확인되지 않았다. 문제의 빈도·비용·기존 시스템 대비 미충족 수요는 현장 검증 대상이다.

| 근거 | 확인 내용 | 해석의 한계 |
|---|---|---|
| LHCS 2025 LLM 플랫폼 발주 [S1] | 데이터 관리 부담 경감, 원문 매칭, 이력·검증·버전·배포 요구 | 실제 구축 완료·일상 운영 방식·개선 성과의 증거가 아님 |
| LHCS 공식 직무 [S2] | 데이터 표준화·품질관리와 시스템 개발 역할 존재 | 이번 제품의 실제 구매자·매 건 승인자는 미확인 |
| 양산 실제 정정공고 [S3] | 원공고와 정정 공고가 연결되고, 날짜 오기를 바로잡은 이력 확인 | 모든 공고에 정정 연결이나 충분한 이력이 있다는 보장은 없음 |
| 공식 단지 CSV와 공고 [S3, S4] | 코드로 연결 가능. 일부 값은 자료 간 차이가 존재 | 값 차이가 오류인지, 집계 범위·시점 차이인지는 별도 판단 필요 |
| 우아한형제들 BADA 사례 [S9] | 여러 저장소의 정보 탐색·버전·담당 정보 문제를 설명 | 타사 사례이며 LH의 손실 규모나 KG 필요성을 입증하지 않음 |

**기존 도구가 없다는 주장은 사용하지 않는다.** LHCS 발주는 벡터·키워드·하이브리드·온톨로지 검색과 데이터 수명주기 기능까지 요구한다 [S1]. 차별성 후보는 ‘온톨로지 사용’ 자체가 아니라, 특정 업무에서 변경 검토의 총부담과 오류를 더 줄이는지다.

### 2.2 To-Be와 검증할 가치

| 사용자 작업 | 제공할 결과 | 검증할 효용 |
|---|---|---|
| 자료의 표현을 공통 개념으로 정리 | 정의·예시·근거·허용 관계를 가진 온톨로지 초안 | 사람이 초안부터 작성할 때보다 수정까지 포함한 시간이 줄어드는가 |
| 자료 간 동일 대상 대조 | 공식 ID와 검토된 별칭에 근거한 연결 | 동명이인·유사 명칭 오병합을 늘리지 않는가 |
| 정정·개정 반영 | 변경 전후 사실과 재검토 대상·연결 이유 | 누락을 늘리지 않으면서 불필요한 검토 후보를 줄이는가 |
| 지식의 사용 가능 여부 확인 | 대상·조건·시점·원문을 함께 표시 | 오래되거나 범위가 다른 근거를 현행 일반 규칙으로 사용하지 않는가 |
| 특정 대상의 관련 지식 탐색 | 개체에 연결된 공고·조건·서류와 인용 답변 | 필요한 관계·근거를 찾고 다른 대상의 조건을 섞지 않는가 |
| 등록 자료 전체의 공통점·차이 파악 | 주제별 종합 답변과 공고별 차이·예외·근거 | 문서별 조회보다 종합 작업이 쉬워지고 서로 다른 조건을 일반 규칙으로 합치지 않는가 |

온톨로지는 의미와 연결 가능한 범위를 정하고, KG는 실제 대상·사실·출처·의존 관계를 담는다. 이 분리가 효용을 낼 것이라는 가설을 검증한다. 동일 작업을 ID·메타데이터·관계형 테이블로 충분히 처리하면 그 방식을 유지한다. 그래프 DB 도입이나 그래프 규모 확대는 목표가 아니다.

## 3. 대상 사용자와 업무 흐름

### 3.1 논리적 역할

| 역할 | 해야 할 일 | P0 책임 경계 |
|---|---|---|
| 지식 운영자 | 자료 등록, 변경 발견, 후보 묶음 준비, 작업 실패 재실행 | 프로젝트 평가자가 수행 가능 |
| 업무 검토자 | 개념 정의·동일성·조건·시점 확인, 수락·수정·보류·기각 | 실제 현업 검토자 미확보. 평가자가 검토하면 그 한계를 기록 |
| 배포 책임자 | 검토 완료 묶음 활성화·되돌리기, 미해결 사항 확인 | 단일 운영자가 겸임 가능. 역할 분리가 구현됐다고 주장하지 않음 |
| 지식 사용자 | 개체·관계 검색, 전체 자료 종합 검색, 적용 범위·근거 확인 | P0 지식 화면 사용, P1에서 민원 담당자 화면 연결 |
| 시스템 운영자 | 로컬 실행·백업·실패 확인 | 기관 운영 권한·SLA는 후속 협의 |

### 3.2 현재 절차에 대해 더 확인한 내용

공식 발주는 자료 제공·품질검증 참여, 추가·변경·삭제 관리, 원문 매칭, 검증 후 배포와 이력을 요구한다 [S1]. **승인된 사용자의 수정 권한은 내용별 승인 절차와 같은 의미가 아니다.** 실제 담당자의 변경 건 처리 순서와 도구는 확인하지 못했다.

따라서 아래는 기존 LH 프로세스의 복제라고 주장하지 않는 **제품 제안 흐름**이다.

1. 운영자가 자료와 출처·버전을 등록한다.
2. 로컬 AI가 개념·사실·연결·변경 후보를 작성한다.
3. 시스템이 ID 존재·근거 위치·스키마 적합성을 확인한다. 온톨로지 생성·변경 묶음에는 AI 반례 검토를 적용하고, 사실별 추가 AI 채점은 요구하지 않는다.
4. 업무 검토자가 원문과 후보를 나란히 보고 변경 묶음을 검토한다.
5. 배포 책임자가 검토된 부분만 새 스냅샷으로 활성화한다.
6. 지식 사용자는 활성 스냅샷에서 특정 대상의 관련 지식을 찾거나 등록 자료 전체를 종합해 질문한다. 답변의 근거를 조회하고 미해결·현행성 불명 항목은 별도로 확인한다.

## 4. 범위와 우선순위

| 구분 | 포함 | 제외·후속 |
|---|---|---|
| P0 업무 범위 | 국민임대 공개 지식과 양산 공고 계열 | LH 전체 사업·모든 회사 도메인 동시 구축 |
| P0 자료 | 선택 등록한 CSV, HTML, 텍스트 PDF, HWPX | 대규모 크롤러, 구형 HWP·스캔 OCR 자동화 |
| P0 자동화 | 로컬 역할별 AI의 초안 생성과 반례 검토 | 자율적 사내 시스템 탐색·권한 확대·무제한 토론 |
| P0 핵심 | 원문 보존, ID 연결, 온톨로지 검수, 변경 영향 후보, 활성 버전 조회 | 실시간 법률 판단·입주 자격 확정·자동 업무 처리 |
| P0 저장·화면 | SQLite 기반 지식 원장, 검토 목록·원문 대조·근거 경로 | 전용 그래프 DB, 전체 그래프 시각화 플랫폼 |
| P0 검색·종합 | 개체·관계 검색(Local)과 등록 자료 전체 종합 검색(Global), 원문 인용 | LH 전체 자료 검색, 무제한 다단계 질의·자율 탐색, 전체 조건의 법률 규칙화 |
| P1 활용 | 민원 워크벤치에서 지식 근거 조회·답변 보조 | 기존 민원 시스템 전면 교체 |
| 기관 운영 | 도입 조건을 문서화 | 인증·권한·SSO·다중 테넌트를 P0에 일괄 구축 |

구형 PRD `General Complaint Knowledge Layer v1.0`와의 관계:

- 민원 사례 중심에서 회사 지식 중심으로 변경한다. 민원 `case_id`는 코어의 필수 키가 아니다.
- 온톨로지 후보 검토를 후순위에서 P0로 올린다. 로컬 AI가 초안을 자율 작성하되 운영 반영은 검토를 거친다.
- 기존 Search/QA·민원 구조화·Intelligence 보존, SQLite 우선, 근거·ID 검증 원칙은 유지한다.
- 완전 자율 운영, LLM에 의한 무검토 개념 통합·삭제는 계속 제외한다.
- 재사용 가능한 라이브러리·코드·프롬프트는 직접 호출 또는 최소 이식한다. OntoGPT의 작성 자산과 LinkML 스키마 처리 등을 실제 구현에 사용하며, 전체 엔진이 필요한지와 기능 단위 재사용을 구분한다 [S11, S13]. 구체적인 채택 결정은 [구현 계획 §2~7](../05_plans/company_knowledge/implementation.md)를 따른다.
- GRAG 논문 전체 재현은 범위 밖이다. 그래프 관계를 검색·텍스트 근거로 활용하는 것과 논문 모델 재현을 구분한다 [S12].

## 5. 데이터 범위와 수집 계약

**2026-09-26 자료·과제 고정:** [파일럿 입력/평가 계약](../../configs/knowledge/pilot_v1/README.md)에 문서 파일 10개·CSV 1개와 평가 12건(개발 6·신규 6, Local 3·Global 3·구축/변경 6)을 기록했다. 원문 범위·해시·판정 기준을 고정했으며 실행 결과는 아니다. 신규는 다른 절에서 선정한 과제로 독립 비노출 자료가 아니다. ### 5.2 P0 입력 제한과 권리

- 최초 실험 예산은 **문서 버전 최대 20개와 CSV 1개**로 제안한다. 이는 조사 결과나 산업 기준이 아닌 구현 범위 제한이다. 장문 규정은 관련 절만 추출하되 원본 위치를 유지한다. CSV 전체는 ID 등록부로 활용하되 최초 사실 검토 대상은 공고와 연결된 단지로 한정한다.
- 등록부에 원 URL·발행기관·취득일·파일 해시·문서 식별자·문서 날짜·이용 조건 상태를 남긴다. 공개 열람 가능과 재배포 허용은 구분한다.
- CSV [S4]의 이용 조건과 LH 전체 첨부문서의 권리를 동일하게 취급하지 않는다. 개별 원문의 처리 가능 범위를 확인한 뒤 사용하고, 불명확한 원문 전체를 Git/공개 배포물에 포함하지 않는다.
- LH청약플러스 robots는 일부 첨부 다운로드 경로를 제한한다 [S10]. P0는 허용된 제공 경로와 선택 등록을 사용하며 차단 우회·전면 수집은 하지 않는다.
- API 키를 실제 호출한 검증은 없다. OpenAPI는 P0 필수 의존성에서 제외한다. 과거 언급한 `15038398`은 동작 미확인으로 채택하지 않는다.
- 입력은 허용된 자료 목록으로 제한한다. 사내 시스템은 소유자가 제공한 스키마·필드 사전·비식별 샘플만 후속 등록하며, 에이전트가 임의 DB·계정·로컬 폴더를 탐색하지 않는다.

## 6. 온톨로지와 지식 모델

### 6.1 두 계층

**온톨로지:** 개념의 정의, 포함·제외 기준, 속성 자료형, 관계 방향, 허용 주체·객체 유형, 별칭의 적용 범위를 관리한다. 업무 개념은 자료에서 후보를 만들고 검토한다.

**지식그래프:** 특정 조직·단지·공고·규칙·제출서류와 그 관계를 원문 근거·조건·버전과 연결한다. 단순 `(주체, 관계, 객체)`만 저장하지 않고 각 사실 주장에 근거와 적용 맥락을 붙인다.

고정하는 최소 메타모델은 `개념`, `개체`, `사실 주장`, `출처/버전/원문 위치`, `검토 결정`이다. `조직`, `주택단지`, `공고`, `요건`, `제출서류`, `업무절차`는 **LH 자료용 초기 후보**이며 모든 회사에 강제하는 완성 온톨로지가 아니다.

### 6.2 초기 관계 후보와 금지하는 단순화

| 후보 관계 | 의미 | 혼동 방지 |
|---|---|---|
| 공고→대상 단지 | 공고가 명시한 적용 대상 | 같은 지역이라는 이유만으로 포함 금지 |
| 규칙→적용 대상·조건 | 원문이 명시한 요건과 적용 맥락 | AND/OR·예외를 읽지 못하면 요약 규칙을 확정하지 않음 |
| 절차→필요 서류 / 서류→발급기관 | 해당 단계·조건에서 요구되는 서류와 기관 | 신청자가 항상 모두 제출한다고 일반화 금지 |
| 조직→제도 담당 / 조직→접수 담당 | 서로 다른 책임 관계 | 중앙 정책 담당과 현장 접수를 한 담당자로 합치지 않음 |
| 문서 버전→정정 대상 | 공식 연결 또는 검토된 명시적 정정 | 게시일이 최신이라는 이유만으로 모든 기존 문서를 대체하지 않음 |
| 파생 지식→사용 근거 | 생성 당시 사용한 사실·원문 의존 관계 | 의미가 비슷하다는 이유만으로 영향이 확정됐다고 표시하지 않음 |

### 6.3 필수 논리 데이터

물리 테이블 분리는 구현 시 최소화한다. 아래 정보가 손실 없이 표현되는 것이 요구사항이다.

| 객체 | 필수 정보 |
|---|---|
| Source / SourceVersion | 내부 ID, 원 URL·발행기관, 외부 ID·네임스페이스, 파일 해시, 문서군/정정 연결, 발행일·수집일, 이용 범위. 파서 버전·옵션·추출 실행을 별도 참조하여 원문 변경과 재파싱 구분 |
| Evidence / ParsedBlock | source_version_id, parse_run_id, block_id, 문단/표/셀 위치, 원문 텍스트·발췌·문자 범위·정렬 상태, 정규화 전후 대응. PDF 물리 페이지와 인쇄 페이지 분리 |

| Assertion | 주체·관계·객체 또는 값, 단위·집계 범위, 적용 조건·예외, 유효기간과 그 근거, Evidence 목록, 추출 방법, 검토 결정 |

## 7. 로컬 AI 역할과 자동화 경계

고정된 순차 작업으로 시작한다. 새로운 멀티에이전트 프레임워크·상주 토론 시스템은 만들지 않는다.

| 역할 | 입력 | 출력 | 할 수 없는 일 |
|---|---|---|---|
| 자료 분석 | 승인된 문서 절·CSV 스키마·샘플 | 용어·개체·관계 표현·근거 위치 후보 | 보지 못한 회사 시스템·업무 관행 추측 |
| 온톨로지 설계 | 분석 결과와 기존 개념 사전 | 추가/재사용/별칭/관계 정의 제안, 기존 정의와 차이 | 운영 온톨로지 직접 통합·삭제 |
| 반례 검토 | 후보와 관련 원문, 기존 정의 | 범위 혼동·누락·근거 불일치·오병합 의심 | 다수결 또는 모델 자신감을 정답으로 취급 |

- 반례 검토는 온톨로지 생성·변경 묶음당 1회로 하고, 모든 사실·모든 질의에 재적용하지 않는다. 최초 개념 후보 생성→검토 의견 반영은 **최대 1회 수정**으로 제한한다. 해결되지 않은 항목은 사람이 검토한다. 실행마다 처리 절·호출 수·소요 시간을 기록한다.
- 모델은 설치된 Ollama 설정을 재사용한다. 초안에는 현재 `STRUCTURING_MODEL`, 반례 검토에는 `CIVIL_LLM_RUBRIC_MODEL` 값을 초기 후보로 사용하되, 민원 평가 프롬프트는 사용하지 않는다. 새 역할의 품질은 별도로 검증한다.
- Qwen 검토는 비추론 모드로 시작하고 실제 요청의 `think=false`를 확인한다. 스키마별 출력 예산을 정하며 긴 문서는 절·표 단위로 나눈다. JSON 절단을 정상 성공으로 기록하지 않는다.
- 같은 모델의 역할 분담은 독립적인 전문가 합의가 아니다. 모델 점수나 다중 에이전트 일치율로 정확도를 인증하지 않는다.
- LLM은 표현·관계 후보를 제시한다. 공식 ID 존재 확인과 원문 발췌 일치는 코드에서 검증한다. 이름의 의미와 ID의 실제 대상 일치까지 자동 보장되는 것은 아니다.
- 초기 온톨로지가 없는 단계는 고정 메타모델로 원문 표현·개체·관계 후보를 수집한다. 업무 질문(CQ)과 근거에서 개념 초안을 유도한 뒤 승인된 스키마로 사실을 추출한다. 초기 개념 유도와 승인 스키마 기반 추출을 같은 기능으로 취급하지 않는다.
- 기존 Pydantic·Ollama 호출 경계를 재사용하고, LinkML의 스키마 해석·JSON Schema 생성과 LangExtract의 위치 정렬은 라이브러리로 사용한다. OntoGPT의 작성 자산은 회사 도메인에 맞게 이식한다. 후보 YAML에서 Python 코드를 생성·import하거나 외부 온톨로지 서비스를 자동 호출하는 흐름은 넣지 않는다. 의존성 버전은 [구현 계획 §8](../05_plans/company_knowledge/implementation.md)에 따라 필요한 범위에서 조정한다.

## 8. 기능 요구사항과 수용 기준

P0는 아래 FR-01~FR-09 및 FR-11~FR-12가 하나의 작업 흐름으로 작동해야 한다. 기존 FR-10은 P1로 유지한다. 수용 기준은 아직 통과 결과가 아니다.

| ID·우선순위 | 사용자 요구·기능 | 수용 기준 |
|---|---|---|
| FR-01 P0 자료 등록 | 운영자가 허용된 자료를 등록·재등록한다 | 동일 문서 ID와 동일 해시 재등록은 새 버전·사실을 중복 생성하지 않는다. 변경된 내용은 별도 버전으로 남는다. 출처·해시·수집일·권리 상태를 조회할 수 있다 |

| FR-04 P0 개체 연결 | 여러 표기의 같은 대상을 연결한다 | 공식 ID+네임스페이스 일치 우선. 이름만 같거나 유사도만 높은 경우 후보로 남긴다. 별칭 수락 시 대상·근거·범위를 기록한다. 잘못된 통합을 취소할 수 있다 |
| FR-05 P0 사실·조건 관리 | 사실마다 근거·대상·시점을 확인한다 | 근거 위치가 유효하지 않은 주장을 활성화할 수 없다. 조건/집계 범위가 다른 값은 공존한다. 근거 없는 법 조항·상식 보충은 사실이 될 수 없다 |
| FR-06 P0 검수 | 변경 묶음을 원문과 대조하여 처리한다 | 수락·수정·보류·기각, 결정자·시점·사유가 남는다. 일괄 수락 전에 포함 후보와 미해결 수가 보인다. 스키마/ID/근거 오류 항목은 일괄 수락에서 제외된다 |
| FR-07 P0 변경 영향 | 새 버전과 기존 활성 지식의 관계를 비교한다 | 변경 전후 값·원문·정정 연결·직접 의존 대상을 제시한다. 연결이 없는 변경은 ‘영향 없음’ 대신 ‘연결 미확인’이다. 의미 검색으로 찾은 항목은 간접 후보라고 표시한다 |
| FR-08 P0 활성화·되돌리기 | 검토된 변경을 일관된 버전으로 공개한다 | 온톨로지·사실·근거 참조가 함께 활성화된다. 실패하면 기존 활성 버전이 유지된다. 이전 스냅샷으로 되돌릴 수 있고 사유가 남는다. 버전 충돌 시 다시 비교하게 한다 |
| FR-09 P0 조회·내보내기 | 사용자가 지식과 근거 경로를 확인한다 | 활성 버전·대상·기준일·원문 위치·미해결 상태를 반환한다. ID/근거/상태 포함 JSON 및 검토용 CSV를 내보낼 수 있다. 권리 불명 원문 전체는 공개용 내보내기에서 제외한다 |
| FR-10 P1 민원 활용 | 담당자가 민원 화면에서 회사 지식을 참고한다 | 기존 민원 API 계약·Q0~Q7·인용 검증은 유지한다. 별도 지식 근거와 기존 민원 인용을 구별하고, 출처를 열 수 있다. 확정 자격 판정이나 이행 확약을 자동 실행하지 않는다 |
| FR-11 P0 개체·관계 검색 | 특정 단지·공고·서류를 자연어 또는 ID로 검색하고 관련 지식을 질문한다 | 검토된 ID·별칭으로 대상을 찾고 최대 2단계 관계와 연결된 원문을 함께 사용한다. 짧은 답변·관계 경로·원문 인용을 반환한다. 동명 대상이 여러 개면 선택을 요청하고, 근거가 부족하면 확인 불가 또는 부족한 항목을 표시한다 |
| FR-12 P0 전체 자료 종합 검색 | 등록한 파일럿 자료의 공통 조건·차이·예외를 자연어로 질문한다 | 선택 범위 내 사용 가능한 활성 지식을 주제별로 묶어 종합한다. 공통 내용과 공고별 차이·조건·예외를 구분하고 주요 사실에 원문 인용을 붙인다. 포함·제외 자료와 요약/입력 제한에 따른 누락 가능성을 표시한다. 일부 검색 결과만 사용한 답변을 전체 자료 분석으로 표시하지 않는다 |

### 8.1 두 검색의 최소 범위와 처리

- 두 모드는 같은 지식 조회 화면에서 사용자가 선택한다. P0에 자동 질의 분류기나 별도 대화 시스템을 만들지 않는다. Local/Global은 사용자 기능의 구분이며 Microsoft GraphRAG의 특정 알고리즘 재현을 뜻하지 않는다.
- 공통 입력은 질문·활성 스냅샷·선택 자료 범위·기준일이다. 범위를 지정하지 않으면 §5.2 예산 내 등록 파일럿 전체를 대상으로 한다. CSV는 ID 조회에 사용하며 종합 대상 사실은 공고와 연결된 검토 대상 단지로 한정한다.
- Local은 대상 연결→최대 2단계 관계 및 관련 원문 검색→인용 답변 생성으로 시작한다. 임의 길이의 경로 탐색·반복 후속 질의는 제외한다.
- Global은 선택 범위의 사용 가능한 활성 주장 전체를 훑고 개념/주제별로 묶는다. 컨텍스트에 들어가면 직접 종합하고, 초과하면 묶음별 요약 후 한 번 종합한다. 중간 요약은 원문 근거 ID와 조건·예외를 유지한다. 관련 묶음만 선택하거나 입력을 줄인 경우 사용 범위와 제외·잘림을 표시한다. 무관한 주장까지 답변에 나열할 필요는 없다.
- Global 입력 묶음과 출력 예산은 실제 파일럿 자료 크기에 맞춰 정한다. 다층 커뮤니티 생성·DRIFT·무제한 map-reduce·자동 재작성 루프는 P0 필수가 아니다. Microsoft GraphRAG를 포함한 구현 도구는 이 기능과 근거 연결을 충족하는지로 선택한다.
- 두 검색은 활성·사용 가능한 지식과 그에 연결된 원문을 사용한다. 미검토 문서는 탐색 대상 목록에서 구분하며 확정 답변 근거로 섞지 않는다. 답변은 스냅샷을 바꾸지 않는 조회 결과이고, 재사용을 위해 지식으로 저장하려면 기존 후보 검토 흐름을 거친다.
- 입력/참조 ID·사용 상태·인용 위치는 기존 검증 경계를 재사용해 확인한다. 매 질문마다 별도 LLM 평가·전문가 합의·사람의 답변 승인을 추가하지 않는다. 상충하는 조건은 함께 제시하고 자동으로 우선순위를 확정하지 않는다.

### 8.2 상태와 갱신의 의미

- 입력 처리: `registered → parsed → extracted` 또는 `failed`. 실패한 절과 완료한 절을 구분하고 실패한 단위만 재실행한다. 실행 중 취소 요청은 `cancel_requested`로 기록하고 현재 모델 호출/처리 단위가 끝나면 다음 단위를 시작하지 않고 `cancelled`로 마친다. 완료된 후보는 비활성 상태로 남는다.
- 후보 검토: `proposed → accepted / deferred / rejected`. 수정 시 기존 제안과 결정 이력을 남긴다.
- 수락은 활성화와 다르다. 검토 완료 묶음을 스냅샷으로 활성화해야 일반 지식 조회에 사용된다. 해당 사실이 참조하는 개념·관계 정의·개체 연결·근거도 모두 해당 스냅샷에서 검토 완료여야 한다. 보류·기각된 의존 항목이 있으면 그 사실을 활성화에서 제외하고 이유를 표시한다.
- 새 버전 등록만으로 과거 사실을 삭제하지 않는다. 명시적인 정정·철회가 확인됐거나 기존 근거 변경이 발견된 사실은 `needs_review`로 표시하고 현행 확정 근거에서 제외한다. 스냅샷 자체는 불변이며, 제외·재허용은 별도 상태 이력으로 남긴다. 조회 응답에는 `snapshot_id`, `status_revision`, `status_checked_at`을 함께 반환하여 사용한 상태를 추적한다.
- 새 문서가 정정인지 불분명하면 자동 대체하지 않는다. 관련 기존 지식에 현행성 확인 필요를 표시한다. 최신 확인일을 항상 반환하며 ‘기관의 현재 모든 지식’이라고 표현하지 않는다.
- 검토자는 영향 후보별로 **영향 없음·수정·철회·보류**를 결정하고 근거를 남긴다. 영향 없음 확인은 재허용 이력으로 사용 가능 상태를 복원한다. 수정·철회는 다음 활성 스냅샷에 반영하고, 보류는 사용 제외 상태와 잔여 작업으로 유지한다. 사용 중단된 원문을 다시 허용하려면 이용 조건 확인도 필요하다.
- 영향 후보는 직접 출처 의존과 검토된 관계를 우선 사용한다. P0 관계 탐색은 최대 2단계로 제한하고 경로·잘린 여부를 표시한다. 범위 밖 의존관계를 모두 찾아냈다고 주장하지 않는다.
- 원문이 철회·사용 중단된 경우 해당 근거와 직접 파생 결과를 검색·내보내기에서 제외한다. 이전 스냅샷으로 되돌려도 최신 사용 중단 상태는 해제되지 않는다. `as_of`는 업무상 적용일을 뜻하며 시스템의 과거 상태 재현과 구분한다. 과거 상태 재현은 저장한 스냅샷·상태 이력의 검토용 확인으로 한정한다. 감사용 보존과 실제 삭제의 범위는 자료 이용 조건에 맞추며 별도 상태로 남긴다.
- 모델 confidence는 검토 순서의 보조값일 뿐이다. 낮은 confidence만 보류하거나 높은 confidence만 자동 배포하는 정책은 사용하지 않는다.

## 9. 화면·상호작용

P0는 그래프 전체를 그리는 화면보다 다음 네 작업을 먼저 완성한다. 한국어 용어·오류 메시지·날짜를 기본으로 한다.

| 화면 | 반드시 보여야 할 정보·행동 |
|---|---|
| 자료 목록 | 자료군·버전·처리 결과·출처·최근 확인일·권리 상태, 등록과 실패 단위 재실행 |
| 온톨로지·사실 검토 | 왼쪽 원문/표, 오른쪽 제안·기존 값·정의·근거, 수락/수정/보류/기각, 필터·묶음 검토 |
| 변경 검토 | 이전/후속 원문, 직접 영향과 간접 후보, 연결 이유·누락 가능 범위, 활성화 전 포함/제외 항목 |
| 지식 조회 | Local/Global 선택, 질문·자료 범위·기준일 입력, 인용 답변, Local 관계 경로, Global 공통점·차이·예외와 사용 자료 범위, 원문 이동, 활성 버전·현행성 미확인 표시 |

빈 결과·처리 실패·연결 미확인을 구분한다. 운영 지식 화면은 mock 데이터를 실제 결과처럼 자동 대체하지 않는다. 근거 위치가 열리지 않으면 오류를 알리고 확정 검토를 요구한다. 키보드로 주요 검토 동작과 원문 이동을 수행할 수 있어야 한다.

P1 민원 화면은 기존 답변 작성 영역 옆에 별도 지식 패널을 제공한다. 지식 패널의 답변 보조에는 사용한 지식 스냅샷과 문서 근거가 표시된다. 코어에 민원 분류·감정·중복 민원 규칙을 넣지 않는다.

## 11. 비기능 요구와 환경

**구현·검증 원칙:** P0는 단일 운영자의 제한된 자료를 다루는 파일럿이다. 기존 Pydantic·DB 제약·근거 확인·검토 상태 경계를 재사용한다. 원문/ID 연결, 조건·시점 구분, 미검토 지식 제외, 활성화·되돌리기 일관성은 유지하되 별도 안전 프레임워크·다중 승인 체계·모델 자동 선택기·복잡한 fallback·상시 LLM 평가를 만들지 않는다. 변경한 기능의 대표 사례와 명확한 오류를 대상으로 확인하고, 전체 테스트 반복·조합별 전수 검사·대규모 벤치마크는 요구하지 않는다. 추가 검사는 실제 실패나 구현 변경으로 필요성이 확인된 경우에만 한다.

**실행 경계:** P0의 검토/활성화는 같은 운영자의 한 화면·묶음 결정으로 충분하며 별도 승인 담당자나 티켓을 요구하지 않는다. 사용 중단 상태와 근거 검사는 DB/API 경계에서 수행하고 중복 검증 계층을 만들지 않는다. Global 중간 요약은 요청 안에서만 유지하고 Run에 의존 ID를 남긴다. 현업 인터뷰·기관 승인·Windows 환경 확보는 Mac 로컬 구현의 진입 조건이 아니다. 불명확한 자료 이용 범위는 기록하고 금지된 이용을 하지 않되, 공개 배포 승인을 개발 승인으로 오해하지 않는다. 확인은 해당 기능을 만든 단계에서 누적하고 전체 12건 비교는 기능 준비 후 한 묶음으로 수행한다. 상세 [점검 결과](../70_research/company_knowledge/planning_scope_review_2026-09-26.md).

|---|---|---|
| NFR-01 호환성 | Python 3.11.9, Mac/Windows 네이티브, 필요한 의존성 버전 조정 허용 | pathlib·UTF-8·상대 기본 경로 사용. 채택 라이브러리와 기존 기능이 함께 동작하도록 관련 버전을 맞춘다. 같은 소규모 입력으로 양 OS 등록→조회 smoke 확인 전 Windows 검증 완료라고 보고하지 않음 |
| NFR-02 로컬 처리 | LLM 입력·출력은 설정한 로컬 Ollama로 처리 | 외부 LLM 키·클라우드 추출 서비스 불필요. 자료 다운로드와 모델 추론 네트워크 경계를 구분 |
| NFR-03 무결성 | 활성 버전과 근거 참조 일관성 | 원문 없는 활성 주장 0건, 미검토 후보의 일반 조회 유출 0건을 고정 회귀 사례에서 확인 |
| NFR-04 운영 가능성 | 실패·재실행·백업·복구가 단순해야 함 | 작업 종료/중단 후 재실행 시 중복 없음. 정지 상태 백업→복원 1회로 활성 snapshot·근거 참조 동일 확인 |
| NFR-05 관측 | 시간·오류·검수 수정량을 남김 | run별 처리량·모델 호출·시간·실패 사유·수락/수정/보류 수. 원문 전체를 일반 로그에 반복 기록하지 않음 |
| NFR-06 응답성 | 입력 예산 안에서 사용자가 상태를 확인 | 자료 등록은 source_id/source_version_id를 반환하고, 장시간 파싱·추출 실행은 run_id를 반환하여 상태 조회 가능. 취소는 다음 처리 단위 전에 반영. 속도 SLA는 최초 측정 후 확정 |
| NFR-07 사용 범위 | P0 단일 신뢰 운영자의 로컬 사용 | API·FE loopback 실행, 불필요한 외부 노출 없음. 이것을 사용자 인증 대체나 사내 운영 보안 완료로 주장하지 않음 |

최소 설정 제안은 `KNOWLEDGE_ENABLED=false`, `KNOWLEDGE_DB_PATH` 두 개다. 기존 `.env`를 로컬에서 분리하고 `.env.example`에는 비밀 없는 상대 경로 예시만 둔다. 기존 생성·평가 모델 설정을 재사용하며, 역할 품질 때문에 분리가 필요하다는 결과가 나온 경우에만 설정을 추가한다.

현재 FE fallback 포트는 8001이며 API 실행 포트와 다를 수 있다. 실행 안내에서 `NEXT_PUBLIC_API_BASE_URL`을 실제 API 포트와 맞춘다. 공통 코드에 Mac 사용자 경로·Homebrew 전용 명령·Quartz 등을 넣지 않는다. PDF/HWPX는 [구현 계획 §2](../05_plans/company_knowledge/implementation.md)에서 선택한 라이브러리를 도입하고 원문 위치 어댑터를 작성한다. 특정 파서가 이미 설치돼 있다고 가정하지 않는다.

## 12. 효용 검증 설계와 출시 판단

### 12.1 비교 조건

**아직 이 제품의 효용 비교 실험은 수행하지 않았다.** 공개자료 조사는 데이터 접근·연결 가능성의 증거이며 업무시간 절감·추출 정확도의 증거가 아니다.

| 방식 | 구성 | 확인 목적 |
|---|---|---|
| B0 수작업 기준 | 동일 원문, 문서 비교, ID·변경 검토표 | 프로젝트 평가자가 직접 구축·갱신하는 비용 |
| B1 단순 시스템 기준 | 동일 파싱·공식 ID·메타데이터·문서 diff·기존 RAG, 같은 모델의 원문별 사실/변경 요약 초안, 수동 관계표 허용 | 기본 자동화와 문서 관리로 얻는 효과 |
| B2 제안 방식 | B1 + 개념 정의/관계 제안·검토·근거 관계 기반 변경 영향 후보·Local/Global 검색 | 제안 기능 묶음의 추가 이익 및 유지 비용 |

B1을 일부러 약하게 만들지 않는다. 같은 원문/버전/과제/필터/생성 모델을 사용한다. RAG 비교는 같은 컨텍스트 예산으로 수행하고 근거량·호출 수·총시간을 함께 기록한다. 사람 작업시간, LLM 대기시간, 최초 구축 비용, 반복 갱신 비용을 분리하고 총합도 제시한다. B1/B2 결과는 기능 묶음의 효과이며 KG 단독 효과로 해석하지 않는다. KG 단독 효과를 주장할 때만 후보·검토 결과를 고정하고 관계 탐색 사용 여부를 바꾸는 제한 비교를 추가한다.

### 12.2 평가 자료와 작업

**2026-09-26 준비 상태:** [파일럿 고정 기록](../70_research/company_knowledge/company_knowledge_pilot_freeze_2026-09-26.md)에 따라 개발 6건·새 6건의 총 12개 과제를 고정했다(Local 3건·Global 3건 포함). 새 과제도 같은 자료의 다른 절을 사용하며 AI·설계자에게 노출되어 독립 인간 맹검 자료가 아니다. 후속 [비교 절차](../05_plans/company_knowledge/evaluation_protocol.md)와 [최소 데이터/API 계약](../05_plans/company_knowledge/contracts.md)으로 K1 설계 산출물을 완료했다. M0의 실사용 권리 확인·실제 참여자 확보와 제품 실행 결과까지 완료했다는 뜻은 아니다.

최초 예산은 **12개 작업 사례**로 제안한다. 아래 이미 조사한 6종은 개발·회귀용이며 독립 평가라고 부르지 않는다. 새 6건은 다른 공고/절에서 선정하여 정답과 판정 기준을 잠그는 원칙이며, 튜닝에 사용하지 않은 경우에만 별도 확인 결과로 보고한다. 충분한 새 자료를 확보하지 못하면 개발 확인으로만 보고한다.

12개 작업 중 Local 3건, Global 3건을 배정하고 구축·변경 작업과 같은 자료를 재사용한다. 별도 검색 벤치마크를 추가하지 않는다. Local은 대상의 관련 정보, 조건별 서류, 대상 모호성 또는 근거 부족을 확인한다. Global은 공통 조건, 개별 공고의 차이·예외, 구버전/미검토/부분 처리에 따른 사용 범위 표시를 확인한다. 실제 입력과 기대 근거의 고정 상태는 아래 2026-09-26 기록을 따른다.

| 개발·회귀 사례 | 기대 동작 |
|---|---|
| 양산 원공고→정정 공고 | 정정 연결과 날짜 변경 근거를 보존하고 수정 전 값을 현행 확정 근거로 재사용하지 않음 |
| 단지 코드와 명칭 차이 | 실제 6개 대상의 ID 연결. HTML 공통 스크립트의 무관한 코드 제외 |
| 세대수 차이·혼합 임대유형 | 정의·시점 확인 전 단일 값 확정 금지. 혼합 단지 전체에 한 유형 조건 적용 금지 |
| 예정 입주일과 최초 입주일 | 다른 속성으로 유지. 값 차이만으로 충돌 판정 금지 |
| 일반 안내와 개별 완화 공고 | 적용 범위·예외를 구분. 자동으로 일반 규칙을 전면 덮어쓰지 않음 |
| 현행성 미확인 과거 규정·근거 없는 추가 주장 | 현행 확정 근거에서 구분. 제공 자료에 없는 주장·ID를 근거 있다고 통과시키지 않음 |

근거 없는 주장을 넣는 경우 원래 원문을 바꾸지 않고 별도 음성 후보로 명시한다. 실제 사례와 인위적 후보를 섞어 자연 발생 빈도처럼 보고하지 않는다. 정답은 원문 위치·ID·범위·시점을 보고 확인하며 LLM 점수를 정답으로 삼지 않는다. 평가자가 판단할 수 없는 항목은 보류하고 그 수를 공개한다.

M0에서 **공통 자료 준비 이후 최초 구축 1회 + 선정한 12개 작업 전체**를 비교 묶음으로 고정한다. 등록·초안 검토·수정·활성화·최종 근거 확인까지 필수 산출물을 동일하게 정하고, 실제 사람 조작 시간과 모델 대기를 따로 측정한다. 시간은 사람이 준비 자료를 열고 작업을 시작할 때부터 완료 또는 보류 사유 기록까지 잰다. 공통 자료 수집·평가 정답 작성 비용은 방법 비교에서 제외하되 프로젝트 비용으로 별도 기록한다. 초기 구축과 반복 작업의 개별 비용도 함께 제시하며, 실제 갱신 빈도 없이 연간 절감이나 투자 회수기간을 계산하지 않는다.

B0/B1/B2를 한 사람이 같은 순서로 반복하면 학습 효과가 생긴다. 가능한 경우 방법별 순서를 교차하고 동등 난이도 과제를 배정한다. 사람이 한 명이면 순서·사전 노출과 한계를 기록하고 산업계 ROI를 주장하지 않는다.

### 12.3 지표·판정

| 지표 | 계산·판정 |
|---|---|
| 원문 근거 정확성 | 검토된 주장 중 해당 위치의 원문이 실제로 주장·대상을 뒷받침하는 비율, 오류 건수 병기 |
| 연결 정확성 | 정답을 정할 수 있는 연결 후보의 정답/오답/누락 수. 이름만 맞는 ID는 오답 |
| 변경 영향 | 정답 재검토 대상 중 놓친 수, 제시 후보 중 불필요한 수. 후보가 0이면 정확도 100%로 처리하지 않음 |
| 조건·시점 오류 | 범위 다른 규칙 적용·구버전 현행 사용·근거 없는 법령 등 중대한 오류를 사례별 보고 |
| 검토 부담 | 최초 구축 및 변경 1건당 사람 작업시간, 수정/보류 후보 수, 대기시간, 전체 경과시간 |
| 유지 비용 | 온톨로지 정의·별칭·관계 수정 시간, 재추출·재색인 횟수와 시간 |
| 활용 가능성 | 정답이 있는 과제의 완료 수와 미해결 수, 근거까지 추적 가능한지 |
| Local/Global 검색 품질 | Local의 대상·관계·필요 근거 누락, Global의 공통점/차이·예외 누락 및 잘못된 일반화, 주요 사실의 인용 대응을 원문으로 확인. 호출 수·총시간·부분 처리 여부도 함께 기록 |

**P0 기술 통과:** FR-01~09·FR-11~12·관련 NFR의 고정 사례를 만족하고, 확인 가능한 중대한 오병합·범위 오적용·구버전 확정 사용·없는 근거 통과가 0건이어야 한다. 두 검색은 각 3개 작업에서 필요한 정보 또는 근거 부족 사유와 원문 인용·사용 범위를 확인한다. 실패하면 해당 처리만 수정하고 관련 사례를 다시 확인한다. 이는 해당 소표본의 출시 조건이지 일반 정확도 보증이 아니다.

**B2 확장 조건:** B1 대비 중대한 오류·영향 누락이 늘지 않고, 동일 필수 산출물 완료 조건에서 위 고정 묶음의 **총 사람 작업시간이 10% 이상 감소**해야 한다. 10%는 미세한 시간차만으로 확장하지 않기 위한 초기 제품 의사결정 기준이며 산업 표준·관측 성과·통계적 유의성 기준이 아니다. M0에서 측정 구간과 기준을 확정하고 결과를 본 뒤 낮추지 않는다. 고정 과제를 끝내지 않은 방식은 빠르다는 이유로 우수하다고 보지 않는다. 표본이 작거나 순서 효과 등 비교가 불공정하면 ‘추가 효용 미확인’으로 보류한다. 개선이 없으면 B1을 유지하고 관계 자동화 확장을 중단한다.

이 확장 판단은 P0 두 검색의 제공 여부와 구분한다. 추가 관계 자동화의 효용이 없으면 B1의 수동 관계표·기본 RAG와 자료별 요약으로 Local/Global을 제공할 수 있다. Global 비교에서도 B1에 동일 예산의 원문별 요약·종합을 허용한다. 두 검색 각각의 결과를 따로 보고하고 초기 도입을 위해 여러 프레임워크·모델의 전체 조합을 벤치마크할 필요는 없다.

**P1 민원 예시 진행 조건:** B2 채택 여부와 분리한다. 채택한 방식(B1 또는 B2)의 근거·버전·상태·조회 품질이 기술 통과 조건을 만족하고, 실제 민원 작업에서 필요한 활용 과제가 정의되어야 한다. B1을 선택한 경우 관계 기반 구축 효용이 검증됐다고 홍보하지 않는다. 민원 패널의 호출·인용·기존 API 보존을 별도로 확인한다.

실제 기관 도입의 절감률·처리량·SLA는 담당자 인터뷰와 실작업 측정 후 정한다. 근거 없는 목표 수치를 산업 표준으로 제시하지 않는다. 개발 중 확인을 위해 전체 기존 테스트를 반복하거나 대규모 벤치마크를 구축할 필요는 없다.

| M0 자료·과제 고정 | 출처/권리 등록부, 원문 샘플, B0/B1 작업표, Local 3건·Global 3건을 포함한 총 12개 과제와 판정 규칙 | 사용 가능한 자료와 확인 가능한 근거가 없으면 범위 축소 | 자료 이용 조건 확인 |

| M2 변경·효용 | 실제 정정 재생, 영향 후보, 두 검색에 변경/제외 상태 반영, B0/B1/B2 비교 보고 | FR-07·NFR, 관련 검색 사례 재확인과 오류·총작업시간 공개. B2 확장 조건 미충족 시 추가 관계 자동화 확장 중단 | M1 |
| M3 민원 예시 | 별도 지식 패널/assist, 출처 확인, 기존 기능 회귀 확인 | P1 진행 조건 충족 후 FR-10. 기존 API 손상 시 연결 비활성화 | M2 |
| M4 기관 파일럿 | 실제 역할/자료/운영 조건 합의, 제한 사용자 평가 | 접근 통제·권리·백업·운영 책임과 실제 업무 기준 확인 | 현업 참여·별도 배포 설계 |

**바로 구현하기 좋은 첫 작업:** K1 설계 산출물은 준비됐다. K2에서 선정 원문의 등록·파싱·근거 조회를 먼저 구현하고, 이후 M1에서 AI가 만든 사실 한 묶음을 원문과 대조하여 활성화·Local 검색하는 기능을 만든다. 이어 같은 기반에 일반 안내와 관련 공고를 추가해 Global을 제공한다. 전체 회사 온톨로지 설계나 변경 관리 전체 구현부터 끝내려 하지 않는다.

**재사용 구현의 배치:** [1~2일 단위 마일스톤](../05_plans/company_knowledge/milestones.md)에 따라 K1은 CQ/근거 과제, K2는 pdfplumber·python-hwpx 어댑터와 관련 버전 조정, K3는 OntoGPT/AutoSchemaKG 자산·LinkML, K4는 LangExtract·ID 연결, K5는 검수·원장, K6는 Local, K7은 GraphRAG 프롬프트를 활용한 Global, K8은 DeepDiff·시간/출처 기반 변경 관리, K9는 누적 결과와 호환성 미확인 사항, K10은 민원 활용을 다룬다. 기존 17/19업무일은 추정치이며 라이브러리를 도입했다는 이유로 단축이 입증됐다고 보지 않는다.

## 16. 문서 검수 상태

작성 후 제품·산업 적용과 기술·데이터 관점의 별도 AI 에이전트가 이 파일을 검토했다. 발견된 중요 지적을 수정하고, 최종 판정과 반영 내역을 [검토 기록](../70_research/company_knowledge/company_knowledge_prd_review_2026-09-25.md)에 기록한다. AI 검토는 실제 LH 직원 인터뷰·인간 도메인 전문가 승인·구현 성능 검증과 구분한다.

v1.1의 두 검색·최소 검증 원칙 추가는 사용자 요청에 따른 문서 수정이다. 기존 AI 검토 기록이 이 추가 범위까지 검수했다는 뜻은 아니며, 이번 수정에서 앱 코드·의존성·Git 커밋은 변경하지 않았다.

v1.2는 사용자 요청에 따라 [구현 계획 §2~7](../05_plans/company_knowledge/implementation.md)의 재사용 결정·어댑터·이식/재구현 범위와 [구현 계획 §8](../05_plans/company_knowledge/implementation.md)의 버전 조정 계획을 추가했다. 기존 조사에서 버전 충돌을 이유로 보류한 권고보다 이 문서의 채택 방침을 우선한다. 공식 소스와 설치 배포 메타데이터를 대조했으며 LinkML의 main/배포본 제약 차이도 반영했다. 이번 수정은 PRD·마일스톤·기존 조사 안내의 문서 변경이며 앱 코드·패키지 설치·모델 실행·커밋·푸시는 수행하지 않았다. v1.2의 별도 제3자 전문가 검수 및 통합 실행 검증은 미수행이다.


v1.3은 문서 체계 정리 버전이다. 회사 지식 제품을 메인 기준으로 명시하고 v1.2의 상세 설계·구현 내용을 별도 문서로 분리했다. 자료/과제 고정은 K1 부분 완료이며 B0/B1/B2 측정 계약과 최소 API 계약은 미완료다. 기능 구현 완료·성능 확인·기관 운영 승인을 뜻하지 않는다. 이번 문서 체계 검수는 [정리 검토 기록](../documentation_reorganization_review_2026-09-26.md)을 따른다.

### v1.4 문서 배치 변경

PRD를 `docs/00_overview/company_knowledge_prd.md`로 이동했다. 요구사항 변경은 없으며 상세 설계·구현·마일스톤은 `docs/05_plans/company_knowledge/`에 유지한다.

### v1.5 K1 계약과 검증 범위

비교 절차·12건 실행표·측정 양식 및 최소 데이터/API 계약을 확정했다. 반례 검토는 온톨로지 묶음에 한정하고 P0 단일 운영자 검토, 요청 내 요약, 단계별 관련 확인을 명시했다. 기능·실험을 실행한 결과는 아니며 기존 AI 검수 기록이 이번 개정을 검수한 것으로 간주하지 않는다.
