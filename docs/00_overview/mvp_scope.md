# MVP 범위 문서

문서 버전: v1.0  
기준 문서: [PRD](prd.md)  
작성일: 2026-03-11

## 1. 문서 목적

본 문서는 졸업작품 1차 완성 및 데모 성공을 위해 반드시 구현해야 하는 최소 기능 집합(MVP)을 정의한다.  
PRD의 전체 범위 중 실제 8주 일정, 4인 팀 규모, 로컬 추론 환경, 데모 안정성을 고려해 **필수 / 권장 / 후순위**를 구분한다.

## 2. MVP 정의 원칙

### 2.1 우선순위 원칙

1. 데모에서 끊김 없이 동작하는 기능을 우선한다.
2. 여러 모듈이 동시에 의존하는 인터페이스를 먼저 고정한다.
3. 멋있어 보이지만 검증 비용이 큰 기능은 후순위로 둔다.
4. 발표에서 설명 가능한 완성도를 우선하고, 확장성은 차순위로 둔다.

### 2.2 MVP 판단 기준

아래 조건을 만족하면 MVP 범위에 포함한다.

- 핵심 유스케이스(구조화, 검색, QA) 중 하나를 직접 완성시킴
- 팀 병렬 개발을 가능하게 하는 인터페이스를 제공함
- 8주 내 구현 및 통합 가능성이 높음
- 로컬 환경에서 안정적으로 시연 가능함

## 3. 이번 프로젝트의 MVP 한 줄 정의

**"민원 원문을 로컬에서 구조화하고, 벡터 검색을 통해 유사 민원을 찾고, 검색 근거를 인용하는 RAG 답변을 제공하는 데모 가능한 오프라인 시스템"**

## 4. MVP 범위 요약

### 4.1 반드시 포함해야 하는 기능

| 구분 | 기능 | 포함 여부 | 이유 |
| --- | --- | --- | --- |
| 데이터 입력 | CSV/JSON 배치 업로드, 수동 텍스트 입력 | 필수 | 데모 입력 경로 확보 |
| 전처리 | 기본 정제, PII 마스킹 옵션 | 필수 | 보안성과 품질의 최소 요구 |
| 구조화 | Observation / Result / Request / Context 추출 | 필수 | 프로젝트 핵심 차별점 |
| 엔티티 추출 | LOCATION, TIME, FACILITY, HAZARD, ADMIN_UNIT | 필수 | 검색·설명·분석 기반 데이터 확보 |
| 스키마 검증 | 필수 필드, 타입, confidence 범위 검증 | 필수 | 파이프라인 안정성 확보 |
| 인덱싱 | 임베딩 생성 + ChromaDB 저장 | 필수 | 검색 기능 구현의 기반 |
| 검색 | Top-K 시맨틱 검색 + 메타데이터 필터(기간/지역/카테고리 중 최소 2개) | 필수 | 핵심 유스케이스 완성 |
| QA | 검색 결과 기반 RAG 답변 생성 | 필수 | 데모 임팩트 핵심 |
| 근거 제시 | chunk_id, case_id, snippet 인용 | 필수 | 설명 가능성 확보 |
| API | `/ingest`, `/structure`, `/index`, `/search`, `/qa`, `/health` | 필수 | FE/BE 병렬 개발 기준점 |
| UI | 민원 큐/워크벤치 화면(구조화 확인 + 검색/QA) | 필수 | 데모 운영 최소 조건 |
| 평가 | 구조화 F1, Recall@5, 응답 지연시간 측정 스크립트 | 필수 | KPI 추적 필수 |
| 로깅 | 실패 원인, 응답시간, 검색 점수 저장 | 필수 | 디버깅 및 발표 근거 확보 |

### 4.2 권장 기능

| 기능 | 우선순위 | 포함 조건 |
| --- | --- | --- |
| 증분 인덱싱 | 권장 | 배치 인덱싱 완료 후 추가 |
| 하이브리드 검색(키워드 + 벡터) | 권장 | Recall@5가 목표 미달일 때 |
| JSON 파싱 실패 재시도 로직 | 권장 | QA 안정성 확보에 매우 중요 |
| OOM 폴백 로직 | 권장 | 로컬 GPU/메모리 한계 대응 |
| 관리자 통계 대시보드 | 권장 | MVP 1차 동작 안정화 이후 |
| 중복 민원 탐지 | 권장 | ingest 품질 향상 필요 시 |

### 4.3 이번 단계에서 제외해도 되는 기능

| 기능 | 분류 | 제외 이유 |
| --- | --- | --- |
| 실제 행정시스템 연동 | 제외 | 외부 시스템 의존성과 보안 검토 부담이 큼 |
| 모바일 앱 | 제외 | 데모 본질과 무관 |
| 다국어 민원 처리 | 제외 | 한국어 품질 집중 필요 |
| 대규모 분산 인프라 | 제외 | 졸업작품 범위 초과 |
| 자동 정책 제안 생성 | 제외 | 발표용 확장 포인트로 충분 |
| 완전한 AES-256 영속 저장 | 후순위 | 구현 대비 검증 비용 큼, 권장 수준 유지 |

## 5. 화면 기준 MVP 범위

### 5.1 화면 1: 민원 큐 선택 및 구조화 결과 확인(워크벤치 상단)

**필수 요소**
- 민원 큐(샘플/대기 목록)에서 항목 선택
- 선택 민원의 원문/메타데이터 표시
- 구조화 결과 JSON 표시
- 엔티티 추출 결과 표시
- confidence 표시
- 스키마 검증 성공/실패 상태 표시

**비고**
- CSV/JSON 적재(`POST /api/v1/ingest`)는 데모 UI에서 직접 다루지 않고, 스크립트/배치로 수행해도 MVP 범위에 포함된다.

**제외 가능 요소**
- 전처리/마스킹 옵션 UI
- 파일 업로드 UI
- 고급 편집기
- 사용자별 권한
- 시각화 대시보드 연동

### 5.2 화면 2: 검색/질의응답 화면

**필수 요소**
- 자연어 질의 입력
- Top-K 검색 결과 카드
- 필터(기간, 지역, 카테고리 중 최소 2개)
- RAG 답변 출력
- citation 리스트 표시
- 원문 snippet 표시
- 실패 시 limitations 또는 fallback 메시지 출력

**제외 가능 요소**
- 피드백 수집 UX 고도화
- 복수 세션 대화 기록
- 사용자 맞춤 프롬프트 편집

### 5.3 화면 3: 관리자 통계 대시보드

**판단**
- PRD상 In Scope이지만, MVP 1차 필수는 아님
- 구조화/검색/QA가 안정화되면 단순 집계 수준으로 추가 가능

**최소 축소안**
- 카테고리별 건수
- 기간별 민원 수
- 위험요소(HAZARD) 상위 빈도

## 6. 기술 선택의 MVP 고정안

### 6.1 1차 고정 스택

| 영역 | MVP 선택 | 이유 |
| --- | --- | --- |
| API | FastAPI | 명확한 인터페이스, 테스트 용이 |
| UI | Streamlit | 데모 구현 속도 빠름 |
| 벡터 DB | ChromaDB | 로컬 개발 생산성 높음 |
| 임베딩 | BGE-m3 | 다국어 대응 가능, 한국어도 무난 |
| LLM 추론 | Ollama + Qwen2.5 7B Instruct | 로컬 구동성과 범용성 균형 |
| 구조화 | Prompt 기반 추출 + 룰 보정 | 빠른 구현과 보정 가능성 |

### 6.2 MVP 단계에서 고정해야 할 것

- 데이터 계약(JSON 스키마)
- API 요청/응답 형식
- chunk 메타데이터 키 구조
- 평가 지표 계산 방식
- 기본 모델 1종, 임베딩 1종
- 디렉토리 구조 및 모듈 경계

### 6.3 MVP 단계에서 유연하게 두어도 되는 것

- 임베딩 모델 교체 실험
- FAISS 전환 여부
- 4-bit vs 8-bit 세부 비교
- 검색 reranking 적용 여부
- 관리자 대시보드 시각화 수준

## 7. 팀별 MVP 책임 범위

### FE
- Streamlit 업로드/검색/QA 화면
- 결과 카드와 citation 표시
- 오류/지연 상태 UI

### BE-A
- 로더, 정제, 마스킹
- 구조화 추출 체인
- 스키마 검증

### BE-B
- 청킹 전략
- 임베딩 생성
- ChromaDB 인덱싱
- 검색 및 필터 로직
- Recall 평가

### BE-C
- FastAPI 엔드포인트
- Ollama 연동
- RAG 프롬프트
- JSON 파싱/재시도
- 성능 및 폴백

## 9. MVP 완료 정의(Definition of Done)

아래 조건을 모두 만족하면 MVP 완료로 판단한다.

### 기능 완료 조건
- 샘플 민원 데이터 업로드가 가능하다.
- 단건 민원을 4요소 구조로 변환할 수 있다.
- 구조화 결과를 인덱싱할 수 있다.
- 자연어 질의에 대해 유사 민원 Top-K를 반환한다.
- 검색 결과를 기반으로 답변과 citation을 생성한다.
- Streamlit 화면에서 E2E 흐름을 한 번에 시연할 수 있다.

### 품질 완료 조건
- 구조화 스키마 검증 통과율 95% 이상
- JSON 파싱 성공률 95% 이상
- 데모 시나리오 3종 연속 성공
- 응답 실패 시 사용자에게 의미 있는 오류 메시지 제공

### 운영 완료 조건
- 실행 방법이 README에 정리되어 있다.
- `.env` 또는 설정 파일이 정리되어 있다.
- 기본 로그가 파일로 남는다.
- 평가 스크립트를 독립 실행할 수 있다.

## 10. 권장 실행 순서

1. 구조화 JSON 스키마 확정
2. API 명세 확정
3. 샘플 데이터셋 30~50건 정리
4. ingest → structure → validate PoC
5. embedding → index → search PoC
6. search → qa → citation PoC
7. Streamlit 화면 연결
8. 평가 및 병목 개선

## 11. 최종 판단

이 프로젝트의 MVP는 **기능 수를 늘리는 것**이 아니라 **구조화 → 검색 → 근거 기반 QA가 안정적으로 이어지는 것**이다.  
특히 발표와 데모 관점에서는 관리자용 확장 기능보다, **정확한 citation이 붙는 질의응답 흐름**이 훨씬 중요하다.
